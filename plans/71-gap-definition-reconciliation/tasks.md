### Phase A — Definition and calibration (GD-1 to GD-5)

- The rubric must explicitly distinguish *missing capability*, *unreliable capability*, and *missing evidence of capability*; the latest state must be dated and tied to real observations.
- Decide the abstraction by four tests: independently valuable outcome, closure possible without all neighbors closing, implementation independence, and non-duplication of nearest gap. These are proposed tests, not assumed final philosophy.
- Use a holdout across categories; an independent critic must be able to give a contrary verdict. Material disagreement triggers rubric revision, not dismissal of examples.
- **Stop at GD-5** if the owner has not accepted the reviewed version. Running the entire census to force-fit a draft definition is not useful.

### Phase B — Baseline and catalogue migration (GD-6 to GD-14)

- Start from authoritative GitHub issue data, not title lists, a `gap:ID` label or an issue's `About` field. Capture pagination and a stable time/revision boundary; explicitly represent unavailable records.
- A single issue may evidence several gaps or none, and discovery in Plan 61 does not imply that Plan 61 owns the eventual fix. Keep issue implementation routing independent from vision-gap significance.
- Completed plans and successful CI establish only the exact result proved; they do not automatically close a gap or imply released user experience.
- Every original gap gets one documented disposition, even if it remains unchanged. A new gap must be traceable to a specific vision goal and current evidence; some aspirations have no issue reports but still deserve assessment.
- For split/merge/retire decisions, preserve source and destination identity as agreed; do not silently delete stable IDs, conflate supersession with `Closed`, or change current project ownership.
- **Test contract boundaries:** retain existing `check_gap_boundaries` first-principles record per material change; do not duplicate this in a new PR mechanism. If moving to Goals metadata, follow the accepted Plan 53 / PR #1059 contract with the paired App consumer, not a custom schema. The actual affected tests/fixtures must be inventoried just before edit, including changes not visible from a filename alone.
- Phase B may yield *zero* new gap files if the accepted evidence justifies the current catalogue. The aim is an accurate map, not a target count.
