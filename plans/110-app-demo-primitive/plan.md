# Directable Astrid App demonstrations

**Project:** Directable Astrid App demonstrations

**Goal:** A creator or agent can import one Astrid Video primitive, author a timed demonstration of the actual Astrid interface with configurable chat, actions, gallery, extensions and timeline edits, and render it locally as an ordinary reusable video scene without rebuilding the interface or running a real workspace backend.

## Outcome and scope

**Draft scope — owner requested the project and its direction on 28 November 2026. Independent critique and scope greenlight are still pending. This plan authorizes no implementation or release.**

A single data-driven `appDemo(spec)` scene is imported from Astrid Video (proposed entry point, not a shipped API). It mounts the real App once in a dedicated browser document using App-owned code and a disposable in-memory project. The scene can be previewed, scrubbed and captured on a presentation clock, then placed and composited using ordinary Astrid Video media and editing paths. The default is the interface itself: no tour text/cards, forced headings, welcome/Next/Finish, or onboarding story. Chat text and tool cards remain optional native content. Creative editorial text belongs in the surrounding composition.

Included:

- Complete the existing App candidate, using authentic App frame, header, native editor, real player, shared conversation/composer/action UI, gallery controls and tile components, existing extension panels and data lanes. Extract only genuinely common presentation and operations from onboarding; the homepage stays read-only and onboarding keeps its behavior, including touch/reduced-motion handling. Delete redundant candidate/project-specific bridges when their replacements are proved.
- One isolated fixture workspace with declared media, profiles, versioned documents, immutable objects and local-only preferences. Real native operations place, move, trim, select, replace and update clips/tracks using existing validated timeline commands/patches; no canonical writes or invented success receipts. Explicit local rendering-element/extension catalog, no live agent, generation, credential access, discovery, pack admission or Runtime requests. Never turn a demo flag into authority over a real project.
- Independently composable cues for chat open/close and model identity, typing/send/streamed replies/attachments, action start/result/failure including parallel actions, gallery open/close/reveal/selection/variants, native timeline patches, panel/layout/lane changes and extension-defined typed controls, play/pause/seek, cursor and measured spotlight. Support multiple authored exchanges and named conversations; one visible active chat at a time initially. Show only supplied/recorded outcomes and identify scripted material; no invented real execution. A simple data spec, not an arbitrary UI automation language.
- Extend the existing browser-demo director with cumulative ordered events and sampled continuous transitions; presentation clock distinct from the current timeline and source-media clocks. Mutations apply once at a cue, with stable IDs, deterministic reset/replay, observed native state, acknowledged decode/empty/still/live scene readiness, semantic anchors and real DOM identity. No hidden wall-clock animation in a recorded frame. Preserve existing extension showcase authoring compatibility via a thin migration or adapter.
- A single documented local preparation/render function and command consuming the same spec and exact pinned App/pack/asset closure, plus integration into the existing Astrid Video scene preparation/assembly path. Output a verified ordinary video asset with editable spec, receipt, and reusable cache identity; retain exact frame timing, media bindings and anchor snapshots for supported editorial handoffs. No direct nested editor in a Remotion effect. No new effect descriptor until separately needed/proved.
- Two public, reproducible qualification fixtures: first, migrate the existing nine-example extension showcase (three panels, three lanes, three preview treatments, intro/outro); second, start with a small empty/rough timeline, type a prompt, show two overlapping tool actions (including a failure case), reveal prepared gallery assets, apply real timeline edits, show feedback and a replacement, play the revised result. A second author must make a different short demonstration from data alone, without a new React bridge, renderer, selectors or source patches. Use existing bundled Lantern Valley media or small generated public fixtures, not owner/private media.

Deferred: arbitrary cross-domain workspace/control API, multiple simultaneously mounted whole Apps, native/Rust rewrite, live agent/generation execution, automatic capture of arbitrary recorded sessions, new extension security model, live interactive nested Remotion export, general project-pack media-binding changes, broad onboarding redesign, publication of marketing videos, and native pack action admission unless separately agreed and qualified. Ordinary capture should need no fake Runtime HTTP service, CI, private repo or GPU/model spend.

## Completion

- From clean pinned checkouts, a local user follows the documented command and imports/renders an App Demo without App source rewriting, Runtime/ACP calls, live generation, account credentials, or CI. The same entry point accepts both fixtures, and the second author uses only a new data spec/assets.
- Show the genuine editor in all eleven extension destinations. Render the 728-frame 24fps showcase (30⅓ seconds) and a separate roughly 20-second collaboration scene. Inspect real output and transition midpoints, matching native baseline chrome and source media. Identify illustrative data and player prototypes; do not claim newly shipped extension APIs.
- The collaboration film shows typed prompt, sent message, streamed reply, overlapping native action cards and their truthful statuses, gallery arrivals, native clip placement/trim/replacement and matching player. Verify actual timeline state and stable workspace/player identity across pane changes, while the empty-state preview may initialize on first content. Preserve valid source clocks when clips change and no repeated applied mutation on same-frame sampling. Backward seek/reset replay yields the same semantic state and equivalent frame observations at sampled checkpoints.
- Fail closed on unknown cues, missing/foreign assets, invalid timeline patch, failed action represented as successful, stale/unsupported extension or decode failure, unexpected real-network attempt, media clock mismatch or missing visible anchor. Prove no real workspace or persistent user-state mutation; negative tests exercise two independently mounted/disposed runs in fresh documents and cleanup. Existing homepage/onboarding/native-editor and admission tests remain green relative to exact base.
- The normal scene assembly consumes the captured file as media, validates receipt and final frame count; changing editorial audio or unrelated scene does not invalidate the unchanged capture. Prove local native placement/preview/export of the captured ordinary clip through the supported route if claiming that integration. Do not call standalone capture a native pack-effect or native export PASS. Final review compares exact integrated source, tests and actual MP4s; acceptance, merge and release remain separately authorized.
