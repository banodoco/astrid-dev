## Planning evidence

**Scope decision:** Pending — On 28 November 2026 the owner asked for the onboarding-demo capability as an importable Astrid Video function with configurable chat, actions and timeline placement and no explanatory tour text, and created the first draft of this project ([#2084](https://github.com/banodoco/astrid-dev/pull/2084)). Later that day the owner reviewed the critique below and asked for this revision. Next: independent critique, then D1–D4 and a recorded greenlight.

**Prior art:** Source read on 28 November 2026 at the identities below.

- App main already contains the host the first draft planned to build: `src/app/demo/{index.tsx,AstridDemoSurface.tsx,fixture.ts}` (merged in `08c585c`), the isolation fix that keeps injected hosts out of Runtime pack discovery (`912c1da`, with a `VideoEditorProvider.test.tsx` case), and three later changes: optional chat, a theme toggle and seeks through the timeline (`8c594aa`). The controller exposes `ready/setView/seek/selectClip/focus/currentTime`; `chat` accepts only a React node, so a pack-authored spec cannot drive it yet. The only demo test is `fixture.test.ts`.
- The tour already applies real timeline patches through the store (`EditorTourTimelineDriver.tsx` calls `ops.apply(createEditorTourStagePatch(...))`), so patching needs no new path. `TourChatPanel.tsx` exports `IdleChatPanel`/`TourChatPanel` over native composer, model line, message and action views; its turns are hard-coded in `tourChatTurns.ts` and timed by `performance.now`. `buildRenderedTurns.ts` pairs calls and results by ID.
- Pack `shared/scene/browser-demo.mjs` (87 lines) compiles beats/views/numeric actions and captures sequentially with identity and anchor checks; `browser-demo.test.mjs` passes 5/5 locally. `render_project.py` dispatches engines through a fixed dict to `render_*.py` beside it and records a receipt; it has no browser engine and no cache.
- Internal astrid-marketing `projects/astrid-extension-showcase/importable` (read with owner permission at `df7e2bb`) is already a generic launcher, not a one-off: `local.sh APP PACK OUT serve|smoke|full [--demo ID] [--hide-chat] [--theme]` stages `index.html`/`entry.tsx`/`demo-types.ts` and one `demos/<id>/` into the App checkout's `examples/` directory, serves it with the App's Vite config, and removes it on exit. `capture.mjs` drives `browser-demo.mjs` with Playwright, waits for the decoded source frame, checks workspace and player identity and aborts Runtime and off-origin requests; `encode.py` composites frames with a section/title/detail header and checks frame count with ffprobe. `DemoDefinition` (TypeScript) holds workspace seed, profiles, source clock, panels, lanes, views and beats; a demo may add `effects.tsx` (trusted extensions and preview painters) and `capture.mjs` (named Playwright interactions). Two demos exist: Lantern Valley (the nine-example showcase, with interactions and prototype effects) and Passing Shapes (47 lines of data, no custom code). `plan.mjs` pins App `8c594aa` but pack `611742a`, older than pack main.
- The marketing README and the pack skill both report the showcase passed local Chromium on macOS (11 destinations, one player, zero Runtime/off-origin requests, 728 frames at 24 fps, 1920×1080). No receipt or MP4 is committed (`evidence/` holds only the earlier prototype summary), so this is **reported, not verified here**.
- Every other `astrid_video` tool has a schema with defaults (`element.yaml`), a renderer in `tests/packs/astrid_video/preview/`, an example spec, a `test-*.cjs` or `.test.mjs` test, a parameter reference, a skill entry and a catalogue row. App Demo has a skill and two investigation documents (`app-demo-integration.md`, marked historical; `importable-app-demo-host.md`), and its examples and launcher live outside the pack.

**Approach:** Keep the first draft's architecture: the real App in a dedicated browser document, the pack's director and a plain data spec, the capture as ordinary media, no nested Remotion effect and no copied UI. Change its scale: build on the merged host instead of re-qualifying a candidate; add two controller methods rather than a new capability registry; keep reset as remount; let the director own all time and the App render snapshots; put the renderer, examples and docs where the pack's other tools keep theirs; defer gallery, multiple conversations and typed extension controls until a film needs them. Alternatives retained from the first draft: a routed fake Runtime (extra services for a scripted film), the whole App inside a native effect (conflicts with element source closure and nested player lifecycle), a pack-only replica of the UI (not an accurate demonstration), a general workspace API (Plans 24 and 46), and one manual recording (not repeatable).

**Challenge:** Partial — In this session (28 November) the first draft was critiqued against App `8c594aa` and pack `81c60a3`. Findings: the draft predated the merged host, the isolation fix and the generic marketing launcher it planned to build; it proposed a second controller interface and in-place reset; its cue vocabulary approached a UI automation language; it did not cover pack parity (catalogue, skill, consolidated reference, renderer location, schema). This revision applies all four. The same session wrote the revision, so this is not the required independent critique. Next: a fresh high-judgment advisor reads these files and the cited source, especially the APD-1/APD-2 contract and whether the collaboration film is the right second proof.

**Proof and limits:** New proof must come from the pack's own command on public inputs: both MP4s, receipts, the negative cases in [plan completion](plan.md#completion) and the runner integration. The reported marketing qualification is a donor, not evidence for this plan. No production-generation claim, native export or gap closure.

**Review rounds:** Pending — recommend one final round R and no review stop: the only load-bearing seam (the snapshot and patch contract) is small, written in the plan, and covered by the critique before greenlight; the estimate is at or below five days. Next: the owner confirms.

## Owner decisions

- D1 — Boundary and name. Recommend: `appDemo` is an Astrid Video **footage tool** (spec, command, runner engine) and not an admitted effect; the catalogue says so explicitly. Alternative: wait for a native effect host, which no current plan delivers.
- D2 — First cue set. Recommend: views, lanes, seek, select and focus (existing), plus chat snapshots, actions with failure and overlap, and timeline patches. Defer gallery, multiple named conversations, cursor and extension-typed controls. Alternative: the first draft's full set (about 3–4 more days).
- D3 — Publishing the donor. The launcher and both demos are in internal astrid-marketing; workers must use public sources. Recommend: authorize copying `importable/{local.sh,plan.mjs,capture.mjs,encode.py,entry.tsx,index.html,demo-types.ts}` and `demos/{lantern-valley,passing-shapes}` at `df7e2bb` into poms_packs, with the source commit recorded in the APD-3 PR. Alternative: keep them internal and have the pack reimplement the launcher (about +1 day, and two launchers to keep in step).
- D4 — Release, accountable session, the 3–5 day estimate, the R budget and relative priority. Recommend the ordinary queue with no impact on Release 16 qualification. Do not add to priority or a release without the owner's choice.
