## Planning evidence

**Scope decision:** Pending — On 28 November 2026 the owner asked for the onboarding-demo capability as an importable Astrid Video function with configurable chat, actions and timeline placement and no explanatory tour text ([#2084](https://github.com/banodoco/astrid-dev/pull/2084)). In a planning session the same evening the owner reviewed two rounds of critique, asked for the result to feel like the real interface rather than stiff, deferred the cursor, asked what should be shared with the pack's other demos, moved the launcher into the pack (`poms_packs` `5134312`, `astrid-marketing` `4605b21`), and directed: "We should be building in astrid-video for video demo features." Next: independent critique, then D2–D6 and a recorded greenlight.

**Prior art:** Read on 28 November 2026 at the identities below.

- **App host.** `src/app/demo/{index.tsx,AstridDemoSurface.tsx,fixture.ts}` (merged `08c585c`, isolation fix `912c1da`, follow-ups to `8c594aa`). `DemoController` exposes `ready/setView/seek/selectClip/focus/currentTime`; `chat` accepts any React node. `seek` pauses the player and moves the playhead with `ops.onClickTimeArea`. The only demo test is `fixture.test.ts`.
- **Chat presentation.** `src/shared/components/conversation` exports `ConversationPresentation({items, footer})`, `ConversationMessage` and `ConversationToolGroup({pairs})`. `importBoundary.test.ts` forbids it from importing video-editor, session, auth, pane or network modules. The pack can therefore build chat from data without new App code. The tour's `tourChatTurns.ts` is hard-coded and timed by `performance.now`.
- **Timeline patches and frame readiness.** The tour applies patches through `ops.apply` (`EditorTourTimelineDriver.tsx`). `ReadinessVideo.tsx` publishes `data-preview-presented-frame` as the player's absolute timeline frame for each clip, with `data-preview-media-src`; readiness is therefore already in timeline time, and only the launcher's single-source match prevents multi-clip playback.
- **Archive reading.** `timeline-transfer.ts:importTimelineArchive` reads and verifies an `astrid.timeline/1` archive (manifest, entries, transcripts) in the browser, then calls Runtime to commit. The pack's `prepare-archive.py` repeats the reading in Python with stricter limits (one embedded video, no transcripts, effects, transitions or elements).
- **Pack launcher (owner commit `5134312`).** `astrid_video/shared/browser-demo/{local.sh,plan.mjs,capture.mjs,entry.tsx,index.html,encode.py,demo-types.ts,prepare-archive.py}`, moved from astrid-marketing with only path and commit-recording changes. `local.sh APP OUTPUT serve|smoke|full [--timeline FILE | --demo ID]`; named demos come from `ASTRID_DEMO_FIXTURES`. Capture uses Playwright with `reducedMotion: 'reduce'` and `deviceScaleFactor: 1`; `encode.py` fixes 1920×1080 and draws section/title/detail in DejaVu Sans with hard-coded colours; archive captures always carry "ASTRID · LOCAL PROJECT". No tests, no runner engine, no public example in the pack. Marketing keeps `demos/{lantern-valley,passing-shapes}` and a wrapper that pins App `8c594aa` and pack `5134312`. Both demos use only App-bundled media (`/astrid/light-study/passing-shapes.mp4`, `/astrid/onboarding/lantern-valley-14s-v1/`). Marketing's README reports a local 728-frame showcase render; no receipt or MP4 is committed, so this is reported, not verified here.
- **Pack director and tools.** `shared/scene/browser-demo.mjs` (5/5 tests pass) compiles views, beats and numeric actions with a single-source clock and a camera capped at 5% zoom. Living Composition demos (`docs/references/example-{journey,exchange,extension}.yaml`) use items, timed poses, transitions and accents, with an `inspect` summary and storyboard contact sheet. `shared/timeline/model.ts` eases one move/trim/replace revision and runs one timeline clock across clips and players. `shared/activity/model.ts` (Agent at Work) is a pure event clock with fixed-rate typing, done/failed/waiting statuses and overlap, but no messages, composer, send or streaming. About seven renderers inline their own ffmpeg calls; only `render_project.py` writes a receipt. `node --experimental-strip-types` cannot import the activity or timeline models because their relative imports omit extensions; `tools/source_closure.py` already resolves explicit `.ts` imports.
- **Stepped clock check.** In a planning-session Chromium test, pausing Playwright's clock, advancing it one frame at a time and pinning every `document.getAnimations()` entry to that time produced byte-identical frames across two runs with motion in every frame (CSS transition, CSS keyframes and a `requestAnimationFrame` loop). The App animates with CSS (Tailwind, `tailwindcss-animate`), not a JavaScript motion library. Not yet checked: Remotion player playback, the Three.js sandbox iframe, native smooth scrolling.
- **Recorded feedback.** The recreated interface was rejected for looking unlike Astrid (`demonstrating-astrid-app/SKILL.md`; marketing `evidence/prototype-summary.json`); the owner asked for no tour text; one early capture showed an empty transcript panel. In this session the owner said stiff, stilted footage would not be good enough. No other attributed feedback on pacing or motion was found.

**Approach:** Keep the real App in a dedicated browser document, a plain data spec, and the capture as ordinary footage; no nested Remotion effect and no copied UI. Build in Astrid Video. Let the App's own animations run on a stepped clock instead of disabling them. Render chat in the pack from the App's transport-free presentation components. Reuse the pack's timing grammar, timeline and activity models, renderer conventions and review artefacts rather than inventing parallel ones. Alternatives considered: a routed fake Runtime (extra services), the whole App inside a native effect (conflicts with element source closure and player lifecycle), a pack-drawn replica of the UI (rejected by the owner), a general workspace API (Plans 24 and 46), real-time screen recording (feels natural but is not repeatable or frame-exact), and one manual recording (not repeatable).

**Challenge:** Partial — In this session the first draft was critiqued against current source: it predated the merged host, isolation fix and marketing launcher; it proposed a second controller and in-place reset; its cue list approached a UI automation language; it lacked pack parity. Later rounds found that the launcher's disabled animations make footage stiff, that multi-clip playback is blocked only by the launcher's single-source match, and that timing, timeline, activity, encoding and receipt logic should be shared with the pack's other demos. This revision applies all of these. The same session wrote it, so this is not the required independent critique. Next: a fresh advisor checks the App seams, the stepped-clock risk and whether eight tasks is the smallest sound split.

**Proof and limits:** New proof must come from the pack command on public inputs: both films, byte-identical repeat renders, the side-by-side comparison, the negative fixtures, the runner manifest, the Timeline Assembly and Agent at Work regressions, and `run_local.py`. Marketing's reported showcase render is a donor, not evidence. No production-generation claim, native export or gap closure.

**Review rounds:** Pending — recommend one final round R and no review stop: the App seams are small and written in the plan; the stepped-clock risk is gated inside APD-2. Next: the owner confirms.

**Run start:** Pending — No run is authorized. Next: after greenlight, choose a release and accountable session, record bases and authority.
