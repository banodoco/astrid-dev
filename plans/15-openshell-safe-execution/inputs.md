### Alternatives and decisions pending

- Reuse existing attached transport instead of changing project/timeline contracts or mounting the host filesystem. No host mounts in the proposed normal connected path. Qualify the relay and ComfyUI API with actual image/video/media round trips; no assumption that arbitrary custom nodes are safe.
- Keep a strict no-host-integration profile; connected mode should preserve existing models/custom nodes where compatible with a declared trust policy. A native ComfyUI is a trusted external execution service, not automatically contained. Decide the smallest outside-guest enforcement sufficient for the claim, with a narrowly scoped broker or isolated GPU worker as follow-up if necessary.
- Keep standard browser and chat UI. Prefer the existing browser door over new protocols; decide hosted versus guest-served pinned App and extension restrictions based on threat model/compatibility, not just where JS is served.
- Treat deployment isolation as a persistent installation-mode selection distinct from guest process-control mode. Reuse choice/consent machinery, decide exact flags and guest/host handling for start-at-sign-in, terminal and skills. No silent fallback or host-side agent provisioning.
- Agent support: qualify bundled Astrid first, Codex alongside where feasible; independently assess Claude Code and Hermes. No claim of parity or current provider connectivity without a real login/session/tool proof.
- Upstream version, supported platform matrix, guest app/extension boundary, safe attached-node policy, import/update/backup design, and proof environment remain pending. Independent security/architecture critique required before greenlight; no reviewer or execution has been claimed. Local documentation validation and product tests not run in this exploratory assessment.

## Follow-up: one lifecycle, costs and eventual default — 25 November 2026

Owner asked how auto-launch works with OpenShell, what its practical downsides are and what would need changing if isolation were used for every Astrid installation; then requested that this direction be made clearer in the plan. Proposals (not owner-approved defaults): make the initial option experimental/opt-in; investigate isolation as recommended/default on qualified platforms after measured gates; retain native and do not build another product.

- [OpenShell gateway installer](https://github.com/banodoco/astrid-agent/blob/dc45d97c6bc2734cbfb9b2a25b43cb40ed5757e5/scripts/openshell/install-openshell.sh#L160-L263) writes start/stop-gateway.sh and starts the gateway in the background; its own comments and output explicitly say it does not start at login. Its config defaults are 4 vCPU, 8192 MiB RAM and 32768 MiB overlay capacity. These are configuration values, not measured host consumption. The old setup uses detached Runtime in the VM without systemd.
- [Guest start/restart and door](https://github.com/banodoco/astrid-agent/blob/dc45d97c6bc2734cbfb9b2a25b43cb40ed5757e5/scripts/openshell/astrid-openshell.sh#L570-L630) start guest Runtime and relay, then forward the local door; HTTP 200/403/404 answering is not sufficient evidence of correct deployment identity. Stop/resume are distinct operations; host startup, identity, recovery and policy verification need a cohesive owner. Existing [installer service](https://github.com/banodoco/astrid-agent/blob/dc45d97c6bc2734cbfb9b2a25b43cb40ed5757e5/astrid/installer/service.py), [runtime lifecycle](https://github.com/banodoco/astrid-agent/blob/dc45d97c6bc2734cbfb9b2a25b43cb40ed5757e5/astrid/installer/runtime_lifecycle.py) and [update job](https://github.com/banodoco/astrid-agent/blob/dc45d97c6bc2734cbfb9b2a25b43cb40ed5757e5/astrid/installer/update_job.py) already implement native lifecycle/choices; reuse the public behavior but route isolated startup to the host supervisor, not direct native Runtime. Exact service implementation/host APIs pending.
- App surfaces to rebind at dispatch: [RuntimeConnectionProvider](https://github.com/banodoco/astrid-app/blob/cc1d48f016fde55ad6b0609c619d8a4bcec56823/src/integrations/runtime/RuntimeConnectionProvider.tsx), [connection panel](https://github.com/banodoco/astrid-app/blob/cc1d48f016fde55ad6b0609c619d8a4bcec56823/src/shared/components/RuntimeConnection/RuntimeConnectionPanel.tsx), [connection pill](https://github.com/banodoco/astrid-app/blob/cc1d48f016fde55ad6b0609c619d8a4bcec56823/src/shared/components/RuntimeConnection/RuntimeConnectionPill.tsx), [update routing](https://github.com/banodoco/astrid-app/blob/cc1d48f016fde55ad6b0609c619d8a4bcec56823/src/shared/lib/updates/resolveUpdate.ts), [update Settings](https://github.com/banodoco/astrid-app/blob/cc1d48f016fde55ad6b0609c619d8a4bcec56823/src/shared/components/SettingsModal/sections/AstridUpdatesSection.tsx) and [agent setup card](https://github.com/banodoco/astrid-app/blob/cc1d48f016fde55ad6b0609c619d8a4bcec56823/src/tools/video-editor/components/AgentChat/AgentSetupCard.tsx). Current update logic distinguishes installation provenance including Pinokio/source; do not overload that ownership with deployment mode. Prefer independently verified deployment mode, with no unchecked inference from frontend storage or port health.
- Alternatives: eager start-at-login matches current behavior but consumes resources when idle; a lightweight always-running host launcher and on-demand VM can reduce idle cost but creates a privileged control surface and wake latency; manual launch is a safe fallback when autostart is off or no authenticated wake path exists. No browser wake via arbitrary commands, no automatic fallback, and no automatic idle stop until all jobs/dirty data/activity are accounted for. Compare both before selecting the default lifecycle; no need for optional wake/idle to block initial eager/manual opt-in if those are qualified.
- Measure matched native/isolated cold install, cold and warm startup, idle/peak RAM/CPU/disk, same GPU job duration and transfer, editing and CPU render/export. Separate VM/gateway overhead from baseline and from configured capacity; actual requirements, overhead ceilings and platform support are unmeasured and must be agreed before proof. A container backend or direct GPU passthrough has a different security/operational trade-off; never silently swap to an unqualified driver.
- Independent architecture/security critique, product runs and local documentation checks remain pending. This is an exploratory plan-only amendment, not permission to implement, schedule, publish, recommend by default, or change other plans.
