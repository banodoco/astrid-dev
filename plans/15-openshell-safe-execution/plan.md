# Sandboxed execution with OpenShell

**Project:** Sandboxed execution with OpenShell

**Goal:** Make an isolated Astrid installation a first-class choice in ordinary onboarding, preserving normal creative workflows and assessing whether it can become the recommended deployment by default.

**Status:** queued

## Goal and scope

Exploratory revision (25 November 2026). The owner asked for an ordinary onboarding checkbox to run Astrid inside OpenShell and for investigation of the compromises for existing agents and ComfyUI. This is a deployment option for Astrid, not a separate product, a new agent framework, or a claim of absolute safety. Keep native installation unchanged. The proposed trajectory is experimental opt-in on qualified platforms first, then consider recommending isolation by default only after measured usability, compatibility, performance and security gates pass and the owner agrees. Native remains an explicit alternative; never silently substitute it. No implementation, scheduling or release is authorized by this draft.

- **Onboarding:** add a visible, initially opt-in choice, proposed copy: “Run Astrid in an isolated environment (OpenShell)”. Explain that the agent and its tools run in a separate VM, personal files and unrelated services are not exposed, and external agents may need to be installed and signed in again. Use the existing App setup surface, copied coding-agent instructions, terminal setup and [Plan 20](../20-zero-to-first-image/plan.md) choices contract. A host launcher must create and verify the VM before running the guest installer; the existing internal `--sandbox` process-control flag is not itself an isolation mechanism. Preserve the choice on repair, update and restart; never fall back to a native install after an isolation failure. Do not show an actionable option on an unqualified platform.
- **Boundary:** default to a dedicated microVM, no host directory mounts, no inherited host credentials or agent config, no ambient LAN or unrestricted outbound access, explicitly selected services and user-mediated file transfer. The Agent, Runtime, chat/ACP processes, terminals, pack code, project data, renderer and their children run in the guest. The host browser and small trusted launcher/gateway are outside. Reuse the browser door; qualify the App build, authentication, instance identity and media/events transport. Investigate pinned/local App serving in the guest, but do not assume browser-executed extensions inherit guest network policy. Review their trust, egress and exposed host interfaces separately before claiming full-stack isolation.
- **Existing ComfyUI:** make API-only attachment to a user-authorized existing host ComfyUI a first-class connected mode, reusing the current relay and HTTP upload/history/`/view` artifact path without exposing the output folder. The strict mode has no host ComfyUI grant. Model discovery and generation using already available models/nodes should remain familiar; host installation, model downloads into host folders, node management and process control cannot be silently performed by the guest. Explicitly separate these operations and consent. Test node/parameter and job-scope restrictions enforced outside guest control; unrestricted native custom nodes can exercise host permissions, so endpoint allowlisting alone is not strong isolation. If a narrowly scoped trusted broker or isolated ComfyUI worker is needed, scope it from evidence; do not require a new GPU isolation architecture for an initial connected option. No weakening of strict mode to make connected mode work.
- **Agents:** preserve the existing chat/ACP, CLI, skill, tool and project interfaces. Discover, install, authenticate and launch agents inside the guest; do not copy or mount host agent homes, credentials, MCP configuration or binaries, or silently launch a native agent. Astrid's bundled agent and Codex have historical OpenShell setup paths. Claude Code and Hermes exist in the current product catalog but lack equivalent qualified sandbox setup. Investigate each agent's guest dependencies, provider access, login flow, skill sync, terminal commands, cancellation, session recovery, and nested sandbox assumptions. Show honest unavailable/setup-needed states rather than breaking the native agent menu. An outside coding agent may perform the explicitly approved initial host setup; it is not the same thing as Astrid's in-guest agent.
- **Host lifecycle:** retain one user-visible Astrid lifecycle. A small trusted host launcher/supervisor, integrated with the existing start-at-sign-in choice and OS service manager, owns the OpenShell gateway, verified VM driver/identity, VM boot/resume, guest Runtime and browser forward. The guest installer does not create a second host autostart service. The App cannot directly start host processes from ordinary browser JavaScript; when no launcher is available, provide the exact safe manual/agent start action. If a browser-triggered wake is pursued, use a narrow authenticated, origin-checked control endpoint that accepts no arbitrary commands, files or arguments; prove refusal of unrelated origins/instances. Start at sign-in on/off, manual start, stop, crash recovery, host reboot, app reconnect, upgrade and uninstall must be coherent; no orphan gateways/forwards or native fallback. Investigate keeping only the lightweight launcher idle and starting the VM on demand, or starting at sign-in as today. Automatic idle shutdown is optional until outstanding jobs, session activity, renders, updates and state flush can be reliably observed; never stop active work or auto-wake after explicit stop without agreed semantics.
- **Resource and compatibility budget:** compare native and isolated on the same supported hardware, release tuple, models and projects: installation and cold/warm connection time, idle/peak host memory (including gateway and VM), CPU, disk actual usage versus capacity, timeline responsiveness, HTTP media transfer, host GPU throughput, CPU render/export and shutdown/recovery. The existing allocation (4 vCPU, 8 GiB RAM, 32 GiB overlay) is not measured overhead or a product requirement. Measure a modest-memory machine as well as a workstation, and agree acceptable deltas before qualification. Keep GPU passthrough and alternative containment drivers as investigated follow-ups, not implicit equivalent security or mandatory V1 work.
- **Lifecycle and custody:** retain project/media IDs, manifests, generation settlement and browser editing contracts; import/export files through an explicit trusted transfer path rather than exposing personal folders. Keep guest data through stop, restart, update and rollback. Provide recovery, permission inspection and revocation, emergency stop and safe removal. A failed install/update must restore restrictive policy or stop the VM. No destructive rebuild as normal setup.
- **External inference:** explicitly selected network/service and spend permissions, scoped credentials where supported, and visible data sent outside the VM. No claim that network permission is equivalent to privacy from an authorized provider or that all packs are isolated from each other inside one VM.

## User experience and App changes

The installation choice is the only new top-level setup decision. The rest should feel like ordinary Astrid, with details exposed when a user needs to grant access or recover. Reuse existing surfaces, not a separate OpenShell dashboard or duplicate project/generation path. Proposed UI scope:

| Existing surface | Change |
| --- | --- |
| SetupBlock, copy and shared install choices | Visible “Run Astrid in an isolated environment (OpenShell)” checkbox; fresh-install command and agent brief agree; preserve saved selection on start/repair/update; unsupported platform and resource preflight explain why unavailable. Start at sign-in retains its meaning and controls the host lifecycle, not a service inside the guest. |
| Runtime connection provider, panel and pill | Use verified deployment provenance/instance identity rather than a cached checkbox. Distinguish gateway absent, VM stopped/starting, guest Runtime unready, policy or identity failure and connected; show bounded progress, honest diagnostics and a safe manual/agent recovery action. No connection to a native instance merely because it answers the same port. |
| Existing Settings and update surfaces | Show current native/isolated mode, strict or connected policy, actual approved services, start/stop/restart, revoke and diagnostics; use the existing updater's identity-based routing and maintain projects/agent sessions. Actions must be authorized by the trusted host boundary. Mode migration is explicit, not a toggle that silently moves or deletes a project. |
| Agent setup card and agent menu | Use guest discovery/ready states, guest installation and login commands, and honest unsupported states; retain same ACP and chat UX. No host CLI or account discovery disguised as guest readiness. |
| Generation setup | Detect/authorize a specific host ComfyUI using a trusted host step (no guest LAN scan), show it as an external execution service with its residual custom-node risk, preserve generation results and progress through existing HTTP transport. Declining must leave strict mode intact. |
| Media import/export and extension surfaces | Use existing project media APIs where possible, user-selected transfer instead of mounts, and assess browser-executed extension permissions/egress. No general host shell, file bridge or unrestricted local API. |

Normal timelines, project DB, generation gallery, rendering and core editing contracts stay shared with native. If a gap appears, fix the actual boundary; do not fork the App.

## Proposed delivery increments

1. **Exploration and boundary decision:** source reconciliation, real OpenShell platform/driver assessment, agent and mount-free ComfyUI feasibility, launch/reconnect design, performance baseline and independent security critique. Agree support and overhead gates before implementation greenlight.
2. **First useful opt-in on a qualified platform:** strict mode plus separately consented connected ComfyUI; one installation flow, existing App/ACP/project experience, host lifecycle and safe update/recovery, minimum supported agent(s), real creative proof. Unqualified agents/platforms remain clearly unavailable. An optional stronger connected-node boundary, additional agent/provider routes and platform expansion are evidence-scoped, not promises of parity.
3. **Broaden and assess default:** measure on representative supported machines, resolve meaningful incompatibilities, qualify more agents/platforms, consider safe on-demand/idle lifecycle, and only then seek an owner decision on making isolation recommended/default per platform. Do not require universal GPU isolation, all four agents, or a major refactor just to deliver the first useful opt-in unless the agreed security claim requires it.

## Sequence

1. Reconcile the release candidate, upstream OpenShell version/driver/platform support, and existing code. Investigate mount-free ComfyUI, actual agent compatibility, onboarding/installer, host lifecycle, resource budget and browser trust boundaries in parallel.
2. Agree the strict/connected threat model, platform/agent support matrix, resource/latency acceptance budget and install/instance/lifecycle contract. Independently critique this security boundary before seeking implementation greenlight.
3. If approved and scheduled, adapt the existing launcher, App setup choice, guest agent setup and API-only generation attachment in bounded lanes; preserve native behavior. Integrate once the shared mode/permission and Runtime identity contracts are settled.
4. Qualify a real installed creative journey and negative cases on each declared supported platform before surfacing the option. Linux x86-64 with usable virtualization is a proposed first lane; macOS and Windows require their own qualification, and current upstream support must be rechecked.

Coordinate at actual shared surfaces with [onboarding](../20-zero-to-first-image/plan.md), [agent setup](../16-streamlined-agent-experience/plan.md), [generation placement](../32-generation-placement-targets/plan.md) and [inference routing](../12-multiple-inference-routes/plan.md). These are not blanket scheduling dependencies.

## Completion

On a declared supported platform a person selects the checkbox, completes the normal setup (including agent-led setup), connects the browser to the intended VM, connects an approved agent account, creates a project, generates from authorized existing ComfyUI without a host folder mount, retrieves media into guest custody, edits, saves/reopens, renders and exports. Demonstrate cancellation, service revocation, start-at-sign-in on/off, clean host reboot and automatic reconnect, manual stop/restart, update/recovery and project preservation, no orphan lifecycle processes and no hidden native fallback. Compare measured native/isolated resource and performance budgets. Qualify any optional wake/idle behavior before enabling it; default promotion is a later owner decision, not automatic completion of the initial opt-in. Strict mode refuses host ComfyUI; both modes refuse unrelated host files, credentials, sockets, native execution and unapproved network access; connected mode documents and tests its narrower boundary and residual host custom-node risk. Show unsupported agent/platform states and failed-setup refusal, plus native-install regression checks. Record version-pinned positive and negative installed evidence, not just script or unit-test existence. Integration and publication follow the [shared run contract](../../agent/shared/run-contract.md).
