**LE-1 contract card.** Today a placement is only reachable through `place_element`, which opens its own session and submits one `clip.set-element` (`astrid/sdk/timeline_elements.py:419`, `:455-457`, `:507-546`); nothing in `model.py` or `edits.py` stages one. After LE-1 a commit function can stage it, and the pin and schema inputs are captured the way `place_element` captures them now (`_admitted_element_inputs`, then `execute(..., schema_inputs=...)`). `place_element` and the CLI keep their one-target behaviour, so `test_placement_writes_exact_admission_pin_and_retries_by_identity`, `test_stale_expected_head_refuses_before_commit` and `test_sdk_first_placement_rejects_unsupported_element_kinds` stay as they are; add the mixed cases beside them. Makes untrue: `generated-elements-authoring.md:65`, which teaches one `place-element` call per clip as the way to retarget. Two things to prove rather than assume: `clip.add` refuses occurrences (`astrid/sdk/timeline/_clip_commands.py:16-18`), so a text clip added inside a shot must travel as the `doc.patch` that `_capture_free_edits` emits (`commit_session.py:485`); and a native `clip.set-element` must coexist with those free edits in one request (`_commit_patch.py:293` switches such a request to atomic merge). If either fails, fix it in this task; do not fall back to two commits. Find other pinned assumptions with `rg 'place_element|clip.set-element' tests astrid` and re-check against the code at dispatch.

**LE-2 contract card.** The Runtime runs the Agent's commit code in its own process (`runtime_protocol/timeline_commit_provider.py:70-99`), and the element registry there is an `lru_cache` (`astrid/core/element/registry.py:197`). `element_schema` already clears it when a known provider changes on disk (`astrid/sdk/timeline_address.py:471-492`) but not when an element was missing, so a pack installed later stays invisible until restart. The fix is one retry on that miss path, in the Agent; no Runtime change and no new message between processes. Makes untrue: `tests/core/pack/test_cli_manage.py:test_packs_add_with_a_pending_host_refresh_prints_the_one_availability_line`, which pins "The pack is available after the host's next start." The pack host in fact acknowledges the refresh while idle (`GenericPackHost.acknowledge_pack_refresh`), so reword the line to say the pack is picked up by the running host, and update that assertion. Find other pinned wording with `rg 'next start|refresh_pending' tests` and re-check against the code at dispatch. The restart link was reported from one run, not reproduced: the first step is to reproduce the miss in a test, and if the cache is not the cause, say so and fix the real one.
