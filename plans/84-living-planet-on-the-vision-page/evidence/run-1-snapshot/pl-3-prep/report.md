## Camera, resize, and stage seam

- `initPlanetEngine(canvas, ...)` starts with perspective camera at `(0, 1.45, 12.6)`, looking toward the origin, FOV 38°, aspect 1 (`worktrees/pl-1/src/pages/Home/planet/planetEngine.ts:6757–6759`). `planetZoom` starts at 1.83 (`:8388–8389`).
- **Parent size is the camera's layout input.** `updateCameraProjection()` gets `stage = canvas.parentElement`, reads `stage.clientWidth/clientHeight`, and reads `heroH = stage.parentElement?.clientHeight || h` (`:8391–8400`). It sets aspect, FOV from `minHalfH = max(5.05, 5.1/max(.48, heroAspect))` and `halfWorldAtZoom1 = minHalfH*(h/heroH)`, then zoom and view offset (`:8401–8412`). The view offset has an `x = -0.23*w` shift only when the **stage width** is at least 1024 px, and y bias uses the stage height vs. its parent hero height (`:8407–8411`). Zoom is `planetZoom*.72` only when **stage width** is under 640 px (`:8405–8406`).
- In current `PublicAstridPlanet.tsx`, the canvas is a direct child of `.astrid-vision-juggler.astrid-vision-planet` (`:41–44`). The shared `.astrid-vision-juggler` CSS still gives that stage `width:65*--px`, `height:100*--px` (`PublicAstridVision.css:66–77`): 260×400 at the base 4px scale, 195×300 for widths 761–1000, and roughly 130–195×200–300 at phone widths from the mobile `--px: clamp(2px,.75vw,3px)` (`:407–423`). As currently composed, stage width remains far below both camera thresholds at all viewport sizes; page viewport breakpoints therefore do not select the camera's 640/1024 branches as the code may suggest. A PL-3 stage expansion changes both the camera's crop math and these branches.
- `resize()` uses the same stage dimensions for `renderer.setSize(w,h,false)` and a 260px-high pixel render target with aspect-derived width (`:8415–8426`). Renderer pixel ratio is capped at 2 (and forced to 1 for software GL; `:6740–6755`). Resize is registered on `window.resize` and called once at init (`:8447–8448`); there is no `ResizeObserver`. Parent-only layout changes, such as hero/content or CSS-driven stage size changes without a window resize, do not independently refresh projection. A new stage size should be observed at the stage boundary or otherwise explicitly invalidate the engine. The fixed 260px pixel-filter target is a separate sharpness/quality tradeoff for PL-5 to assess.
- Engine code makes no placement outside its canvas. Stage location, overflow/clip, viewport anchoring, and responsive geometry are owned by `PublicAstridPlanet`/page CSS. Current hero markup puts the planet in the hero grid next to copy (`PublicAstridVision.tsx:496–533`, planet at `:531`); its phone rule switches the hero to one column and moves the planet below copy at the existing 760px breakpoint (`PublicAstridVision.css:412–421`). Keep copy geometry stable while giving the camera a larger stage/view area. Manager's picture review is the visual constraint: tablet and landscape need enough world detail without overwhelming copy; desktop off-right placement is good but the left edge and flying props cross headline; do not collide with nav or headings.

## Pointer and touch behavior in current engine

- Listeners are on the WebGL canvas: `pointerdown`, `pointermove`, `pointerup`, `pointercancel` (`planetEngine.ts:8236–8386`). There is no `pointerType` filter, no `preventDefault`, and no current canvas `touch-action` rule in the inspected page/mobile CSS.
- Down records pointer ID and start point, begins drag, clears any target quaternion, starts the idle delay, and calls `canvas.setPointerCapture(id)` (`:8236–8254`). Move updates NDC; while dragging, only the primary pointer moves the world; each `dx/dy` is clamped to ±40px and converted to yaw/pitch. A move can also update mink glances when not dragging (`:8256–8286`).
- A second active pointer turns off dragging, clears primary ID, and zeros inertia (`:8236–8244`), but the cancellation branch does not itself release the first pointer's capture. `pointerup`/`pointercancel` share `onPointerUp`, remove the ID, and return early unless it matches `primaryPointerId`; the matching path clears drag, releases capture if held, and treats movement under 7px as a tap (`:8370–8381`). Cancellation during a short gesture can therefore still reach tap handling; primary/secondary cancellation and capture cleanup deserve focused coverage.
- Since touch defaults to browser `touch-action:auto`, the browser can take over a vertical page pan and issue `pointercancel`; the engine currently does not explicitly arbitrate vertical scroll versus horizontal spin. To preserve the required page scroll while supporting horizontal rotation, the canvas interaction surface should allow browser vertical panning (typically `touch-action: pan-y`) while reserving horizontal movement for the planet, and reliably clear/release state on `pointercancel` and multi-touch. `touch-action:none` would block the required vertical scroll. Validate on a real touch-capable browser; desktop emulation alone is not evidence of the finger-scroll requirement.

## Layering and pointer-events implications for PL-2/PL-10

- Vision CSS makes direct page children (apart from sky, details, and bar) positioned at `z-index:1`; the sky is a behind-page layer (`PublicAstridVision.css:482–485`). The nav bar has sticky `z-index:12` (`:1726–1732`). This protects navigation above ordinary sections, but a viewport-sized planet stage must not create a higher stacking context over the bar or hero copy.
- The PL-2 requirement that the transparent canvas be behind content and let clicks/scroll pass through conflicts with PL-10's need to receive horizontal spin. If the canvas or wrapper uses `pointer-events:none`, engine pointer listeners cannot receive drag. If it uses `pointer-events:auto` over the full page, it can block links, card/dialog triggers, and nav, or intercept touch input over text. Keep the canvas hit region bounded to the visible globe/interaction area, content/nav above it and hit-testable, and don't blanket-disable events on the globe if it must spin. Use a deliberate touch-action policy on the canvas, not an ancestor covering page content.
- PL-10 needs a user-horizontal-spin signal from the pointer path while PL-3 owns touch arbitration. Define that callback seam before edits: PL-3 can report user-driven horizontal angular delta from the canvas gesture path; PL-10 consumes it to update the sky session. Keep engine/session-driven time application separate from that callback so camera/touch changes do not echo time back to the session.

## Suggested disjoint ownership between PL-3 and PL-10

- **PL-3 owns** camera projection/zoom/view-offset math, stage sizing and resize observation, responsive framing CSS, pointer capture/cancel/multitouch behavior, and the engine's horizontal-spin callback *emission* at the gesture seam. Keep its callback semantic narrowly `user horizontal spin delta`, not general orientation-changed.
- **PL-10 owns** sky-session subscription and hour-to-engine synchronization in `PublicAstridPlanet`/`PublicAstridVision`, the engine's time-of-day mapping/lighting path, callback consumption that calls `session.setManualHours`, and suppressing any sync echo/autonomous drift. Both tasks touch `planetEngine.ts`; keep PL-3 confined to camera/resize and pointer-event blocks, PL-10 confined to `PlanetEngineAPI`/callback type, time mapping/light blocks, and session wiring in component/page. Integrate sequentially and rebase/review exact hunks; do not replace or reformat the shared engine file wholesale. Existing component edits should be coordinated before touching `PublicAstridPlanet.tsx`.
