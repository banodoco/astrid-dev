# PL-10 preparation: sky/session and planet rotation interfaces

Read-only route N preparation. Product code and the donor are unchanged. The inspected sources are the PL-10 prep worktree at its dispatch base and PL-1 worktree commit `5bfdabb` (`Add still planet and exercise lifecycle boundary`).

## Current boundaries and calls

- **The sky session owns effective time.** In `worktrees/pl-10-prep/src/pages/Home/publicAstridSkySession.ts`, `PublicAstridSkySettings.hours` is `number | null` (lines 41–44); default `null` means derive the visitor's current zoned hour (`effectiveHours`, lines 188–190). `createPublicAstridSkySession` uses `Date.now` by default (lines 280–285), and `onClock` refreshes the snapshot on the one-minute `CLOCK_TICK_MS` (line 26; `onClock` around 449–451). `getSnapshot().hours` is the effective current hour; `getControlsSnapshot().hours` is exposed to React's controls subscriber.
- `setManualHours(hours)` wraps into `[0,24)` and sets `settings.hours`, thereby pinning the session and stopping replay (`publicAstridSkySession.ts:527–530`). `setNow()` clears the pin (`hours: null`) and resets `dayOffset: 0` (`531–534`), returning subsequent session ticks to the visitor clock. The sky session already exposes this API, but regular page UI does not appear to surface it: the existing `PublicAstridSkyPreview` has a `Live` button wired to `setNow()` (`PublicAstridSkyPreview.tsx:59–68`) and renders only for the owner-only `?sky=` preview flow. Manager should choose whether/how PL-10 exposes a visitor-facing real-time reset.
- **Replay is session-owned and frame-driven.** `startHomeReplay(onEnd?)` is available only when mounted, visible, motion-enabled, and sky-enabled (`publicAstridSkySession.ts:535–560`). It adds `replayOffsetHours(elapsed)` to the session base hour; the eased offset advances 24 hours over 9 seconds between 500 ms turn and settle beats (`:35–38, :177–190`). Replay emits raster changes each animation frame; it ends and returns to the base hour at completion. `setManualHours`, `setNow`, and `cancelHomeReplay` stop/replace replay. Existing page mink interaction in `PublicAstridShell.tsx:220–267` starts this session replay; reduced motion skips it. PL-10 should follow `getSnapshot().hours` while replay runs rather than creating a second replay clock.
- **Page and sky palette already follow this owner.** `PublicAstridVision.tsx` gets its session through `usePublicAstridSkySession` and `usePublicAstridSkyControls` (`worktrees/pl-10-prep/src/pages/Home/PublicAstridVision.tsx:264–283`); `registerPaletteTarget(..., 'vision')` binds the page (`:390–391`); palette values are applied as CSS variables and theme (`:505–513`). `PublicAstridSky` reads controls with `useSyncExternalStore` (`PublicAstridSky.tsx:47–54, 194–196`) and paints from session snapshots. Thus calling `session.setManualHours` is the established path to update sky, palette, and any planet subscriber together.
- **The engine/component boundary is not integrated yet.** PL-1's `PublicAstridPlanet` accepts only `{ live, fixedPose, loadEngine }` (`worktrees/pl-1/src/pages/Home/PublicAstridPlanet.tsx:12–14`) and initializes the engine with `{ onReady }` only (`:24–28`). `PublicAstridVision` currently mounts `<PublicAstridPlanet live={visible && !reducedMotion} />` (`worktrees/pl-1/src/pages/Home/PublicAstridVision.tsx:531`). The engine API has `setTimeOfDay(hours)` but no getter (`planetEngine.ts:27–38`); init callbacks declare `onTimeChange(hours)` (`:42–49`). PL-10 needs a session snapshot-to-engine path through this component boundary, and a distinct drag-to-session path.

## Rotation, drag, and light representation

- The donor engine's presentation pose is a quaternion on `planetGroup`, initialized from Euler `(0.18, -0.32, 0)` (`worktrees/pl-1/src/pages/Home/planet/planetEngine.ts:8186–8187`). `fixedPose` controls deterministic simulation and initial lighting, but does not change that orientation. The time mapping in `applyTimeOfDay` anchors hour `18.6` to the donor Euler orientation: `phase = ((h - 18.6) / 24) * 2π`, `tiltX = 0.18 + sin(phase)*0.22`, `yawY = -0.32 - phase`, then creates a `targetQuat` (`:9005–9016`). Therefore the orientation naturally aligned with the current donor pose is **18.6h**, not noon. Noon is separately the engine's fixed-pose initial *lighting* (`:9005`) and the manager's requested comparison anchor; keeping noon lighting while retaining the donor pose requires documenting/implementing an explicit noon offset rather than assuming current yaw formula maps noon to the initial donor pose.
- Lighting is independently applied immediately by `setTimeOfDay`: it updates sun position, colors and intensity through `applyLightingForTime` and calls `callbacks.onTimeChange(h)` (`:8970–9003, :9007–9016`). Planet orientation then eases toward `targetQuat` in the animation loop (`:8518–8522`). The engine never currently calls `onTimeChange` from pointer input; it calls only from `setTimeOfDay`.
- Drag uses pointer deltas, capped at 40 px per event, and premultiplies yaw and pitch quaternions: `stepYaw = clamp(dx*0.006, ±0.055)` and `stepPitch = clamp(dy*0.006, ±0.055)` (`:8236–8277`). On release those angular velocities decay by `0.91` each frame (`:8518–8530`). Two active pointers cancel drag/inertia (`:8236–8244`). The `turnaroundGroup` branch changes the mink's yaw only; it is not planet rotation (`:8268–8270`).
- **Hazards for one turn = 24h:** current orientation is a full 3D quaternion with pitch, target-quaternion slerp, pointer inertia, `rotateToLandmark()` targets and autonomous idle rotation. Reading a single absolute yaw from the resulting quaternion is ambiguous across pitch/turns and risks jumps/wrap errors. Existing `onTimeChange` cannot be used as the drag signal, since it fires only on `setTimeOfDay`; if reused naively for both user drag and session-to-engine sync, a session update would echo back as a second manual-hour update. Add/retain a clear authoritative horizontal-spin phase/delta and report it only for user/inertial rotation, while applying sky-driven time without a callback (or an explicit source/suppression guard). Coalesce updates as appropriate; do not feed engine's automatic motion back into session.
- **No-autonomous-clock hazard:** on desktop, once `idleTimer` ends, the donor continuously applies tiny yaw and pitch deltas while not paused/reduced-motion (`:8526–8536`). Those deltas would incorrectly change session hour if every physical rotation were observed. PL-10's ruling requires disabling this motion for synchronized planet mode or excluding it from the reported spin; no independent planet clock should drift the session.

## Integration behavior and proof targets

1. On engine ready, initialize its time from `session.getSnapshot().hours`. Subscribe to the sky session's existing updates and apply changed hours to the engine. The session remains the only owner; replay and real-clock ticks enter by the same route.
2. On user horizontal rotation, advance session time continuously by the observed horizontal angular delta, with `2π` representing 24 hours and vertical drag remaining tilt. Call `setManualHours` once per meaningful change. Do not send the engine's session-originated target rotation back into the session. Ensure any release inertia is accounted for consistently if it is allowed to affect the actual displayed spin.
3. A session replay should cause planet rotation and lighting to follow every replay hour, alongside sky raster and page palette. Under reduced motion, don't sweep the planet; the hour/time and non-motion lighting state still follow the session.
4. The manager's intended noon anchor is not implicit in the donor mapping: capture/fixed-pose lighting starts at 12h, while existing `setTimeOfDay(12)` rotates away from the donor's 18.6h orientation. Decide and document how arrival noon preserves the authored donor view while a full horizontal turn still spans one day.
