## Where the cost is

The merged engine is a large, detailed single scene. Relevant code is in `worktrees/pl-2/src/pages/Home/planet/planetEngine.ts`:

- Renderer profile (`:6716-6776`): it identifies software renderers by `WEBGL_debug_renderer_info`; software GL disables antialiasing and shadows and fixes pixel ratio at 1. Other renderers use the device pixel ratio capped at 2 and enable a 2,048 × 2,048 directional shadow map with PCF. The current software-renderer branch is a static startup distinction, not a runtime quality guard, and the hardware branch is the more expensive starting profile.
- Scene workload (`:7103-7164`, `:8810-8915`): 25 `MinkAgent`s share geometry/material/texture assets, plus a separate turnaround mink. Each visible frame updates controllers, world motion and all agents. Mink-to-mink collision separation has two passes over pairs (up to 600 pair comparisons for 25 agents); each pass also checks agents against world obstacles. Mink animation and secondary effects include smoke, props, water ripples and articulated poses.
- Render pipeline (`:8189-8206`, `:8419-8426`, `:8923-8931`): the optional pixel-filter path renders the scene into a 260-pixel-high `WebGLRenderTarget` and then renders a post-quad, making two scene submissions. `usePixelFilter` is false by default, but `setPixelFilter` exists. Resizing updates the target dimensions by aspect ratio.
- The PL-1 cleanup/audit reports 952 geometries, 345 materials, 12 textures, one render target and 26 skeletons created/disposed per sequential mount; its resource counts and repeated-mount parity are useful lifecycle evidence, but are not GPU byte usage or per-frame workload figures. The PL-0 trial explicitly could not report actual GPU memory.
- PL-0 intercepted actual WebGL draw methods from the donor build, not `renderer.info`: median calls/frame ranged 1,201–1,678 across the tested viewport/CPU profiles. Its local software-GL p50 intervals were about 347–477 ms on the 390×844 phone viewport and 760–1,058 ms on the 1440×900 laptop viewport. The donor's fence polling plus 80 ms delay dominated some samples. These diagnostics say the scene is expensive on this software host; they do not set native thresholds. Source and Three.js versions differ between donor and merged App candidate, so remeasure the candidate itself.

The order of inexpensive profiling should be: capture `renderer.info.render.calls` and triangles after warm-up; record renderer pixel ratio, canvas backing dimensions, shadow-map enabled state/size and render-target dimensions; then compare one setting at a time. `renderer.info.memory` gives counts, not texture bytes, so report estimated texture/target bytes separately and label the estimate. Avoid claiming the intercepted software-GL 80 ms fence loop measures a normal device frame budget.

## Current scheduling and pause surfaces

- The engine owns a continuous animation loop (`planetEngine.ts:8428-8456`, `:8460-8490`, `:8493-8946`). It uses direct global `requestAnimationFrame`, timers, `performance.now`, document visibility and canvas/window events; no scheduler or visibility source is injected. Software GL adds a fence poll every 5 ms and then an 80 ms timer before the next frame.
- The engine listens to `visibilitychange` and flips `isVisible`. A hidden callback schedules another animation frame and returns (`:8493-8498`), so it skips drawing but continues waking the callback loop. There is no `IntersectionObserver` or offscreen-stage pause. Context loss cancels work (`:8429-8439`); restoration unconditionally schedules a frame (`:8440-8444`) instead of consulting an offscreen/hidden gate.
- `setPaused` currently only sets a flag that makes simulation `dt` zero (`:9043-9045`); the frame loop and render still run. `setReducedMotion` scales animation delta but does not stop engine rendering (`:9046-9048`). The page currently passes `live={visible && !reducedMotion}` to the component (`PublicAstridVision.tsx:531`), and `visible` is `!document.hidden` (`publicAstridLifecycle.ts:12-17`); changing `live` disposes/recreates the engine through the component effect. Thus tab hiding currently unmounts the engine rather than preserving it paused, and ordinary page scrolling does not stop its work when the stage is off screen.
- The page's sky is a separate renderer. `PublicAstridSky.tsx:80-100,162-173` coalesces active-view raster work into one RAF and skips its paint when the shared session is hidden; its session cancels reveal/parallax/replay RAFs on hide. The ambient and clock intervals remain allocated but guard their callbacks, and sky geometry has no offscreen gate. This existing environment/session is reusable as a state source, but it is not the planet's scheduler.
- `PublicAstridPlanet.tsx:12-39` already avoids importing the engine when `live=false`, ignores a late import after unmount, and disposes on cleanup. Its `onReady` callback is currently a no-op; `initPlanetEngine` returning null or the import rejecting only logs an error, leaving the live canvas in place. The current still image path only renders when `live=false`; explicit engine failure/slow-first-frame poster transitions are planned in PL-4 and should share that poster state.

## Small, testable runtime plan

1. Keep the live scene as the normal phone mode, with a measured phone profile for portrait and landscape. Start lighter there (candidate starting dimensions from the accepted plan are a DPR cap around 1.5, smaller or disabled shadow mapping, fewer expensive draws and cheaper decorative mink animation). Those are measurement candidates, not final thresholds or a claim that a phone can sustain them.
2. When repeated actual frame-time windows exceed a threshold for several seconds, step down one level at a time. Measure the changed DPR/backing pixels, shadow state, draw calls/triangles, render-target size, first-frame time and visual output at each level. Give recovery a separate stable window/hysteresis to prevent rapid toggling. If the lowest live profile still misses the measured budget, stop the engine and show the poster. Data-saver and a first-frame deadline can choose the poster before loading the engine. No one-frame spikes should trigger a downgrade.
3. Treat visibility as a two-input gate: document visible **and** stage intersecting the viewport (with a small prewarm margin). When either is false, cancel the pending RAF and any fence-poll/quality timers and do no scene update or render. On return, reset the last-frame clock and schedule exactly one frame; do not catch up elapsed hidden time. Keep component disposal for route unmount and explicit poster fallback. Context restore should use the same visibility gate.
4. Add a narrow scheduler boundary, either by injecting `requestFrame`, `cancelFrame`, `now`, timer functions, visibility and intersection state into the engine loop, or by extracting the loop/quality controller into a small pure module with those inputs. Keep renderer creation and the 9K-line engine out of deterministic unit tests. This lets tests use a fake clock and a counted `draw()` callback without relying on WebGL availability or hardware cadence.
5. Prefer simple hardware-quality switches in a safe order: render scale/DPR, shadow resolution/enablement, then less frequent or reduced decorative mink/effect work; preserve the scene and interactions while a live profile remains viable. Configure profile before the first shadow allocation when possible. If settings change after allocation, ensure the shadow map is reconfigured/disposed correctly rather than leaving a stale allocation. Reaching still mode disposes all existing resources and must not leave an animation callback or lazy import able to recreate them.

Exact frame thresholds, duration windows and profile cuts should come from PL-5 measurements and the runtime frame monitor. The plan's accepted staged behavior is clear; numeric gates are not yet evidence-backed.

## Sustained-session resource audit supplement

Read-only review of the merged engine at `95a061b3ba24a0bdec598da449f04ee82c6acf5c` found no concrete unbounded resource/listener queue growth in the current interaction burst path:

- `own()` keeps disposables in an instance-local `Set` and replaces each object's `dispose()` with an idempotent wrapper that removes the object from the Set and decrements the live count (`planetEngine.ts:51-75`). This registry intentionally retains scene resources that remain live until engine teardown; it is not itself a per-interaction history. The PL-1 audit's equal created/disposed counts and zero live-after-dispose report exercise that teardown path.
- Balloon-pop shards are the only detached scene-resource burst called out by teardown. `popBalloonItem` is idempotent (`:7448-7456`); each burst creates five owned materials/geometries (`:7421-7434`), then the update loop removes the shard, calls geometry/material disposal, and splices the burst record after its 0.42-second life (`:8556-8569`). Because the `own()` wrapper deletes each disposed resource from the registry, shard disposal also keeps the registry bounded. The burst is allocated anew per pop rather than pooled/reused; only the finite, one-time balloon set can pop in an engine instance. Popped balloon meshes themselves stay allocated but hidden as part of the static scene.
- Balloon landing adds one persistent collision obstacle (`:8610-8617`) and then changes `balloonMode` to `landed`, so this update is one-shot, not one append per visible frame. Popped balloons are also removed from `interactiveProps` (`:7454-7455`). Other input paths update fixed scene state (rotation, four ripple slots, agent state); the reviewed code did not create more listener registrations or persistent scene assets per pointer event.
- There is one registration each for the canvas pointer/context events, window resize, and document visibility (`:8383-8386`, `:8445-8456`); `dispose()` removes those registrations (`:9074-9081`). `scheduleTimeout` deletes fired IDs; the fence path deletes completed syncs and their registry entries (`:6741-6747`, `:8460-8490`); both context loss and disposal clear pending timers/syncs (`:8429-8439`, `:9060-9067`). It uses no interval. While visible, the loop intentionally schedules its next single frame or fence callback; this is repeated work, not an accumulating callback queue. The separate hidden-state RAF wakeup remains the pause inefficiency described above.
- Per-frame math does create temporary `Vector3`/`Quaternion` objects in portions of animation/collision updates, so possible allocation/GC cost is distinct from retained-resource leakage and can be watched in a sustained-run profile. No heap-growth or allocation measurement was performed for this supplement.

Conclusion for PL-5 preparation: interaction burst resource release and listener/timer cleanup have concrete existing safeguards. The still-live costs are the intentional scene/resource set, per-frame scene/render work and hidden-state callback wakeups, not an observed growing burst registry. This is source inspection only, not a new sustained-session runtime proof.
