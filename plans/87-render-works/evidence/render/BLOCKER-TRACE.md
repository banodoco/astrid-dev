# Attempt 1 blocker trace

Attempt 1 failed after about 77 s with the two reasons reproduced verbatim in `attempt-1.log`: asset `a09025f7-40ed-4202-ba40-2d4a61d352a9` has retired field `thumbnailUrl`; and the Remotion consumer process environment does not match any launch-validated context.

## Retired thumbnail locator

This is an installed-source projection/validation mismatch, not evidence that the clip needs different media. In the installed package tree (`~/astrid-release/release-14-plan-69/program/versions/5bf20639e293/a`), `astrid/packs/rendering/actions/render/managed_timeline.py:45-72` removes some editor metadata but not `thumbnailUrl`. `_runtime_snapshot_registry` (`:584-638`) validates only `url`, `file`, `path`, `source_path`, `locator`, and `realm` (`:630-638`), so the thumbnail field remains in the projected registry. Snapshot resolution then calls that projection and writes the full registry into attempt-local `assets.json` (`managed_timeline.py:1131-1174,1179-1200`).

The downstream materializer checks **every** registry asset entry, including unused ones, and explicitly rejects `thumbnailUrl`/`thumbnail_url` as well as `sourceUrl`/`remoteUrl` (`astrid/core/rendering/assets.py:249-279`). There is no unused-asset exclusion switch in the render materialization path. Thus even an unused stale entry can block the render. The authoring schema still admits `thumbnailUrl` (`astrid/core/timeline/banodoco_schema.py:368-385`), while the render-time validator disallows it: this is an inconsistency.

The editor's Render action does not preflight this backend registry rule. The button calls `startRender` (`editor/src/tools/video-editor/components/TimelineRenderControls.tsx:258-266`); the Astrid path saves the timeline and builds a local payload (`editor/src/tools/video-editor/hooks/useRenderState.ts:865-930`). That builder receives `assetRegistry: null` and locally projects an empty fallback registry plus any output-config clip assets (`renderRouter.ts:817-848,859-892`), but **that payload registry is not sent as the admission authority**. `enqueueAstridRuntimeRenderTimeline` creates the Runtime task spec with `timeline_ref`, selector, output name, and canonical metadata; it sends `input_object_ids: []` and no timeline or registry bytes (`renderRouter.ts:938-989`, especially `:961-979`). Runtime resolves the pinned canonical snapshot at admission, as its code comment states. So the active editor path is the managed `timeline_ref` route; the thumbnail survives through the server's canonical registry projection, independently of the editor's local registry projection. This explains why the Render button can admit the task before the worker rejects the asset.

## Launch validation consumer context

The exact check is `astrid/core/rendering/remotion_runtime.py:1234-1268`: it computes a canonical probe/registry/configuration context from the consumer's current environment (`:1239-1247`), reads the launch-bound validation artifact, and requires exactly one matching variant (`:1264-1268`). It emits the generic error from the log when that context has no match; this source path does not report which context field differed.

Launch preparation is in `astrid/sdk/host_bootstrap.py:1312-1374`: it builds contexts from the host environment and `_launch_worker_probe_environments(...)` (`:1347-1362`). That helper explicitly retains only launch-known Remotion-capable capability worker variants when `remotion_only=True` (`astrid/core/execution/generic_host.py:2116-2135,2204-2265`). At execution, the host sets validation role to `worker` and reconstructs a readiness environment before validating it (`generic_host.py:10232-10282`). Therefore this was a worker-context mismatch, not merely lack of validation on the editor button path; the source/error alone does **not** establish which exact environment field or extra context caused it. No consumer-context diff or diagnostic in `attempt-1.log` identifies the cause. In particular, do not infer that adding a worker profile or changing shell environment will fix it without a measured diff.

I found no supported setting in the installed service environment for adding validation variants or bypassing `_validated_runtime`. `_validated_runtime` is fail-closed on a launch artifact mismatch. Removing validation variables or invoking Remotion outside its managed task would bypass launch-bound checks, not provide a supported remedy. A clean supported launch can rebuild the known contexts, but if it produces the same actual worker environment, retrying will fail the same way.

Add a bounded context-difference diagnostic so a future failure names the differing projected inputs without exposing secrets.
