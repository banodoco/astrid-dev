# Heartbeat source review

Reviewed source: Agent `wt-r14-r6-fixes` and Runtime `wt/runtime-src`. This is source behavior only; it does not identify which path actually occurred in either incident.

## Findings

- **Verified — normal heartbeat ownership is a dedicated daemon thread.** `run_task` creates `astrid-heartbeat-<task-id>` and starts it before later setup/session waiting and `_run_task_impl` (`astrid/core/execution/generic_host.py:12279-12288`). `pump_lease` loops with 50 ms stop polling, and on each poll interval reads the task then calls `renew_progress(liveness=True)` (`:12024-12108`; exact interval is scaled from `_LEASE_POLL_SECONDS` and authority-window policy at `:12024-12027`). The thread exits on stop, terminal `recorded`, shutdown/cancel, absolute lifetime expiry, or a refused authority/read/heartbeat condition. Transient task read or heartbeat errors continue the loop; thus a transient RPC error is not itself a permanent heartbeat stop (`:11896-11904`, `:12047-12064`, `:12108-12118`).

- **Verified — heartbeat can silently no-op.** Under `completion_lock`, `renew_progress` returns without an RPC after stop/recorded/forced/deadline, if a renewal is already in flight, or if neither progress changed nor `liveness=True` (`:11917-11924`). The observer passes `liveness=True`, so unchanged progress alone does not suppress observer heartbeats. Producer-side calls use default `liveness=False` and send only changed progress (`:11906-11924`, `:13542-13548`).

- **Verified — process-wide protocol-client lock can serialize heartbeats with delegated authority RPCs.** `RuntimeProtocolClient.heartbeat` must acquire `_heartbeat_lock` with a bounded timeout and raises `TimeoutError("runtime heartbeat authority is busy")` if it cannot (`:5667-5672`); it releases in `finally` (`:5694-5696`). The source comment explicitly says delegated admission holds this same lock across its fenced RPCs (`:5667-5668`). Sequence-specific idempotency keys avoid replaying an earlier heartbeat receipt (`:5663-5682`). The host uses a second, per-task `renewal_inflight` gate (`:11921-11924`). A prolonged lock holder or RPC can therefore delay a pulse; if it lasts beyond the lease, the next request may be rejected. The lock's bounded wait itself is not a multi-minute wait in this code, though a running RPC/delegated holder may occupy it.

- **Verified — current uncommitted stopgap requests 7,200 seconds, not 600.** The diff at `astrid/core/execution/generic_host.py:5684-5686` adds `lease_seconds: 7200` and raises the heartbeat HTTP timeout up to 20 seconds (`:5690-5694`). This is a requested lease duration for successful heartbeat mutations; it is not a local timer and does not generate a heartbeat. Runtime accepts positive `lease_seconds` (`runtime_protocol/service.py:10181-10186`) and defaults to 30 when omitted (`:10239`). The stopgap diff comment asserts starvation while Runtime serves inputs, but source alone does not establish that this occurred in the incident.

- **Verified — Runtime caps the requested lease.** `_task_lease_deadline` takes the minimum of now plus requested seconds, the task absolute deadline, and (when present) attempt runtime deadline (`runtime_protocol/store.py:4034-4037`). The default absolute task deadline is 24 hours (`:457-461`). `heartbeat_task` checks current running status, lease token, fence, and whether the *existing* expiry has elapsed before extending it (`:6252-6269`). Thus a heartbeat received after expiry does not revive the lease. Reaping is invoked by the service heartbeat path and store heartbeat path (`runtime_protocol/service.py:10227-10239`; `store.py:6255-6257`); ordinary expiry revokes worker authority and leaves blockers pending reconciliation (`store.py:4081-4105`).

- **Verified — Runtime's service method serializes store access.** `heartbeat_attempt` enters `store._mutex`, validates attempt/runtime identity, checks idempotency replay, reaps overdue leases, validates lease, and calls `heartbeat_task` (`runtime_protocol/service.py:10216-10240`). This can queue behind other store operations using that mutex. A replay returns the original receipt before renewing (`:10223-10226`), which is why unique heartbeat keys matter. This is distinct from the Agent-side `_heartbeat_lock`.

- **Verified — heartbeat progress events are not emitted on every liveness pulse.** Host reads `.astrid-progress.json`; it sends progress only if its digest differs from sent/rejected progress (`generic_host.py:11906-11915,11925-11939`). Runtime appends `task.progress` only when progress is present, while it still updates lease expiry for a heartbeat without progress (`service.py:10231-10239`). Therefore event-log gaps cannot prove heartbeat gaps.

- **Verified — some post-render work remains covered by the observer.** The pump begins before setup and remains active through `_run_task_impl` (`generic_host.py:12279-12288`). After child completion, producer code makes a final progress renewal before harvesting (`:13538-13548`), then prepares/publishes outputs and invokes settlement (`:13783-13801`); pump is stopped in outer cleanup (see `:12360-12400`). The final producer renewal is progress-only and may no-op if unchanged; liveness observer is the intended coverage during long harvest/upload/settlement. There is a deliberate carveout: while `publication_pending`, observer avoids aborting on a stale terminal snapshot and sets reconciliation state; this keeps settlement owner in charge (`:12047-12057`, `:12108-12118`). A heartbeat can still be attempted, but lifetime-expiry gating allows it while publication is pending (`:11917-11920`).

## Can a 600-second lease explain 772 s / 1,205 s?

**Inferred, conditional:** if the deployed path truly requested a 600-second lease and the last successful heartbeat was near the start of the attempt, lease expiry should occur around 600 seconds after that heartbeat; it does not directly explain failure at 772 seconds. A failure at 772 seconds is compatible with an earlier final heartbeat roughly 172 seconds after the chosen start anchor, followed by a 600-second silence. A failure at 1,205 seconds is compatible with a last successful heartbeat roughly 605 seconds after that anchor. Those are arithmetic possibilities, not source-established histories. The lease is measured from the last successful Runtime heartbeat, not admission/claim or process birth, and Runtime rejects renewals after its current expiry (`store.py:6252-6269`).

The inspected uncommitted diff now asks for 7,200 seconds, whereas the earlier incident report described a 600-second stopgap. This tree/version mismatch means 600 seconds should be treated as the report's asserted deployed setting, not what the current uncommitted diff contains. Neither a 600-second expiry nor heartbeat starvation is evidenced for these failures by this source review alone.

## Failure / stall routes to check against retained evidence

1. Heartbeat never starts because earlier admission/claim setup fails; once started, a process/thread interruption or host shutdown can stop it (`generic_host.py:12279-12288`, `:12024-12046`).
2. The pump observes a terminal/status/attempt/fence/epoch change and aborts, or an authority refusal makes `lease_transport_fault` force lease loss (`:12065-12118`, `:11900-11904`).
3. The pulse returns early behind the per-task in-flight gate, or the shared protocol authority lock times out (`:11917-11924`, `:5667-5672`).
4. Runtime mutex/service work delays a pulse; if the last expiry passes before heartbeat validation, Runtime rejects it (`service.py:10216-10239`, `store.py:6255-6269`).
5. A repeated idempotency key would return a prior receipt without renewing, but current source generates a monotonically sequenced key (`generic_host.py:5674-5682`; Runtime replay path `service.py:10223-10226`).

No source evidence here establishes which, if any, applies to C or B. To attribute either duration to lease expiry requires the actual deployed stopgap version and last successful heartbeat expiry/time for that attempt; task progress events alone are insufficient.

## Specific starvation / serialization checks

- **No `progress_lock` deadlock found.** `generic_host.py` has the per-task boolean `renewal_inflight` gate under `completion_lock`; the heartbeat RPC executes after leaving that lock, and `finally` clears the flag under the lock (`:11917-11924,11929-11939,11977-11978`). I found no `progress_lock` symbol in this source file. This rules out that named lock as a source-supported deadlock, while leaving ordinary stuck I/O/thread scheduling possible.
- **Input-byte serving does not appear to hold the Runtime store mutex for the full stream.** `open_object` holds `_mutex` only to look up metadata and open the CAS stream, exits the `with` block, then stats/verifies and returns the stream (`runtime_protocol/service.py:6116-6138`). Thus a large object stream itself is not shown blocking `heartbeat_attempt` on `_mutex`. Other Runtime work can still hold that mutex; the inspected code does not establish how long.
- **No evidence that this is the incident's cause.** Current stopgap comment at `generic_host.py:5684-5686` says renders starve heartbeats while Runtime serves inputs. The code review supports potential contention via the heartbeat lock, heartbeat RPC, or Runtime store mutex, but does not show input serving holds either for the media transfer duration. Without per-attempt successful heartbeat acknowledgements/expiry or thread traces, starvation remains an unverified hypothesis. This is especially important for the noted F failure at 22:04:18 with a 7,200-second lease: if that requested lease succeeded and was still capped beyond 22:04, expiry is not a plausible explanation; if no such heartbeat succeeded, the configured request alone proves nothing.
