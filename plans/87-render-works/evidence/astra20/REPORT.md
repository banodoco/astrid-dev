## Heartbeat path and ways it can fail

**[VERIFIED] Host lifetime:** `Agent/astrid/core/execution/generic_host.py:12279` starts a dedicated `astrid-heartbeat-<task>` thread before setup, session waiting, and execution. `pump_lease` at `:12029` polls every five seconds (`:555`, authority window 300 seconds). Each cycle first calls `task_snapshot()` (`:11732`), then `renew_progress(liveness=True)` (`:12107`). Consequently, repeatedly failing full task reads can prevent heartbeat submission even when the renewal endpoint could work. This is a concrete coupling in the code, but **[UNKNOWN] whether it caused A/C**.

**[VERIFIED] Local serialization and no-ops:** `renew_progress` reads the progress file and updates stall diagnostics before entering `completion_lock`; it then checks stop/recorded/forced/lifetime-expired and `renewal_inflight` (`:11906–11924`). An in-flight pulse suppresses other renewals. The flag is cleared in `finally` (`:11976`). The RPC runs outside `completion_lock`. Unchanged progress suppresses a producer update, but not the observer's `liveness=True` update. Progress read errors are advisory; invalid progress can be retried without progress (`:11931–11939`). There is no deliberate frame-phase switch that disables liveness.

**[VERIFIED] Protocol client:** `heartbeat` resolves the attempt epoch, then acquires `_heartbeat_lock` with a bounded wait, normally two seconds (`:5659–5672`). Delegated-child issuance/admission shares this reentrant lock (`:5728`, `:5820`), so a long fenced RPC can delay other attempts. Each pulse uses attempt/fence/epoch plus random client-session and increasing sequence in its idempotency key (`:5674–5682`). A lock timeout raises, rather than silently succeeding. The normal render request contains no delegated children; **[UNKNOWN] whether another operation held this lock during A/C**.

**[VERIFIED] Stopgap arithmetic:** `_lifecycle_client` shallow-copies the generated client before setting its timeout (`:5647–5657`), so the changed timeout is not assigned to the shared original client's `timeout` attribute. The generated default HTTP path creates a fresh urllib opener per request (`Agent/astrid_runtime_client/generated.py:37–41,652–692`); no shared transport mutex appears there. The stopgap raises the copied heartbeat socket timeout toward twenty seconds (`generic_host.py:5690–5694`) and requests 7,200 seconds; receipts prove earlier B/C pulses requested/effectively received 600 seconds. `_lifecycle_client` raises if the deadline is already non-positive. The stopgap's 0.1-second floor can overshoot a nearly exhausted deadline slightly, but **[INFERRED] it does not explain a stoppage at 156 seconds or a ten-minute silence**. Socket timeout is not a total end-to-end deadline for lock waiting, scheduling, or a response that continues trickling bytes.

**[VERIFIED] Error handling:** `lease_transport_fault` records diagnostic categories and continues on non-authority transport faults (`:11895–11904`). A definitive lease/fence/epoch refusal triggers `force_abort('lease_lost')`; the main execution cancellation guard then stops owned work. Task-state, attempt, fence, and epoch changes are checked by the pump (`:12065–12118`). Ordinary read timeout does not deliberately kill the task, but because task read precedes renewal it can withhold pulses indefinitely. Uncaught failures outside guarded operations, blocking progress/stall/logging work, and thread starvation remain possible; **[UNKNOWN] which occurred here**. No A/C-specific timeout/refusal trace survived in the inspected host log. **[VERIFIED]** Diagnostic category changes synchronously print/flush stderr while holding `completion_lock` (`generic_host.py:11803–11830`, `astrid/core/execution/host_log.py:35–45`); host stderr is a supervisor-drained pipe. **[UNKNOWN]** A blocked pipe/log sink is another possible wait, with no retained evidence tying it to A/C.

**[VERIFIED] Runtime:** `Runtime/runtime_protocol/service.py:10180–10240` accepts positive integer `lease_seconds`; there is no independent 600/1,200/7,200-second cap. It validates identity/epoch, checks idempotency replay, reaps, validates the existing lease, then updates task/attempt/reservation expiry and writes the receipt. Replay returns the old receipt without renewal, by design. `store.py:6252–6277` refuses to revive an already expired lease. `_task_lease_deadline` (`:4034`) caps expiry at the task's absolute deadline and an explicitly requested attempt runtime limit. Default absolute task bound is 24 hours (`:457–462`).

**[VERIFIED] Actual B/C specs:** both `tasks.execution_request_json` values are NULL; neither the outer immutable spec nor nested `spec` carries `execution_request`. The legacy accessor only reads the outer field (`Runtime/store.py:612`). Thus neither has an explicit `limits.max_runtime_seconds`. Both select `rendering.remotion`; C's window is frames 1,500–3,000 at 30 fps. See `spec-controls.json`. Agent's ordinary lifetime is 3,600 seconds (`guards.py:47–48,200`; `generic_host.py:3040–3100`), shared across setup/execution/collection unless the admitted interactive contract changes it. No 1,200-second limit was found.

**[VERIFIED] Runtime contention exists, but the stopgap comment is not a diagnosis.** HTTP dispatch serializes ordinary routes, including task reads and heartbeats, on `store._mutex` (`Runtime/server.py:1519–1577`). Task reads load/hash/parse the immutable spec and run lease checks. B/C specs are ~572 KB each. However binary media routes are explicitly exempt (`server.py:549–563,1561–1566`); `service.py:6116–6138` releases the mutex before object verification/transfer, and response writes occur after dispatch unlocks. **[UNKNOWN] No retained timing identifies a mutex holder or proves input transfer starved A/C.**

## Why the executor/session stays occupied; recovery

**[VERIFIED] Two independent blockers exist.** Runtime `_reap_expired_leases` deliberately preserves running task/attempt/reservation custody for ordinary expired authority (`Runtime/store.py:4093–4146`): expiry proves loss of authority, not process termination. The claim path counts running tasks (`:4410`). The SDK wait loop notices expired authority and returns `task_reconciliation_required` (`Agent/astrid/sdk/invocation.py:3600–3638`), including a cancel recovery command. It does not itself fail or cancel the Runtime task. This explains A/C and the `active_tasks=1` queue message without assuming a broken count.

**[VERIFIED] Host managed-session release** fences the binding, calls adapter release, and clears `_active` only after verified `{ok:true}` evidence (`Agent/astrid/core/execution/managed_tool_session.py:515–545`). Otherwise it raises `managed session release was not verified` and keeps the slot occupied. `take/ranges-status.log:2–4` records this after B. Runtime cancellation does not automatically repair that host-local slot.

**[VERIFIED] Intended no-restart paths:** for an expired local unbound task, explicit owner `tasks cancel <id>` takes `Runtime/store.py:6561–6667`, reconciles the attempt and releases Runtime reservations; A/C's events show that path was used, with `stop_observed=false`. For a host session, the owner can retry exact-binding/generation `release_managed_session` after admissions become quiescent (`Agent/astrid/core/execution/generic_host.py:7278–7307`). A stale generation must be refreshed. It succeeds only when the adapter can verify release. Terminal publication has an exact-request reconciliation owner (`:12126` onward), not a rerun of rendering.

**[UNKNOWN] There is no verified universal force-clear CLI that safely recovers an uncertain session in place.** The owner release method is an API path, not evidence of a user-facing command for this stack. If original custody cannot prove release, an in-process retry may remain pending. **[INFERRED]** The missing product behavior is a surfaced, owner-bound cleanup/reconciliation workflow that separates database cancellation, native stop proof, reservation release, and session retirement. Blindly zeroing occupancy or pretending a LIVE process is dead is not a proper fix. No recovery mutation was performed here.

## Practical advice for tonight

**[VERIFIED] A 50-second range with a 7,200-second lease is not safe from these failures: F already failed on custody after 200 seconds.** **[INFERRED]** If the long lease is accepted and remains unexpired, it buys substantial room against the A/C symptom for a roughly 7–13-minute render. **[VERIFIED] `complete:100` is producer progress, not Runtime completion.** The renderer writes it after its output manifest (`Agent/astrid/packs/rendering/actions/render/run.py:506–510`); the host still performs command cleanup, output validation/harvesting, ingest, session observation/settlement, and Runtime publication (`generic_host.py:10977–11035,13534–13556,13763–13804`). Those operations can fail or stall even with a valid lease. Ordinary host deadline remains a separate one-hour bound. **[INFERRED]** Judge success by `task.completed` and registered output, not the progress file; retain a finished output spool when reconciliation is required.
