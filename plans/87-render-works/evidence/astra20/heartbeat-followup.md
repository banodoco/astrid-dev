# Heartbeat stop-path follow-up

Read-only source review of Agent `wt-r14-r6-fixes`, Runtime `wt/runtime-src`, and the stated retained log observations. No live sampling or process inspection.

## Pump event, terminal flags, and post-render lifecycle

- **Verified: no event rebinding/shadow found.** `run_task` creates `stop` and `abort` as separate `threading.Event`s and puts `stop` in `terminal["pump_stop"]` (`generic_host.py:11657-11669`). It creates `pump_thread` once, stores it in `terminal["pump_thread"]`, and starts it (`:12261-12283`). `_run_task_impl` only aliases these references (`:12670-12671`); searches found no later reassignments. Stage publishing only writes `terminal["stage"]` and updates diagnostics; it does not set the stop event (`:11980-11987`).
- **Verified: legitimate stop paths are terminal or outer cleanup.** The pump exits if `stop` is set, lifetime expires, task becomes recorded, host shuts down, the task/attempt/fence/epoch is terminal/changed, or a classified authority refusal forces abort (`:12029-12118`). Outer `run_task` cleanup sets stop after publication reconciliation or ordinary return/exception, then joins at most two seconds (`:12344-12380`). `_run_task_impl` deliberately leaves pump alive through harvest, uploads, and settlement, and sets the aliased stop event only if terminal publication has been recorded (`:13876-13900`).
- **Verified: publication has one explicit early pump exit.** If `publication_pending` and task snapshot is terminal or ownership changed, the pump returns so the publication/reconciliation owner resolves the outcome (`:12058-12064`). This is intentional settlement race handling, not prep/render stage behavior. Deadline while publication is pending marks `reconcile_cancel` instead of forcing failure (`:12034-12039`).
- **Inference: C's last heartbeat at the prep/render boundary is not explained by stage switching itself.** Stage writes do not stop the pump, and the observer continues while `_run_task_impl` waits/runs/harvests. Source cannot exclude a thread scheduling pause or an I/O call blocking the pump.

## Stall diagnostics and cancellation locks

- **Verified: 90-second faulthandler logic does not deliberately stop or gate heartbeats.** The process-wide `TaskStallDiagnostics` coordinates one timer, protects its bookkeeping with an `RLock`, and calls `faulthandler.dump_traceback_later` / cancel while holding that lock (`stall_diagnostics.py:30-47,62-109`). Its timeout action is a stack dump only; there is no callback to the heartbeat pump (`:1-10,111-151`). The observer calls `update` / `stalled` before beginning its per-task renewal section (`generic_host.py:11906-11924`). This can produce short bookkeeping lock contention; source gives no multi-minute wait/deadlock path in this component.
- **Verified: the cancellation signal is separate from pump stop.** The producer's `cancelled()` checks lifetime/authority, shutdown, and `cancel_signal` (`generic_host.py:12754-12772`); expiry/evidence failures set this signal (`:12767-12788`). `force_abort` sets the same abort signal, then attempts a lifecycle terminal RPC; it does not set `stop` (`:11989-12027`). No source evidence found for a cancellation callback holding a lock that the pump must acquire.
- **Observed stack limitation:** the reported faulthandler snapshot showing the pump in `Event.wait(0.05)` is evidence it was waiting normally at that snapshot instant, if correctly attributed. The snapshot has no timestamp, so it cannot establish where the pump was at the prior successful heartbeat or during the missing-heartbeat interval. A truncated dump could reflect an interrupted/blocked stderr path, but source plus this snapshot do not prove that.

## Strongest non-socket source path: diagnostics print can block under completion lock

- **Verified: a lifecycle diagnostic may synchronously write stderr while holding the per-task completion lock.** `record_lease_diagnostic` acquires `completion_lock`, updates diagnostic fields, then calls `log_lease_diagnostic` before releasing it (`generic_host.py:11803-11830`). That logger does `print(..., file=sys.stderr, flush=True)` (`host_log.py:35-45`). The completion lock is an `RLock` (`generic_host.py:11658-11663`), but reentrancy does not make a blocked write return.
- **Verified: in the supervised service launch, host stdout/stderr share a pipe with a separate log-drainer thread.** The Runtime service supervisor launches the service with `stdout=PIPE, stderr=STDOUT`, starts `_pipe_log` in a daemon thread, reads pipe chunks and writes them to the service log (`runtime-src/runtime_protocol/services.py:248-257,266-288`). `RotatingLog` uses an unbuffered file and its `write` holds its own lock during the underlying file write (`runtime_protocol/logs.py:21-62`).
- **Inference, explicitly conditional:** if the log file write/drainer blocks long enough, the pipe can fill and a host stderr `print(..., flush=True)` can block. If the observer is the thread performing a diagnostic transition, it would then be stuck inside `record_lease_diagnostic` while holding `completion_lock`; it could stop issuing future heartbeat cycles. Because `renew_progress` logs after a heartbeat response, this could make the just-acknowledged heartbeat the last one. The diagnostic function only prints when its category/signature/verdict changes; normal `observing` cycles do not print (`generic_host.py:11819-11830,11974-11975`). Thus this is a specific plausible stall, not a general per-heartbeat logger cost.
- **Unknown:** nothing in retained evidence establishes a blocked service log writer, full pipe, or that the pump was in `record_lease_diagnostic`. A truncated faulthandler dump and absence of target-ID diagnostic lines are compatible with several causes and do not prove this one. Conversely, absence of diagnostics is weak evidence against ordinary authority-refusal handling only if the relevant host log was being drained and retained.

## Assessment against new heartbeat data

A and D/F have continuing heartbeat acknowledgements close to completion/custody, so this source path was not continuously blocking their pumps before those last acknowledgements. For C, the last acknowledged expiry was 20:58:59.340 UTC and no later heartbeat was observed; the prep/render boundary is a plausible time for a changed diagnostic category or a log write transition, but no source event specifically guarantees one there. For C, the synchronous diagnostic-to-stderr path is the strongest additional local stall candidate found, but it remains unverified absent contemporaneous thread stacks with timestamps or evidence that the Runtime log drainer/file write blocked.
