## Scope and method

Read `twentymin/REPORT.md` first. The source stack selected by `fixed/start-source-stack.sh` is `~/astrid-release/release-14-r6-fixes`; `services.json` runs the `pack-host` service from `~/Developer/astrid-release-src/wt-r14-r6-fixes` (services.json lines 5–16), and `profile.json` selects that source and the runtime checkout (profile.json lines 2–13). The matching open-file inspection showed the current editor process log. No process was started, stopped, or modified.

SQLite was read through `mode=ro`; after building the export, I rechecked the receipt counts in ordinary read-only mode to ensure WAL-visible rows were included. The database is `~/astrid-release/release-14-r6-fixes/data/runtime/realms/221335d5-722e-48d0-a0ab-d9fde94b2277/realm.sqlite3`. `timeline.tsv` merges every task event row for A/B/C/D/F with every matching `command_idempotency.command_kind='attempt.heartbeat'` success receipt, plus available terminal receipts. A heartbeat row's `aggregate_id` and result `attempt_id` identify the attempt; `created_at` is the receipt timestamp and `result_json.lease_expires_at` is the expiry acknowledged by Runtime. Local timestamps in the TSV use Europe/Berlin (UTC+01:00 on this date).

## B/C request limits and scope of what is known

The stored render specs reveal the requested ranges in legacy-render fields. B's `task_specs.body_json.spec.inputs` has no `render_window`; its admitted storage estimate records range 0–5897, 5,897 frames at 30 fps (`5897/30` seconds), 1920×1080. C's `spec.inputs.render_window` explicitly records `start_frame: 1500`, `end_frame: 3000`, `fps_rational: [30,1]`, i.e. 1,500 frames / 50 seconds at 1920×1080. Both selected ranges and estimated scratch/output bytes are verified from `spec.admission_metadata.storage_estimate`; estimates are not actual space consumed. The parent timeline's authored duration is 5,897 frames in both specs, so C's shorter request is a subrange, not a shorter authored timeline. The task rows' `execution_request_json` is null; no execution deadline appears in the saved nested request/spec fields or task event payload. D's 3,600-second guard is from a different task and is not evidence of a B/C request limit. These rows therefore support exact frame-range limits but not a per-request time limit.

## Evidence provenance and gaps

- `events`: A rows 133–137; B rows 138–340; D rows 444–500; C rows 501–505; F rows 506–512. Exact row timestamps and event payload summaries are in `timeline.tsv`.
- `attempts` / `reservations`: queried by task ID; each listed task has one settled attempt and one render reservation. The acknowledged expiry matches the persisted attempt/reservation expiry. In particular, B reservation release is 20:09:35.329 UTC and F release is 21:04:18.799 UTC.
- `command_idempotency`: `command_kind='attempt.heartbeat'`, matching by JSON `result_json.task_id`; complete receipt rows for all five attempts are exported in `timeline.tsv`. The TSV also includes corresponding `attempt.fail`, `attempt.settle`, and `task.cancel` receipts when present. Primary provenance identifiers are receipt `idempotency_key` values.
- B custody JSON: `astrid-custody-e5vwhj91/observed-containment.json` (compact JSON; `capture_failures`, item with PID 10078), plus `retained-cleanup-containment.json`.
- F custody JSON: `astrid-custody-7wigzxag/observed-containment.json` (compact JSON; its only `capture_failures` item has PID 25622) and `retained-cleanup-containment.json`.
- Service configuration provenance: `fixed/start-source-stack.sh`; stack `services.json` lines 5–16; `profile.json` lines 2–13. Generic host failure/shutdown: stack `data/runtime/service-pack-host.log` lines 1778–1779; no task/attempt identity is present there.

Heartbeat command receipts are acknowledgments, not evidence of worker progress or host health. There is no retained per-attempt heartbeat pump log, explicit reaper receipt, or command-line identity for either failed candidate. Source files may have changed since the incident, so these historical conclusions use persisted DB/containment/log records rather than current source as a proxy for past behavior.
