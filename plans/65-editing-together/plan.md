**Goal:** A person in the editor and an agent edit one timeline at the same time without blocking, overwriting or surprising each other: unrelated changes both land, the person sees who changed what within seconds and keeps their place, and a real clash parks one change and says which.

## Outcome and scope

**Editing together.** One of four plans cut from the save work on 18 November 2026 ([Plan 63](../63-dependable-saving/plan.md) is first; the structure is from the independent four-questions check, section 2, accepted by the main thread). It is queued, in no release, with the release open: the owner said to add it to astrid-dev and not do it yet.

**The four plans and their order:** A, [Plan 63](../63-dependable-saving/plan.md) Dependable saving, first; B, [Plan 64](../64-fast-saving/plan.md) Fast saving, in parallel with A from day one; **C, this plan, after A**; D, [Plan 18](../18-timeline-editing/plan.md) Extensible editing, after A. Solid arrows: cannot start product code before. This plan needs A's four outcomes and parked change; D and B need nothing from it. B helps it; D delivers the exact forms.

**The rule, for every writer** (this is [Plan 63's](../63-dependable-saving/statements.md) statement with five words added):

> **Read the head, change your own copy, and send what you changed with the head you read, a key you keep, and what you relied on.** The Runtime lands it if nothing you relied on has changed, wherever the head is by then. If something has, the answer is `moved`: a person's change is parked and shown, an agent reads again and runs again (at most three times). Nobody waits for anybody, nobody's screen is taken from them, and nobody overwrites without being asked.

**Why only this is needed.** The server already merges by address, down to a field (verified, `_commit_patch.py:976-999`, `commit.py:1427-1557`): two writers' guards are (thing, path) pairs and clash only when the thing is the same and one path is a prefix of the other, **or when either side names the whole timeline**. It fails today because most agent edits, and some editor edits, claim the whole timeline (a `doc.patch` with no declared reads is forced to `atomic`; an agent's function commit is `atomic` over the whole timeline unless it declares reads; a document publish is `atomic`), so unrelated changes clash. Narrow reads by default fix case (a), the common one. Robustness does not need the intent model: the server replays changes by address, and the editor never does until Plan 18.

**The five cases, and what should happen** (the "should" column is this plan's end state):

| Case | Today | Should |
| --- | --- | --- |
| **(a) Different clips** | Lands only if both writers declared what they read. Not when either is `atomic` (an element or parameter edit, any agent function, any document publish): the second writer gets a clash though nothing overlapped. The person sees the agent's work at their next accept or up to 30 s later, with their undo history cleared and no notice | **Always lands, both ways, silently.** Narrow reads are the default for every writer; the whole timeline is something a writer asks for. The change appears within about a second of the person pausing, in place, with one quiet line saying who and what |
| **(b) The same clip or field** | The second writer gets a clash. Person second: the screen is reset, the bar shows, the whole queue is held, and the retry cannot succeed. Agent second: a function runs again on the new head; a list is saved as a pending change | **The second writer gets `moved`, and nobody is blocked.** The person's change is parked with everything queued behind it and the clip named ("The agent changed this clip first"), with two buttons, **Keep mine** (send it on the current head, where it now lands: the person overwriting on purpose) and **Discard**; it is **never re-applied automatically** ([D16](../63-dependable-saving/inputs.md#owner-decisions)); the screen shows the agent's value; they keep editing. The agent reads again and runs again, at most three times, then reports; a list is parked. Nobody overwrites silently |
| **(c) A big agent bundle while the person has queued edits** | The bundle's base is the head pinned at checkout, possibly minutes earlier; every edit the person saved since must be replayed over, one history entry at a time. If the bundle is `atomic` or touches anything the person touched, it is refused once and the writer keeps no copy of the request; each of the person's quick saves is another head change to lose to, so three attempts can all lose (`head_busy`) | **The bundle is an addition with narrow reads:** it relies only on what it attaches to, so it lands under any amount of unrelated editing. If it is `moved`, the agent re-reads and re-attaches without generating anything again, and keeps its request and key until it has an answer. The person sees "Agent added 12 animations" when they pause |
| **(d) The person deletes what the agent edits** | Delete first, agent second: right already, apart from the words. Agent first, delete second: the person gets the bar for a delete (inferred, not run) | Delete first: `moved`; the re-run is refused with a code and the agent reports "that clip was deleted in the editor; skipped". **Delete second: the delete parks** ("The agent edited this clip; Keep mine deletes it"), like any clash: one rule, no exception list (D16); "a delete beats an edit" is cut |
| **(e) The person is offline** | Edits kept in IndexedDB and retried; the agent keeps committing; on return the queue is sent one edit at a time and at the first clash the screen is reset | **The same rule, no special mode.** The offline queue is sent as one batch (Plan 63); steps that merge land; a clashing step and what follows it are parked and listed by name; the screen keeps the person's edits until the queue is empty |

**What the person sees when an agent's change lands.** *During a gesture, or while their own saves are out:* nothing; the screen is theirs. *Within about a second of pausing:* the change appears in place; selection, playhead, scroll and undo history are kept; one quiet line for a few seconds, "Agent · Added 12 animations"; no bar. *Only if their own change clashed:* the one bar, naming the clip and the other writer.

**Must-haves (about 12 days; none needs the command layer).** **ET-0** states the clash rule and the undo rule, and the `moved` reply names the addresses and the commits that changed them (0.5 day); **ET-1** narrow reads by default, **agent half only** (2 days, was 3: the editor half is cut, because the editor declares nothing new and never declares reads; the server derives the addresses a patch writes, Plan 63's CC-16); **ET-2** the editor notices a foreign head in seconds, not 30 (1 day; first check: a `timelines-updated` listener already exists, and if it fires for an agent's commit, relax the gating and add no 2 s check); **ET-3** adopting keeps the person's place: **undo goes by `timeline.inverse` of the person's own records and the snapshot stacks are deleted on the Runtime-backed path**, selection, playhead and scroll are kept (2 days); **ET-4** "who and what", the quiet line (1.5 days); **ET-4b** undo an agent's change from the line (1 day; **promoted from nice-to-have to a must: it is the safety valve for narrow default reads** ([D17](../63-dependable-saving/inputs.md#owner-decisions)); unverified that the server lets one actor invert another's commit); **ET-5** a bundle publish survives `moved` (2 days); **ET-6** a test with both writers on a real stack, reusing Plan 63's CC-13 harness (2 days). **Already in Plan 63** (the must-haves this plan rests on, and where they stay): a clash or refusal parks the change and never blocks editing (CC-5b); four outcomes for both writers, with `head_busy` meaning "send again" to the Agent too (CC-4, **CC-4b**); the one guidance paragraph for agents (**CC-12**); a read is an address (CC-16). CC-4b and CC-12 are not moved here, because they serve the four outcomes and the guidance for every writer; this plan only adds "and what you relied on" to the paragraph once ET-1 lands. **The target architecture is stated once, in [Plan 63's end state](../63-dependable-saving/plan.md#outcome-and-scope); this plan is its client policy on `moved` and its undo.**

**Nice-to-haves, deferred** (listed in [inputs.md](inputs.md#deferred)): push in place of the 2 s check (3 days), the agent's change visible in the middle of a burst (Plan 18's TL-5), a table test of finer merges (1 day plus what it finds), and highlight what changed and "an agent is working here" (3 and 2 days). **Cut:** "Keep mine" as a separate feature (it is the one bar's button, decided in D15), "delete beats edit" (a delete parks, D16), and undo of an agent's change as a nice-to-have (a must, ET-4b).

**Deferred or out of scope:** the editor replaying queued edits (Plan 18's TL-5); a third queue for bundles; push events before the 2 s check has been found wanting; merging the editor's and the Agent's queue implementations (they share a contract, not code).

## Existing work and decision

## Completion

Done when cases (a) to (e) behave as the "should" column, each as a row of the two-writer test (ET-6) on a real stack, with the editor in a burst, an agent function and a bundle on one timeline; the person sees who changed what within seconds and keeps selection, playhead and undo; a bundle survives `moved` without being generated again. Negative cases: a writer that omits its reads (it is `atomic` by request, not by default), an agent function over a whole timeline, a delete beside an edit of the same clip. Limits: how fine the merge is in practice depends on how narrow each writer's patch paths are (only "different clips merge, the same clip clashes" is pinned by a test today); case (d), delete second, waits for Plan 18; narrowing a function commit's default reads is safe only for intents that do not depend on things they do not change (a ripple, "tighten the intro" keep `reads="timeline"`); which built-in intents need it has not been surveyed.
