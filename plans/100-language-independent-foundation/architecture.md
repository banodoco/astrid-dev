# Native creative foundation — architecture proposal

[Plan 100](plan.md) · [Plan 106 investigation](../106-creative-foundation-investigation/plan.md) · [Gap LS-006](../../vision/gaps/LS-006-independent-creative-foundation.md) · [Owner discussion / umbrella issue #2038](https://github.com/banodoco/astrid-dev/issues/2038)

**Disposition:** Direction agreed in owner conversation, 26 November 2026; this document and six project scopes are draft proposals pending independent critique and scope/release decisions. No product execution, spend or cutover is authorized.

## Why this matters

Astrid is not trying to be a fixed video editor. It is a creative environment in which people and agents continually add, compose and change tools. A fragile foundation multiplies the cost of every new modality, agent, provider and installation. A reliable, small and independently recoverable foundation makes the layers above it liquid. Rust is a proposed implementation choice because compiled native distribution removes interpreter bootstrap dependence, ownership and types can encode invariants, and native concurrency and efficient memory representation help CPU-heavy paths. Rust does not fix incorrect protocols, duplicated state, filesystem semantics, GPU drivers, cloud latency, or costly algorithms by itself. The user-facing goal survives choosing a different implementation.

## Target design

```text
Hosted React | local bundled React | desktop shell | CLI | Python/TS SDKs | agents
                     authenticated versioned API + events
                                      |
               Rust workspace runtime (one authoritative writer)
               project/storage, edit commits, task/lease, grants, events
                   |             |               |
          native timeline     worker ABI      agent-session control
          pure Rust library   local/remote    provider adapters
                   |             |               |
          WASM preview        Python/Node/    Claude/Codex/custom
          (not authority)      native packs     agents/models
                                     
      independent Rust bootstrap/controller: manifest, environment,
      launch/attach, health, update, recovery, static UI, OS integration
```

A single user installation can ship several executables/crates: recovery/bootstrap must survive a broken core update; the core can run headless without any shell. Keep package management external where appropriate (uv, pinned artifacts, user-managed ComfyUI); don't build a package manager or inference engine. Managed services can own their own descendants within declared custody, not install/version authority. One native controller owns selected program versions, lifecycle and recovery; a workspace runtime owns durable project/task state. Credential grants, process identity and recovery transactions have explicit authorities, not shared mutable side files. External managers such as Pinokio keep their own exclusive installation ownership; delegate/attach or explicitly transfer, never silently adopt.

### Interfaces and timeline

React remains the extensible frontend. Production build static assets are served locally; hosted astrid.haus still connects through a separately qualified local connection/permission route. A desktop shell (Tauri vs Electron/other remains a choice after media/webview evaluation) displays the same React build, not a second product. Developers and agents can opt into Vite/HMR and independent UI/pack updates without compiling Rust. Node may still be required for builds, agents or Remotion, not for serving static production UI or workspace authority. Browser/desktop sessions keep per-client transient UI state while canonical project selection/preferences follow approved state ownership. Loopback binding, exact origin/handshake, least privilege, CSRF/local-network permission and remote pairing remain explicit; a same-origin local UI must not expose privileged credentials to web content.

Agents call the same generated Python SDK, CLI or MCP adapter; e.g. an illustrative batch trim/move/add operation becomes typed commands with project/timeline IDs, expected revision, idempotency key and permission context. The native authority validates, computes and atomically publishes one revision/receipt/event. The editor and agent receive the same outcome and conflict/refusal. Rust pure editing kernel defines frame/time/rational rounding, nested composition, command validation, dependency changes, undo and deterministic projections; Python/TS remain ergonomic clients. WASM or PyO3 bindings are optional for measured pure local preview/calculation, never direct persistence or an alternate authority. Preserve Remotion and custom elements as extension/rendering capabilities and define independent domain contracts so a future music/image/3D engine need not become a video-timeline fork. Rendering parity includes custom elements, time mapping, audio and readback, not only JSON equality.

### Agent and execution

The core owns durable session identity, scoped project/context references, admitted tasks, receipts, observable checkpoints, permissions and coordination. Provider-specific prompts, conversation formats and reasoning are owned by adapters; no automatic reconstruction of hidden state. A provider replacement explicitly resumes from supported checkpoint/project/receipt data, not a promise that all provider sessions are portable. Existing ACP/CLI/skills remain valid. Existing ComfyUI and Python tool ecosystems remain outside the native core, under declared capability and worker contracts. Reuse lease/fence, cancellation, idempotency and verified source identity, with real failure/expiry/cleanup proof. Agents do not get unrestricted shell/network/credential rights by being first-class. Resource budgets, sandbox policy and approval remain explicit.

### Local and remote

Same runtime source and public contract for local and headless deployment, with platform-specific packaging/adapters and explicit workspace custody. A local authority may delegate scoped execution to a remote worker; a fully hosted workspace is a different selected authority, not a hidden replica. No multi-master sync or transparent failover promise. Remote workers authenticate, use bounded input transfer, return verified results, reconcile interrupted execution, and enforce spend consent. Existing Plans 25/26 own actual cloud product journeys; Plan 32 owns placement and F-008 generation portability. Plan 105 proves shared core/worker deployment, not a second hosted product or scheduler.

## Creative domains: one resource contract, separate engines

A timeline is the first domain, not the universal data model. A creative resource has a stable identity, domain/type and schema version, authoritative revision, typed asset/resource references, permissions and declared operations. The common runtime supplies resource lifecycle, transactional publication, revision/receipt/event infrastructure, dependency graph, grants, storage/CAS, tasks and recovery. It does not know what a brush stroke, ripple trim, 3D transform or MIDI quantization means. A domain engine owns those semantics, its document representation, validation, conflict and inverse-operation rules, import/export and rendering inputs. It can run in a reviewed Rust crate or through a versioned isolated service/pack; contributions must not require Rust, a core rebuild or privileged database access. Domain data storage and migrations must coordinate with Plan 57; do not silently reinterpret its owner-approved direction.

Each domain manifest advertises resource types, schema versions and migrations, typed operations (input/output, grant/effect, touched resources, preview support, error/undo semantics), available views, capability/engine requirements and typed ports. A shared operation envelope names resource identity, expected revision, idempotency key and actor scope; the domain computes a candidate change against bounded immutable state; the core validates authority and preconditions and atomically commits the result. No untrusted engine may write canonical storage or mint authority. A domain engine may expose optimized native, WASM or local calculation bindings for preview; final edits still go through the same authoritative commit path. High-frequency brush, scrub, viewport and audio interactions stay local, coalescing meaningful changes or streaming bounded ephemeral state; avoid RPC per pointer sample or mesh vertex. Heavy effects, raster/vector/GPU work, geometry, simulation and inference are tasks or specialist rendering services, not generic core functions.

| Domain | Owned resources and operations | Specialist interface/processing |
| --- | --- | --- |
| Timeline | tracks, clips, nested compositions; trim/split/move/ripple/retime | React timeline/player; existing Remotion, FFmpeg |
| Image canvas | layers, raster tiles, vectors, masks, transforms; paint/composite/filter | React canvas/brush controls, WebGL/WebGPU/native processing |
| 3D scene | nodes, geometry/asset references, materials, lights, cameras; transform, animate, assign material | Three.js viewport; Blender or other qualified renderer/geometry workers |
| Music/sound | notes, clips, instruments, tempo, routing; arrange, automate, mix | DAW-style controls; real-time audio/DSP service |
| Writing | text/blocks, links, revisions; insert, replace, restructure | React rich text/document views |
| Independent domain | contributed schemas and operations, bounded migration | pack-defined client/service without core fork |

For example, an agent can use Python to trim a timeline clip, add a canvas layer, set a 3D material, render a scene and place the output on a timeline. These are separate domain calls using the same authority; an image texture or scene reference can follow an explicit latest revision or remain pinned. A dependency change does not implicitly grant permission to regenerate, upload or overwrite other resources. Plan 45 owns explicit connections, including type compatibility, invalidation, cycle handling where relevant and reversible bindings.

Plan 100 extracts only the shared contract that actual timeline and a bounded non-video witness justify. Plan 102 is its first substantial native domain, not a generic timeline-shaped storage model. Before 0.3 closure, prove a small genuinely different resource (a canvas with layer/transform/mask edit or structured 3D scene with object/transform edit) can be implemented separately without changing the core and without duplicating its persistence, authorization or event logic. This is an abstraction witness, not a full 0.5 image product. Plan 43 owns later independently scoped mature modalities; Plan 11/current Three.js work is reusable prior art. In particular, [existing Three.js authoring](https://github.com/banodoco/astrid-agent/blob/dc45d97c6bc2734cbfb9b2a25b43cb40ed5757e5/astrid/packs/rendering/ui/threejs-live-editor/authoring.ts) already includes asset packages, revision captures and placement publication; preserve its useful contracts instead of inventing a second scene store.

## Agent-controlled interface: the workspace as a resource

Distinguish three operation classes: domain editing changes creative data; workspace control opens/arranges/binds/focuses existing views; software extension creates or changes executable components/capabilities. They have different authority and must never collapse into browser automation or arbitrary code execution. An agent should be able to ask what tools and resource types are installed, what workspace/window it is acting on, and which operations and bindings are allowed.

A component definition has a stable type/version, owning pack, supported resource types, input/output ports, size/layout constraints, lifecycle and mount capability. A component instance names its definition and explicit bindings; a workspace layout declares instances and placement/focus intent. Canonical saved layouts/presets and resource bindings are versioned through the workspace authority; window/viewport state, focus, selection, hover, transient drag and previews remain scoped to the target client/session unless the user saves them. Use existing Plan 35 state ownership, not a new shadow store.

Illustrative command sequence (not existing SDK syntax):

```python
workspace = astrid.workspace(session_id="editor-session")
workspace.discover(resource_type="image.canvas")
canvas_view = workspace.open(tool="canvas.editor", resource=canvas_id)
workspace.open(tool="timeline.editor", resource=timeline_id, beside=canvas_view)
workspace.open(tool="lighting.inspector", bind={"scene": scene_id})
workspace.focus(canvas_view)
```

Open an existing resource is not create/edit. A request to create a canvas uses the distinct domain create command with its own grant and receipt, then opens that resource. The workspace operation includes target session/client/window, requested action, expected layout revision if persistent, idempotency, scoped grant and typed resource binding. The Runtime/session service routes validated requests/events to the selected client; the React shell resolves the installed component definition and mounts/updates the view; it returns actual applied/refused/disconnected/unavailable acknowledgement. An accepted command is not proof that a view is visible. Do not silently redirect to another device, reopen a closed window, steal focus against user preference, or queue surprise UI mutations for a future session. In a headless session, resource operations still work, but interactive presentation returns no active target; only an explicitly saved layout may persist for later opening. User-selected local settings, responsive placement and locked panels are respected; stale or concurrent changes are reconciled with revision/receipt and undo. Failed or missing components show scoped diagnostics without losing the layout or creative work.

A tool may be a transient panel, docked editor, modal, viewport or multi-component preset; a single reusable composition contract covers them. Agents and humans use the same operations for ordinary open/close/dock/resize/bind/focus/save/restore. Agent-authored new React components, shaders or tools use existing pack installation/activation and live reload, scoped capabilities, review/consent and safe rollback (Plans 06, 41, 47); ordinary interface changes never need source generation or a Rust rebuild. The renderer remains React/TypeScript and domain-specialized views (e.g. Three.js), not Rust-generated UI. Privileged native IPC is not exposed to untrusted frontend code.

Prior art at App `cc1d48f016fde55ad6b0609c619d8a4bcec56823`: [panesStore](https://github.com/banodoco/astrid-app/blob/cc1d48f016fde55ad6b0609c619d8a4bcec56823/src/shared/state/panesStore.ts) holds pane visibility, locks and size; [DynamicComponentRegistry](https://github.com/banodoco/astrid-app/blob/cc1d48f016fde55ad6b0609c619d8a4bcec56823/src/tools/video-editor/runtime-components/DynamicComponentRegistry.ts) supports dynamic registration and versioned subscriptions; [agentToolRegistry](https://github.com/banodoco/astrid-app/blob/cc1d48f016fde55ad6b0609c619d8a4bcec56823/src/tools/video-editor/runtime/agentToolRegistry.ts) is provider-mount-scoped with manifest contributions, handlers, validation and disposal. These are source observations, not proof of a unified cross-domain layout API.

Ownership: Plan 24 supplies portable definitions/instances/layout lifecycle; Plan 45 supplies typed resource/capability bindings; Plan 46 supplies safe agent-visible operations and real targeted-client acknowledgement; Plan 100 supplies the shared resource and operation boundary; Plan 101 supplies the common native/local/hosted shell and session discovery; Plan 104 supplies actor/session grants and durable task context, not a second UI command implementation. This avoids a new overlapping plan. First prove an agent opens an existing canvas and a timeline next to it, shows an appropriate inspector, binds it to the selected resource, and restores the prior layout; close the targeted browser, revoke the grant, race a human edit and break a component to verify truthful outcomes. A minimal non-video witness is enough for the early contract; actual rich canvas/3D tooling remains Plan 43 scope.

## Agent-authored tools and replaceable default interfaces

The core must enable liquid software, not turn the compiled application into a new constraint. A creator or agent can configure an existing tool, extend a registered component/behavior, author a complete independent React/TypeScript tool (optionally with Python or another backend), or select an alternative implementation of a default tool against the same resources. These are distinct from ordinary workspace operations. The long-term direction is for Astrid's default timeline, canvas, gallery, inspectors, generation controls and other creative interfaces to use the public pack/component contracts too. Move defaults progressively when there is real reuse and parity; the minimal recovery, consent, capability mediation and workspace shell must remain available if a creative extension breaks. Do not require every privileged system function to be a replaceable pack.

**One contract, not a second tool system.** A pack declares its stable identity, version, components/tools/commands, supported resource types, extension slots or replaceable view roles, capabilities, dependency and compatibility requirements, owned state/migrations and optional backend services. Expose public extension points for custom panels, actions, renderers, tool controls and view substitutions; add a reviewed contract when a real need cannot be expressed, rather than granting an extension private imports or monkey-patching core. An alternative timeline UI reads and edits the same authoritative timeline, not a fork of its schema, history or database. A replacement can be selected per workspace with an explicit fallback; no implicit override or second canonical domain engine. React provides the presentation; the shared operation SDK supplies authority. An entirely new domain uses Plan 100's separate domain contract, not a privileged UI override.

**Live authoring loop.** The agent edits a scoped project/pack checkout, selects compatible dependency versions, compiles and tests in a managed build environment, previews the proposed artifact in the running app, and registers or switches the selected version through the existing admission/activation path under the creator's trust policy. The compiler and optional Node/Python backend are managed services, not requirements for the Rust core to start or repair itself. Build into content-addressed artifacts; validate manifests, compatibility and imports, distinguish a successful build from a successful mount, make source and versions inspectable, and retain the last working activation. A failed build, mount, hot update or data migration never destroys the existing view, layout or creative state. Use existing dynamic registry/version subscriptions, HMR where appropriate, and a bounded restart of an affected backend if required; no Rust rebuild, whole app restart or browser reload for ordinary compatible frontend changes. Preserve in-flight jobs, active view bindings and persisted resource revisions through compatible swaps. Do not claim every incompatible state migration can be hot-swapped: refusal or explicit recovery is the safe outcome. Old rendering references continue to use their exact admitted revision; the active editor's selected version must not silently change old project output.

**Local and hosted parity.** A locally bundled shell and astrid.haus load the same extension artifact format and compatible public SDK, including agent-authored local tools; the production base UI may remain static. Do not assume Vite is reachable from a hosted browser or that arbitrary remote JS can be imported under its origin policy. Qualify the artifact delivery, cache/version invalidation, CORS/CSP, permissions and mount acknowledgements in both routes, offline local mode and declared native shells. Hosted editing need not upload private source or data; any transfer is explicit. Keep React singleton/SDK compatibility, module resolution, CSS isolation and lifecycle disposal deliberate. Build and backend dependency resolution are separate from frontend mounting; ordinary supported operations work without invoking a source compiler.

**Trust and fault containment.** Plan 78 explicitly treats local project-pack code as trusted creator-owned build source; its digest-pinned admission and live-edit path are integrity safeguards, not a general sandbox. Do not retroactively claim that it isolates untrusted code or silently reopen its accepted scope. An arbitrary same-origin React module can reach the app's own browser privileges; an error boundary is only fault containment, not security isolation. For trusted local authoring, honor the established creator's approval/trust policy without a new prompt on every edit inside the authorized scope. For untrusted or newly shared code, use a separately reviewed execution boundary (for example an isolated origin/sandboxed frame or restricted worker, mediated typed capability messages and scoped tokens, depending on the actual UI requirements). Prevent direct access to native IPC, host filesystem, other projects, credentials, privileged origin, network/spend or unrestricted backend execution; enforce authorization in the core rather than relying on the component. Qualify Python/Node build/install code and backend services separately; package install scripts can also execute code. A new dependency, broader grant or trust elevation requires the relevant authorization, not implicit approval from opening a tool. Scope the sandbox design with existing Plan 15/F-007; no claim that a particular browser feature alone makes arbitrary code safe.

**Useful witnesses, not framework completion by declaration.** An agent (1) adds lighting controls to an existing creative tool, (2) writes a complete React lighting/character exploration tool with a typed Python or 3D capability and opens it through Plan 46, (3) changes it again while the creator works without restarting the application, (4) selects an independently authored alternative view over the same timeline or canvas and returns to the default without migration, and (5) recovers from a bad build or incompatible update without losing work. Repeat through hosted and local routes with exact artifact/runtime identities; exercise denied grants, missing dependencies, incompatible schemas, failed mounts, disconnected target, stale revisions and untrusted boundary attempts. The default-versus-alternative test must prove same resource ID, canonical operations, revisions and undo, not visual similarity. Preserve approved Plan 78 rendering invariants. This is a bounded first qualification, not a claim that every default tool or arbitrary code is already replaceable.

Ownership: Plan 41 owns the agent create/adapt/test/maintain workflow and functional replacement witness; Plan 47 qualifies difficult frontend/backend pack and hot activation/rollback cases; Plan 06's accepted lifecycle and Plan 78's exact live-element/revision semantics are retained prior art, not reopened. Plan 100 owns the shared resource/operation and extension boundary, Plan 101 owns cross-interface artifact hosting/recovery, Plans 24/45/46 own composition and bindings, Plan 57 owns extension-data decisions, and Plan 15 owns isolation. Before scope review, [Plan 106](../106-creative-foundation-investigation/plan.md) inventories existing public SDK/manifest extension slots and default editor private dependencies; agree the smallest useful view substitution and avoid creating another extension manager or rewriting every default at once. Candidate work is on the path to 0.3, with richer independently contributed foundations at 0.8; no release assignment or additional estimate until overlap with existing Plans 41/47 and actual contract gaps are assessed.

## Requirements shared by all six projects

1. One canonical authority per resource and installation; make ownership transfer, startup, shutdown and recovery explicit; delete redundant paths after qualified cutover.
2. Existing user data, credentials, project identity, revisions, media CAS bytes, receipts and backups survive supported migrations; never downgrade schema silently, share simultaneous DB writers or erase data for compatibility.
3. Preserve public operations and negative guarantees; version changes deliberately, generate clients, and distinguish supported version matrix from internal implementation.
4. Native bootstrap/core starts with Python and Node missing/broken; managed dependencies provision with visible consent, verified sources, progress, cancellation, resume and safe rollback. Do not bundle GPU stacks gratuitously.
5. One UI codebase; browser/desktop/local/headless are access modes, not divergent features. Keep pack/React iteration live. Respect offline limitations of optional providers.
6. Explicit security model: process custody, grants, secret storage, filesystem boundary, origin and remote authentication; never weaken proofs to get parity.
7. Qualify supported Windows/Linux/macOS distributions, architectures and hardware explicitly; don't claim universal GPU support. Include Pinokio/external ownership where selected.
8. Separate black-box conformance from implementation unit tests. Run against pinned Python and Rust candidates in isolated roots with deterministic fixtures, actual installed journeys, negative/adversarial cases and performance baselines. Changes to expected behaviour require independent review, not wholesale golden regeneration.
9. The old implementation is a behavioral reference, not an architectural template. Modular crate boundaries, explicit domain separation and measurable invariants; don't reproduce service.py or generic_host.py as a single native monolith.
10. No GPU spend, production deployment or release promotion by planning alone. Cross-repo integration uses exact manifests, native artifact provenance/signing, rollback eligibility and reviewed evidence.

## Alternatives and sequencing

- Keep Python entirely: lowest disruption; optimize algorithms and process reuse, but recovery foundation still depends on a managed interpreter and private imports remain unless fixed.
- Only native launcher: useful independently and appropriate early; doesn't solve workspace authority or semantic duplication. Do not present it as full native core.
- Big-bang Rust translation: reject; high integration and regression risk, accumulated behavioural knowledge lost, no independently useful intermediate states.
- New modular native implementation behind existing contracts: recommended end state. Start with independent boundary proof (100), native distribution (101) and deterministic timeline engine (102); workspace authority cutover (103) requires their accepted interfaces and migration proof. Agent infrastructure (104) and local/remote parity (105) build on the shared core, with early adapters allowed against the reference contract. Parallel work must coordinate ownership and exact source pins.

Existing releases 15–18 remain the reference and active delivery path.
