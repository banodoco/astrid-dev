## Shared rules for every card

- **Environment.** Checks run with the scripts that [E1](#e1) adds, by literal in-repo path from the checkout root: `bash scripts/worker-env/agent-pytest.sh` (Agent, exists), `bash scripts/worker-env/astrid-cloud-pytest.sh` and `bash scripts/worker-env/runtime-pytest.sh` (gaps today), and for the App `npx vitest run <file>` and `npx playwright test --config playwright.direct.config.ts <spec>` (an `app-setup.sh` is a gap; Plan 20 also names it).
- **No live resource in a check.** Supabase, Stripe, fal and the Runtime are fakes or local Postgres everywhere except A1 (read-only), A18 and A10.
- **The Agent never names Supabase.** `authority_lint` flags `supabase` in product code and journey logs (`scripts/reshape/authority_lint.py:90`, `:1365-1367`). The Agent talks only to the service origin.
- **Refusal codes are stable; their wording is T3's.** Functional tasks use plain placeholder messages.

### A2

**Outcome:** the money and key rules hold in Postgres itself, so no caller can break them. **Input:** A1's note; the tag's ledger, Stripe idempotency and token migrations (`supabase/migrations/20250113000000_add_credits_system.sql`, `20260130220000_add_stripe_idempotency.sql`); reigh-app's task idempotency (`20260213200001_task_idempotency_key.sql`). **Deliverable:** fresh migrations (not a replay of the 476 at the tag) in schema `astrid_cloud`:
- `accounts` (balance in cents, never negative), created by `ensure_account()` from the App on first sign-in, not by a trigger on the shared `auth.users`;
- `ledger` rows of kind `purchase`, `spend` or `refund`, each spend with `units`, `unit`, `provider_usd_per_unit`, `markup`, `charge_cents`, the endpoint and the task; a unique purchase per Stripe session; at most one refund per task;
- `model_prices (endpoint, unit, provider_usd_per_unit)` and `markups (category, value)` seeded `generation = 1.6`; the charge is `ceil(units × cost × markup × 100)` cents, computed only in SQL;
- `device_keys`: sha256 of a high-entropy key, label, scopes (`{generate}`), `revoked_at`; `mint_device_key(label)` and `revoke_device_key(id)` require `auth.uid()`, return the raw key once, and can't be called with a device key;
- `tasks` with `(account_id, idempotency_key)` unique **only among live tasks** (not `failed` or `cancelled`), plus a request hash;
- `submit_task(key_hash, idempotency_key, request_hash, endpoint, units, payload)`: checks the key and scope, the price row, the daily provider-spend cap and the test-mode allowlist (settings rows), locks the account row, refuses below zero, then writes the task and the spend row in one transaction; same key and hash returns the existing task; same key and another hash is a conflict;
- `claim_task(worker_id, lease_seconds)` with `FOR UPDATE SKIP LOCKED`; `complete_task`, `fail_task` (refunds once), `cancel_task` (refunds only before the provider call), `credit_purchase(session_id, account_id, cents)`;
- row-level security: a signed-in user reads only their own accounts, ledger, tasks and devices; only the service role writes.

Also `docs/api.md`: routes, headers (`Authorization: Bearer <device key>`, `Idempotency-Key`), request and response shapes, and refusal codes (`signed_out`, `device_revoked`, `insufficient_balance`, `model_unpriced`, `service_cap`, `idempotency_conflict`). A7 builds against this before A3 exists. **Route:** S: billing, concurrency and a security boundary in a project shared with Hivemind. **Estimate:** 3. **Proof:** `bash scripts/worker-env/astrid-cloud-pytest.sh -q tests/sql` with new tests showing:
- 20 concurrent `submit_task` calls at 30¢ on a 100¢ balance: exactly 3 succeed, the balance is 10¢, 17 are refused `insufficient_balance`;
- the same key and hash twice gives one task and one spend row; another hash gives `idempotency_conflict`; after `fail_task`, the same key creates a new task with a new charge (the Runtime's retry reuses the task id, `astrid-runtime/runtime_protocol/service.py:8111-8149`); another user's identical key is independent;
- `fail_task` twice refunds once; `cancel_task` after the provider call refunds nothing;
- two connections claiming from 5 queued tasks get 5 distinct tasks; an expired lease is claimable again with its attempt count raised;
- `mint_device_key` with no JWT claims fails; a revoked key fails `submit_task`; a device key can't mint;
- as user A, B's rows are invisible and every write is refused;
- a markup change prices new tasks only; an endpoint with no price row is refused `model_unpriced`;
- `credit_purchase` with the same session twice credits once.

**Stop:** nothing is applied to Banodoco here (A18 does that).
