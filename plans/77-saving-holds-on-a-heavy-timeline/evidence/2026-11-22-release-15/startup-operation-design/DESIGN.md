# Plan 77 second cut — one startup operation and observable progress

Runtime owns a single operation for an exact installation and candidate realm. Both the managed workspace inspection and native daemon startup treat an in-progress verification as an operation to observe. Admission remains the authority for health and editability. The first start after upgrade, a crash or an ambiguous prior shutdown still runs the full existing verification. The future sidecar is a separate step.

## Operation and ownership

The layer that launches admission establishes an operation identity before the long inspection. Bind it to the exact install/source generation, target realm, invoking owner, and live process birth or an existing custody reference. Runtime acquires the normal realm and workspace fences. Repeated requests for the same owned startup join its status. A request for a different realm, program generation or live owner receives the existing scope or ownership conflict. If moving from managed offline inspection to the native daemon, keep the same operation identity and its verified custody transfer. Show each stage that runs. An offline successful inspection alone does not establish native service health.

Use a locally authenticated status read available before the workspace HTTP listener is ready. A Runtime-owned IPC channel, or an owner-only operation record validated through the existing local custody and process-birth checks, is the design boundary. Select the transport with source proof before changing any public API. The record keeps the operation identity, current stage and observed work counts. It exposes no credential, private path contents or unverified project material. Confirm identity again when joining, and reject swapped, stale, wrong-owner or wrong-generation records. Mark ready only after current realm verification, exclusive custody and that instance's healthy listener all agree.

Runtime owns the start deadline and terminal result. Its bounded handoffs and liveness checks can still report genuine ownership, process, corruption or transport failure. The previous 120 s limit must let an owned healthy verification continue. The detached parent observes the same operation when its existing wait reaches 125 s and transfers exit supervision to the owner. There is no timeout-driven restart or termination by observers. A failed observer can reconnect. The process lifecycle distinguishes an absent or exited owner from a slow verifier. A terminal bad-integrity result still refuses synchronously and carries the existing reason.

## Progress and callers

Report observable stages such as verifying workspace identity, checking realm data and objects, inspecting accepted history, and establishing service health. Counters can name completed units already visited. Use a total only where the work has an exact known count. Send a stage or heartbeat during long indivisible work, with no fabricated percent or early ready. Keep operation progress distinct from successful verification.

- Runtime detached parent and managed workspace inspection join the operation before interpreting their previous wait limits. The native foreground service identifies the same operation. Starting twice does not give two owners.
- Agent CLI, the 90 s installer service verifier and the SDK launcher use the same operation status. Their individual I/O deadlines can bound a request. A pending status keeps waiting or returns an explicit resumable pending receipt without aborting the active operation, inducing retry/rollback or reporting corruption. OS relaunch applies to actual terminal failures. It never starts a second process merely because an observer’s wait elapsed.
- The local App launcher observes startup before launching the normal editor health and preview checks. The healthy Runtime and editor-ready markers stay after verified admission. Hosted editor pre-ready reporting requires a separate authenticated door design and ships later.

## Proof before promotion

Fail first at the old clock boundary. Exercise both managed offline inspection and native detached/foreground startup with a valid realm whose full pass crosses the old budget, one operation identity, progressing status across former caller deadlines and no healthy response until verification completes. Observe the same owned operation from two callers. Check absent and dead owner, mismatched process birth or install generation, stale record, real corruption and a custody conflict. An observer disconnect/reconnect leaves Runtime verifying the same lease.

Repeat the existing protected accepted-history corruption and active-restart assertions with no fixture or test relaxation. Keep the exact doctor checks, current startup integrity requirements, held browser route boundaries and Runtime refusal semantics. Measure startup milestones independently of editor navigation on the next exact installed stack. Review must challenge a false ready, double launch, stale status, process reuse and interruption following offline success.
