## Existing ownership and visibility

- Installed managed service builds `astrid-runtime run --profile astrid --data-root … --source-manifest …`; the embedded launch prelude calls `launch_admission(...)` before Runtime CLI main (`astrid/installer/service.py:347-401`). This is the existing selected-install/custody boundary; `Backend.run` strips ambient Runtime endpoint/credential and installer operation variables (`backend.py:598-620`). macOS launchd restarts crash exits, Linux systemd restarts failures after 5 s, Windows Task Scheduler retries failures every minute (up to 999); these are process restart policies, not one logical startup operation or progress observers (`service.py:478-515`).
- `astrid/runtime_cli.py` is another installed-CLI adapter: `up` does preflight `workspace inspect`, and `RuntimeCLI.up()` does a second inspect before `up`; both inspect calls are separately bounded 120 s, then up is separately bounded 120 s (`runtime_cli.py:129-167,195-220,377-403`). Keep both exact workspace identity validations; the CLI is not a live progress reader while `subprocess.run` captures the child output.
- Installer readiness verification is separate: `Backend.verify(timeout=90)` polls Runtime status (3 s subprocess), current discovery, endpoint health/realm, and compares runtime instance, release and selected realm identity (`backend.py:1807-1887`). After healthy Runtime discovery, it polls identity-bound `/health` service rows and validates unchanged instance/workspace/release while pack-host is starting (`backend.py:1909-1969`). `timeout=90` is the default, not the pack-host declared readiness budget.
- SDK `ensure_runtime` waits for launcher `up`/`connect` to return before it accepts credential-file handoff; it retries exactly once only after launcher timeout/interrupted handoff (default 120 s admission + 15 s wrapper; `autobootstrap.py:139-149,341-401,458-512`). Only after that does `host_bootstrap` read worker credential, authenticate `RuntimeProtocolClient.health()`, and poll supervised host readiness every 5 s (`host_bootstrap.py:2127-2229,2023-2078`). Its 300 s wait can identify a host as still starting, but this is downstream of Runtime being healthy enough to issue credentials.
- `resolve_runtime_connection()` demands an explicit loopback endpoint and bearer credential/path; credential files are opened with no-follow/identity checks (`workspace_client.py:148-225`). Existing authenticated service-row observers are therefore available only after healthy discovery/credential handoff. Before discovery, installer verify and SDK cannot authenticate health; SDK is waiting on CLI output, and login service is only a process manager. Runtime CLI can still run local `workspace inspect`/`status`, but no Agent-side API currently consumes an authenticated pending-startup operation while discovery is absent.

## Recommended owner and integration

Runtime `up`/managed `run` should own one startup operation ID, owner lock/lease, deadline, and progress transitions. It should expose a *read-only* startup observation through the same local Runtime authority, with a timestamp and the existing selected realm plus Runtime instance/process birth identity. A reader must bind the exact operation/owner snapshot and recheck it on every poll; expiry, disappearance, malformed state, identity change, terminal failure and cancellation remain typed outcomes, never “still starting.” Do not let Agent, installer, SDK, or OS supervisor mint a second operation/deadline. Keep per-process timeout as a last-resort bound only above Runtime's declared deadline.

Before discovery, only the Runtime owner/its existing local custody boundary can truthfully publish authenticated pending progress. The managed CLI/service can consume that observation if Runtime provides a local authenticated operation-status subcommand under the same selected data root/owner lock. Installer verify and SDK can consume the same state only through that Runtime-owned local CLI boundary until normal discovery is healthy; after discovery they keep using existing identity-bound health (the SDK health read uses its worker credential). Login supervisors cannot consume it today and should retain their crash restart policy; do not translate their relaunches into “same operation” or report them as readiness. Agent wrapper inspect x2 remains workspace preflight/identity validation, then one `up` request; on an in-progress result it should observe the same Runtime operation ID, not issue another `up` or guess from age. Installer verify 90 s and SDK wait 135 s are caller ceilings; if they return before Runtime's operation deadline they should report pending with operation ID/timestamp and preserve owner. They must not cancel, rollback, or signal a still-live owner because their local wait expired. Explicit terminal Runtime failure still reaches existing installer failure/rollback classification; user cancellation stays cancellation.
