## Storage and marker facts

- RealmStore opens/ensures SQLite WAL mode and refuses if it cannot (`runtime_protocol/store.py:1524-1540`). It sets `foreign_keys=ON` and 10,000 ms busy timeout. No explicit `PRAGMA synchronous` or checkpoint policy was found in the reviewed Runtime source; do not infer effective sync mode beyond SQLite defaults.
- Normal store writes use `BEGIN IMMEDIATE` (`store.py:1202-1225`). Startup snapshots the main DB and `-wal`, `-shm`, `-journal`, checks file identities did not move, then inspects an isolated copy (`store.py:1300-1369`). This protects a read from concurrent movement; it does not certify which writer caused a committed change.
- `admission-state.json` is a Runtime-created, fsynced/replaced JSON hint with clean/active verification fields and physical component identities (`store.py:1409-1444`). Reader accepts a parsed dict if `sqlite_components` matches current component stats (`:1380-1389`); it does not authenticate the file or compare an exact set of marker keys. Startup calls inspection with `allow_active_marker=False` (`:1122-1129`), so only the clean-shutdown branch can trust prior verification there. Offline doctor defaults to `allow_active_marker=True`; it may also trust an `active_verified` state when the owner lock is still held (`:1360-1362,7011-7020`). Missing/malformed/stale identity marker falls back to deep (`tests/test_realm_tiered_admission.py:43-61`).
- A clean marker is written after orderly store close, based on `_admission_active`; there is no final full integrity pass before setting `clean_shutdown=true` (`store.py:1690-1705`). Therefore orderly shutdown alone does not prove all changes since startup were sanctioned or valid. DB/WAL stats are a cache invalidation hint, not a content-authenticated write ledger.

## Can Runtime account sanctioned vs direct in-owner SQL writes?

Not durably with the source mechanisms found. `store.conn` is a live SQLite handle exposed to service/internal callers, and the protected tests deliberately mutate it directly (`tests/test_timeline_commit_acceptance.py:766-769`; `tests/test_timeline_commit_integration.py:1323-1332`). Commit verification uses live SQL reads, hashes/replay, and physical DB/WAL snapshots; `_physical_version()` samples DB/WAL stats (`timeline_commit_store.py:384-400`) and is an in-process cache/version guard, not a durable statement of sanctioned writes. `total_changes`/file movement can invalidate live cache state but cannot survive restart as proof of allowed semantics. A database row or trigger written in the same database cannot independently attest that a transaction was Runtime-authorized when an untracked writer can edit that database.

SQLite WAL provides transactional recovery and structural checks (`quick_check`, FK check), not proof that recovered rows came from approved Runtime operations. After unclean shutdown the owner lock is released; active marker trust is not available to startup. There is no identified durable engine invariant in this source that can prove an uncleanly recovered suffix is sanctioned.

For a suffix-only attestation to be justified, evidence would need an independently protected anchor for the verified prefix plus a complete, ordered, durable record of every permitted post-anchor write, bound to the realm and database/WAL generation, with crash gaps or ambiguity forcing the existing full doctor. It must also demonstrate that all mutation routes—including exposed in-owner SQLite access—are observed or rejected, and preserve the head/hash/closure checks against rewriting both data and its witness. This source review finds no such write ledger/anchor. A suffix computed from the DB’s current head, event rows, or a marker whose trust comes only from matching DB file stats is circular.

The restore semantic port invokes bounded integrity preflight (`timeline_commit_port.py:152-177`). These are not durable post-crash suffix attestations.
