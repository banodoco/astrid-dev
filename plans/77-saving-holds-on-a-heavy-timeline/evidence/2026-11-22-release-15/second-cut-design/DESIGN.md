# Plan 77 second-cut admission and startup state

Two changes are needed. Runtime owns the startup operation and reports its progress across callers. A separately qualified attestation can make an exact clean restart eligible for a cheaper admission. First start after an upgrade, an unclean stop, any mismatch, and any state without sufficient proof use the full scan with the same progress and cancellation contract.

This is the read-only review proposal for the Release 15 Lead. ## Sanctioned-write attestation

The current marker carries a previous deep result and the database, WAL, SHM, and rollback-journal identities at publication. Orderly close records the file identities after closing the SQLite connection. A raw write through the owned connection can therefore produce a structurally clean final image and a matching marker whose deep result predates the write. Today the timeline history walk runs even when other deep checks can reuse the marker, and it still catches that corruption. The marker cannot authorize skipping the walk as it stands. See Runtime `runtime_protocol/store.py:1381–1444,1690–1707,7012–7020,7523–7526`.

**Proposed clean proof.** Anchor the exact admitted snapshot to a successful complete verification under existing identity and custody checks. For a live writable connection that derives from it, give sanctioned write entry points an explicit transaction scope. Reconcile that scope with a mandatory observation of executed persistent writes and their commit or rollback. The existing store transaction boundary is only a starting point for the audit (Runtime `runtime_protocol/store.py:1203`). Inventory all persistent paths, including autocommit, nested transactions and savepoints, initialization and migration, timeline publication, idempotency and event updates, lifecycle reconciliation, other writable connections, and storage and CAS changes relevant to checks being deferred. An unscoped or unobservable write makes the session ineligible, including the direct owned-connection edits in the existing tests. Opening another writer, losing the observer or its coverage, replacing an owner or a database component, or losing continuous custody also makes it ineligible. A process health flag, a mutex, a digest or counter inside the same writable database, and source-code convention cannot establish coverage on their own.

Start conservative. An exactly matched stable snapshot verified in the background, with proof of zero subsequent writes, is eligible only after those boundary tests pass. Extend eligibility to a finite covered set of sanctioned mutations as the independent review proves each path. Keep transaction attribution private to Runtime and distinct from SQLite rows a raw write can create. Tie any clean attestation to its verified snapshot and format, exact realm, selected SQLite component identities after orderly checkpoint and close, and the unbroken admission and owner generation. Bind the attestation to a Runtime-owned integrity authority outside SQL mutation scope. Raw data must never self-certify. The security design must show how an old or forged attestation fails verification and how rolling back or losing that authority falls back to a scan. Close may publish it only if all observation and identity fences settle. A missing or forged field, an older format, lost provenance, a restore or migration, an unknown writer, a partial close, or a mismatch selects the full existing admission. Do not add a synchronous full history pass to orderly close. If coverage cannot be proved, there is no fast path to ship.

**WAL and the crash attempt.** Runtime forces and checks SQLite WAL in `runtime_protocol/store.py:1519–1540`. This path does not set a synchronous mode or an autocheckpoint policy, so effective installed durability settings still need measurement before a durability claim. The main DB header counter does not advance on every WAL commit. `PRAGMA data_version` is a comparison within one connection and does not observe that connection's own commits. `total_changes` counts changes on one connection and is unavailable across restart as a durable witness. WAL/SHM counters and frame offsets can reset or disappear at checkpoint or recovery. WAL recovery establishes an atomic committed image. It gives no independent evidence of which sanctioned path created it. [SQLite file format](https://www.sqlite.org/fileformat2.html#file_change_counter) · [WAL format](https://sqlite.org/walformat.html) · [Data version](https://www.sqlite.org/pragma.html#pragma_data_version) · [Connection change counts](https://www.sqlite.org/c3ref/total_changes.html)

A prepare-time authorizer can help classify calls but needs execution-time coverage of prepared statements and cursor paths. A row update callback omits some SQLite operations. A WAL callback runs after a commit and can be replaced by the autocheckpoint policy. A separately persisted post-commit seal by itself leaves a crash window. An in-table transaction receipt by itself can be forged by the untracked writer that the attestation covers. A later crash-proof design would need an independent durable anchor and a verified mapping of every committed image since it, including checkpoint, reset, truncation, rollback, and crash before and after commit and proof publication. No existing source contract establishes that mapping. For now the unclean path runs full admission. [Authorizer](https://www.sqlite.org/c3ref/set_authorizer.html) · [Update callback](https://www.sqlite.org/c3ref/update_hook.html) · [WAL callback](https://www.sqlite.org/c3ref/wal_hook.html)

**Suffix and background.** A timestamp, row count, maximum publication ID or event-chain tip alone cannot establish an immutable verified prefix. A suffix-only pass requires an independently verified old prefix plus complete append-only write attribution and an exact predecessor link and position. Any old-row change, split lineage or uncertainty runs the whole scan. A low-priority background pass must still cover the entire semantic history from a stable read snapshot, outside the writer lock, after any attested startup. A lost or forged resume cache may increase work and may never skip a required verification. Publish findings through the existing integrity/degraded and mutation-admission boundaries as appropriate. Measure and review background contention and the time until detection.

**Release 14 rollback check before marker changes.** Its static parser compares `sqlite_components` and reads known JSON keys without rejecting additional top-level fields. This suggests that an optional additive field can be ignored without reducing Release 14's own verification. Static source does not establish that an installed start or doctor succeeds. Before enabling or publishing the format, qualify the exact previous installed Runtime on separate copies of the same synthetic database with the old marker and the proposed field. Include a valid clean image, a mismatched marker, and an in-owner corruption case. Exercise ordinary start with exact identity and explicit doctor with unchanged results, and keep the old file properties and safe teardown. If Release 14 cannot start or diagnose one correctly, stop before the change and return the rollback boundary to the Lead. See Release 14 `runtime_protocol/store.py:1380–1389,7010–7019,7522–7525`. The design phase ran no such probe.

## Single owner and an observable startup operation

A Runtime startup coordinator holds the one logical operation for the selected installation and canonical realm. An owned launch can hand it to the exact managed service child with a process-birth and operation-ID proof. That handoff preserves the operation and its clock. The detached native parent and the managed service must distinguish authoritative process loss, cancellation and integrity refusal from “this observer stopped waiting.” Keep deadlines for bounded I/O and custody operations. The scan's elapsed-time threshold changes the progress state. A still-owned healthy scan keeps going. A terminal result comes from the owner, including a real integrity or identity failure and explicit cancellation. A lost living process or lost custody is a problem to report. A caller cannot cancel or launch a duplicate because its wait elapsed.

The owner exposes read-only, fresh, attempt-scoped status with the verified installation and realm binding, process birth and operation identity, phase, monotonic progress sequence, and measured work units where there is a known denominator. Missing or expired status leaves connectivity unknown. No fabricated percent, data about the timeline, credential material, early ready discovery, or mutation authority is needed. Publish the ordinary admitted endpoint and credentials only after existing custody, schema, realm and integrity gates pass. Keep explicit failure details for corrupt and ambiguous roots. When local identity or browser permission is unavailable, show waiting or unknown until an authentic observation is available.

| Existing caller | Required behavior |
| --- | --- |
| Runtime scan and native parent | Share one attempt. At the elapsed scan budget, the owner reports what is still checking. The parent's short discovery waits observe state and do not terminate a progressing owned scan. Preserve explicit cancellation and same-child discovery and health checks. |
| Agent CLI inspections and `up` | The two current inspections and the later `up` retain their selected realm and immutable identity guarantees. They observe or join the same pending operation and do not restart or return corrupt/unavailable on the three 120 s waits. Reuse a proof between stages only across the original custody fence and revalidation at handoff. |
| Installer and OS login service | The current 90 s verify caller observes the operation. A pending result leaves the same owner in place. Terminal integrity and readiness failures retain existing rollback, and OS restart policies handle actual exited processes. No retry loop replaces a progressing owner. A managed provider that cannot expose authentic progress has an unknown state. |
| SDK | Its current 135 s caller can stop waiting with a typed pending result and the same operation ID. One existing handoff-recovery retry remains scoped to true interruption. Normal worker credential and health/ready checks still happen only after admission. |
| App launcher and hosted editor | The local launcher can show owner-issued progress while it waits and still verifies discovery, identity, handshake and realm before starting Vite. The hosted door currently binds after integrity admission. A pre-ready browser status needs a separately reviewed read-only transport authenticated to the chosen Runtime and expected origin. Browser permission gates and wrong-origin refusals stay intact. The 5 s and 60 s probes are observations. They cannot report a verified owner attempt as failed or make it ready. Without authentic status the current connectivity evidence and retry behavior still apply. |

The clean case still proves schema, identity, owner custody and exact marker eligibility before admitting. An old marker or an upgrade, unclean stop, absent protection, or mismatch initiates the original complete check on a stable snapshot and can report progress for as long as the owned scan takes. The person may cancel explicitly. Cancelled or interrupted attempts leave no eligible clean witness. No health or mutation admission is published from a pending state.
