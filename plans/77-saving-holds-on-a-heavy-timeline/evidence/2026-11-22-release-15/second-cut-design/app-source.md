# Plan 77 follow-up — single-owner checking-state design input

## Current boundary and recommended shape

The local launcher already has an authoritative observation: it launched `astrid-runtime up` and is awaiting its exit (`scripts/dev-local-workspace.mjs:124-147,605-627`). The child being alive proves only that the CLI has not exited; it does not prove startup is advancing or identify which phase is checking. A process-alive spinner can be labeled “Waiting for Runtime startup” but should not claim authenticated Runtime readiness. For truthful `checking` progress, the Runtime startup authority must expose progress for that exact invocation (for example, a read-only attempt status event/endpoint with attempt ID, phase, sequence/heartbeat, and final result). App can present that state while awaiting the owner; it must neither start Vite nor pass any credential to consumers until the existing post-ready discovery and full `verifyRuntime` succeed.

Hosted `RuntimeConnectionProvider` cannot infer an in-progress local boot from the present protocol. Its first meaningful signal is `/v1/health`; browser-door refusal and no listener currently both begin as failed fetches, and refusal is distinguished only by a follow-up `no-cors` answer (`RuntimeConnectionProvider.tsx:84-127`). Current discovery proxy workspace config and Runtime forwarding also require a valid discovery/credential (`scripts/runtime-discovery-proxy.mjs:45-59,81-107,406-428`). Do not relax those routes or accept an early/partial discovery record to make a spinner. If hosted UX needs owner progress before the door opens, it needs a distinct, read-only bootstrap status channel exposed by the startup authority through a separately authenticated/admitted path. Bind it to the page's expected origin and a per-attempt nonce or equivalent freshness mechanism; carry no bearer token or mutation capability; expire it and fall back to unknown when stale. The browser must still retain local-network permission gates: `prompt` stays permission-pending without probing; `denied` stays blocked/no requests; `unsupported` and mobile remain their own outcomes.

A useful model keeps **transport evidence** separate from **Runtime identity/admission**: `checking` only when the owner reports a current attempt in progress; `connected` only after the existing health, schema, handshake actor/realm/scopes and realm checks pass; `down` only from an authoritative failed/stopped result or confirmed no listener after the allowed wait; `refused` only when an endpoint answered but origin access is denied; `corrupt/incompatible` only when readable owner status or the ordinary validated response gives a specific integrity/protocol failure. Missing, stale, malformed, or foreign-attempt status is `unknown`/ordinary transport failure, never `checking` and never connected. Do not treat generic HTTP 503 or a syntactically valid but identity-unverified status payload as admission.

One owner should enforce the deadline and publish its result. App-side waiting must consume that owner result, not install a competing timer that kills a healthy start. If the owner does not provide progress, show honest “waiting for startup command”/unknown state while it is alive; do not fabricate a progress percentage. If it exits or the owner deadline expires, retain the existing classified failure behavior.

## Existing assertions to preserve; focused additions for a future implementation

- Preserve local startup's full authenticated validation: selected profile/catalog/root, scoped product credential, health status/protocol/instance/schema, handshake protocol/actor/realm/exact scopes/schema, and realm ID (`scripts/dev-local-workspace.mjs:365-400,419-490`). Existing launcher coverage verifies valid health→handshake→realm and offline refusal (`scripts/dev-local-workspace.test.mjs:434-458`), and rejects identity/credential/profile substitutions without spawning App services (`:461-489`).
- Preserve proxy boundary: no valid discovery means no Runtime forwarding/workspace config, and current proxy uses the credential from that validated discovery (`scripts/runtime-discovery-proxy.mjs:45-59,81-107,406-428`). Progress must be a new read-only route/contract, not a bypass in these handlers.
- Preserve browser permission and classification coverage: no refusal probe before permission grant; prompt/denied states remain distinct; one failed reading remains `connecting`; two silent readings become `not_running`; a genuine no-CORS answer becomes `refused`; incompatible schema and explicit identity mismatch retain their dedicated states (`RuntimeConnectionProvider.test.tsx:530-538,540-596,828-898,1540-1686`). Keep the late successful answer path that remains pending through a slow response and only connects after health plus realm (`:598-665`).
- Add narrowly targeted tests when a status contract exists: fresh matching attempt reports `checking` while discovery/door are absent; stale, malformed, wrong-attempt, or unauthenticated status cannot report checking/admitted; final timeout/down/refused/corrupt map to distinct outcomes; `checking` never mounts editor children or sets authenticated/connected; later ordinary identity verification alone transitions to connected; permission prompt/denial suppresses status probes where local-network permission applies; local launcher never starts Vite or proxy mutations before admission; App consumes owner timeout/result without independently killing/restarting the Runtime. Include an interrupted/abandoned attempt so stale progress cannot mask a later down state.

## Unresolved boundaries

App source does not establish whether the native Runtime CLI can publish progress or expose safe pre-admission status, what phases it can honestly report, how a hosted page can reach that channel before door admission, or how a manager (such as Pinokio) exposes its own startup attempt. Those decisions belong with the single startup authority and its transport/security design. Browser network permission can prevent all local status access until granted, and browser CORS/no-CORS cannot distinguish a closed port from an origin refusal in every deployment. The current UI's two-failure classifier is a UX heuristic; it is not authoritative proof that an owner startup has stopped.
