# Release 15 Lead decision on persisted verification

The Lead’s 23 November 2026 decision applies after the first cut qualifies. Give startup one operation owner and authenticated progress before building a sidecar. Each caller observes the same operation through the complete verification and can distinguish ongoing work from failure. Hosted editor pre-ready reporting remains a separate later slice. The clean-close attestation proposal is shelved.

The sidecar design has two content-keyed success entries, one for deterministic replay and one for document validation. Keys use exact stored bytes and the effective verifier and schema identities. Group receipt lookups once. Keep the structural walk and all current live checks that each entry cannot establish. The design must list the uncached gates after both entry types and measure each on the 32-edge fixture. Doctor always checks independently, and installed Release 14 start and doctor must tolerate the sidecar before relying on it. Review must try omitted inputs, verifier changes and malformed or stale cache state.

A sidecar tracks verification work already performed. Missing, damaged, or stale success entries cost more verification. Scope the integrity promise to accidental damage, crashes, and SQL changes by the Runtime or another process that cannot also generate trusted success entries. Deliberate writes to the realm directory with correctly constructed success digests are outside the current live database boundary. If the Runtime already has an independent key that authenticates live realm state, use it to authenticate the sidecar. The exact first-cut source check found the backup HMAC only authenticates a backup or restore handoff (`backup.py:248,526–540,600–618`). The service’s child-authority key is generated per process after admission (`service.py:708–717`). Live marker checking compares filesystem component identities (`store.py:1380–1390`), while current realm integrity checks replay history and check object and event digests (`store.py:7520–7534`). These paths expose no independent signing authority for live realm state. This is a source finding, with the threat boundary still subject to independent review of the eventual cache design.

A warm walk estimated at 22–27 s at 1,000 batch-sized edges is acceptable. It scales with stored bytes. Build the first real deep fixture with the candidate on the Lead’s machine, measure per-commit timing as it grows, and measure start, open, reopen, tenth save, and add-clip at about 30 and 1,000 edges. Include actual cold I/O. The pre-candidate repeated archive read measures byte volume only.

A history format change is a saving-plans handoff. Its migration and rollback decision is separate from the sidecar. The [issue draft](issue-history-as-summaries.md) records the amplification and the closest measured single-command storage sample.
