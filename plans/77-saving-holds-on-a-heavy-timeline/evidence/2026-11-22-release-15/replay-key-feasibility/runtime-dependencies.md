## Key coverage, omissions, and cost

The current key is a good *within-process memo discriminator* for the exact replay arguments reconstructed immediately before it. It binds full ledger/edge rows; content closures for source and base; materialization continuation set; inverse history; predecessor event-chain hash; project realm id; and a recomputed row+receipt prefix chain. It does not itself attest those values, authenticate its own storage, or bind the current verifier/schema implementation. The cache remains in-memory (`_replay_memo` initialized as `set()` and cleared on version/refusal boundaries, `:360-381,662-687`); there is no persisted-key trust format here.

The row/edge key does not include all SQL result sets as raw lists; rather, current query outputs are folded into closures/continuations/history/event hash/realm, and read inputs are rechecked within the verification scope. Adding persistence must prove every helper read that affects replay is represented or rerun. In particular, do not treat a successful prior `validate()` as authority over current authorization, service schema/validator, active scope, live source/base/dependency rows, physical CAS bytes, or event prefix.

Complexity: `_event_prefix` extends an in-memory event prefix and `_history_chain` advances from `chain_tails`; an ordered all-history pass can hash prefix rows incrementally (`:1065-1085,1127-1146`). A naive persisted implementation that hashes the entire prefix separately for each of N keys becomes O(N²); preserve rolling per-scope chain checkpoints and distinguish a trusted checkpoint from a value read from the DB. `integrity_errors()` uses one verifier across ordered rows; `_verify_accepted` also deduplicates ancestry nodes within a traversal. However each row’s source/base closure and undo/continuation graph can still be large, so hashing full nested closure material for every key can duplicate substantial work. No wall-time/cost claim made here.

## Sidecar / store version caveat

Live memo reuse is already gated by SQLite connection identity, `total_changes`, `PRAGMA data_version`, DB/WAL/SHM/directory stat metadata, and package-owner/perms (`timeline_commit_store.py:384-400,463-508`). These detect live movement and prevent retaining memo across unsafe physical/code-owner conditions; they are not durable authenticity. DB/WAL/SHM stats and the current `admission-state.json` component identity map are forgeable/rollbackable by a principal who can edit the realm. SQLite WAL checksums/recovery can reject malformed frames and preserve transaction atomicity, but do not prove Runtime-authorized semantic writes. A sidecar containing replay keys beside the realm would be equally forgeable unless separately authenticated and rollback-bound by an independent trust root; even then it must handle crash ordering so incomplete witness => full replay/doctor.

## Candidate safe boundary

Only consider persisting successful pure replay outcomes after keeping every current per-request authorization and current-state dependency check above, and only if persisted proof binds `(realm, project, timeline, publication, project_seq, exact ledger/edge, predecessor/receipt chain, event-prefix anchor, source/base closure and CAS identities)` plus an explicit verifier/schema ABI digest. Provide independently protected, anti-rollback storage and a crash-consistent completeness protocol; otherwise a matching DB-resident key or mutable same-owner sidecar is not evidence. The conservative fallback is the existing in-memory memo and full current replay/doctor, with no persisted shortcut. This source inventory does not establish a safe persistent design.
