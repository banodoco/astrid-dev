## Outcome and scope

**Otto (O-T-T-O)** is the reusable importable repository/package, not an Astrid product or a mandatory organisational process. It provides the basic structure for authoring and discovering work, syncing skills and validating documents and relationships. The first consumers are Astrid Dev and Astrid Marketing. A third workspace can be unrelated to Astrid. A workspace can be small, have one or multiple pipelines, or use projects, tasks and issues without a named pipeline at all.

Three layers: (1) Otto's generic mechanisms and small operating invariants; (2) reusable opt-in starter templates and workstreams (common project structure, standard and loop from Plan 97, minimal blank starter, Dev example); (3) workspace-owned records, local templates, roles, pipelines, skills, views, checks, permissions and actual work. The initial Dev configuration is a reference template stripped of active work and history. New workspaces choose which defaults to adopt; a framework upgrade must not overwrite local authored methodology. Otto imports no Astrid-specific module except by an explicitly selected trusted workspace extension boundary; workspaces import Otto, never each other as a runtime requirement.

**Named pipelines are first-class, but not execution engines.** One discoverable definition in the workspace (proposed pipelines/<id>.toml or an equivalently small Markdown declaration) describes a purpose, selected registered record kinds, relationship kinds/directions, and relevant workstreams; optional root or scope (e.g. one project) and view use the same traversal mechanism. Definitions reference the existing registry and source-owned links; they never create a second set of relationship facts or a separate task/status ledger. Pipelines can overlap, branch, converge and have feedback loops; queries must terminate deterministically on cycles. Membership is by canonical links and the selected composition, not copying records, assuming all stages are sequential, or granting permission from a status. A workspace may add/remove a pipeline independently; deleting a definition never deletes its data. A project can participate in many workspace pipelines or be the scope of a local view/composition without a duplicated owner, tasks or evidence. Don't add nested pipeline execution, scheduler, universal DSL or automatic propagation of decisions.

**Included mechanisms and boundaries:**

- Explicit workspace root, stable ID, local identity policy (Dev numbers, Marketing slugs), repository context and skill namespace. A pinned framework revision has one authoritative declaration. Wrong or ambiguous workspace fails; source-only agents can discover the pinned workspace entrypoint and local documents without a checkout.
- Extract shared Markdown/Git helpers, record discovery and small trusted reader registrations, Plan 72 relationship index (stable workspace-qualified identity, typed endpoints/roles, duplicate/conflict/cardinality/provenance, cycle-safe traversal). Keep record meanings, identity rules and local semantic constraints in workspace registrations; external record references identify source/revision and unavailable evidence is unknown, not a successful shipment. No central graph store or automatic cross-repo synchronization.
- Discover and validate pipeline definitions against the registered graph, expose deterministic traversal/query and a readable view or listing (reuse the check/view registry; no second renderer). Dev demonstrates goal-gap-project-release and issue-release compositions from its existing canonical sources; Marketing demonstrates goal/project/campaign and idea/project where useful. Same project is referenced by multiple pipelines; a fresh agent adds a pipeline referencing existing records with no core edit.
- Extract Plan 97/98 project/identity/template machinery as reusable opt-in defaults: one common project record, tasks, issues and selected template; common standard/loop scaffolds with local workstream and additional docs; no mandatory gaps, releases, numeric IDs, project pack or project grouping in every organisation. A campaign and release are locally defined optional grouping records and relationships, not a new generic campaign-release supertype. Keep lifecycle and readiness policy local; status alone never authorizes work.
- Separate existing Plan 48 check runner and generated-view engine from their local registrations, with safe output ownership, deterministic generation, stale detection and fail-closed missing/invalid registration. Allow local checks, renderers and new record/pipeline definitions with simple Python/Markdown and small config; do not build a general-purpose schema language. Keep Dev's domain checks, public feed, issue/claim/review/auto-merge and protected writeback semantics local.
- Extract Plan 73 Markdown-to-skill build/check/install/sync. Workspaces declare namespaces and ownership, may install simultaneously, and can retire only their own generated entries; preserve Dev skill identities and historical references. Reuse final package safety and link resolution, no mandatory local installation for GitHub-only agents. A simple versioned CLI (proposed otto check, otto views generate, otto skills build/check/install or a thin sync convenience, otto init) operates on the selected workspace; choose smallest API and supported platform/package method at RS1. Existing supported Dev commands may delegate to the package as compatibility entrypoints. Pin framework and shared guidance, upgrade or roll back independently; no mutable remote instructions or uncontrolled copying.
- A small common operating contract for scoped authority, accountability, evidence/provenance, proportionate review, delegation, recovery and improvement. Local templates/workstreams own actual hierarchy, check-in cadence, model routes, stop rules, external action/merge rights and product or campaign policy. Keep release/GPU qualification, installer pins, App consumer and publication jobs in Dev. New workspace has no inherited secret, privileged app, bypass, publication or spend authority. Validate untrusted inputs without write credentials; load only explicitly trusted extension code in privileged contexts. Git merges do not grant external authority.
- Two-consumer proof: migrate Astrid Dev at an agreed boundary preserving exact semantics and oracles after the separately reviewed rename, then establish minimal real or owner-authorized candidate Marketing consumer with shared project templates, simple goal/project/campaign graph, optional campaigns, issues-as-ideas, local docs/check/view/skill and a bounded draft/review task. Prove both use the same unchanged pinned package and can independently add a template, pipeline, record kind, check/view and skill. Provide blank starter and read-only GitHub navigation. Full operational Marketing (strategy/skills/representative standard and loop projects/campaign) belongs to [Plan 96](../96-astrid-marketing-organisation/plan.md); do not duplicate its pilot or make live posting a framework requirement.

**Not included:** automatic pipeline execution, visual builder, generic orchestration or scheduling service, central database/graph, elaborate template inheritance, a new analytics/evidence platform, automatic publication/outreach/spend, generalising product release implementation, mandatory campaign/goal/gap schema, rewriting active run instructions or historical receipts. Otto is small infrastructure and reusable defaults; local organisations are flexible.
