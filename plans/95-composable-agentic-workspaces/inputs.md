### Alternatives

1. **Fork Astrid Dev:** fastest bootstrap but duplicates scripts and policy, collides on names and makes upgrades/reviews diverge; reject as ongoing architecture.
2. **Only parameterise repository names:** fails when Marketing needs different kinds, graph, lifecycle and workstreams. Not enough.
3. **Universal pipeline DSL, scheduler or graph database:** unnecessary to prove two consumers, forces future concepts into speculative machinery and introduces operations/security surface; reject.
4. **Extract small package with explicit trusted registries and Markdown policies:** reuses actual contracts, lets workspaces own differing semantics; recommended. Test a blank start and real Marketing use; keep one implementation of common machinery.
5. **Do less:** first prove a minimal workspace fixture with no distribution change; useful as an intermediate milestone but not completion because Dev/Marketing coexistence, installation and upgrades remain unproved. If final prerequisite code makes an extraction smaller, remove proposed layers rather than add more.

## Owner decisions

- **D1 (direction selected, 24 November 2026; scope approval pending):** one foundational plan and a separate marketing operations plan, after Plans 71–73. Different stages and skills are expected; current Dev config is a starting template. No request to begin implementation now.
- **D2 (open):** shared repository name, visibility, package distribution and version pin/rollback method. Recommend a small pinned package, not submodules or mutable unversioned shared sources; prove GitHub-only entrypoints. No repository creation or package publication before authority.
- **D3 (open):** extension interface and explicit workspace identity/reference form, permitted roots and local/external source semantics. Recommend simple manifest plus local Python registration and existing readers, not a schema DSL. Keep records/relations/workstreams/lifecycle separate.
- **D4 (open):** Dev migration boundary and integration route, including whether the owner permits a dev-only run or assigns a release, with no active-run rewrite. Recommend after prerequisites and at a safe release boundary. Record affected competing writers and preserve their authority.
- **D5 (open):** initial Marketing repo visibility, minimal pilot item and approved access. Recommend private or restricted by default for real strategy; use public/synthetic fixture for unprivileged CI. No actual spend, account contact or publishing required by this plan.
- **D6 (open):** common operating principles versus template/local policy, and review stops/budget. Recommend smallest shared Markdown contract; owner chooses review counts and separately authorizes external actions.
