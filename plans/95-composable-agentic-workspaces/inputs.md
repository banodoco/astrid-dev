### Ten vivid statements

1. Now Otto is a plan; after, it is a public repository that any workspace pins by tag, and nothing in it names Astrid.
2. Dev's code imports Otto for everything generic and keeps only what is Dev's own: gaps, releases, the public feed and its automation.
3. A pipeline is a small file naming stages, links and basic constraints; it never moves, schedules or approves anything.
4. A workspace can declare several pipelines; one project can sit in two of them with one task list.
5. `otto check` fails, with file and line, when a record breaks a declared cardinality, role, kind or status rule.
6. A project is standard unless its header says `**Template:** loop`; only Plans 77 and 94 change in Dev.
7. Adding a template, kind, pipeline, check or skill is a workspace edit, never an Otto edit.
8. Otto ships a playbook for standing up a new organisation, and the generic run contract and roles that Dev and Marketing overlay.
9. Dev's folder stays `plans/`; renaming it is a separate decision the owner may never take.
10. Otto's proof is Dev unchanged plus a synthetic Marketing workspace; whether Marketing works is Plan 96's question.

## Owner decisions

- **D1 (decided, 24 November 2026):** Otto is an importable framework; Astrid Dev and Astrid Marketing are its first consumers; workspaces declare several pipelines with basic constraints and tests that they hold; shared project templates; the sequence and scope [above](#owner-direction-24-november-2026). This replaces the earlier D1, and the earlier D3–D6 (manifest, trust boundary, cutover after Plan 98, review budget across three repositories) are settled by this design or renumbered below.
- **D2 (decided, 25 November 2026): repository and distribution.** Otto belongs to the `banodoco` organisation and is public: `banodoco/otto`, a `pyproject` package (distribution `banodoco-otto`, import name `otto`, an `otto` command; plain `otto` is taken on PyPI by an unrelated package). Consumers pin a git tag plus its commit in one place (`otto.toml` and the requirements line), for example `git+https://github.com/banodoco/otto@v0.1.0`; no PyPI release; no secrets in its CI. Licence: MIT (the owner delegated this open choice on 25 November 2026). The owner said on 25 November 2026 that Otto belongs to `banodoco` and that the plan should simply run; the owner created `banodoco/otto` (empty, no commits yet) on 25 November 2026 and the orchestrator's session has push access to it, so no repository-creation step remains.
- **D3 (decided, 25 November 2026, accepting the recommendation): run route.** An owner-authorized dev-tooling exception covers astrid-dev, Otto and the private `banodoco/astrid-marketing` workspace, and nothing else: no product repository, no Astrid release, no publication or spend. Under it, the accountable agent may merge card PRs into Otto `main` and Marketing `main` and cut Otto `v0.x` tags after the integrated proof passes. Merges into astrid-dev `main` still need the owner's go (given per project; see the run board).
- **D4 (decided, 25 November 2026): accountable session.** The same arrangement as every other run: the named orchestrator is the accountable agent, doing the Lead's packet review and integration, with a manager for this plan preparing packets.
- **D5 (decided, 25 November 2026): review budget.** None to set; the owner said none is needed. The plan keeps RS1 (the contract, one round) and R (one round), both read-only Pro sessions at the orchestrator's REQUEST, because Dev's own tooling will depend on Otto; it drops the separate sense check SC (owner direction on 25 November 2026 to trust the Opus recommendation, which was to cut every review stop).
