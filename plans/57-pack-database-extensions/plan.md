## Outcome and scope

The owner's direction, in her words where quoted:

- Packs should be able to "add tables and add rows", and in general "extend the database in whatever way they want".
- "We should obviously have some protected fields in the database": what Astrid itself owns is not a pack's to change.
- "We need to have a way to accommodate for that in updates and everything": a pack's tables must survive Astrid's updates and the pack's own updates, rollback and removal.
- We need "to test for it and protect against them doing destructive actions".
- Some things Astrid does in core today should become packs once this exists, installed by default: "for example, references, how we deal with references, and possibly some others".

The smallest complete outcome is a useful independently authored creative tool with its own relational data model: the creator and their agent can add and query related records, evolve the schema while working, see changes through the React interface, install an updated pack, retain creative history through failure and move the project between supported environments. The author should write creative data and logic, not implement a separate database server, storage synchronization, permission manager or backup system.

### Core-owned versus pack-owned data

Prefer SQLite for the protected workspace store and pack relational storage at the outset, including an isolated hosted Runtime. Keep a single authoritative workspace owner and durable resource identities independent of implementation language or physical storage. The Runtime owns persistence and admission; a pack owns the meaning and schema of its data. Existing typed project documents remain appropriate for small structured values; do not force every pack to use SQL or a new storage format.

The core owns genuinely shared and protected infrastructure: realm/project/user identity, resource ownership and type/schema registration, grants, canonical operations/revisions/receipts, media/CAS associations and reference integrity, task/worker execution, pack admission/version and migration receipts, dependency and recovery metadata, and appropriately scoped saved workspace/preferences. Distinguish references to resources from their domain-specific payload and rules. Do not make generic tables for characters, layers, materials, musical notes or every new feature. Existing timeline data and semantics remain protected until a separately reviewed domain migration (Plans 100/102/103); this is not a blanket rewrite of the core schema. Credentials remain in Plan 36's system, large immutable media in existing object storage, temporary work in disposable scratch. Hosted account/billing identity belongs to the hosted product service, not to a pack or necessarily the same SQLite file.

Each pack gets a stable logical storage namespace keyed by its admitted identity and appropriate scope, ordinarily project-scoped; user-wide private libraries/preferences are separately scoped and explicitly granted, not silently shared. The namespace outlives a pack's installation version and machine. The Runtime resolves identity from its authenticated session/grant, never from a client-supplied table prefix or filesystem path. Pack code can define and evolve tables, constraints, supported indexes and relational queries in its own namespace; no unrestricted DDL/DML on protected core or other pack tables. Cross-pack capabilities are exposed through versioned public operations and explicitly shared data/read projections with grants. Stable typed resource/media references carry scope, identity, pinned/follow policy, and defined missing/deleted/uninstalled behavior. No naked cross-tenant foreign keys, implicit regeneration, broad SQL read privilege or hidden second authority. Preserve useful direct relational joins inside the pack; public cross-pack joins, if necessary, need a reviewed projection/contract.

### Authoring and lifecycle contract

- Extend the existing pack declaration with the minimum storage/schema/migration contribution and compatibility requirements; one manifest and one admitted artifact identity. Supply human/agent-discoverable schema and operation descriptions, versioned SQL migration files (or equivalently reviewable declared operations), and generated/typed Python and TypeScript clients or wrappers derived from the public contract. Use parameterized queries and supported transaction batches through Runtime; simple React tools consume a scoped data client or typed pack actions, never the database file or an unrestricted privileged SQL connection.
- Agents can inspect their authorized schema, create tables and evolve it, develop a changed React tool or backend action, validate and dry-run the candidate schema on a disposable copy, propose/apply authorized compatible changes, and update the active view without a native rebuild. Reuse the existing pack transaction/admission, development reload, trust and permission model. Don't impose per-edit prompts for routine already-authorized data edits; destructive changes, new grants, schema rewrites with data loss, or transfer to another custody require the relevant consent. Report incompatibility honestly; not every migration can be live.
- Each namespace has a durable schema version, ordered immutable migration identity/digest and compatibility bounds tied to the exact admitted pack version; no silent rewriting of applied migrations. Validate upgrades from supported populated versions, preserve unknown retained data and references, serialize/fence migrations against active writes and old clients, record actual outcome, and recover interrupted migration. Schema creation/evolution is distinct from normal data mutation. A failed activation or migration retains the last usable pack/data version, or refuses safely when compatibility cannot be maintained.
- Keep data version, pack version, schema version and workspace version distinct. Rolling back software must not discard newer creative work. A downgrade is allowed only if the prior version can read/write the current data compatibly or a separately approved, lossless migration exists; otherwise refuse or open read-only with a clear recovery option. Retain user data on disable/uninstall by default; compatible reinstall recovers it. Explicit deletion/export/retention and project duplication/account deletion are separately authorized and tested.
- Runtime owns transactions, expected revisions, conflict behavior, idempotency, durable receipts and change events. React subscriptions and external agents observe committed changes; reconnect reads a current snapshot and revision, invalidates cached queries, and does not treat ephemeral notifications as durable proof. Batch useful queries and writes; no polling loop or second browser database for authoritative pack data. Align creative undo/redo and multi-resource edits with the operation contract; a generic SQL write is not automatically a creative undo operation. Require explicit atomicity boundary or recoverable idempotent workflow for changes that span pack/core resources. Do not claim cross-database ACID or silently compensate away user work.
- Backup/restore, project export/import, cloning, ownership transfer and storage accounting include all relevant pack data, schemas, migration history, artifact versions and referenced media at a coherent cut; unknown or unavailable pack payloads remain recoverable and portable rather than discarded. Verify exact schema/data identities and reference continuity; credentials and private data outside the transfer scope do not travel. Reuse existing Runtime/CAS verification instead of a second backup product.

### Local and hosted parity, trust and physical layout

The public storage contract is identical whether the authoritative Runtime is local or hosted. In cloud-assisted local mode a remote worker gets only scoped inputs/operations and returns results; it does not open the local database file or become a second writer. For hosted mode qualify an isolated headless authority with persistent local storage and scoped API clients first; full account isolation, retention, backup and load are Plan 26's responsibility. Coordinate Plan 105 deployment and Plan 103 native runtime with the same versioned contract and corpus. Keep SQLite by default where measured writer concurrency permits; storage engine/hosting implementation is hidden behind the stable contract, not a second SDK. No network-mounted SQLite file shared across writers, arbitrary remote SQL port, dual-primary local/cloud sync, or mandatory hosted dependency for local work.

Compare protected pack-owned tables in the canonical SQLite file (shared atomic commit, harder schema admission/isolation), separate Runtime-managed SQLite files per logical pack/project namespace (stronger physical separation and independent migrations, difficult cross-file commits and coherent backups), and existing namespaced documents for small tools. Prefer separate files for ordinary independent relational data only if the actual cross-resource atomicity and portability proofs justify it. SQLite WAL does not guarantee crash-atomic transactions across attached files; for genuinely atomic core/pack mutations either use a single authority's proven transactional representation or explicitly specify a recoverable publication protocol and its failure semantics. Do not turn cross-file commits into a new general transaction coordinator without evidence. Decide physical arrangement at PD-2/RS1, not in the public API. Keep strict core schema admission; do not simply allow all extra tables in the current canonical database.

SQL mediation must enforce tenant/project/pack scope in the trusted Runtime; declared trust and sandbox boundaries (Plan 15) are essential for arbitrary frontend, Python and build code. SQLite has no per-pack users or row-level role system. Use separate handles or scoped compiled statements, parameter binding, schema object validation and restrictive authorizer/defensive settings where justified; explicitly block unauthorized attachment/path access, extension loading, unsafe pragmas, triggers/views or functions that escape permitted effects, unbounded SQL, cross-namespace reads/writes/DDL, and resource exhaustion. Test locks, deadlines, cancellation, DB size, result size, query budgets and denial of service; prefix naming, manifest declarations and frontend error boundaries are not security guarantees. A local trusted pack with filesystem access is a distinct trust case, not proven malicious-code isolation. Preserve minimal recovery when a pack's database is corrupt or incompatible.

## Completion

- Fresh contributor or agent builds a useful React/Python tool (e.g. characters/outfits/scene relationships) using only public storage, operation and pack interfaces. Create related tables, indexes and records, query/update from both clients, inspect authorized schema, and show committed UI updates; no core source change or bespoke server/database setup.
- Upgrade that tool's populated schema and implementation with real existing work, validate data and references, exercise interrupted/failed and destructive migrations, incompatible downgrade, uninstall/disable and compatible reinstall. Existing work, exact artifact/data versions, migration receipts and last usable version remain inspectable; no silent data loss.
- Demonstrate supported transaction batches and conflict/replay semantics; run a real operation touching core and pack resources with chosen atomicity or recoverable publication semantics, including crash between steps. Undo/redo and pinned references behave as declared. Refuse unsupported mixed transactions explicitly.
- Plant denied cross-project, cross-tenant, cross-pack and core read/write/schema operations, including indirect SQL through permitted objects and excessive queries. Correct denial, cancellation/quotas and grant revocation; unaffected workspace and core integrity. Separately prove only the actual trust boundary, not arbitrary untrusted code isolation from SQL tests.
- Backup/export/clone/import/restore populated pack data plus referenced media at coherent version, including missing pack or incompatible source; verify data digests, preserved user control and recovery. Core upgrade/rollback and pack upgrade do not rewrite each other's storage outside the agreed migration.
- Same supported pack artifact and SDK calls work on local and isolated hosted/headless authority; local-first remote worker cannot open or write another authoritative DB, and return/retry paths preserve scope. Full hosted accounts/load are separately qualified in Plan 26.
- Convert one real existing core creative feature (references proposed) into a default-installed pack, preserving existing data, behavior, IDs, references and migration/rollback compatibility; it uses the same public contract as independent contributions. Do not move system custody or trust controls into packs.
- Independent review of actual data-safety, trust, migration, rollback and parity evidence. Record candidate identities, commands and limits, resolve material findings and hand off to existing projects. Plan completion does not automatically close a vision gap.
