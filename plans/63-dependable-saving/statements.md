# Statements — Dependable saving

[Plan](plan.md) · [Inputs](inputs.md) · [Tasks](tasks.md)

For the owner to scan in a minute. The plan is two ideas: **one home and four outcomes** (the editor), and **a settled head** (the Agent and Runtime). The first five statements are the plan's five invariants in plain words; the rest are the edges. Each is true of the plan as written on 18 November 2026, after the independent check cut it to its lean form. Say "no, not that" to any of them before tasks are dispatched, and the plan changes.

**The one rule, for both kinds of writer.** Anyone who changes a timeline, a person in the editor or an agent through any tool, sends one commit to the one commit route, with the head they read and a key they keep. The Runtime merges what does not clash and answers with one of four outcomes. **Accepted:** take the head it returns; it may include someone else's changes. **Moved:** the head changed and your change clashes; read the new head, then run an intent again on it (at most three times) or park a fixed decision. **Refused:** it will never be accepted as sent; it is parked with the reason. **Unavailable:** nothing was decided; send the same bytes with the same key. **`head_busy` is `unavailable` for every client** (today the editor retries it and the Agent parks it as refused). Parked work is listed and has two ways out: try again or discard. The editor and the Agent keep separate queues, because a browser tab and a short-lived process cannot share one, but they read one reply the same way, and one fixture of replies proves it. This replaces the three vocabularies the rule is now stated in (the Agent's editing guide, D11 and the editor's code).

1. **An edit is saved, waiting, or not saved, and the editor always shows which, in one place, with a way out, and many quick edits never undo each other.** While anything is queued, the screen keeps your own edits; an accept moves only the base the next save is sent on; the screen takes the server's document when the queue is empty. There is one queue of unsaved changes per timeline, one bar drawn from it, and nothing else that stores a document. After a reload, and in a second tab, you see the same thing.
2. **Every reply to a change, for every writer, is one of four things, and the server says which:** it is in (`accepted`), the head moved and your change is applied to the new one (`moved`), it will never be accepted (`refused`), or nothing was decided (`unavailable`, so the same bytes are sent again). The editor does not read error text. A Runtime too old to say which is read by its status code, and an expired session counts as "try again", not as a refusal.
3. **A refusal parks the change and everything queued behind it, and you can always get out.** They leave the timeline together and wait in the bar with Try again and Discard, the same two buttons as every other state, and you can keep editing meanwhile. Adding the next edit never throws because of an earlier one. You can discard any unsaved change, in any state, before or after a reload. (D15, open, is this form: the owner may prefer a refused change left visible and marked, or a Restore button as well.)
4. **A new rule cannot refuse a document for an old problem it did not cause, and Astrid cannot store what it later refuses.** Every whole-document rule goes through one gate and registers itself under an owner prefix; a test runs each rule against each known old shape of document. A selection is judged by its identity and bytes, not by the whole head. Media and catalog entries are checked once, when written. Accepted history cannot be changed by an update or a delete, so it is never re-proved.
5. **An edit costs the change.** A save does the change plus one pass over the document, however long the history, and a count-based test fails if that stops being true. Adding one object reads that object. An import does not wait behind a commit, and we measure that again.
6. **Unsaved work already stored in your browser is carried over.** Each old owner with work becomes one parked entry in the new row, oldest first; a draft is dropped when the queue holds the same work. Placement and timeline creation use the same row.
7. **One set of long-lived test documents** (synthetic, no content from your timelines) runs the server side, and one model test plays every outcome at every queue position, a lost reply, a reload between any two steps, a second tab, an old-Runtime reply on the editor side, and the editor beside an agent on one head (disjoint changes both land; a clash gives the second writer `moved`).
8. **It deletes more than it adds.** The draft database, owners, the session's document copies, five of the six save surfaces and at least seven throws go; the nine-kind failure classifier is folded into the one decoder, not kept as a second path. Added: the `outcome` field, the parked entry and one write-time admission function.
9. **Agents are told the rule in one paragraph, in one home.** The Agent's timeline skill carries it, including what to do when the Runtime is unavailable and which timeline a test may write to (a duplicate, never the one you are viewing); the other skills link to it, and the installed skills that still teach checkout-and-publish are brought into line.
10. **It does not make the editor send intent, does not resume an upload across a reload, and does not promise a sub-second reply.** The editor sending a named command for every gesture, the durable upload record and the closed reason list with headlines are Plan 18. A dropped file is retried for as long as the tab is open; if you close it mid-upload, you drop the file again.
11. **It is queued, in no release, and nothing starts until you choose.** Release 15 is recommended: the save fixes already merged on Release 14 (N1 to N12, the `_reference_basis` fix) carry the behaviour, and this plan carries the structure that makes it impossible to break again. It goes ahead of Plan 18, whose code gate is a week of your editing. The one decision that blocks the critical path is D15, before CC-5b.
