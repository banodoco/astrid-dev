# Statements — Dependable saving

[Plan](plan.md) · [Inputs](inputs.md) · [Tasks](tasks.md)

For the owner to scan in a minute. This is the first of four plans (Dependable saving; [Fast saving](../64-fast-saving/plan.md) in parallel; [Editing together](../65-editing-together/plan.md) and [Extensible editing](../18-timeline-editing/plan.md) after it). The plan is two ideas: **one home and four outcomes** (the editor), and **a settled head** (the Agent and Runtime). The first five statements are the plan's five invariants in plain words; the rest are the edges. Each is true of the plan as written on 18 November 2026. Say "no, not that" to any of them before tasks are dispatched, and the plan changes.

**The one rule, for both kinds of writer.** Anyone who changes a timeline, a person in the editor or an agent through any tool, sends one commit to the one commit route, with the head they read and a key they keep. The Runtime merges what does not clash and answers with one of four outcomes. **Accepted:** take the head it returns; it may include someone else's changes. **Moved:** the head changed and your change clashes; read the new head, then run an intent again on it (at most three times) or park a fixed decision. **Refused:** it will never be accepted as sent; it is parked with the reason. **Unavailable:** nothing was decided; send the same bytes with the same key. **`head_busy` is `unavailable` for every client** (today the editor retries it and the Agent parks it as refused). Parked work is listed and has two ways out: try again or discard. The editor and the Agent keep separate queues, because a browser tab and a short-lived process cannot share one, but they read one reply the same way, and one fixture of replies proves it. [Plan 65](../65-editing-together/plan.md) adds "and what you relied on" to what a writer sends.

1. **The screen is your document, however fast you edit.** One save is in flight; everything you edit meanwhile waits as one batch and goes as the next commit, each edit still its own undo step. An accept moves only the base the next save is sent on; the screen takes the server's document only when nothing is in flight or waiting. Nothing is refused or undone, nothing jumps, everything is saved in order, and the queue stays bounded whether you edit once a second or twenty times. There is one queue of unsaved changes per timeline, one bar drawn from it, and nothing else that stores a document; after a reload, and in a second tab, you see the same thing.
2. **Every reply to a change, for every writer, is one of four things, and the server says which:** it is in (`accepted`), the head moved and your change is applied to the new one (`moved`), it will never be accepted (`refused`), or nothing was decided (`unavailable`, so the same bytes are sent again). The editor does not read error text. A Runtime too old to say which is read by its status code, and an expired session counts as "try again", not as a refusal.
3. **A refusal or a clash parks the change and everything queued behind it, and you can always get out.** They leave the timeline together and wait in the bar with two buttons, **Keep mine** and **Discard**, the same two as every other state, and you can keep editing meanwhile. **Keep mine** sends the parked change on the current head, where it now lands: you overwriting on purpose. **Nothing is ever re-applied for you automatically.** For a clash the bar names the clip ("The agent changed this clip first"); a delete after an agent's edit to the same clip parks the same way ("The agent edited this clip; Keep mine deletes it"). A refused batch is resent step by step once, so only the bad edit and what follows it are parked. You can discard any unsaved change, in any state, before or after a reload. (Decided by the owner on 18 November 2026.)
4. **A new rule cannot refuse a document for an old problem it did not cause, and Astrid cannot store what it later refuses.** Every whole-document rule goes through one gate and registers itself under an owner prefix; a test runs each rule against each known old shape of document. A selection is judged by its identity and bytes, not by the whole head. Media and catalog entries are checked once, when written.
5. **Agents are told the rule in one paragraph, in one home.** The Agent's timeline skill carries it, including what to do when the Runtime is unavailable and which timeline a test may write to (a duplicate, never the one you are viewing); the other skills link to it, and the installed skills that still teach checkout-and-publish are brought into line.
6. **Unsaved work already stored in your browser is carried over.** Each old owner with work becomes one parked entry in the new row, oldest first; a draft is dropped when the queue holds the same work. Placement and timeline creation use the same row.
7. **One set of long-lived test documents** (synthetic, no content from your timelines) runs the server side, and one model test plays every outcome at every queue position, a burst of edits at any rate, a lost reply, a reload between any two steps, a second tab, an old-Runtime reply on the editor side, and the editor beside an agent on one head (disjoint changes both land; a clash gives the second writer `moved`).
7a. **Undo is a command.** Undo of an edit still waiting is removing it from the queue; undo of an edit in flight or accepted is `timeline.inverse` of your own record, through the same queue and the same four outcomes; if someone changed the same thing since, the undo parks ("The agent changed this since; Keep mine undoes it anyway"). Your undo list survives an adopted foreign head. (Plan 65 deletes the snapshot stacks and lets you undo an agent's change from the "who and what" line.)
7b. **The server derives; nobody compares.** The Agent works out what a change wrote and what it relied on by running it, in one record shape per effect kind; a read is an address, never a value you saw; the Runtime checks identity and applies. A value your editor declared can no longer refuse your own edit. Every kind of edit is proved by one matrix through the real Runtime route (CC-13), so a gesture that cannot save is found by a test, not by you.
8. **It deletes more than it adds.** The draft database, owners, the session's document copies, five of the six save surfaces, the 500 ms save debounce and at least seven throws go; the nine-kind failure classifier is folded into the one decoder, not kept as a second path. Added: the `outcome` field, the batch, the parked entry and one write-time admission function.
9. **It does not make the editor send intent, does not resume an upload across a reload, and does not make saving fast.** The editor sending a named command for every gesture, the durable upload record and the closed reason list with headlines are Plan 18. How fast an accept is, is Plan 64. A dropped file is retried for as long as the tab is open; if you close it mid-upload, you drop the file again. An agent's change shows at your next pause, not in the middle of a burst, until Plan 18; a clash on the same field parks your change rather than re-applying it; a delete after an agent's edit to the same clip is a parked change, not a delete.
10. **It is in Release 15 by your decision, queued until you say go, and ahead of Plans 65 and 18's editor half.** All four plans are Release 15 (Plan 64 in parallel from the same day); Release 14 gets only a stop-gap of about 3 to 4 days (the two landed fixes, a sweep of every edit kind, what an ordinary session hits, and the speed bisection). The save fixes already merged on Release 14 (N1 to N12, the `_reference_basis` fix, and `quick-edits`, the first step) carry the behaviour, and this plan carries the structure that makes it impossible to break again. Plan 18's agents-and-packs half does not wait for your week of editing; its editor half does. The decisions are recorded in [inputs.md](inputs.md#owner-decisions).
