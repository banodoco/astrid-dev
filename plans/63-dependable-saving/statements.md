# Statements — Dependable saving

[Plan](plan.md) · [Inputs](inputs.md) · [Tasks](tasks.md)

For the owner to scan in a minute. The first five are the plan's invariants in plain words; the rest are the edges. Each is true of the plan as written on 18 November 2026. Say "no, not that" to any of them before tasks are dispatched, and the plan changes.

1. **An edit is saved, waiting, or not saved, and the editor always shows which, in one place, with a way out.** There is one queue of unsaved changes per timeline, one bar that is drawn from it, and nothing else that stores a document. After a reload, and in a second tab, you see the same thing.
2. **Every reply from the server is one of four things, and the server says which:** it is in (`accepted`), the head moved and your change is applied to the new one (`moved`), it will never be accepted (`refused`), or nothing was decided (`unavailable`, so the same bytes are sent again). The editor does not read error text, and a reply it cannot read counts as `refused`, not as "try again for ever".
3. **A refusal removes only that change, and you can always get out.** The change that was refused, and only what depends on it, leaves the queue and is listed with the reason. You can discard any unsaved change, in any state, before or after a reload. Adding the next edit never throws because of an earlier one. (How the refused change looks is D15, open: removed from the timeline and listed with Restore, or left visible and marked.)
4. **A new rule cannot refuse a document for an old problem it did not cause, and Astrid cannot store what it later refuses.** Every whole-document rule goes through one gate and registers itself; a test runs each rule against each known old shape of document. A guard on what you drop or select is judged by what it reads, not by the whole head. Media and catalog entries are checked once, when written.
5. **An edit costs the change.** A save does the change plus one pass over the document, however long the history, and a count-based test fails if that stops being true. Adding one object reads that object. A file you already have is not downloaded again, and a file you drop is never lost to a save in progress.
6. **A dropped file is a record in the queue.** It is stored in the row, and sent again if the connection is cut. The upload's own recovery and the "Failed to save asset" toast go. (This moves out of Plan 18's TL-10; "a drop is a named command" stays there.)
7. **One set of long-lived test documents** (synthetic, no content from your timelines) runs all of this. A model test plays every outcome at every queue position, a lost reply, a cut upload, a reload between any two steps and a second tab.
8. **It deletes more than it adds.** The draft database, owners, the session's document copies, five of the six save surfaces, the nine-kind failure classifier and at least seven throws go. Added: the `outcome` field, `discardScope`, the one bar, the one object reader and the one reply writer.
9. **It does not make the editor send intent, and it does not promise a sub-second reply.** The editor sending a named command for every gesture is Plan 18; this plan only stops the old checks growing. Validation still costs about the change, not nothing.
10. **It is queued, in no release, and nothing starts until you choose.** Release 15 is recommended: the save fixes already merged on Release 14 (N1 to N12, the `_reference_basis` fix) carry the behaviour; this plan carries the structure that makes it impossible to break again, and goes ahead of Plan 18. The code gate for Plan 18 is a week of your editing. The one decision that blocks the critical path is D15, before CC-5.
