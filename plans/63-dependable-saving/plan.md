**The end state.** The owner edits "Almost Ready" for a week and meets no stuck state, and the fast-edit property below passes in the model test and on the staging stack. Two ideas, no dependency between them: **idea A, on the App: one home and four outcomes** (the screen is the person's document; an unsettled change has one home; a reply has one of four meanings named by the server, for every writer), and **idea B, on the Agent and Runtime: a settled head** (a check judges only what a change introduces, and the server derives what a change wrote and relied on).

**The target architecture, stated once (the other three plans link here and do not copy it).**

1. **Effect list** (the Agent produces, the Runtime stores): the one representation of an edit; ordered writes of `(address, before, after)` in a closed set of kinds; a read is an address, never a value. It is the patch, the write set, the read set, the inverse and the history record.
2. **Command** (the Agent's registry): a named function from head, selector and arguments to an effect list. A raw patch is the identity command. Packs register commands here. Ops are open; effects are closed.
3. **Acceptor** (the Runtime): one commit at a time per timeline. It applies the effect list and compares nothing the provider already computed.
4. **Proof rule** (stated once, checked in the Agent): nothing relied on or written was changed by another writer since the named head, and no new finding. A writer's own earlier queued records do not count as another writer.
5. **Head** (the Runtime): immutable history; the head's findings stored with it (a cache keyed by rule-set version).
6. **Identity and binding** (the Runtime): ids, revisions, object digests, keys. The only thing the Runtime checks about a provider's answer.
7. **Rule registry** (the Agent): pure `findings(document)`, under the delta gate. Packs register rules here.
8. **Outbox** (each writer): ordered records with an opaque payload, sent as a batch; parked entries live in the same row. A record holds a patch, never a whole document.
9. **Four outcomes** (set where each reply is built): the only thing a client branches on.
10. **Client policy on `moved`** (each client): an agent runs again (at most three times); a person's change parks with everything queued behind it, and its two buttons are **Keep mine** and **Discard**. Nothing is ever re-applied automatically.
11. **Undo** (a command): `timeline.inverse` of the writer's own record; a queued edit is removed from the queue; the snapshot stacks go on the Runtime-backed path.
12. **Preview** (the App): a disposable local picture of a gesture; never a judge.

Who decides what: the Agent decides what an edit means and what it wrote and relied on, by running it; the Runtime applies it and checks identity; the App previews and queues. **Where a fact is still held twice** (and why it stays): what an edit means (the handler, and the editor's preview, for instant feedback); how an effect is applied (the recorder, and the applier, held together by one test: applier(effects, base) equals the provider's document on every matrix row); bindings and identities (about 158 sites, ending only if the Runtime allocated identities itself, which no plan proposes: the largest remaining duplication); the inverse (stored `before` values and the Runtime's inverse-stage code, left alone, a candidate once the applier is proven); the outcome of a reply (the App's decoder and the Agent's client, one pinned fixture); old-Runtime fallbacks (give both an end date); the command schema (the Agent's registry, generated App constants, one direction); the queue (the editor's outbox and the Agent's pending record, one contract, two implementations); a `before` value in a raw patch (an address only, CC-16); edit kinds (`EDIT_KINDS` in the App and the Agent's registry, until Plan 18's TL-5 generates one from the other).


**The property, first.** A scripted test, at two levels (the model test with a scripted `send`, and one run on the staging stack): *for N from 1 to 20 edits a second, for 30 seconds, mixed (drag, nudge, drop, trim, field), with each save taking anything from 0 to 10 s, and accepts, a lost reply and one foreign commit landing at any point in the burst:*
1. **None refused or undone.** Adding an edit never throws and never declines.
2. **No jumps.** After every step the screen equals the person's own edits applied in order. It changes for only two reasons: the person edited, or the queue was empty and the head had moved.
3. **All saved, in order.** When the burst ends and the queue drains, the Runtime's head equals the starting head plus the N edits in order (plus any foreign change), and equals the screen.
4. **Bounded.** At most one save is in flight and one is waiting, whatever N is. The number of commits sent is at most (burst length ÷ save time) + 2, not N.
5. **Soon.** The last edit is accepted within two save times of the gesture ending.

Lines 1 to 3 are the failures the owner sees today. Lines 4 and 5 are what makes it hold at any rate; without them a fast enough person outruns the saves and the queue grows without limit (at 5 edits a second and 3 s a commit, 30 seconds of editing takes 7.5 minutes to drain).

**The root cause.** Two things, one for each idea.
- *Editor:* nothing gives an unsettled change one home, and at every accept the session puts the server's document on screen, which does not hold the edits still queued, so three guards in a row refuse the next edit (`checkHead`, the same-document check, `replaying`). A change can be in an outbox owner, a session copy, a draft slot and six React flags at once, and a reply can be classed nine ways by status code. Each of the sixteen incidents on one timeline ([inputs.md](inputs.md#planning-evidence)) is a path through that space nobody designed. Release 14 has not built this centre: the draft database, the owners, the six inputs to the bar and the edit-blocking throws are all still in the code.
- *Server:* nothing in the stack treats an accepted head as settled. Every request re-proves the accepted base from scratch against today's code, and when that disagrees the only outcome is a refusal. That produced whole-head refusals ([#842](https://github.com/banodoco/astrid-dev/issues/842)), writers that stored what readers later refuse, and states nothing could discharge ([#732](https://github.com/banodoco/astrid-dev/issues/732)). The cost of re-proving (commits that took 3 minutes) is [Plan 64's](../64-fast-saving/plan.md).

No test held a document with a history or with size, so each slipped through.

**The six invariants** are the plan's statements (the plain-language form is [statements.md](statements.md)). Each is held by the type, the model test, the edit-kind matrix or a named count, nothing more.

1. **The screen is the person's document; one queue is the only home of unsaved work.** **The model:** the screen is the person's document. One save is in flight; everything edited meanwhile waits as one batch and goes as the next commit, each edit still its own step. An accept moves only the base. The server's document reaches the screen only when nothing is in flight or waiting (and the screen snaps to it without refusing if it differs). Nothing compares a new edit with the head: adding to the queue has no precondition, in the session or in the handoff. One ordered queue per timeline, in IndexedDB: the existing outbox, one row per timeline. **A record holds a patch, never a whole document: an append costs the edit, not the row** (today a record holds about three whole documents on the named-command path and about five on the document-patch path, and every append reads, clones and rewrites the whole row; CC-5b measures it in a real browser on a real-size document against the 50 ms "kept" budget). A record is `{id, key, basis, label, payload}` and **the payload is opaque to the queue**, so Plan 18's TL-5 only swaps the payload (a document patch for `{op, select, args}`). The badge, the bar and what a reload shows are one pure function of that row. One gesture is one record; a field edit commits when the edit ends. **The proof is the property above.**
2. **Every reply to a change is one of four outcomes, for every writer, and the server says which.** `accepted` (adopt the head, drop the record), `moved` (apply the same change to the new head and send it), `refused` (these bytes will never be accepted; invariant 3), `unavailable` (nothing was decided; send the same bytes again, same key). The commit and import routes carry the outcome as a field, **set where each reply is built: by the Runtime for the errors it builds, and by the Agent's `failure()` (where most commit refusals are built) through one mapping table kept beside the reasons**: `conflict` and `stale_head` are `moved`; `head_busy` and a 503 are `unavailable` (**for every client**: today the editor retries it and the Agent files it as a refused pending change); `invalid` and every other `refused` are `refused`. Reasons are for people and never decide behaviour. One decoder, total, in `send(request): Promise<Outcome>`, the only function in the save modules that sees an HTTP status; against a Runtime that sends no `outcome`, it falls back to the present status table collapsed to four values, private to `send`; 401, 403, 408 and 429 are `unavailable`. The Agent's own client reads `outcome` too (CC-4b).
3. **A refusal parks itself, and nothing ever blocks an edit.** On `refused`, that record and everything queued behind it are parked together as one entry in the same row; a refused batch is resent step by step once, so only the bad edit and what follows it are parked. The document returns to the head plus what is left. The bar keeps its two buttons for every state: **Keep mine** (queue the parked entry on the current head, where it now lands: the person overwriting on purpose) and **Discard**. **A clash follows the same rule as a refusal** (decided, [D16](inputs.md#owner-decisions)): a person's clashing change parks with everything queued behind it, with the clip named ("The agent changed this clip first"), and is never re-applied automatically; a delete after an agent's edit to the same clip parks the same way ("The agent edited this clip; Keep mine deletes it"); an agent reads again and runs again, at most three times, then reports. Any unsaved change can be discarded, in any state, before and after a reload. ([D15](inputs.md#owner-decisions), decided 18 November 2026.)
4. **A check is signed by what it reads, and refuses only what the change introduces.** The delta gate, and a guard on a change's inputs signed the same way: a selection by identity and bytes, not the whole head. One writer admits what readers will accept. (Accepted history cannot change: that is [Plan 64's](../64-fast-saving/plan.md) CC-11.)
5. **One rule for both kinds of writer.** The editor and any agent send one commit to the one commit route, with the head they read and a key they keep, and read the reply the same way; one fixture of canned replies proves the editor's decoder and the Agent's client give the same outcome ([statements.md](statements.md)). Agents are told the rule in one paragraph in one home (CC-12). **What a writer relied on is derived, never declared** ([D17](inputs.md#owner-decisions)): for a named command, the addresses its handler read through the recorder plus the addresses it wrote; for a function commit, the union of its commands'; for a document publish, the addresses in its diff, derived on the server; for the editor's document patch, the addresses it writes (the values it sends are ignored). Relying on the whole timeline (`reads="timeline"`) is opt-in. [Plan 65](../65-editing-together/plan.md) surveys which intents need it.
6. **The server derives; nobody compares.** Between the Agent and the Runtime there is one proof rule (see the target architecture above): the Agent derives what a change wrote and relied on by running it, in one record shape per effect kind; a read is an address, never a value the writer saw; the Runtime checks identity and binding and applies, and never branches on an op name. A mismatch at the writer's own base is never a real clash; it is a misstatement, so nothing a writer declares can refuse its own edit (the refusal that said "declared field read does not match" was the App declaring a thicker copy than the server's, and the removal that the Runtime wanted whole was recorded as one row's clear). `invalid_records` stays a `refused` outcome with a plain "our fault, not your edit" wording, and is unreachable from any row of the edit-kind matrix.
