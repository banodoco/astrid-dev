**Approach.** Two ideas, two tracks. **Idea A (App): one home and four outcomes.** One queue row per timeline with an opaque record payload and a parked entry (CC-5b), four outcomes on the commit and import routes with one decoder (CC-4), an in-memory upload retry (CC-10), and a model test that compares the screen with the row (CC-5a). **Idea B (Agent and Runtime): a settled head, here the rules.** A rule registry and one delta gate (CC-3) so no rule can re-judge an accepted head; one write-time admission (CC-6) so a writer cannot store what a reader refuses; one corpus (CC-7) that runs all of it. The cost half of a settled head (the scaling test, closing what is red, immutable accepted history, transport proof) is [Plan 64](../64-fast-saving/plan.md). The batch (CC-5c) and the burst property are new from the four-questions check. **The type and the model test carry the enforcement; the other layers are dropped:**

1. **The boundary.** `send(request): Promise<Outcome>` is the only function in the save modules that sees an HTTP status. `Outcome` is a four-member union, so a fifth state cannot be written without changing it. A cheap lint, scoped to the save modules (not the page, the placement requester or history), forbids `ApiError`, `.status` and a match on error text.
2. **The model test, one file.** A scripted `send` plays every outcome at every queue position, a lost reply, a reload between any two steps, a second tab, a Runtime that sends no `outcome`, unsaved work already stored in the old shape, and a drop while the head moves. After every step it asserts: adding an edit never throws; what the screen shows equals the function of the row; every record is accepted, parked, or queued behind an `unavailable`; Discard always leaves a saved state, and the next edit saves. It speaks only of rows and outcomes, never of `doc.patch` shapes. A new state or surface cannot be added without this test failing, because the screen is compared with the function.
3. **Server side.** The generated grid: every operation on every corpus head introduces no finding. The corpus gains a selection whose lifecycle advanced between select and commit, and a head with many audio sources. (Counts at 3, 30 and 300 history entries are Plan 64's.) Each error reply from the two routes carries an `outcome`. The only ratchet is the Agent's `_fail` count (and its corpus shape set); a count held at zero is a lint or a test, not a ratchet file.

Alternatives rejected: **the first draft's wider form** (an independent check cut it: `outcome` on every mutating route, a closed reason list with a sync script here, a stored `File` in the queue for uploads, one object reader as a refactor, a ratchet file in each repository, per-clip dependents and Restore/Dismiss; see Challenge); a cache keyed by base revision (every ordinary edit creates a new base, so it only helps retries); a second resolver for the legacy probes called "equivalent" (the pattern the 17 November review named; the collect pass reuses the evaluator and the old probe stays as a test oracle); a clock gate (the owner forbids it); keeping this inside Plan 18 as a phase (superseded: one cause, one home); **pulling TL-5 (the document as head plus queue) in** (it is the heart of Plan 18's command layer and, with TL-6 to TL-11, about 60 days of conversions: it would make "stability" a 90-day project and delay the result now; with the upload half of TL-10 moved in as CC-10, this plan completes its five invariants in the form a person can observe, and what remains for phase 1 is the deletion of one stored copy); doing extensibility first (each conversion would be built against code that is then deleted, every pack rule could refuse an old document, the gesture matrix would be generated twice, and the owner could not edit dependably for the length of phase 1).

**D15 — Open (owner), new: what a refused change looks like.
