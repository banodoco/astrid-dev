# Tasks — One model for astrid-dev's records, checks and generated pages

[Plan](plan.md) · [Inputs](inputs.md). **Phase 1 is accepted and authorized to run** (owner's go, 11 Nov 2026, in [inputs.md](inputs.md#planning-evidence)). Phase 2 and the proposed phases are not.

Routes: **N**, **X**, **S**, **T** per the [run contract](../../skills/astrid-dev-shared/run-contract.md). X and S tasks delegate reading, mechanical edits and checks to N helpers.

**Where work lands.** Every task lands by PR on `int/48-one-record-model` in astrid-dev, cut from `main` when the run starts. Record each task's base SHA when it starts. Only astrid-dev changes.

**Critical path, Phase 1:** PM-0 → PM-1 → PM-2a → PM-2b → PM-3 → PM-4 → PM-5t → R1. This is one dependency chain: run it in one checkout on one task branch, in order, pushing after each task. Only PM-5 is independent; it may run beside the chain in a second checkout. **Phase 2:** PM-6 → PM-7 → R, with PM-8 and PM-9 in parallel after PM-6. Phases 3 and 4 (PM-11a to R4) are proposed only and start only if owner decision D7 accepts them; their path is stated below.

Affected: `scripts/test_check_docs.py`, `test_check_completion.py`, `test_check_gap_boundaries.py`, `test_check_project_planning.py`, `test_claim_project.py`, `test_review_intake.py`, `test_export_public_vision.py`, `test_project_contract.py`, `test_gap_relationships.py`, `test_vision_subject.py`. Not affected, and must stay green: `test_model_usage.py`, `test_baseline_diff.py`, `test_runtime_fixture_preflight.py`.

**Critical path, Phases 3 and 4** (proposed). Phase 3 is three tracks that share no function, so they run in parallel, each in its own checkout: A, PM-11a → PM-11b (→ PM-11c); B, PM-12a → PM-12b; C, PM-13a → PM-13b. They join at PM-13t → R3. The finish is bounded by track B, which also waits for Phase 2. Phase 4 is one chain: PM-14a → PM-14b → PM-14c → R4, with PM-14t beside PM-14c once PM-14b is in.

The whole inventory runs in seconds, so by the run contract's cost exception the manager runs all of it at every load-bearing moment.

**Recommended manager route, Phases 3 and 4: X.** The manager's own work is judging whether a refactor of a gate kept every verdict, and merging three tracks that register checks in one tuple; that is coupled reasoning, not deep design. The T rows and R3 and R4 go to a named high-judgment sub-agent, which the Phase 1 run showed an N manager cannot stand in for.

**Checks a worker can run.** The worker's attached repository is astrid-dev itself, the scripts are standard library only and need no other repository or network, so no `env/` setup script applies:

```text
python3 -m unittest discover -s scripts -p "test_*.py"
python3 scripts/check_docs.py
python3 scripts/export_public_vision.py --output /tmp/vision.json
```

**Two standing proofs** used by most rows:

- **Same verdicts:** PM-1 first commits a set of small fixture trees under `scripts/fixtures/` (one clean, one per broken case the unit tests cover today as inline strings). On the task's base and its candidate, the old commands and `astrid_dev.py check` print the same errors for the real tree and for each fixture tree. In Phase 1 the old `check_*.py` modules stay importable as thin shims, so no existing test or trusted-workflow import changes.
- **Same feed:** `export_public_vision.py --revision <one fixed SHA> --output` gives byte-identical JSON on base and candidate.
