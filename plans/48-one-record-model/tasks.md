## Phase 2 cut-over order

One PR moves the facts and every reader at once, so there is never a commit on `main` where the catalog is generated and a gate still reads it. Everything before step 5 can be repeated; step 6 is the owner's.

**Before the day**

1. **Gates.** Release 12 is published; R2 has no open blocking finding; the owner has said go for C-1; the owner confirms `CLAIM_AUTO_MERGE_ENABLED` is unset (the host cannot read repository variables). If PM-8 is to ride along (D16), O-1 is done and PM-8h has passed; otherwise `task/48-pm8` is not merged into the integration branch.
2. **Notice.** Through the owner, every manager with a live run (Plans 20, 29, 32 and 40-machine-lifetime-controls at planning time) is told the time and three things: change `**Status:**`, `**Owner:**`, `**Estimate:**` and `**Waiting on:**` in your own `plan.md` from then on; do not edit `plans/index.md`; `python3 scripts/check_docs.py` becomes `python3 scripts/astrid_dev.py check`.

**The cut-over**

3. **Bring `main` in.** Merge `origin/main` into the integration branch and note its SHA. The only expected conflict is `plans/index.md`; take either side, because step 4 rewrites it.
4. **Migrate again from that SHA.** Take the script from the commit before PM-6d deleted it (`git show <sha>:scripts/migrate_catalog.py`, saved outside the repository) and run it with `--root . --from-ref <main SHA> --write`, then `astrid_dev.py sync`, then the script's `--verify`. This copies every status, owner, estimate and row order that changed on `main` since PM-6d, and picks up any pack added there. Then run the whole inventory, `astrid_dev.py check` and the same-feed comparison against that `main` SHA (identical but for the renumbered project's `id` and `githubUrl`). Commit and push. The script is never committed again.
5. **Open the PR** to `main` and let both required checks run. The completion gate sees a base from before the cut-over and must report no move to `done` (PM-6a pins this). If `main`'s `plans/index.md`, or the header of any `plan.md`, changes before the merge, GitHub shows a conflict or the host sees it with `git diff --quiet <main SHA> origin/main -- plans/`: go back to step 3.
6. **Merge on the owner's go,** with a merge commit, so one revert undoes it.

**Straight after**

7. **`main` is green** on the merge commit, and the feed on `vision-published` for that commit differs from the one before only in the source revision and the renumbered project.
8. **Sweep the open PRs.** List every open PR whose files include `plans/index.md` (REST: the open pulls, then each one's files). Each must show a merge conflict, because the cut-over changed every row line of the table (D15); comment on each with the notice's three lines. One that still shows as mergeable is taken to the owner at once, since its checks ran on the old code.
9. **The trusted workflows now run the new scripts.** Read the first `review-intake` run after the merge: it must print a routing result, not `Review intake failed`.
10. **Tell the managers it is done,** and tick C-1 with the evidence.

**What a stale PR meets afterwards.** One opened or updated after the cut-over runs the new checks on its merge with `main`: a hand-edited row fails `generated-views`, naming the plan file to edit. One that was open and green before the cut-over conflicts in git and cannot merge. One that changes nothing in the catalog is unaffected.

**Undoing it.** Revert the merge commit by PR. Status edits made in `plan.md` files after the cut-over are then copied back into the table by hand from `git log -p -- plans/*/plan.md`; after a day of them, fixing forward is cheaper than reverting.

**If the refresh job follows separately (C-2).** Between C-1 and C-2 a PR that changes a plan's fields must also run `sync` and commit `plans/index.md`, and two PRs that add plans conflict on the count line in the root README, as two scope PRs do today. C-2 removes both. After it merges, the host watches the job's first commit and the owner sees it; if the job misbehaves, the owner unsets `GENERATED_REFRESH_APP_ID`, which stops it, and authors run `sync` again until it is fixed.
