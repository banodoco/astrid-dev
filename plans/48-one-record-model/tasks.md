| PM-6m **The migration script, proven dry, then applied.** `scripts/migrate_catalog.py --root <dir> --from-ref <rev> [--suffix .fixture] [--write] [--verify]`. It reads the hand-written table from `git show <rev>:plans/index.md` (or, with `--suffix`, from the file `<dir>/plans/index.md<suffix>`, reading and writing every file under that suffix) with `check_docs.catalog_rows`. For each row it writes a block of six lines into that row's `plan.md` at lines 3 to 14, directly under the title (line 1 is always a `# ` title and line 2 is blank: checked in every pack), each line followed by a blank one, in the order `**Project:**`, `**Goal:**`, `**Status:**`, `**Owner:**`, `**Estimate:**`, `**Waiting on:**`, with the row's cell text; relative links in a cell gain one `../` (one cell has one today: Plan 40's `Waiting on`). It writes `plans/priority.md` (a two-sentence preamble, then `## Order` and one `- <folder>` line per row in row order) and `plans/catalog-notes.md` (the catalog's `## Delivery context` section, word for word). It changes no other line of any file. Without `--write` it prints each file and its planned lines and writes nothing. The block is defined by position: when lines 3 to 14 already hold the six labels in order, `--write` replaces their values from the table and reports no change when they match; this is how the cut-over copies the catalog's latest values. ## Phase 2 cut-over order

One PR moves the facts and every reader at once, so there is never a commit on `main` where the catalog is generated and a gate still reads it. It does not carry the renumbering (PM-9) or the refresh job (PM-8): both follow as their own PRs, so the cut-over's migration finds every row's folder and its feed is byte-identical. Everything before step 5 can be repeated; step 6 is the owner's.

**Before the day**

1. **Gates.** Release 12 is published; R2 has no open blocking finding; the owner has said go for C-1; the owner confirms `CLAIM_AUTO_MERGE_ENABLED` is unset (the host cannot read repository variables).
2. **Notice.** Through the owner, every manager with a live run (Plans 20, 29, 32 and 40-machine-lifetime-controls at planning time) is told the time and four things: change `**Status:**`, `**Owner:**`, `**Estimate:**` and `**Waiting on:**` in your own `plan.md` from then on; then run `python3 scripts/astrid_dev.py sync` and commit `plans/index.md` with it, until told the bot does that; never edit `plans/index.md` by hand; `python3 scripts/check_docs.py` becomes `python3 scripts/astrid_dev.py check`.

**The cut-over**

3. **Bring `main` in.** Merge `origin/main` into the integration branch and note its SHA. A conflict in `plans/index.md` is expected: take either side, because step 4 rewrites it. A conflict in `README.md`'s summary region or `vision/README.md` is settled by `sync` in step 4. A conflict in a doc or skill that PM-10t reworded is settled by hand, keeping `main`'s new content and PM-10t's wording, and shown in the PR.
4. **Migrate again from that SHA.** Take the script from the commit before PM-6b deleted it (`git show <sha>:scripts/migrate_catalog.py`, saved outside the repository) and run it with `--root . --from-ref <main SHA> --write`, then `astrid_dev.py sync`, then the script's `--verify`. This copies every status, owner, estimate and row order that changed on `main` since PM-6m, and picks up any pack added there. Then run the whole inventory, `astrid_dev.py check` and the same-feed comparison against that `main` SHA, which must be byte-identical. If `test_golden.py` then differs, and only in lines of PM-6a's eight fixtures, regenerate `golden.txt` and say so in the PR; any other difference stops the cut-over. Commit and push. The script is never committed again.
5. **Open the PR** to `main` and let both required checks run. The completion gate sees a base from before the cut-over and must report no move to `done` (PM-6a pins this). If `main`'s `plans/index.md` changes before the merge, GitHub shows a conflict, and the host also checks with `git diff --quiet <main SHA> origin/main -- plans/`: go back to step 3.
6. **Merge on the owner's go,** with a merge commit, so one revert undoes it.

**Straight after**

7. **`main` is green** on the merge commit, and the feed on `vision-published` for that commit differs from the one before only in the source revision.
8. **Sweep the open PRs.** List every open PR whose files include `plans/index.md` (REST: the open pulls, then each one's files). One that edits, adds or removes a table row must show a merge conflict, because the cut-over changed every row line (D15); comment on each with the notice's four lines. One that still shows as mergeable is taken to the owner at once, since its checks ran on the old code. The column move protects rows only: a PR that edits the catalog's prose merges clean, which is why the sweep reads every such PR and does not trust the conflict alone.
9. **The trusted workflows now run the new scripts.** Read the first `review-intake` run after the merge: it must print a routing result, not `Review intake failed`.
10. **Tell the managers it is done,** and tick C-1 with the evidence.

**What a stale PR meets afterwards.** One opened or updated after the cut-over runs the new checks on its merge with `main`: a hand-edited row fails `generated-views`, naming the plan file to edit. One that was open and green before the cut-over and touches a row conflicts in git and cannot merge. One that changes nothing in the catalog is unaffected.

**Undoing it.** Revert the merge commit by PR. Status edits made in `plan.md` files after the cut-over are then copied back into the table by hand from `git log -p -- plans/*/plan.md`; after a day of them, fixing forward is cheaper than reverting.

**Between C-1 and C-2.** A PR that changes a plan's fields must also carry the regenerated `plans/index.md`, and two PRs that add plans conflict on the count line in the root README, as two scope PRs do today. No claim can be auto-merged in that window, because a claim may change only one file; the claim bot is off anyway. C-2 removes all three. After C-2 merges, the host watches the job's first commit and the owner sees it; if the job misbehaves, the owner unsets `GENERATED_REFRESH_APP_ID`, which stops it, and authors run `sync` again until it is fixed.
