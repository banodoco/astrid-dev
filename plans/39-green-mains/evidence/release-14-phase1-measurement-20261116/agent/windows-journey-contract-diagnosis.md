# Windows task-host journey: CLI contract diagnosis

## Finding

**Cause: stale journey harness entrypoint for pack-management commands, not evidence of a missing product `packs` command.** The failure is reproducible in both shell variants at the same step, but the test driver invokes `python -I -m astrid packs list --json`. In the installed Agent package selected by this run, `python -m astrid` enters the product gateway, whose top-level command table does not include the management verb `packs`; the gateway therefore intentionally returns `unknown command 'packs'` (exit 2). The installed `astrid` console entrypoint separately routes `packs` to the pack-management CLI. The harness is selecting the wrong public entrypoint for its pack list/add setup calls.

This diagnosis is read-only. It does not claim the journey passes or that the installed-profile SDK, host startup, settlement, or output assertions succeeded; the two jobs stop before the SDK invocation. It does not clear Plan38 or Plan55 ownership. No tests were run and no product, workflow, or remote state changed.

## Why the command fails, and the supported route

At the installed Agent pin, `astrid/__main__.py` imports `astrid.core.gateway.main`. The gateway accepts product/operational family routes; its dispatch table has no `packs` management route, and it raises the exact unknown-command error for a name outside that table ([gateway dispatch](https://github.com/banodoco/astrid-agent/blob/9814193a73f606719e81883a8be197d27dd361d4/astrid/core/gateway/dispatch.py#L19-L29), [table](https://github.com/banodoco/astrid-agent/blob/9814193a73f606719e81883a8be197d27dd361d4/astrid/core/gateway/dispatch.py#L661-L675)). This matches the log's `valid options` list.

The same pinned Agent declares the installed `astrid` console script as `astrid.console:main` ([pyproject entry points](https://github.com/banodoco/astrid-agent/blob/9814193a73f606719e81883a8be197d27dd361d4/pyproject.toml#L62-L69)). `astrid.console.main` explicitly dispatches `packs` to `astrid.core.pack.cli.main` ([console](https://github.com/banodoco/astrid-agent/blob/9814193a73f606719e81883a8be197d27dd361d4/astrid/console.py#L7-L30)); the pinned parser explicitly defines `list --json` ([list parser](https://github.com/banodoco/astrid-agent/blob/9814193a73f606719e81883a8be197d27dd361d4/astrid/core/pack/cli_parser.py#L136-L163)) and the `add` subcommand ([add parser](https://github.com/banodoco/astrid-agent/blob/9814193a73f606719e81883a8be197d27dd361d4/astrid/core/pack/cli_manage.py#L401-L450)). The supported replacement candidate for the two setup operations is therefore the actual installed `astrid` console executable (on Windows, the venv's `Scripts/astrid.exe`) for `packs list --json` and `packs add ...`, with the installed version's environment. It is not `astrid-tools`: the App's vendored command surface names that separate binary, and its declared families omit `packs` ([App CLI surface](https://github.com/banodoco/astrid-app/blob/de7dd1e668aa6dcf3cbce013c701fa7c76615f99/config/astrid-cli-surface/cli-surface.json#L1-L8)).

The driver helper explains the mismatch: `cli(module, ...)` always executes `[installed_python, "-I", "-m", module, ...]`, and `install_journey_packs()` passes module name `astrid` for list/add ([driver helper and caller](https://github.com/banodoco/astrid-agent/blob/fc391dea696ec5799db222799a34f9de6a69659b/scripts/ci_windows_journey.py#L484-L489), [pack install caller](https://github.com/banodoco/astrid-agent/blob/fc391dea696ec5799db222799a34f9de6a69659b/scripts/ci_windows_journey.py#L728-L734)). `python -m astrid` is the gateway route, not the `astrid` console script. The compatibility seam should be narrowed to pack management and use the installed console entrypoint; ordinary product-family SDK commands should keep their existing gateway/SDK calls.

## Assertion boundary and disposition

The failure happens inside `install_journey_packs()` before SDK admission. After pack setup, the driver creates a project, invokes `astrid.omp_invoke`, requires exactly one admitted task reference, follows the task to terminal state, and checks a successful settled task with materialized `sfx`/`sfx_meta` outputs and nonzero SHA-256 digests ([journey settlement assertions](https://github.com/banodoco/astrid-agent/blob/fc391dea696ec5799db222799a34f9de6a69659b/scripts/ci_journey.py#L2409-L2476)). The pack-management entrypoint change described above does not alter those SDK, host, task-settlement, or output assertions. The saved failures do not execute them, so equivalence of the end-to-end journey remains unverified until a subsequent properly sourced run.

**Disposition:** stale harness invocation is established for this `packs` error; the product pack-management command exists at the installed console entrypoint. A narrow harness correction is supported by the pinned primary sources. Keep the full journey red/unresolved until the unchanged SDK/host/settlement assertions actually run and are reviewed. This card makes no judgment that those downstream contracts are outside Plan55, and it does not touch Plan38 or Plan55-owned behavior.
