## How work is proved

Plan 39 runs as Plan 91 does ([releases/16/run.md](../../releases/16/run.md)). Packet sessions have no network and run no hosted test. Each packet posts `READY-PROOF <repo> <PR> <head> <selectors>`, and the orchestrator runs the proof.

1. **The card's check, run by the orchestrator.**
   - **Runtime:** the card's pull request into `release/16/plan-39` runs the full CI, because `ci.yml`'s `pull_request` trigger has no branch filter. A Nightly card's proof is a `nightly.yml` dispatch with the `tests` input that GM-3 adds.
   - **App:** a pull request into a plan branch starts `direct-journey.yml` when it touches `tests/e2e/local/**`, `tests/e2e/support/**` or the three-products config. It also starts `dockerfile-check.yml`, and `public-vision.yml` and `installer-windows.yml` by path. Red on Direct Journey there is the known baseline red. Every other App proof is a dispatch of `e2e.yml`, `lanes.yml` or `test.yml` on the card's branch, with the `tests` input that GM-5 adds.
   - **IDs:** GM-0 writes each card's IDs and focused selectors as `evidence/release-16-<sha>/cards/<task>.tsv`, as Plan 91's AG-0 does, because packets can't measure.
2. **The batch run.** After merging up to five cards, the orchestrator dispatches the full workflows on `release/16/plan-39`, including `nightly.yml`. It compares the results with the sealed baseline using the gate tool (GM-3), which checks three things:
   - every job's conclusion: any non-success is no result, and turns the comparison red;
   - each failure: a regression, a new failing test or a missing test blocks;
   - the ceiling: what passed leaves it.
3. **The baseline is a ratchet only the orchestrator edits.** `ci/runtime-baseline.txt` and `ci/app-baseline.txt` hold one status line per test ID from the sealing runs: the passing inventory and the ceiling of failures. Cards never touch them. After a green batch, the orchestrator moves every ID that passed from FAILED to PASSED and commits the file.

## Triage rules

[Plan 91's triage rules](../91-agent-main-green/tasks.md#triage-rules) apply unchanged: prune before fixing, reproduce first, one kind per cause with evidence, the allowed fix and proof per kind, no other change, prove by ID, and stop at twice the size. Here:
- "D5" in those rules means this plan's [D12](inputs.md#owner-decisions), and "D6" means [D21](inputs.md#owner-decisions) for an Agent bug, or an owner-accepted ceiling entry for any other bug;
- **any deletion,** in any card, goes on GM-P1's list with its citation or covering test, and passes the same proof;
- **the `S` rows** (RT-14, RT-15, RN-4, RN-5, AP-17), and any card that changes what the product accepts or refuses, get the high-judgment per-card check of the [run contract](../../agent/shared/run-contract.md#review-and-promotion-boundaries);
- **dating:** the Runtime's history is squashed to 27 October, and the App's is grafted (whole-tree commits `2dc109b`, `f72e869`). A stale-test card dates the change by its pull request, plan task, issue ruling or brief line, never by `git log` alone ([why](evidence/release-15-measure/app-stale.md));
- **a failure in a file another active plan is changing** goes to that plan first ([green skill](../../agent/shared/workstreams/green.md), 3A step 4): Plan 89 (Runtime timeline commit and history), Plan 77 (App save path), Plan 38 (custody, bootstrap, host spawn), Plan 75 (the effect list).
