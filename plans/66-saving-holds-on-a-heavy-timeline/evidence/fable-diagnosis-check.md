## Missed by the diagnosis

- M1. The outbox also taxes the drain. Start-to-start spacing is 4.95-5.64 s against a ~4.3 s handler; the gap falls 1.39, 1.36, 1.25, 0.95, 0.99, 0.75, 0.74, 0.65, 0.40 s as the queue empties (read from the log). That fits `dispatch()` doing two whole-record read-clone-put passes on a record that shrinks by one intent per commit. About 8 of the 64 s in E2. Batching does not remove this; storing a patch (not three documents) per intent does.
- M2. Outbox rows are never deleted when a session ends. `own()` writes a row on every claim with a fresh random ownerId; only `discardScope` deletes (read). So one empty row per editor load, and rows holding only `accepted` (a whole canonical document + graph) stay for good. `list()` does `getAll()` + deep clone over every row of every realm on each editor start.
- M3. Two draft stores with different keys (outbox: realm-scoped; `timeline-drafts`: timeline id only). This is the root of E4's bar-says-unsaved / badge-says-Saved split, and of a draft from another realm being offered for a timeline that merely shares an id.
- M4. No sub-timing inside the provider. The only nested span is `port_store_accept` (inside provider_commit, 198-468 ms); `durable_reconciliation` is after it. ~3.8 s of each commit is unattributed.
- M5. E1 is the cold first commit (5116 ms); steady state is ~4.1 s. Use 4.1 s as the baseline for any before/after.
- M6. Timing lines carry no timeline id, revision or size, so growth with document or history cannot be read from the log. Within this burst there is no clear growth.
- M7 (unverified, worth one look): `_check_reservations` keeps its history memo on the provider instance (`self._reserved`); the provider is loaded once per Runtime process, so the first commit after every Runtime start rescans the whole history. May be part of E1's extra second.

## Top cause of provider_commit

Not named. Static reading shows no single obvious step, only many whole-document passes per commit in `SP/astrid/sdk/timeline/commit.py:1251` (read): `_load` (deepcopy + `_verify_document`, which serialises the document and digests every revision image), `_hydrate`, `execute`, `validate_final_candidate` (`json.dumps` of the candidate, a fresh `Draft202012Validator` per clip with params at validation.py:643, then timing validation with `compile_authoring_candidate` + deepcopy + `compile_timing`, run again for the baseline when legacy declarations exist), `document_from_bundle`, `_check_readers` (`bundle_from_document` + verify again + projection), `prepared_records`, then `port.accept`. Suspects in my order: timing validation (two compiles of the full bundle), per-clip schema validators, the repeated verify/digest passes. This order is a guess.

Measurement that decides it (not run): wrap `provider.commit` at `SP/runtime_protocol/timeline_commit_execution.py:556` in cProfile on a copy of the stack (or attach `py-spy record --pid <runtime pid>` during one nudge; needs sudo on macOS) and read cumulative time per function. Cheaper permanent form: add `timing.stage(...)` spans around load, hydrate, execute, validate (schema / timing separately), document_from_bundle, check_readers.
