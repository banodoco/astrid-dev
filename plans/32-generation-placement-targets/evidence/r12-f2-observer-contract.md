# R12-F2 retained observer selection: design for review

**UNAPPROVED — proposal only.** No implementation, pin change, installed-pair proof, or security acceptance is implied. Base astrid-dev `d92ea08`; examined Agent `dd6a14838b46cc20fddbd5e2203d72ee260fbd3d` and Runtime `76bb47e081b439e778c90273307fe547221c8244`. The [failure and reproduction](release12-host-attach/README.md) and [R12-F2](../tasks.md) remain authoritative on status. These handoffs are unaccepted; the Agent still calls its general launcher, and Runtime's leaf is not yet independently bound to an owner selection.

## Authority and lifetime

Propose a **new** owner-to-Agent contract; no existing discovery field, health response, executable self-report, alongside hash, or host-launch verifier is this authority. The trusted origin is the running neutral Runtime bootstrap and its explicit trusted local configuration, including its selected data root, under the existing trusted-local model. Before starting an owner, this bootstrap resolves and validates a specific observer installation from that configuration. A new non-secret selection handoff must carry it through both `LocalRuntimeBoundary.start` daemon arguments and the foreground `RuntimeDaemon` construction path; neither existing path currently carries this contract. The owner validates and retains the selection in memory before publication, unchanged for its lifetime. Neither discovery, `runtime_environment`, nor a probe of a candidate executable can select it. The existing private host-specific verifier remains private and unchanged in scope. Implement a separate observer-specific selection validator; do not export its host profile or turn it into an execution service.

Concrete handoff proposed: the owner atomically publishes `runtime/observer-selection-v1.json` under that selected data root, after it has acquired its instance lock and has a live endpoint and identity. Agent derives this fixed path only from the same locally configured data root used for the scoped worker connection, never from discovery or a remote response. Agent validates the trusted parent chain from the explicitly configured root to the support directory using directory handles, rejecting symlinks or unsafe ownership or write access; it opens the fixed record relative to that validated directory without following symlinks, then checks the opened descriptor is a regular file with expected ownership and mode before reading. On POSIX the owner creates the support directory private and record mode 0600; Agent requires the expected local user owner and no group/other write permissions on the record and support directory, and checks the remaining parent chain against a defined trusted-owner/no-untrusted-write policy. Path and descriptor checks must close replacement races within the stated model. On Windows require equivalent current-user ownership and a DACL that excludes other principals' write access, or refuse until a tested equivalent exists. Existing `runtime/discovery.json`, `runtime/instance.lock`, and `runtime/source-profiles/astrid.json` are not this record; no claim is made that their existing checks provide this handoff. File permissions prevent accidental or other-user substitution within their OS guarantees; same-user writers, compromised bootstrap, interpreter, installation, and administrator are trusted, not defended against. No signature or digest supplied by the same record independently establishes trust.

Record v1 is bounded to 16 KiB UTF-8 JSON, duplicate keys and unknown keys rejected: `version` = 1; `operation` = `pack-host-observe-v1`; `selection_id` = freshly generated 128-bit random hex for this owner start; `endpoint`, `instance_id`, `session_id`, positive integer `epoch`; `data_root` (canonical absolute root); `mode` (`installed` or `source`); absolute `interpreter` invocation path; and `import_roots` (empty for installed, exactly the owner's validated Runtime source root and any explicitly required validated dependency roots for source, with an implementation-set count and byte cap). Strings are nonempty, bounded to 4096 bytes, no NUL. The record contains neither credentials nor arbitrary command, flags, module, environment, working directory or executable supplied by discovery. Bootstrap and owner validate selection against their trusted configuration, retain the absolute interpreter invocation path without resolving away its venv symlink, separately validate its symlink target chain and selected installation under trusted local configuration, and reject unsupported layouts; Agent checks syntax, root, permissions, supported mode, and exact identity, but does not invent a selection. The specific platform path validation and permitted source dependency roots must be reviewed with the implementation.

While holding the owner instance lock, publish with a same-directory private temporary file, flush and atomic replace; serialize publication and removal under that lock; an old, partial, absent, malformed or inaccessible record causes refusal. On shutdown remove only the record still bearing this owner's selection ID. A crash may leave a record: it confers no fresh identity by itself. No in-place refresh or selection mutation is allowed during an owner lifetime. A restart, upgrade, relocation, or selection change creates a new owner and selection ID; a fresh worker handshake and a fresh record read are required. Never silently fall back to PATH or an earlier selection. Agent reads the record after worker authentication, retains its exact bytes/identity for the attempt, rereads it before spawn and after observation and refuses on change. It matches endpoint, instance, session and epoch from the worker-authenticated connection and health before and after the owner observation; Runtime also checks discovery and health around its fixed executor query. Observed identity mismatch, restart, endpoint reuse, stale record, or uncertain freshness refuses the attempt, including a detected rollover during observation. These checks establish consistency at the acceptance checks only; subsequent actions must continue to fence on the same instance, session and epoch and refuse on change. They cannot exclude a restart immediately after the final check. The independent origin authorizes selected code; health and identity checks are not executable authorization.

## Fixed operation and process boundary

Agent preserves the scoped worker-first handshake, existing readiness, source/dependency identity and custody comparisons. Only after it succeeds, Agent spawns the retained observer in a separately owned process boundary. Installed mode runs the selected absolute interpreter in isolated mode with fixed `-m astrid_runtime.pack_host_observer`; source mode uses isolated mode and a fixed, shipped bootstrap that inserts only the retained absolute import roots and invokes that same fixed module, ignoring ambient `PYTHONPATH`, current directory and user site. Python `-I` does not suppress selected-environment `.pth` processing or `sitecustomize`; these remain part of the trusted local selected installation. A tested `-S` design may replace this assumption only if imports and all supported layouts are proved. The bootstrap itself is selected and validated as part of the owner's installation; its exact packaging and dependency-root inventory are implementation gates. Construct argv internally with only fixed operation, canonical data root and the bound identity values; reject extra arguments and invalid lengths. Use a minimal allowlisted environment, no shell, no inherited credentials or unrelated descriptors, fixed safe working directory. An explicit configured wrapper may be run only by the trusted neutral bootstrap as configured, to establish its own trusted launch context, never probed as authority or run as the observer; the bootstrap must select a validated fixed leaf independently. Configured command/PATH selection is resolved by the trusted bootstrap at startup, never by Agent at observation time. Installed, source/PYTHONPATH, and separate neutral launcher/daemon venv layouts remain supported when the owner can validate and retain their explicit interpreter and import roots. `runtime_environment` describes the daemon environment and is not automatically the neutral launcher or observer interpreter. If the owner cannot establish a safe fixed leaf for a configured wrapper or layout, refuse with an actionable unsupported-selection result; do not execute a wrapper as observer.

Observer acquires the Runtime owner credential only after validating the trusted parent chain and opening the credential without following symlinks, then checking the opened descriptor is a regular file with expected ownership and private permissions before reading. This descriptor-based acquisition is new implementation and proof, not a property of existing helpers: the current POSIX `read_private_file` uses plain `Path.read_bytes`. Agent does not read or transfer that credential; it is never passed in argv, environment, logs, or response. This is a data-flow constraint, not OS role isolation against another process running as the same user. It performs only GET health and owner-only GET for `astrid-pack-host` on the validated loopback endpoint, with proxy and redirects disabled, bounded connect/read/deadline and response bytes. Worker/non-owner access to that owner-only operation remains denied. No general command, arbitrary URL, HTTP method, executor ID, import root or operation is accepted from Agent or discovery. The owner bearer authenticates the caller to Runtime; loopback and matching health identity do not independently authenticate the server. This proposal trusts the local listener and endpoint within the trusted-local model; a local impersonator able to bind or redirect the endpoint is outside that model, and health checks alone cannot prevent bearer disclosure to it. If that threat is in scope, authenticated server identity and credential protection are a design gate before implementation.

Use one length-delimited UTF-8 JSON response on a private pipe, maximum 64 KiB including framing, one frame and EOF, with bounded stderr discarded. Success schema is exactly `version`, `selection_id`, `instance_id`, `session_id`, `epoch`, and `observation`; observation is the fixed executor ID, readiness, source epoch/digest, dependency digest and bounded ready-capability indication needed by existing Agent checks. Validate types, size, allowed keys and identity; reject duplicate keys, malformed/trailing frames, partial output, and error output. Before emitting, observer rejects serialization containing the actual owner credential; the closed schema limits other output. Errors returned to Agent are fixed categories without remote bodies or secrets; stderr is discarded. Observer PID fields are diagnostic only, never signaling authority. A Python audit hook is defense in depth and cannot establish trusted imports or prove absence of descendants.

Agent creates and retains observer-only custody using the existing `popen_owned_process` and `ProcessCustody` machinery, incarnation-bound process handles and platform primitives, including Windows Job Objects and the Darwin primitives where supported. The selected trusted observer must not intentionally create descendants; the audit hook is only defense in depth. Custody must cover the observer and known descendants, including a descendant retaining a pipe; never infer signal authority from reported PIDs. At deadline, invalid/oversize output or cancellation, terminate only processes established as belonging to this observer custody, reap what can be reaped and check known descendants and retained handles within a separate bounded cleanup deadline. On observable escape, incomplete containment, termination, reaping, or other cleanup uncertainty, retain whatever safe cleanup authority remains, report uncertainty and refuse attachment; never signal the resident host, its PID, or a process named in output. Pipe EOF alone does not prove cleanup. Normal success requires child exit and no known surviving descendants or unresolved custody uncertainty. These primitives do not guarantee containment of an arbitrary hostile descendant that escapes observation; such a hostile process is outside the trusted-local model. Unsupported custody platforms refuse until their primitives and cleanup behavior are proved.

## Required focused proof before implementation acceptance

Write the tests first and run focused CPU-only selectors on the exact coordinated revisions; no real credentials or provider calls. The matrix is acceptance criteria, not evidence that these tests already pass.

| Area | Required cases and observable result |
| --- | --- |
| Authority | Owner-selected A succeeds; discovery advertises decoy B, PATH/config changes after startup, self-hash of B, arbitrary argv/module/import roots, replaced/invalid/unreadable/symlink record, wrong owner or writable permissions all refuse or leave retained A selected. Same-user hostile mutation is outside the model. |
| Lifetime and identity | Fresh start, restart, owner death with stale file, same endpoint/new instance, foreign data root and health/discovery mismatch: stale or mixed identities and record changes observable at the specified checks refuse. Inject session or epoch rollover and record replacement at each named checkpoint: after worker authentication and record read, before spawn, around the owner query and health checks, and after observation at record reread. A new owner requires a new handshake and selection. |
| Authorization | Real local Runtime with synthetic credentials: scoped worker handshake succeeds, worker and other non-owner executor observation remain denied, owner leaf alone observes fixed executor, credentials never reach Agent output, environment, argv or logs; no scope changes. |
| Operation and transport | Reject extra operations, keys, arguments, paths and methods, redirects and proxies; oversized/slow success or HTTP error, malformed JSON, duplicate keys, extra frames, invalid field types, late responses and unavailable owner fail within bounds without leaking response bodies. |
| Layout | Configured and PATH-resolved bootstrap; installed wheel; source with explicitly selected roots; different neutral launcher and daemon venvs; a venv interpreter invoked via its symlink with the target chain validated separately; explicit wrapper bootstrap; and selected `.pth`/`sitecustomize` behavior, plus poisoned ambient path, cwd, user site and environment. Verify exact selected interpreter/import roots, no implicit fallback, and clear refusal where validation cannot be established. Exercise supported POSIX and Windows permissions and launch semantics. |
| Custody and refusal | Normal observer, timeout, malformed/oversized output, child holding stdout, known descendants, an observable process-group escape, cancellation, failed assignment/kill/reap or descendant check and injected cleanup uncertainty. Verify no known survivors and no unresolved custody uncertainty on success; all uncertain cases refuse, return promptly and never signal or retire the resident. |
| Integration | Exact installed Agent/Runtime pair exercises worker-first attach, matching readiness and custody, no credentials transferred, and owner unavailable/foreign/rollover refusal leaving resident untouched. Independent final review and coordinated Runtime pin precede diagnostic re-proof. |

## Decisions still required

The trusted owner bootstrap must actually be able to convey and retain the independently selected observer installation through its startup lifecycle; the current private, host-specific selection does not do so. Confirm the source bootstrap packaging and exact root inventory, OS-specific atomic publication/path checks, platform custody availability, observable escape behavior and cleanup primitives, timeout/cleanup budgets, and whether every currently supported configured wrapper can be mapped to a validated leaf. Unsupported platforms or layouts refuse until implemented and proved, so compatibility is an explicit release gate rather than an accepted restriction. Confirm the observer credential data flow and trusted same-user boundary; if local listener impersonation or same-user hostile writers are in scope, require a separately reviewed stronger design. A design review must resolve these assumptions before implementation or pin changes.
