# R12-F2 retained observer selection: design for review

**UNAPPROVED — proposal only.** No implementation, pin change, installed-pair proof, or security acceptance is implied. Base astrid-dev `d92ea08`; examined Agent `dd6a14838b46cc20fddbd5e2203d72ee260fbd3d` and Runtime `76bb47e081b439e778c90273307fe547221c8244`. The [failure and reproduction](release12-host-attach/README.md) and [R12-F2](../tasks.md) remain authoritative on status. These handoffs are unaccepted; the Agent still calls its general launcher, and Runtime's leaf is not yet independently bound to an owner selection.

## Authority and lifetime

Propose a **new** owner-to-Agent contract; no existing discovery field, health response, executable self-report, alongside hash, or host-launch verifier is this authority. The trusted origin is the user's existing trusted local Runtime bootstrap and its explicitly selected data root, under the existing trusted-local model. The bootstrap resolves and validates a specific observer installation from the owner configuration before starting the owner, passes that selection to the owner over its already controlled startup channel, and the owner retains it in memory unchanged for its lifetime. The existing private host-specific verifier remains private and unchanged in scope. Implement a separate observer-specific selection validator; do not export its host profile or turn it into an execution service.

Concrete handoff proposed: the owner atomically publishes `runtime/observer-selection-v1.json` under that selected data root, after it has acquired its instance lock and has a live endpoint and identity. Agent derives this fixed path only from the same locally configured data root used for the scoped worker connection, never from discovery or a remote response. Agent opens it without following symlinks, validates a regular file and parent path in the local support directory, and on POSIX requires the expected local user owner and no group/other write permissions on the record and support directory; the owner creates the directory private and the record mode 0600. On Windows require equivalent current-user ownership and a DACL that excludes other principals' write access, or refuse until a tested equivalent exists. Existing `runtime/discovery.json`, `runtime/instance.lock`, and `runtime/source-profiles/astrid.json` are not this record; no claim is made that their existing checks provide this handoff. File permissions prevent accidental or other-user substitution within their OS guarantees; same-user writers, compromised bootstrap, interpreter, installation, and administrator are trusted, not defended against. No signature or digest supplied by the same record independently establishes trust.

Record v1 is bounded to 16 KiB UTF-8 JSON, duplicate keys and unknown keys rejected: `version` = 1; `operation` = `pack-host-observe-v1`; `selection_id` = freshly generated 128-bit random hex for this owner start; `endpoint`, `instance_id`, `session_id`, positive integer `epoch`; `data_root` (canonical absolute root); `mode` (`installed` or `source`); canonical absolute `interpreter`; and `import_roots` (empty for installed, exactly the owner's validated Runtime source root and any explicitly required validated dependency roots for source, with an implementation-set count and byte cap). Strings are nonempty, bounded to 4096 bytes, no NUL. The record contains neither credentials nor arbitrary command, flags, module, environment, working directory or executable supplied by discovery. Bootstrap and owner validate selection against their trusted configuration, resolve paths once, and reject unsupported layouts; Agent checks syntax, root, permissions, supported mode, and exact identity, but does not invent a selection. The specific platform path validation and permitted source dependency roots must be reviewed with the implementation.

Publish with a same-directory private temporary file, flush and atomic replace; an old, partial, absent, malformed or inaccessible record causes refusal. On shutdown remove only the record still bearing this owner's selection ID. A crash may leave a record: it confers no fresh identity by itself. No in-place refresh or selection mutation is allowed during an owner lifetime. A restart, upgrade, relocation, or selection change creates a new owner and selection ID; a fresh worker handshake and a fresh record read are required. Never silently fall back to PATH or an earlier selection. Agent reads the record after worker authentication, retains its exact bytes/identity for the attempt, rereads it before spawn and after observation and refuses on change. It matches endpoint, instance, session and epoch from the worker-authenticated connection and health before and after the owner observation; Runtime also checks discovery and health around its fixed executor query. Identity mismatch, restart, endpoint reuse, stale record, or uncertain freshness refuses the attempt, including a result racing rollover. The independent origin authorizes the selected code; live identity checks bind that authority to this particular owner and are not executable authorization.

## Fixed operation and process boundary

Agent preserves the scoped worker-first handshake, existing readiness, source/dependency identity and custody comparisons. Only after it succeeds, Agent spawns the retained observer in a separately owned process boundary. Installed mode runs the selected absolute interpreter in isolated mode with fixed `-m astrid_runtime.pack_host_observer`; source mode uses isolated mode and a fixed, shipped bootstrap that inserts only the retained absolute import roots and invokes that same fixed module, ignoring ambient `PYTHONPATH`, current directory, user site, and startup hooks. The bootstrap itself is selected and validated as part of the owner's installation; its exact packaging and dependency-root inventory are implementation gates. Construct argv internally with only fixed operation, canonical data root and the bound identity values; reject extra arguments and invalid lengths. Use a minimal allowlisted environment, no shell, no inherited credentials or unrelated descriptors, fixed safe working directory. Configured command/PATH selection is resolved by the trusted owner at startup, never by Agent at observation time. Installed, source/PYTHONPATH, and separate neutral launcher/daemon venv layouts remain supported when the owner can validate and retain their explicit interpreter and import roots. `runtime_environment` describes the daemon environment and is not automatically the neutral launcher or observer interpreter. If the owner cannot establish a safe fixed leaf for a configured wrapper or layout, refuse with an actionable unsupported-selection result; do not execute a wrapper as observer.

Observer alone obtains the Runtime owner credential from the existing validated local Runtime support mechanism; no token, credential file contents, or owner capability is sent to Agent, argv, environment, logs, or response. It performs only GET health and owner-only GET for `astrid-pack-host` on the validated loopback endpoint, with proxy and redirects disabled, bounded connect/read/deadline and response bytes. Worker/non-owner access to that owner-only operation remains denied. No general command, arbitrary URL, HTTP method, executor ID, import root or operation is accepted from Agent or discovery.

Use one length-delimited UTF-8 JSON response on a private pipe, maximum 64 KiB including framing, one frame and EOF, with bounded stderr discarded. Success schema is exactly `version`, `selection_id`, `instance_id`, `session_id`, `epoch`, and `observation`; observation is the fixed executor ID, readiness, source epoch/digest, dependency digest and bounded ready-capability indication needed by existing Agent checks. Validate types, size, allowed keys and identity; reject duplicate keys, malformed/trailing frames, partial output, error output, and token-shaped leakage. Errors returned to Agent are fixed categories without remote bodies or secrets. Observer PID fields are diagnostic only, never signaling authority. A Python audit hook is defense in depth and cannot establish trusted imports or prove absence of descendants.

Agent must own the entire observer-only process tree from creation, not infer custody from reported PIDs or process groups alone. Use a retained OS containment primitive with race-free assignment before observer code runs (for example, a Windows Job Object with kill-on-close, or a Linux cgroup with an appropriate retained handle); support other platforms only with an equivalently demonstrated mechanism. A process group alone is insufficient if descendants can escape it. At deadline, invalid/oversize output, or cancellation, terminate only that retained observer boundary, reap the child and prove the boundary empty within a second bounded cleanup deadline. If containment, termination, reaping or emptiness is uncertain, report cleanup uncertainty and refuse attachment; never signal the resident host, its PID, or a process named in output. Do not treat pipe EOF alone as proof of descendant cleanup. A normal result is usable only after successful process exit and proved empty custody. If no appropriate containment primitive is available, refuse rather than weaken custody.

## Required focused proof before implementation acceptance

Write the tests first and run focused CPU-only selectors on the exact coordinated revisions; no real credentials or provider calls. The matrix is acceptance criteria, not evidence that these tests already pass.

| Area | Required cases and observable result |
| --- | --- |
| Authority | Owner-selected A succeeds; discovery advertises decoy B, PATH/config changes after startup, self-hash of B, arbitrary argv/module/import roots, replaced/invalid/unreadable/symlink record, wrong owner or writable permissions all refuse or leave retained A selected. Same-user hostile mutation is outside the model. |
| Lifetime and identity | Fresh start, restart, owner death with stale file, same endpoint/new instance, session or epoch rollover, record replacement before spawn/during query/after output, foreign data root and health/discovery mismatch: every stale or mixed observation refuses. New owner requires a new handshake and selection. |
| Authorization | Real local Runtime with synthetic credentials: scoped worker handshake succeeds, worker and other non-owner executor observation remain denied, owner leaf alone observes fixed executor, credentials never reach Agent output, environment, argv or logs; no scope changes. |
| Operation and transport | Reject extra operations, keys, arguments, paths and methods, redirects and proxies; oversized/slow success or HTTP error, malformed JSON, duplicate keys, extra frames, invalid field types, late responses and unavailable owner fail within bounds without leaking response bodies. |
| Layout | Configured and PATH-resolved bootstrap; installed wheel; source with explicitly selected roots; different neutral launcher and daemon venvs; poisoned ambient path, cwd, user site and environment. Verify exact selected interpreter/import roots, no implicit fallback, and clear refusal where validation cannot be established. Exercise supported POSIX and Windows permissions and launch semantics. |
| Custody and refusal | Normal observer, timeout, malformed/oversized output, child holding stdout, child spawning descendant and escaping process group, cancellation, failed assignment/kill/reap/empty check and injected cleanup uncertainty. Verify containment empty on success; all uncertain cases refuse, return promptly and never signal or retire the resident. |
| Integration | Exact installed Agent/Runtime pair exercises worker-first attach, matching readiness and custody, no credentials transferred, and owner unavailable/foreign/rollover refusal leaving resident untouched. Independent final review and coordinated Runtime pin precede diagnostic re-proof. |

## Decisions still required

The trusted owner bootstrap must actually be able to convey and retain the independently selected observer installation through its startup lifecycle; the current private, host-specific selection does not do so. Confirm the source bootstrap packaging and exact root inventory, OS-specific atomic publication/path checks, safe process containment availability and privilege requirements, timeout/cleanup budgets, and whether every currently supported configured wrapper can be mapped to a validated leaf. Unsupported platforms or layouts refuse until implemented and proved, so compatibility is an explicit release gate rather than an accepted restriction. Confirm that the owner credential stays accessible only to the observer under existing local deployment permissions. A design review must resolve these assumptions before implementation or pin changes.
