## 2. Outcome and boundary

Keep one authoritative owner **per state item, identity, and lifecycle**, not one physical store for every byte. User/project choices, committed work and reusable trust must survive device/profile change and restart; bootstrap and machine inventory must work before Runtime exists; unsent work and unknown-outcome operations must remain recoverable even when Runtime is down. A file containing the only copy of an unacknowledged operation is not a duplicate preference. Conversely a local cache cannot silently defeat the authoritative version or resurrect a revoked decision.

The existing Runtime app-state, project documents/selections and App settings store are the reuse path; no new universal settings service, no second project/selection authority, no copying timeline history into generic documents. Distinguish:
1. Durable user choice: Runtime actor-scoped, versioned; user/project-specific choice scoped explicitly, not inadvertently made shared project state.
2. Durable project work: existing typed project/shot/timeline authority; noncanonical project document only where appropriate; actual accepted timeline writes through P63/P04, not side documents.
3. Cached read projection, boot and device-only state: local, scoped, disposable only when it contains no unsent intent. A UI URL identifies the open project, not a mutable global default.
4. Recovery/outbox: durable local pending intent with precise target, base, operation/receipt identity and ownership until settled. Restore/backup does not magically include unsent local work. Never retry a different writer's flight.
5. Machine/bootstrap/inventory: local install/engine receipts, installed pack source/cache, handles, executable/driver state, locks; provenance and actual observation over saved intent. Secrets: protected credential path, not app-state; trust and paid lease/activation records have their own authority rules and lifetimes.

## 4. Critical seam findings / proposed scope amendments

### F1 — Selection and settings convergence is an actual remaining defect class
**Blocking design issue.** App's project-selection fallback reads/writes two durable-looking sources; extension service retains local-primary access; some raw project/browser keys remain. Existing Runtime app-state has version/idempotency and a **16 KiB** maximum ([limit](https://github.com/banodoco/astrid-runtime/blob/686ca695469bda48cd40a70824c4ccef2a137284/runtime_protocol/service.py#L5035-L5035), [App matching cap](https://github.com/banodoco/astrid-app/blob/ebfdaa7920695e2b0f908e75aa104c57613bd69b/src/shared/settings/settingsStore.ts#L54-L54)). The App pending flush has bounded retries and at lines 262–263 leaves an oversized update in browser storage with a console warning. Do not funnel all extension data or project work into one oversized group. Separate small user preferences from large documents/CAS; expose pending/conflict/oversize state to user and agent, retain intent. Existing project documents are versioned and validation guards canonical writes ([document methods](https://github.com/banodoco/astrid-runtime/blob/686ca695469bda48cd40a70824c4ccef2a137284/runtime_protocol/service.py#L5189-L5302)). Test two writers, read-after-write, fresh profile, explicit URL vs selection and actor isolation. Confirm browser/CLI actor mapping instead of assuming same user means same Runtime actor ID.
