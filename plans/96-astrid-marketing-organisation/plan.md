# Astrid Marketing organisation

**Project:** Astrid Marketing organisation

**Goal:** Astrid has a small independent Otto-powered marketing workspace in which people and agents can find ideas, create standard or loop projects, coordinate optional campaigns and improve their work from evidence.

**Status:** queued

**Owner:** Unassigned

**Estimate:** 2–4 engineering days provisional for initial workspace and representative proof; excludes ongoing marketing operation, audience measurement wait and future integrations. Re-estimate at Otto handoff.

**Waiting on:** [Plan 95 — Otto](../95-composable-agentic-workspaces/plan.md) accepted and integrated with minimal Marketing consumer; owner-approved initial direction, visibility, access and independent critique; named manager.

**Start:** [Astrid contributor skill](../../skills/astrid-dev/SKILL.md) and [domain map](../../skills/astrid-dev/references/domains.md). The six fields above define the catalog row. Leave [priority](../priority.md), release membership and run authority unchanged until separately decided.

**Vision role:** Foundational enabler — establishes a simple independently operated workspace for communicating and learning about Astrid; not a new product capability or gap closure.

## Outcome and scope

Keep the first operational workspace small: strategy/vision, projects with tasks, GitHub issues (ideas, observations, questions, problems), optional campaigns, ordinary knowledge documents, skills and roles. It adopts Otto's shared project and standard/loop templates from Plan 97 and stable local project identities (slugs recommended; no requirement for Dev numbers). The end state is not a comprehensive marketing schema or analytics platform.

Proposed initial layout: README.md, workspace manifest/version pin, strategy.md, vision/ if useful, projects/, campaigns/, knowledge/, agent/ and local template/pipeline/check/view definitions only where necessary. Use ordinary Markdown for positioning, brand voice, audiences, competitors, content briefs, evidence and durable learnings. Do not create distinct audience/asset/content/hypothesis/experiment/learning record kinds just because they might be useful later. A campaign is a locally defined, optional collection of projects/issues serving a shared objective, analogous to a Dev release only in coordination, not release branches or synchronized publication. A small campaign may simply be a project.

**Initial named pipelines:** one campaign-delivery composition (goals/strategy → projects → campaigns, actual link directions declared locally) and a lightweight issue/idea → project composition or view where useful. Same project can participate in both; no duplicate project owner/tasks/evidence. Campaign membership optional; projects may be executed independently and their artifacts may be distributed independently under approval. Do not invent mandatory stage transitions. A campaign document can be a short intent, included project/issue links, timing/coordination and outcome/evidence section; the linked projects own status and task lists.

**Included:**
- Adopt the accepted minimal Marketing workspace from Otto; set up a clear source-only entrypoint, reproducible pin and local skill sync/check. Use one source for workspace strategy, project status and task progress. Define local project/campaign identity, relationship and view using existing registrations, no new generic mechanism.
- Initial vision/strategy and brand/product knowledge agreed with owner; use exact Dev release/capability references for product claims, not a duplicate source of truth. Document what's unknown and where ideas go. Keep project priorities/issue triage light and campaign grouping optional.
- Minimal Markdown skills for start, plan, manage, research, create, critique, campaign coordination and improve; combine roles/skills where useful. Standard projects complete agreed tasks; loop projects use local baseline, measurement, rounds and stop rules, not Dev-specific live-stack/GPU rules. Recurring work is a workstream, not a never-ending compulsory project or scheduler.
- Configure local project catalogue and a useful campaign view, issue intake forms or simple conventions, common template validation and any justified local checks. Do not inherit Dev release membership, branch/pin rules, privileged Apps or public feed publishing.
- Define scoped authority for draft, external publishing/contact, budget, account and personal data; default no outbound actions, spend or credentials. Owner or authorized actor separately approves exact item/channel/action; merged Markdown or project status never confers authority. No raw private analytics, contact lists or secrets in Git.
- Prove the actual workspace with one bounded standard project and one bounded loop project; choose real representative work with owner, link both where appropriate to a short campaign and show independent project work/idea routing. A loop can be a small approved draft/creative comparison or evidence-based improvement on reproducible inputs, with actual observations and a stop decision; not a fabricated growth metric. Reuse Otto's minimal draft where applicable. Demonstrate one source-linked learning informing the next action. External publication and audience metrics are optional for workspace establishment; if a live action is withheld, say so and do not claim measured market impact.

**Not included:** automated social publishing/outreach/spending, generic scheduler, complex campaign/asset database, raw analytics integration, elaborate funnel schema, multiple forced pipelines, mandatory hierarchy, broad user-contact ingestion, automatic synchronization to Dev or proving sustained growth. Actual ongoing marketing work is subsequently created as projects and issues inside Marketing, not a prerequisite to setting it up.

## Sequence and readiness

Accept Otto and its minimal Marketing handoff; owner selects initial direction, approved source/access and two bounded representative projects. Design the smallest local graph and permissions, review before operational setup. Adopt local templates/pipelines and entrypoint, issue/project/campaign views and ordinary knowledge docs; author only useful skills. Prove a fresh agent navigates the workspace, takes an idea to a standard project, runs a bounded loop and coordinates both in an optional campaign, with no core/Dev modification. Record real evidence and learning, and hand to the owner as a usable organisation. [Tasks](tasks.md). Separate authorized read-only discovery may happen earlier; no new workspace or account action from this proposal alone.

## Interfaces and handoff

**Consumes:** Otto's exact accepted package pin, minimal Marketing starter and extension guide, standard/loop template contract, project/issue mechanisms and named composition support. Owner-approved brand/product sources and actual verified Dev release references. No assumed private repository access.

**Produces:** independently operated Astrid Marketing repo, light strategy/knowledge docs, local project/campaign/issue pipeline and templates/skill entrypoint, generated project and campaign views, two small real project examples and optional campaign coordination with evidence. Exact source and approvals, known limits, next useful projects and feedback references. Any genuine missing shared mechanism is a separate Otto issue/proposal, not a fork. No public marketing claim or external authority implied.

## Completion

1. A new agent starting at the repo can find strategy, product knowledge, issue/idea intake, project catalogue, templates, local workstreams and campaign relationships. It can create a small standard project and add ordinary tasks without writing framework code.
2. A real bounded standard project and loop project use the same project structure, different templates/procedure and actual evidence. Loop has baseline/measurement, a round and stop/next decision; not all tasks known upfront. Both have independent ownership and can also appear in one campaign without duplicated statuses/tasks. At least one ungrouped project or fixture is valid.
3. Local named pipeline(s) and views validate through the same pinned Otto; Marketing can add a skill and local template or pipeline without modifying Dev or Otto. No Dev-specific release check, number convention, privileged app or forced gap.
4. Negative controls reject invalid links/template/required check and missing/changed external action approval. No fake publication/analytics or personal data leaks. Any live distribution/metric collection is separately scoped and evidenced; absent authority is a safe hold, not a failed workspace setup or an invented outcome.
5. Actual bounded project results yield a useful recorded learning/next action; fresh agent can use it. Independent review accepts minimal organisation, exact repo/pin, native/source-only proof and remaining limitations. Sustained growth and ongoing execution are later Marketing projects.
