## Outcome and scope

The person says what should happen on screen. Their agent discovers, creates or selects the right capability, binds existing project materials, authors destinations and timing, previews, places and revises it. A creative pack combines technology packs using knowledge, existing public capabilities, and typed artifacts. The ordinary timeline remains the composition authority. Start with two complementary implementations: the Remotion-based Astrid Video living-pixel choreography and an editable HyperFrames HTML composition. No creative worker should have to read internal host code or copy user media into executable source to do this.

### End-state statements

1. A new effect has ordinary versioned source, a declared parameter schema, a discoverable skill/example and a native test path.
2. An element can accept a variable number of authorized existing images/videos; the media binding is not tied to a React prop convention or any particular effect.
3. Changing media or creative parameters does not require rebuilding or readmitting source; changing a transitive source dependency does create the appropriate new source revision.
4. An agent adds an admitted effect directly with validated settings, track and timing; it does not manufacture a built-in dummy clip first.
5. Nested settings are legible and editable through the generic inspector where the supported schema permits. Feedback can still be applied by the agent.
6. A HyperFrames capability can author and render its own HTML-native composition, not merely translate Astrid text clips.
7. The creative pack can recommend either technology, or use both: a HyperFrames clip becomes a living-pixel card; an independently rendered transparent pixel layer sits over a HyperFrames sequence.
8. A rendered intermediate is an editable source's derived result, not a replacement for its source; after feedback only affected outputs need regeneration where existing identity/cache contracts permit.
9. The same native managed media, authoritative timeline, audio, frame clocks and receipt/undo path apply to both. Unavailable or unsupported capabilities refuse truthfully rather than substituting a different result.
10. A fresh agent, using maintained skills and tools rather than internal product source, completes an unseen mixed-technology creative brief and revises the saved work.

### Phase A — Fix the shared boundary

- [#1873](https://github.com/banodoco/astrid-dev/issues/1873): compute new effect revision identity from complete declared executable dependency closure, including shared helpers outside the effect directory. Remove the pack-side fingerprint workaround only after native proof.
- [#1874](https://github.com/banodoco/astrid-dev/issues/1874): reuse Plan 69/78 placement and native add/commit machinery; fill the proven gap in direct parent/occurrence insertion, with initial params and exact admitted identity. Do not add a second editing API.
- [#1875](https://github.com/banodoco/astrid-dev/issues/1875): extend existing schema projection/inspector for a small supported subset (nested objects, strings, arrays with schema-permitted add/remove/reorder, typed media selection when available), preserving scalar controls, unknown untouched values and native transaction behavior. Readable fallback for unsupported schema shapes. No custom choreography UI requirement.

### Phase B — Make HyperFrames a real authorable capability

Promote/reuse the existing fixture renderer, support probe and hybrid planner rather than reimplementing them. Use a normally discoverable, installable, pinned technology pack; prove one supported local CPU setup first, with clear requirements, dependency/license facts and actionable setup/unsupported reports. HyperFrames and Remotion may use different compatible Node versions; use existing pack/environment setup, not hidden npx downloads or a global toolchain replacement.

Expose a supported author/validate/preview/render journey for user-authored HTML/CSS/JS source with declared resources, schema and managed media bindings. Use the existing trusted pack/admitted source and task/publication path; select the smallest adapter needed after critique. Keep deterministic seek, source clock, source revision, permissions and output identity. Place managed video output using normal timeline operations; retain exact editable source and parameters and its link to the result. A live HyperFrames editor/iframe host and arbitrary nested renderer execution are not requirements. Reconcile existing hybrid-planner tests with Plan 91; keep the existing explicit support/refusal behavior. The combined proof may use ordinary clips/layers and native export rather than a new planner. The existing optional LayerRef is prior art, not a reason to implement speculative multi-renderer live dispatch.

### Phase C — The authoring golden path and real creative qualification

- [#1877](https://github.com/banodoco/astrid-dev/issues/1877): make the existing Pack Builder and Rendering skills/guides route naturally to a discoverable effect-authoring workflow. Include minimal working examples, the actual schema/props/managed input interface, deterministic frame evaluation, sample media, native preview and exact revision placement/edit/recovery. Reuse current scaffold/admission/visualize paths and fix demonstrated missing pieces. Keep #1407/#1408 in their owning work rather than duplicate it.
- Import the supplied Astrid Video v0.11 source candidate through normal pack development and make it work natively with generated fixtures. Keep its visual grammar, pure choreography engine, destination authoring, independently controllable scale, transition/rest/flow and edge reveal, persistent item identities and authored timing. Remove local-only integration workarounds once the native replacement is proven. Do not require every effect to be implemented in every renderer.
- Add simple creative guidance to that pack: choose the technology/capability by intent (e.g. HyperFrames for bespoke editorial sequence, Living Composition for moving/presenting objects); compose typed outputs and ordinary layers. Markdown recipes before any new parser, shared program or DSL. Deliver an editable mixed sequence and a separate blind authoring trial.
- [#1876](https://github.com/banodoco/astrid-dev/issues/1876): explicitly assess any remaining cross-pack library reuse need after artifact composition works. Retain the intentional closed import rule and Plan 87's shared-contract alias work. Document a bounded design or defer implementation with a concrete reason; only add a separately scoped implementation if an actual reuse need cannot be met by public capability/typed artifact composition and the owner approves.

Out of scope: new generic scene graph or second timeline, universal animation language, renderer-specific branches in core for every pack, arbitrary executable dependencies or unsafe untrusted code, replacing Remotion, Blender integration itself, universal live renderer nesting, a new package manager, general editor extensibility rewrite, full cross-platform or hosted render isolation claims. Blender/Three.js and future technologies should be able to reuse the proven input/output and placement boundary without being implemented here.

## Existing work and decision

The current [Render Backend Protocol v1](https://github.com/banodoco/astrid-agent/blob/release/15/main/docs/contracts/render-backend-v1.md) already gives renderer/planner/finalizer selection, explicit frame windows, managed materialization, support probes, typed result and provenance. The [Capability Artifact Contract](https://github.com/banodoco/astrid-agent/blob/release/15/main/docs/contracts/capability-artifact-contract.md) already defines semantic ports and scoped configuration. Reuse these contracts; a thin general input declaration/projection at the existing owner boundary is preferable to a second registry or a universal rendering runtime.

HyperFrames exists at [tests/fixtures/renderer_packs/hyperframes](https://github.com/banodoco/astrid-agent/tree/release/15/main/tests/fixtures/renderer_packs/hyperframes), with a pinned CLI adapter and a mixed-window planner. It is a fixture, not yet a qualified general HTML-authoring pack. It supports a bounded text/silent-media subset, refuses unsupported inputs and routes mixed/unsupported windows to Remotion; it does not establish arbitrary simultaneous renderer layering. Existing real render tests have known failures recorded under Plan 91. Plan 69/78 improves compiled admission and live retargeting; Plan 87 fixes renderer pack roots/imports and preview/export identity. This plan completes the new cross-technology authoring journey, not those plans' existing scope. [Inputs](inputs.md#planning-evidence) records source identities, the standalone v0.11 evidence, issue disposition, alternatives, owner request and pending critique.

## Completion

On a clean supported local R16 stack with no local patches and no private helper or direct storage mutation, a fresh agent given an unseen brief and generated images/video/narration discovers the skills; creates/adapts a reusable effect; binds three then eight authorized media items; previews and inserts the exact admitted effect; changes destinations, timing and parameters; creates and renders a real editable HyperFrames HTML sequence; and composes these in one saved Astrid timeline. Show a 1→3→3 new→5→1 living-pixel sequence, reused video content inside a card, a transparent pixel overlay above the HTML-rendered scene, and timeline-owned audio. Prove independent source and param/media revisions, replacement without code readmission, both landscape and portrait, exact source windows, old versus new pin pixels, editor/composed-frame/export parity at selected boundary and midpoint frames, reload, undo/redo and portable export/import in an authorized disposable project. Demonstrate at least one revision to each native source that regenerates the intended clip/layer without disturbing the other; compare unchanged output identities where cache reuse exists, not an unmeasured performance promise. Negative cases: missing/foreign/wrong-kind/forged media, unapproved or missing dependency, invalid schema/timing, failed admission/render and stale timeline head refuse clearly without lost work or altered historical pins. Actual host playback/render receipts and inspection images are required; standalone animation previews and text-only HyperFrames translation cannot satisfy the proof. Record setup/authoring time, friction and unsupported limits. No automatic closure of F-004/LS-005/LS-003 or promise of hosted/untrusted/multi-OS qualification. Final independent review and normal release gates; release publication remains separately authorized.
