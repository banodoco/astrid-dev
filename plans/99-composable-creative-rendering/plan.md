## Outcome and scope

Start with a short creative video, not a new architecture. Astrid Video's living pixels present and rearrange animated editorial cards made with HyperFrames. A living-pixel overlay plays over a HyperFrames scene. The creator requests changes; the agent revises the relevant source or parameters and updates the same timeline. Use ordinary managed videos, including a supported transparent layer, and the existing Remotion element where it is useful. Retain the editable HTML/JS and effect source, settings and provenance behind rendered media; do not flatten away the creator's ability to revise it.

The platform standardizes managed inputs, validated parameters, exact source identity, execution, inspection and ordinary timeline placement. Native tools retain their own formats. Creative recipes are Markdown guidance, not a new interpreter. A second real technology demonstrates generality; do not build features for hypothetical twentieth technologies.

### Included — only the smallest missing path

- **First attempt (CR-0):** on the actual receiving base, use the real v0.11 pack and existing HyperFrames fixture with generated media and a brief. Try normal author/render/inspect/place/revise operations before designing repairs. Record each actual blocker and the smallest owning fix. If a blocker prevents completion, preserve the partial witness and continue independent steps. Do not build a parallel compositor or use unsupported paths as success evidence.
- **General managed inputs — [#1870](https://github.com/banodoco/astrid-dev/issues/1870):** reuse the existing capability/artifact ports and managed registry/materialization to declare and bind a variable number of authorized images/videos by stable role/key, with verified kind and required dimensions/duration. Exact selected schema and source authority, derived host-only locators, correct source clocks, input retention/remapping and honest failures are non-negotiable. No fixed six-card or renderer-specific persisted contract. Start with the narrow shape needed by both implementations. Use the same binding semantics for the effect's native editor, worker and composed-frame inspection, and HyperFrames' native action/backend. Preserve existing six-card behavior and existing supported transfer/occurrence semantics; prove retention at the actual owner and refuse unsupported transfer forms safely rather than introduce a new export/import subsystem. The v0.11 `mediaBindings` / `__astridMedia` proposal is evidence, not a requirement to adopt its names.
- **Source revision identity — [#1873](https://github.com/banodoco/astrid-dev/issues/1873):** changing declared shared executable source must create a new affected revision; old admitted pins still resolve to old bytes. Prefer a deterministic conservative pack-source closure fingerprint using the existing snapshot mechanism over a new precise per-element dependency graph. Exclude mutable project media and parameters from source identity. Broader invalidation of elements in the same changed pack is acceptable; unrelated packs and pinned historical work must not change. Remove the manual fingerprint only once the native identity is proved.
- **Placement — [#1874](https://github.com/banodoco/astrid-dev/issues/1874):** demonstrate the existing R15/R16 native insertion and placement path first. If it already delivers the intended use, document it and add the missing proof; otherwise fix just the missing public route, not all editing forms. No dummy built-in or private helper required for the supported new-effect journey; exact refs, schema validation, native history and atomic conflict/refusal semantics stay intact. Do not duplicate Plans 69/78/88 or R16 editing plans.
- **HyperFrames:** promote/reuse the pinned fixture renderer as a small discoverable authorable technology capability on one supported local CPU setup. Accept real authored HTML/CSS/JS with declared resources, simple validated settings and shared managed inputs. Render through the existing supported task/backend/publication path to an ordinary managed video. Retain exact editable source and input/param/output provenance so an agent can change and regenerate the clip. Use a supported preview render, not a new live HTML editor. No hidden dependency downloads or global Node replacement. Preserve existing support/refusal and hybrid test behavior; coordinate with Plan 91. The existing hybrid planner is useful prior art, not a required expansion.
- **Authoring path and proof — [#1877](https://github.com/banodoco/astrid-dev/issues/1877):** improve the existing Pack Builder and Rendering guides with one minimal working reusable effect/starter, actual native managed input and scalar parameter conventions, supported preview, admission and placement commands. Make the technology-specific instructions discoverable. Import the actual Astrid Video candidate, preserving its established visual identity and useful controls, and add a short Markdown recipe selecting HyperFrames for editorial motion and Living Composition for carrying/presenting items. One cold agent completes the combined proof; no new development toolkit or second qualification project.

## Existing work and decision

The [Render Backend Protocol v1](https://github.com/banodoco/astrid-agent/blob/release/15/main/docs/contracts/render-backend-v1.md) already supplies renderer/planner/finalizer selection, explicit frame windows, managed materialization, support probes and output provenance. The [Capability Artifact Contract](https://github.com/banodoco/astrid-agent/blob/release/15/main/docs/contracts/capability-artifact-contract.md) supplies typed ports and scoped configuration. The [HyperFrames fixture](https://github.com/banodoco/astrid-agent/tree/release/15/main/tests/fixtures/renderer_packs/hyperframes) has a pinned adapter and hybrid planner for a bounded text/silent-media subset; it is not a qualified HTML-authoring product capability. Existing real render failures are tracked in Plan 91. Plans 69/78/87/88 already address much of the admission, placement, preview/render and editing path. [Inputs](inputs.md#planning-evidence) records the source findings, owner choice to reduce scope, earlier evidence and pending independent critique. The 90/10 choice removes required structured-inspector work, speculative cross-pack library design and an expanded acceptance matrix, not the integrity guarantees.

## Completion

On one clean, supported local R16 stack, a fresh agent receives an unseen short creative brief and generated stills/video/narration plus the normal Astrid skills and tools, with no internal product implementation hints. It creates or adapts one reusable effect, authors real animated HTML cards through HyperFrames, uses them as managed media in the actual Living Composition effect (at least three items with an exchange and rearrangement), and places a transparent living-pixel layer over a HyperFrames-rendered sequence on an ordinary saved timeline with timeline-owned audio. It responds to feedback by changing creative parameters/media without source readmission and revising an underlying source in each technology when requested. Preserve editable source, exact source/managed identities, existing scalar controls and unaffected content.

Use actual native preview/inspection and export, compare representative destination and moving frames, reload the saved result and demonstrate ordinary undo or recovery. Target one aspect ratio and one meaningful sequence, not separate feature films, exhaustive eight-item/portrait/export matrices or a standalone renderer substitute. Focused contract tests still guard missing/foreign/forged/wrong-kind managed inputs, retention and supported remapping/transfer, shared-helper change versus retained old pin, invalid settings, failed admission and stale/failed commit. Supported operations must not lose data; explicitly refuse unsupported ones. Record exact candidate, actual time and every workaround/blocker; repair only root causes needed to satisfy this bounded proof, and file residual improvements separately. One final independent review and normal release gates; no automatic closure of the broader gaps or claim of full portability/hosted support. Publication requires separate authorization.
