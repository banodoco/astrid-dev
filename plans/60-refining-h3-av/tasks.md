# Tasks — Refining H3_AV

[Plan](plan.md) · [Inputs](inputs.md)

The plan is a list of task skills, in the order the Into the Minkhole edit needs them. Each is proven the same way, and each tool fix sits under the task skill that needs it. A tool fix no task skill needs is not built: it is dropped or filed as an issue. Every task works through Astrid's own commands, fixes a defect where it lives, and never edits, skips or weakens a test to pass: a deliberate contract change updates the contract, its documentation and its pinned tests together and says so.

## The loop for every task skill

1. Write the skill from what the code and the runs so far show. It takes an agent from "this clip, this intended result" to a reviewed take on the timeline: find the shot, know the words, choose the cut point, write the request, rent the GPU through Astrid, run, check, place, release the GPU.
2. Give a fresh agent on the normal-task model the synced skills, the clip, the intended result and a workspace where Astrid is already running with the project imported. Nothing else. The manager writes that brief down before the trial.
3. The agent does the task end to end, renting a RunPod machine through Astrid within the trial ceiling (D8).
4. Record every place it stalled, guessed, or needed help, and what it cost. Help given is recorded as coaching and means the trial did not pass.
5. Fix the tool or the skill at that place. A tool fix becomes a row under this task skill.
6. Repeat with another fresh agent until one completes it unaided.
7. The owner reviews the take and accepts or rejects it. A rejection, or the task's trials running out first, leaves the task skill unfinished and is recorded that way.

One task skill at a time. Tasks of the same kind share one skill: the three Morpheus lines are one skill used three times.

## RH-1 in detail

**Why first.** On 16 November 2026 the Morpheus pilot's dry run was refused: the Matrix media is 23.976 fps and 1920×800, and the pack accepts only exactly 24 fps and 1024×576, then tells the caller to run an ffmpeg command that would stretch the picture. Version 1 continuation also needs the source range to start at zero, and every asset must be a local file.

**Contract.**

1. *Naming an input.* In a version 1 request, `source.asset`, a reference's `asset` and a mask's `mask_asset` may each be a media handle in the existing forms (`sha256:…`, `run:<id>[/<port>][#n]`, `ref:…`). Handles are resolved at admission by `resolve_media_handle` with the caller's client and project, keeping its project check and its lineage on the task receipt, and then enter the pack's existing managed staging. No resolver is written in the Comfy hook. An asset map of local files stays valid.
2. *Identity.* The public request keeps the caller's source identity and range exactly as written, so its digest and provenance do not change. Preparation records two distinct things: the source (digest, range in source seconds, fit) and the prepared source (digest, frame count, the cut, rate and size mapping applied). `compile_stages` stops overwriting preparation's asset records (`shared/stages.py:119`).
3. *One coordinate view.* After prepare, every stage works in prepared-clip coordinates: time zero is the range start and the canvas is 1024×576. Compile binds the prepared file at offset zero. Compose and verify take their offset from the prepared-source record, not from the request's range as they do today (`shared/compose.py:336-352`; `shared/verify.py:72-88`). Protected pixels and sound are compared with the prepared baseline; provenance names the original.
4. *Conformance, bounded.* The range must lie inside the media, or the request is refused with both values. The prepared clip has `round((end − start) × 24)` frames, timestamps rebased to zero at a constant 24 per second; a continuation needs at least 39. Frame rate is changed by resampling the picture, never by changing speed or pitch. Size is changed by filling or fitting 1024×576 with the shape kept. Over the selected interval, surplus sound is trimmed to the picture; a shortfall or offset of at most one frame (1/24 s) is padded with silence and recorded; anything larger is refused as missing sound, naming the interval. Media that cannot be read or probed is refused; today a file that returns no stream list passes (`shared/prepare.py:213-217`). The existing strict check then runs on the prepared file, so the graph still receives only exact input.
5. *Masks and regions.* A supplied mask or pixel region must already match the prepared canvas and the clip-relative clock. A mismatch is refused, naming what was expected and what was given. Nothing is reprojected in this plan.
6. *Any size in, a chosen canvas out.* Input footage of any dimensions and shape is accepted and conformed with the fit stated. The output canvas is no longer fixed: the request may state `output.canvas` as a shape (`16:9`, `source`, or `W:H`) or as a width and height; unstated, it is the source's own shape for continue and edit and 16:9 for generate. The pack turns a shape into the largest width and height that are both multiples of 32 within its pixel budget (today's 1024×576, about 0.59 megapixels), so 16:9 still gives 1024×576. An explicit size must be multiples of 32 and inside the budget, or it is refused with the nearest valid size named. The dry run always reports the canvas and the fit. Two things stay fixed because the model's own nodes fix them: 24 frames a second and frame counts of 5 + 17k. Evidence: the core H3 nodes take any width and height in steps of 32 with no list of shapes (ComfyUI v0.36.0 `comfy_extras/nodes_minimax_h3.py:93-134`, whose own default is 1344×768) and time everything at 24 fps (`:29-50`); 1024×576 is this pack's choice in the files named in the scope. No source states which sizes the model handles well, so quality on canvases other than 16:9 is settled only on a GPU.
7. *One prepared clip.* The prepared source is made once, on the controller, published as a managed object with its own digest and its source, range and fit recorded, and that exact object is what every stage and the GPU worker use. A worker never conforms again; a missing or mismatched prepared object is refused.
8. *Small rules found by the live work.* A continuation source shorter than 39 frames is refused before submission, with the count named. A port-qualified run handle (`run:<id>/<port>#n`) is admissible although its `/` fails today's file-map key check (`astrid/core/generation/entries.py:646-651`).

## RH-6 in detail

**The route, from reading the node sources.** It is already possible with the pinned nodes and a change to the pack's graph. LanPaint is not needed for it and no pull request to a node pack is required.

- H3's latent holds the picture and the sound as two streams with two separate masks, and the stock sampler applies each to its own stream (ComfyUI v0.36.0 `comfy/samplers.py:1297-1314`, `comfy/model_base.py:2234-2250`; per-stream masks arrived upstream on 17 August 2026).
- The node pack the pack already pins (ComfyUI-H3-Motion-Context-MultiRef at `361624fb`) sets those masks: `MiniMaxH3SetAVNoiseMask` takes a separate `video_mask` and `audio_mask` and resamples a frame-by-frame mask onto the sound's 40-per-second grid (`existing_video_extension.py:1131-1144,1163-1245`); its own documentation gives "allow audio regeneration while retaining video protection" as a use (`KEYFRAMES_AND_INSERTS.md:117`). `MiniMaxH3SourceAudioRegenMask` regenerates a whole clip's sound with the picture protected (`:462-558`).
- The pack's masked edit already uses that pack's `H3V2VGranularFractionalDenoise` and binds `audio_strength=0` (`shared/generation.py:416`). That input is one value for the whole clip (`h3_v2v_fractional.py:443-448`), so a time span needs the mask node, not that input. The commit that introduced the zero (`772e57075`) gives no reason for it.
- What LanPaint's graph added beyond this is its own sampler, which refines the edges of a masked region, and a decode step that blends picture and crossfades sound under the masks (LanPaint `src/LanPaint/nodes.py:890-995,1139-1226` at `32cf848e`). Those are the reference for edge handling, and the reason D1 keeps the packaged graph until RH-5's result.
- Nothing newer changes this: the node pack has no commits after the pin, and ComfyUI core has added no sound-masking node for H3 since v0.36.0.

**Contract.** A version 1 `operation: edit` may carry `changes.audio` entries with `during`, `action: generate` and the line, alone or together with one `changes.video` region over the same span. Sound is regenerated only inside the stated spans, on boundaries of 1/40 s; the picture is kept everywhere, or regenerated only inside the region. Compose puts generated sound inside the spans and source sound outside, with a short stated crossfade; verify checks protected sound and protected pixels against the prepared baseline. A request with sound spans and no usable source sound is refused with the reason.

**Proof.**
1. CPU: the compiled graph for a sound-only request has a picture mask of zero everywhere and a sound mask that is one only inside the span; with a mouth region added, the picture mask is one only inside the region on the span's frames. Compose and verify pass on a real-media case with a click track, and fail when sound outside the span is altered. `test_native_masked_edit.py`, `test_two_edit_cpu_qualification.py`, `test_verify_fail_closed.py` and `test_skill_examples_admitted.py` pass, the last with a new example.
2. GPU, through task skill RH-5, on the same Morpheus clip and a line that fits the span: take A, sound only, picture kept; take B, sound plus a mouth region given as a box in the request or a supplied mask. Receipts, cost, pod released. Each take is placed by the D7 method and the owner accepts or rejects it on words, voice, lips and the joins at both ends of the span.
3. The result is recorded as one of: usable as is; usable only with the mouth region; edges need the LanPaint sampler or an upstream change (then named exactly, as a new row); or not usable, with the evidence. Only then is D1's removal carried out or revised.
