# Tasks — Refining H3_AV

[Plan](plan.md) · [Inputs](inputs.md)

The plan is a list of task skills, in the order the Into the Minkhole edit needs them. Each is proven the same way, and each tool fix sits under the task skill that needs it. A tool fix no task skill needs is not built: it is dropped or filed as an issue. Every task works through Astrid's own commands, fixes a defect where it lives, and never edits, skips or weakens a test to pass: a deliberate contract change updates the contract, its documentation and its pinned tests together and says so.

## The loop for every task skill

1. Write the skill from what the code and the runs so far show. It takes an agent from "this clip, this intended result" to a reviewed take on the timeline: find the shot, know the words, choose the cut point, write the request, rent the GPU through Astrid, run, check, place, release the GPU.
2. Give a fresh agent on the normal-task model the synced skills, the clip, the intended result and a workspace where Astrid is already running with the project imported. Nothing else. The manager writes that brief down before the trial.
3. First a rehearsal that rents nothing: the fresh agent finds the skill and the entry, writes the request, gets a ready dry run, and rehearses checking and placing with media that already exists. A paid trial starts only after a rehearsal passes.
4. Then the paid trial: the agent does the task end to end, renting a RunPod machine through Astrid within the trial ceiling (D8).
5. Record every place it stalled, guessed, or needed help, and what it cost. Help given is recorded as coaching and means the trial did not pass.
6. Fix the tool or the skill at that place. A tool fix becomes a row under this task skill.
7. Repeat with another fresh agent until one completes it unaided.
8. The owner reviews the take and accepts or rejects it. A rejection, or the money running out first, leaves the task skill unfinished and is recorded that way.

Money (D8): one ledger, kept with the trial logs, records every rental: what a cold start cost, every failed attempt, every release receipt. A trial that fails still spends. Caps are set from what the pilot measures and what is left of the one $25; a cap is never raised by resetting it.

One task skill at a time. Tasks of the same kind share one skill: the three Morpheus lines are one skill used three times.

## RH-1 in detail

**Why first.** On 16 November 2026 the Morpheus pilot's dry run was refused: the Matrix media is 23.976 fps and 1920×800, and the pack accepts only exactly 24 fps and 1024×576, then tells the caller to run an ffmpeg command that would stretch the picture. Version 1 continuation also needs the source range to start at zero, and every asset must be a local file.

**Contract.**

1. *Naming an input.* In a version 1 request, `source.asset`, a reference's `asset` and a mask's `mask_asset` may each be a media handle in the existing forms (`sha256:…`, `run:<id>[/<port>][#n]`, `ref:…`). Handles are resolved at admission by `resolve_media_handle` with the caller's client and project, keeping its project check and its lineage on the task receipt, and then enter the pack's existing managed staging. No resolver is written in the Comfy hook. An asset map of local files stays valid.
2. *Identity.* The public request keeps the caller's source identity and range exactly as written, so its digest and provenance do not change. Preparation records two distinct things: the source (digest, range in source seconds, fit) and the prepared source (digest, frame count, the cut, rate and size mapping applied). `compile_stages` stops overwriting preparation's asset records (`shared/stages.py:119`).
3. *One coordinate view.* After prepare, every stage works in prepared-clip coordinates: time zero is the range start and the canvas is the resolved canvas of item 6. Compile binds the prepared file at offset zero. Compose and verify take their offset from the prepared-source record, not from the request's range as they do today (`shared/compose.py:336-352`; `shared/verify.py:72-88`). Protected pixels and sound are compared with the prepared baseline; provenance names the original.
4. *Conformance, bounded.* The range must lie inside the media, or the request is refused with both values. The prepared clip has `round((end − start) × 24)` frames, timestamps rebased to zero at a constant 24 per second; a continuation needs at least 39. Frame rate is changed by resampling the picture, never by changing speed or pitch. Size is changed by filling or fitting the resolved canvas with the shape kept. Over the selected interval, surplus sound is trimmed to the picture; a shortfall or offset of at most one frame (1/24 s) is padded with silence and recorded; anything larger is refused as missing sound, naming the interval. Media that cannot be read or probed is refused; today a file that returns no stream list passes (`shared/prepare.py:213-217`). The existing strict check then runs on the prepared file, so the graph still receives only exact input.
5. *Masks and regions.* A supplied mask or pixel region must already match the prepared canvas and the clip-relative clock. A mismatch is refused, naming what was expected and what was given. Nothing is reprojected in this plan.
6. *Any size in, a resolved canvas out.* Input footage of any dimensions and shape is accepted and conformed with the fit stated. The request may state `output.canvas` as a shape (`16:9`, `source`, or `W:H`) or as a width and height; unstated, it is the source's own shape for continue and edit and 16:9 for generate. One rule resolves a shape to a size: among sizes whose sides are both multiples of 32 and whose area is at most the pack's pixel budget (today 1024×576, about 0.59 megapixels), take the one whose aspect is nearest the requested shape, and among equally near ones the largest. So 16:9 resolves to 1024×576, and a shape that has no exact size on the grid resolves to the nearest one, with Fill or Fit applied to the small remainder. An explicit size must be multiples of 32 and inside the budget, or it is refused with the nearest valid size named. The dry run always reports the resolved width, height and aspect, and the fit. This resolved canvas replaces the fixed 1024×576 everywhere in the pack, including masks and regions. Two things stay fixed because the model's own nodes fix them: 24 frames a second and frame counts of 5 + 17k. Evidence: the core H3 nodes take any width and height in steps of 32 with no list of shapes (ComfyUI v0.36.0 `comfy_extras/nodes_minimax_h3.py:93-134`, whose own default is 1344×768) and time everything at 24 fps (`:29-50`). No source states which sizes the model handles well: quality on canvases other than 16:9 is unproven until a GPU run on one, which is done only if money remains.
7. *One prepared clip.* The prepared source is made once, on the controller, published as a managed object with its own digest and its source, range and fit recorded, and that exact object is what every stage and the GPU worker use. A worker never conforms again; a missing or mismatched prepared object is refused.
8. *Small rules found by the live work.* A continuation source shorter than 39 frames is refused before submission, with the count named. A port-qualified run handle (`run:<id>/<port>#n`) is admissible although its `/` fails today's file-map key check (`astrid/core/generation/entries.py:646-651`).

## RH-6 in detail

**The route, from reading the node sources.** It is already possible with the pinned nodes and a change to the pack's graph. LanPaint is not needed for it and no pull request to a node pack is required.

- H3's latent holds the picture and the sound as two streams with two separate masks, and the stock sampler applies each to its own stream (ComfyUI v0.36.0 `comfy/samplers.py:1297-1314`, `comfy/model_base.py:2234-2250`; per-stream masks arrived upstream on 17 August 2026).
- The node pack the pack already pins (ComfyUI-H3-Motion-Context-MultiRef at `361624fb`) sets those masks: `MiniMaxH3SetAVNoiseMask` takes a separate `video_mask` and `audio_mask` and resamples a frame-by-frame mask onto the sound's 40-per-second grid (`existing_video_extension.py:1131-1144,1163-1245`); its own documentation gives "allow audio regeneration while retaining video protection" as a use (`KEYFRAMES_AND_INSERTS.md:117`). `MiniMaxH3SourceAudioRegenMask` regenerates a whole clip's sound with the picture protected (`:462-558`).
- The pack's masked edit already uses that pack's `H3V2VGranularFractionalDenoise` and binds `audio_strength=0` (`shared/generation.py:416`). That input is one value for the whole clip (`h3_v2v_fractional.py:443-448`), so a time span needs the mask node, not that input. The commit that introduced the zero (`772e57075`) gives no reason for it.
- What LanPaint's graph added beyond this is its own sampler, which refines the edges of a masked region, and a decode step that blends picture and crossfades sound under the masks (LanPaint `src/LanPaint/nodes.py:890-995,1139-1226` at `32cf848e`). Those are the reference for edge handling, and the reason D1 keeps the packaged graph until RH-5's result.
- Nothing newer changes this: the node pack has no commits after the pin, and ComfyUI core has added no sound-masking node for H3 since v0.36.0.

**What that means.** The pinned primitives support it. Astrid still has to construct the route, compose its result and qualify it; none of that exists today. The node pack's own example regenerates all of a clip's sound, not a span of it.

**Contract.**

1. *The request.* A version 1 `operation: edit` with `changes.audio: [{during: [t0, t1], action: generate}]`, alone or with one `changes.video` region over the same span. That is the form the canonical spec already admits (`shared/spec.py:591-600` allows only `during` and `action` on a sound change), so no field is added: the new line is written in `content.prompt` as the exact quoted line, and the proof follows it through canonicalization into the graph's prompt. What changes is admission: compile today requires exactly one changing picture operation (`shared/compile.py:491-494`), and a sound-only edit has none. `shared/spec.py` is touched only if that admission needs it.
2. *The sound mask.* Astrid builds it at the sound latent's own length, 40 ticks a second over the whole run including the padded tail, so the node's resize is the identity and nothing is interpolated from the 24-per-second picture grid. `during` is half-open in clip seconds. A tick is regenerated only if it lies wholly inside the span, so an endpoint that is not on a tick moves inward by less than 25 ms and the dry run reports the effective span. Tail ticks are always kept. A span containing no whole tick is refused.
3. *The picture mask, when a mouth region is given.* A picture frame is regenerated inside the region if any part of it falls in the span; outside the region, and on all other frames, the picture is kept.
4. *"Picture kept."* It means the decoded pixels of the result equal the decoded pixels of the prepared baseline. The picture is VAE-encoded, sampled and decoded on the way, so a zero mask is not that proof. Compose takes the whole picture stream from the source baseline when no picture change is permitted (`shared/compose.py:847-850,889-954`), and verify's existing decoded-hash comparison checks it (`shared/verify.py:123-176,318-365`). With a mouth region, the same holds for everything outside the region. It does not mean the original compressed bytes.
5. *The join.* One policy: the generated sound fades in over the first 20 ms of the span and out over its last 20 ms (the length LanPaint's graph used; changed only on evidence from a take), entirely inside the permitted span; source sound outside the span is untouched. Compose today cuts and joins sound with no fade (`shared/compose.py:955-967`). The compose evidence and verify use the same support: equality outside the span, no constraint inside. A span touching the start or end of the clip has no fade on that side; touching spans are merged; a span shorter than the two fades is refused. Decoded sound is resampled to the source clock and the duration is unchanged.
