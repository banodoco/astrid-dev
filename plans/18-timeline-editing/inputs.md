**Approach:** One command layer, in two phases, extending what exists; revised after the critique below. Phase 1:

1. **The editor sends and adopts.** Every gesture becomes a named Agent op the editor sends through one `sendIntent`, adopting the head that returns. The encoders are dumb: they return only `{op, select, args}`, read no document, build no `reads`/`expect`/`selections` and cannot refuse. The local edit is a disposable preview. Each conversion deletes its expected-diff block and dead refusal sites. The TypeScript capture ports and the test-only `commitSession.ts` family are deleted (D7).
2. **The op layer is the extension point.** `register_operation(name, parameters, handler, intent, singleton)`; built-ins register through it; schema branches, an ops listing and the contract page are generated from the registry. One composite op built from other handlers (`clip.ripple-delete`) proves it in phase 1. How the Runtime provider loads pack-registered ops is a TL-1 finding with a fallback.
3. **One op vocabulary in the App.** The editor extension SDK's `apply()` takes Agent ops through `sendIntent` (preview as a dry-run commit); the `TimelinePatch` vocabulary is retired.
4. **Agents can send ops.** One CLI verb takes a JSON command batch (`--dry-run`, `--json`, `--expected-head`), one MCP tool is generated from the registry, `timelines ops --json` lists the ops. TL-1 fixes one unit and naming convention (lean: integer milliseconds), as a clean break with no aliases.
5. **All writers.** A repo-wide lint forbids the `doc.patch` literal in the App; `placementService.ts` and `shotTimelineDataProvider.ts` convert (TL-10) or are named, dated exceptions; `applyEdit` requires an intent by type; TL-1 decides the non-remote fallback.
6. **`doc.patch` is a second tier through one door.** It stays for document routes; every invariant lives once, in `validate_final_candidate`, which both tiers hit; no generated per-field patch schema. A few raw-parity matrix rows (one per rule class) prove a `doc.patch` that an op would refuse is refused with the same code, or the rule is declared an op-only precondition.
7. **Refusals are a value.** The code list closes on the Agent side, reusing the envelope's `hint`, `suggested_command` and `status` (each entry declares its own `retryable`; `retryable` does not derive from `status`), with a falling ratchet on uncoded `CommandError` sites; headlines live once, in `_commit_wording.py`, with a generated App copy; `unsupported_operation` gets a headline (pin skew).
8. **Responsiveness.** A disposable preview and an ordered intent queue; adoption deferred during a gesture; a refusal returns to the last adopted head; a mismatch snaps and never refuses.
9. **One schema owner** (the Agent; Runtime copy generated; App digest literals deleted) and **one generated suite** (a seeded Agent generator; the Agent replays intents on real documents; the App side is a small gesture-to-op table test), wired into CI inside TL-15a.

Phase 2: Plan 18's original extension proof, one alternate view built only on those commands, using at least one pack-registered op with undo and a coded refusal. Alternatives rejected: keep patching the handoff (each fix adds a third model of the gesture); revive the TypeScript ports (it re-imports the design that failed: a parity test over a dual representation, where a drifting port produces `capture_mismatch`, the same bug class renamed); a Runtime-side "intent" service (the Runtime already delegates op meaning to the Agent, correctly); a generated per-field `doc.patch` schema (a derived copy of each rule); retiring `doc.patch` outright now (it is the lowering for every document-shaped route; its own migration); doing nothing (the same class of bug was filed repeatedly in one week: astrid-app #249, #252, #253, #254 and astrid-dev #635, #720, #732, #745, #769, #838, #839).

## Phase 0: the commit contract

Evidence and decisions for phase 0, added on 18 November 2026. Sources are the reviews and profiles of 17 and 18 November held by the Release 14 Lead (`fable-near-instant-review.md`, `fable-edit-refusals-deeper.md`, `plan-near-instant-commits.md` Rev 2, `near-instant-facts.md`, `sonnet-commit-profile.md`, `live-check-almost-ready.md`, `sonnet-unnamed-edits-on-shot-timelines.md`); they are private and not committed, so what matters is restated here as shapes and counts. Nothing in this plan copies content from the owner's timeline.

**The measured shape.** One timeline with shots, about 8 records and a closure of 7 shots, about 1 MB per revision and about 1,100 distinct stored objects. An uncontended add-media commit took 187 seconds (176 live); profiled, 280 seconds, of which about 190 were CAS re-verification (59 history read passes, 32,686 confirmations, 23,268 physical reads, the Agent loading the base 11 times) and about 80 were legacy timing probes (268 probes, 69 full compiles, each deep-copying the whole bundle). History was only 3 entries, so the reservation scan (2 + 3N closure loads per attempt) is a term that grows by three loads per edit. A clip move was refused after 85 seconds for a legacy declaration it never touched. The editor polls about 110 requests a minute per tab; a history GET took 8 to 9 seconds while holding the store mutex. The handoff has 69 refusal calls (33 with a literal code, 35 without) and about 50 of them re-derive what a named op already encodes.

**The root cause**, in the reviewer's words, restated: "nothing in the stack treats 'accepted' as settled." Each layer re-derives the accepted base from scratch against today's code, and a disagreement can only end in refusal. The five symptoms follow from it (plan.md lists them). It was logged only in pieces: #842 (the principle, closed after four rules), #852 (the editor side), #826 and #846 (cost), #732 (the stuck state), #847 (the same 400 at first start), Plan 54's principle "verify at a trust boundary once; inside a job, carry the digest" (written for generation jobs, per job and not per history), and `releases/12/decisions.md` (a sticky refusal fixed once at one site). Plan 59's handover records the writer-side lesson: "Data was accepted early and refused late." None made it a mechanism, and no test held a document with a history or with size.

**Approach.** Make the principle a mechanism with counts: a counted scaling test (CC-1) so no cost can scale with history again; a rule registry and one delta gate (CC-3) so no rule can re-judge an accepted head; typed reasons and per-change refusals (CC-4, CC-5) so a disagreement has an outcome other than a permanent refusal; one write-time admission (CC-6) so a writer cannot store what a reader refuses; one corpus (CC-7) that runs all of it. Alternatives rejected: a cache keyed by base revision (every ordinary edit creates a new base, so it only helps retries); a second resolver for the legacy probes called "equivalent" (the pattern the 17 November review named; the collect pass reuses the evaluator and the old probe stays as a test oracle); a clock gate (the owner forbids it); a new plan (this one is queued, unowned and already named by #852).

**Challenge:** Independent review by Opus (merge with edits), edits applied (18 November 2026; the report is `opus-phase0-review.md`, held by the Release 14 Lead). Its seven required edits are in this pack. Next: a further fresh reviewer may read the result against the code, briefed to build as little as possible (the same method as the 18 November critique of phase 1).

**Live findings of 18 November 2026** (owner's browser on :2400, read from IndexedDB `astrid.command-outbox`; shapes and sizes only): (1) outbox records are 2.6 to 10.6 MB each, because the whole before and after documents are stored per intent; (2) two editor sessions on one origin each held a pending intent on the same head, so the second gets `stale_head`, and `useTimelineSave.ts:395-399` reportedly throws when more than one owner has pending work at recovery (unverified: CC-5 reproduces it first). Reason: an intent is re-evaluated by the Agent against the new head; a patch is a whole-document claim that the other writer may have invalidated.

**D13 — Phase 1 session ruling, 18 November 2026, updated after the Opus review ("merge with edits") and the coordinator's ruling, both reviews weighed:** one rule home (CC-3's registry; `validate_final_candidate` runs the registered rules under the delta gate, no second list), and one closed refusal list owned by the Agent with one wording home (CC-4 creates it, TL-4 extends it; each entry declares its own `retryable`). CC-8's temporary ratchet stays; TL-12's check replaces it.

**D14 — Open (owner): persist verified trust across restarts (cold start).** Recommended: persist each verified object's `file_identity` (dev, inode, size, `mtime_ns`, `ctime_ns`) in the store database, so a restart does not re-hash every media object (about 8 s on one timeline, growing with media bytes; [#847](https://github.com/banodoco/astrid-dev/issues/847) first start lives here).
