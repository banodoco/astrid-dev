## SR-2: the generated page

**Membership.** Release briefs are taken in number order. The first of kind minor ships 0.1, the second 0.2, and so on; a major ships 1.0. A release belongs to the version shipped by the first minor or major release brief numbered at or after it; release briefs after the last of those belong to the next version. After the ninth minor, pending patches belong to 1.0 while awaiting its major (D13); no release may follow a major.

**The page.** `## Versions` keeps `### Version 1.0` and `#### Version 0.1` to `0.9`, so every existing anchor still resolves. Under each minor heading come the hand-written sentence (`**Aim:**`, or `Open`) and paragraph, then a marker pair `<!-- strategy-0.N:start -->` and `<!-- strategy-0.N:end -->` for all nine. D13 adds `<!-- strategy-1.0:start -->` and `<!-- strategy-1.0:end -->` under the existing major aim, before 0.1. Each generated part holds, per D11 and D13:
- the minor or major release: link, title, state and highlight;
- "On the way:" the patch releases as linked titles on one line;
- the plans of all those releases, one line each: release, plan name as a link, and the release brief's sentence;
- for each release with a frozen issue list, the number of rows, linking to it;
- or `No release yet.` when the version has none.

The `## Sequence` section, its table and the `**Plans:**` and `**Releases:**` lines go. Each "Why this order" sentence moves, word for word, to the end of its release brief's Intent.

**The checks.** `strategy_errors` removes everything between marker pairs before it reads headings and fields, so a generated part is never read back. Kept: the required sections without `## Sequence`; the `Last reviewed` line; one major version with an aim; the nine minor versions in order, each with a sentence or `Open`. New, in the always-on check so the message is readable: all ten marker pairs are present; the release briefs do not declare more minor releases than the page has versions; a major release brief is the last. Removed: the sequence-table rules, the `Plans` and `Releases` rules, the one-version rule for a plan (Plans 29 and 40 are each in two releases), and the rule that a plan completion edits `strategy.md`.

- **Rows.** `python3 scripts/release_issues.py <N>` adds a row for each open astrid-dev issue labelled `plan:NN` for a plan the release brief includes, or `release:<N>`. `Type` is one of the four types, or `—` for an issue with no type label. `State` is `open`, `done`, `decided not to act` or `duplicate`, the guide's own words. `Via` lists the labels that brought it in. Rows are sorted by number. Nothing else is written from an issue, and no line in the block starts with `## `.
- **Rows stay.** A run adds new matches and refreshes the state of rows already there. It never removes a row; a person removes one by hand. Before the freeze a removed row returns at the next run while its issue is still open and labelled.
- **The date** changes only when a row changes.
- **The freeze.** `--freeze` refreshes the states once more and replaces the first line with `Frozen on <date>.` After that the command refuses to rewrite the block. The release manager removes the rows that are not shipping in the pull request that makes the release brief Final; the owner's approval of that pull request is the decision.
- **When.** When the release is first planned, at check-ins, and at the freeze (D3).
- **Renumbering** is SR-7's text in the Release skill, not this command.
