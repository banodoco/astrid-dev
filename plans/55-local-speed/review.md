# Independent review — Local speed

[Plan](plan.md) · [Inputs](inputs.md)

An Astra review of the starting hypothesis, run on 15 November 2026 against astrid-agent `a91c35dfd`, VibeComfy `dba38f86`, Runtime `6855dfa8`, ComfyUI `6bfaacc` and astrid-app `d6ee9af2`. **Verdict:** pursue a resident local executor, but do not promise “IPC plus GPU time” or treat deferred recording as an equivalent implementation of today's result contract. Below 100 ms is credible for a bounded warm workload; it is not a universal bound for user-owned ComfyUI, arbitrary workflows, or large media.

**1. Work that cannot disappear**

Budget assumptions: warm CPU/imports/connections, idle local SSD, modest graph (tens to hundreds of nodes), already admitted inputs, one small output, no competing GPU job. Values are milliseconds unless stated otherwise; individual ranges are not percentile guarantees.

| Necessary work | Linux | Windows | What determines the cost |
|---|---:|---:|---|
| Resident request/reply transport, framing, scheduling | 0.2–2 | 0.5–5 | Persistent authenticated loopback or native IPC; no discovery/handshake per job |
| Validate invocation, authorization/epoch, allocate job identity, deduplicate | 0.1–2 | 0.2–3 | Memory lookup plus bounded request validation; permissions still apply per request |
| Cache lookup, bind inputs/seed/output namespace, serialize exact prompt | 0.2–5 | 0.5–8 | O(graph + input bytes); full compilation is a miss cost outside this budget |
| HTTP POST, Comfy validation, enqueue and wake worker | 1–10 | 2–20 | Custom `INPUT_TYPES`/`VALIDATE_INPUTS` can make this arbitrarily slower |
| Queue wait | 0 idle; otherwise unbounded | Same | Another caller or the person's ComfyUI tab can occupy the GPU |
| Execute graph, decode/encode/write its outputs | Workflow-dependent | Workflow-dependent | Subtract the *whole Comfy execution interval*, not just GPU kernels |
| Receive terminal push, retrieve authoritative history once, validate output descriptors | 1–8 | 2–15 | Completion notification alone contains insufficient result evidence |
| Establish stable output ownership + digest, for one 1 MiB file | 1–8 | 2–20 | Optimized single ingestion; excludes storage flush; current code does more passes |
| Durable job/result metadata, one short commit | 0.3–5 | 1–15 | Assumed local SSD; flush/checkpoint/antivirus tails can exceed 100 ms |
| Flush newly owned output bytes and publish directory entry | 0.5–10 | 1–20 | Small file assumption; ordering and platform implementation matter |
| Format result and deliver to caller | 0.1–1 | 0.2–2 | Excludes terminal rendering by an interactive shell |

New input media must also become stable and accessible to ComfyUI. This is zero extra bulk transfer only for a previously admitted, reusable asset; otherwise budget bytes/throughput plus opens, verification and upload. The attached path currently reads/hashes/uploads each asset (A `astrid/core/generation/backends/comfy_target.py:321`; A `astrid/packs/vibecomfy/local_server_engine.py:453`).
For large outputs, even a single serial copy-and-hash at roughly 0.3–2 GB/s costs about 50–330 ms per 100 MB; Windows filter drivers and additional passes can be worse. A path-sized response does not make ownership of those bytes constant-time.
A fresh CLI additionally needs process creation, runtime imports, argument parsing, endpoint discovery and authentication: budget **3–20 ms Linux / 10–60 ms Windows** for a genuinely tiny native client, or **25–150 ms / 80–500+ ms** for a minimal Python client. The current full Astrid CLI is not that minimal client; a new CLI also is not an “already connected caller.”
Define the metric explicitly: `caller elapsed − this prompt's Comfy execution interval` includes admission, queue wait, input transfer and result publication. Report queue wait separately, but do not silently subtract it. Comfy's current timer includes execution/history completion work (C `main.py:352`, `main.py:367`, `main.py:377`).

**2. Attack on the proposed fast path**

**Resident owner and connection.** Use the Runtime-supervised Agent pack host as the authority-facing owner, with a dedicated resident Comfy transport/executor component; keep arbitrary pack code outside the Runtime database service. Runtime should retain admission, fences and publication. There is already a resident host and concurrent claim slots (A `astrid/core/execution/generic_host.py:14629`, `generic_host.py:14786`). A separate independently elected daemon creates a second owner and update/recovery problem.
Simply retaining the existing client fails: `ComfyTargetClient` deliberately permits **one prompt total per instance**, including failed acceptance, and keeps witnessed prompts on that instance (A `astrid/core/generation/backends/comfy_target.py:104`, `comfy_target.py:267`). Separate reusable HTTP/WS transport from per-attempt submission state; never reset the shared “attempted” flag between concurrent jobs.
The current adapter sends only `{"prompt": prompt}` and waits on history, so having a watchdog websocket is insufficient (A `astrid/core/generation/backends/vibecomfy_local_server.py:34`; V `vibecomfy/runtime/session.py:4178`, default interval at `:4204`). Connect WS first, retain HTTP connections too, submit its `client_id`, and dispatch by prompt ID. C `server.py:1120` routes that client identity; reusing a websocket client ID replaces the old connection (`server.py:273`).

**Push is a wakeup, not the whole result.** C `execution.py:824` emits `execution_success` before constructing `history_result`; C `main.py:367` publishes history and only then emits `executing(node=None)` at `:374`. Prefer the latter as the history-ready wakeup in this version, then read/validate history; handle failure, interruption and cached nodes too. Retain bounded fallback reconciliation after disconnect or incompatible server behavior. V `vibecomfy/runtime/run.py:779` already validates declared sinks and terminal status: preserve that meaning.
The websocket initial state supplies queue status and sometimes the current node, not a replayable completion log (C `server.py:285`). Comfy history is bounded in-memory state (C `execution.py:1321`) and can be cleared (`server.py:1206`). A lost event or restart cannot be repaired by assuming “no history means never ran.”

**One caller message.** One logical invocation is achievable after session setup, but progress, cancellation, reconnect and completion are additional messages. Carry a request ID/idempotency key, realm/session epoch, capability identity and bounded inputs; use OS ACLs/peer identity or the existing authenticated local transport. A direct SDK/agent must get the same admission and result semantics as CLI/App; bypassing the task authority is not an IPC optimization.
There are at least three polling points to remove or bypass: host idle claim (`A generic_host.py:14688`), VibeComfy history (`V session.py:4204`), and SDK await (`A astrid/sdk/invocation.py:3656`, default `:3674`). A faster inner runner alone leaves outer one-second quantization.

**Caching with varying inputs.** Cache immutable canonical graph/templates plus a validated binding plan. Key by canonical workflow/source closure, compiler/adapter version, variant, target schema/epoch, model mapping and authorization policy. Bind and validate prompts, seeds, dimensions, model selectors, staged input identities and unique output prefixes per invocation; freeze the resulting request before POST. Cache an exact compiled prompt only when *all* semantic bindings match. Do not mistake repeated workflow identity for repeated execution identity.
This needs a VibeComfy API change, not a dictionary around `compile()`: `ApprovedProjectionRecord` requires exact input equality and recompiles the live bundle to defeat forged records (V `vibecomfy/workflow_bundle.py:2003`, `:2020`); compilation also rebinds the bundle (`:2759`). A new admitted immutable-template/binding contract must preserve that protection without rereading/re-emitting Python every time.
Changing seeds or text can be cheap binding; changing topology, variant, models, dynamic/custom-node behavior or executable Python can require recompilation. Arbitrary Python workflows may depend on files/time/environment; only a frozen evaluated IR with explicit dependencies is cacheable. Keep a cold path for unsupported builders.
Output-prefix binding is correctness work: A `astrid/packs/vibecomfy/local_server_engine.py:258` explicitly prevents reuse of SaveImage's previous cached result. It currently emits and reloads a bundle for this (`:326`, `:337`). Replace that emission with an in-memory, attempt-scoped binding; never reuse an old filename or seed accidentally.

**“Verify only at state change” needs an observable state owner.** Astrid owns its installed snapshots; it does not own the person's ComfyUI. Nodes can change at restart, models can be added/replaced in-place, paths can change, and custom nodes can load external resources without changing their schema. `/object_info` proves advertised types/choices, not model bytes or executable identity. Comfy's filename cache checks directory mtimes (C `folder_paths.py:489`); same-name content replacement is not a reliable schema change.
On WS loss, stop new fast admissions, increment a target generation, reconcile outstanding prompts, reconnect, refetch relevant schemas/model choices and invalidate target-dependent entries. Bind target generation to both HTTP and WS; an old socket plus a new listener on the same port is not proof of one server instance. Standard handshake data above has no durable server incarnation token. A small optional Comfy extension could supply one and an explicit revision protocol.
Filesystem watchers/dirty bits and background refresh are useful invalidation hints; overflow, races and same-content-name replacement prevent them from proving an unchanged uncontrolled tree. Safe optimistic behavior is: per-request bounds and authorization, server-side validation on POST, slow-path refresh after a definite validation rejection, and honest “target identity unverified” evidence. Do not retry after uncertain acceptance. Strict byte-verified execution requires controlled immutable versions or cooperation from the producer; polling `/object_info` faster cannot establish it.
For Astrid packs, verify once when admitting an immutable snapshot, retain the verified bytes/digest, and switch generations atomically on install/update. Current discovery intentionally hashes complete trees even within request-local caching (A `astrid/core/pack/discovery.py:59`, `:77`); import admission repeats pack digests (A `astrid/core/pack/imports.py:151`, `:204`, `:210`). Managed source checks run git per checkout (A `astrid/core/pack/source_setup.py:263`, `:403`). Replace live-tree assumptions before deleting these checks; memoizing a mutable path/mtime is not equivalent custody.

**“Return the output path” is not today's result.** Attached targets explicitly do not grant local filesystem access (A `astrid/packs/vibecomfy/local_server_engine.py:426`). `AttachedArtifacts` retrieves only outputs attributed to a witnessed prompt via `/view` (A `astrid/core/generation/backends/vibecomfy_local_server.py:55`). SDK results expose managed output associations/handles, not merely producer filenames (A `astrid/sdk/results.py:194`, `:234`).
Runtime settlement requires SHA-256 and either supplied bytes or an existing CAS object (R `runtime_protocol/service.py:9148`, `:9193`). It currently verifies, copies, hashes and verifies again at publication (`:9452`, `:9477`, `:9483`, `:9609`). A raw Comfy pathname cannot substitute for this contract. Comfy SaveImage returns filename/subfolder/type and writes an ordinary mutable file (C `nodes.py:1693`, `:1711`).
Cheapest equivalent result: one ingestion into private immutable Runtime custody, hash once while ingesting, then publish managed association + local CAS path. Remove redundant reads only when the publisher retains trusted ownership evidence. Reflink can save copying where supported; it does not supply SHA-256. Hardlinks and open file descriptors do not freeze file contents. Rename does not revoke an existing writer; cross-volume rename is not available.
True zero-copy needs a cooperative output sink that writes into a private, uniquely allocated destination and hands off a closed/finalized object with trustworthy digest evidence. That is a producer/Runtime contract and may not fit arbitrary custom save nodes. Otherwise offer a distinctly **borrowed, mutable, non-durable output** only if the owner accepts new semantics; it must not masquerade as an existing managed result. Windows sharing modes, reparse points, delete/rename races and cross-volume outputs deserve explicit treatment.

**The child process is doing more than startup overhead.** Its documented role is pack execution with admission/publication left in the parent (A `astrid/core/execution/generic_host_worker.py:1`); it validates captured source/identity (`:26`, `:228`). The parent constructs a restricted environment, network policy and owned task process scope (A `generic_host.py:10633`, `:10781`, `:10801`). This provides killable lifetime, isolated imports/globals, source-version selection and limited authority; it is not proof that all Python is sandboxed.
Current pack imports explicitly assume one interpreter per action (A `astrid/core/pack/imports.py:190`). Current local execution mutates process environment and signal handlers (A `local_server_engine.py:478`, `:577`). Running that function concurrently inside the privileged host is incorrect. Refactor the trusted transport to explicit per-job state, or use a supervised resident helper per admitted code generation; retain disposable children for arbitrary pack/Python execution. Windows task-scope machinery already uses Job Objects (R `runtime_protocol/platform.py:721`); do not kill the shared executor to cancel one prompt.

**Second caller, cancellation, progress.** Use bounded per-target admission, unique request/prompt/output IDs and a prompt-to-owner map; serialize only state that requires it. Shared ComfyUI queue time remains outside Astrid's control. Slow subscribers must not block execution: coalesce progress, bound buffers, retain terminal state for reconnect, and distinguish client disconnect from explicit cancel.
Cancel a queued owned prompt by ID; cancel a running prompt only with an atomic targeted server operation. The Agent currently checks `/queue` then calls `/interrupt` (A `comfy_target.py:307`); the inspected `/interrupt` checks then interrupts without the newer queue-lock helper (C `server.py:1163`). This can race into somebody else's next job. This checkout's `/api/jobs/{job_id}/cancel` handler uses `interrupt_if_running` (C `server.py:950`, `execution.py:1358`): capability-negotiate it; older user servers need a safe fallback/refusal, never a global interrupt. Cancellation and settlement must race through one terminal authority/fence.

**Crash mid-job.** Record request identity, exact bound prompt digest, target generation and acceptance state. Persist intent before POST if restart recovery/no-silent-orphan behavior is promised. The present transport correctly refuses resubmission after lost acknowledgement (A `comfy_target.py:270`, `:294`); cleanup also recognizes the pre-acceptance journal gap (A `vibecomfy_local_server.py:142`).
This Comfy version accepts a client-generated UUID (`C server.py:1093`) but the POST path then enqueues it without deduplication (`:1134`): a chosen ID helps reconciliation, not exactly-once execution. Reconcile queue/history after daemon failure; if both server history and acknowledgement are lost, expose outcome-unknown and require an explicit retry decision. Exactly-once across two independent processes needs server-side durable deduplication/cooperation, not just a daemon WAL. A Runtime restart must fence the old executor from publishing.

**Update/version skew.** Pin the daemon's loaded code generation for active jobs; do not hot-reload imported pack modules. Negotiate protocol/features/result schema and realm/daemon epoch once at connection, reject incompatible requests before enqueue, and re-handshake on reconnect. Drain or explicitly fence old jobs during update and keep their selected code until recovery finishes. App already checks Runtime instance/protocol/schema/actor/realm (P `scripts/dev-local-workspace.mjs:448`, `:470`); installer pins Agent/Runtime/VibeComfy together (P `scripts/installer/pin.mjs:95`). A thin-client protocol must participate in these pins and support an explicit compatibility window; a package version string is insufficient.

**3. What stays, and the Runtime decision**

Keep source/attempt/output custody, per-invocation authorization and cancellation fences, exact input/seed provenance, declared output ports, stable managed output identity, and atomic result/effect publication. Keep explicit install decisions: a missing node/model invalidates readiness and asks for the existing install/repair decision; fast execution must not silently mutate the person's ComfyUI. Move catalog scans, source verification and executable preparation to snapshot admission, not authorization checks or new-output ingestion.
Keep durability with a precise promise: process-crash recovery and power-loss durability are different. Durable success requires output bytes and directory publication to precede the durable terminal record, plus replayable identity/effect metadata. A durable DB row pointing at an unflushed or mutable output is insufficient. Batch/group commits and one journal/transaction can reduce flushes; 100–300 ms is neither a fundamental durability floor nor a guaranteed ceiling. R `store.py:1220` commits transactions, `:1525` selects WAL; R `platform.py:184` skips directory fsync on Windows and `:195` uses write-through replacement. Validate the actual Windows publication path before making power-loss claims.
**No Runtime change is needed to prove transport/compiler savings, or initially to keep existing create → claim → settle.** Schedule claims promptly from the host, remove unnecessary immediate renewal when the fresh lease already suffices (A `generic_host.py:12201`), and retain renewal for long jobs. Existing transactions may already fit the small-output budget on good storage; measure before redesigning them. Move thumbnails off the completion path: they are currently derived synchronously before settlement (A `generic_host.py:13513`), while Runtime already recognizes `generation.thumbnail.attach` (R `store.py:6176`).
**“Record after success” cannot preserve the existing public success contract with unchanged Runtime.** Settlement requires an existing live attempt, lease/fence/current epoch and predeclared effect (R `service.py:8683`, `:8718`, `:8723`); managed associations and project effects appear atomically at settlement (R `store.py:6161`, `:6220`). Creating/claiming afterward either repeats the old work later or bypasses admission/reservations during execution. Returning early changes observable result, cancellation, failure and crash behavior; it is not merely moving bookkeeping.
If the owner chooses provisional availability followed by durable publication, a host outbox can replay **existing** Runtime operations without a new endpoint, but authority must still be obtained before execution and callers must see a distinct provisional result. A durable outbox also needs a flush. Do not claim a completed Runtime task/managed handle until settlement acknowledges it.
For the full low-overhead contract, I would design Runtime **combined local admission+claim**, then one idempotent terminal-publication request accepting a trusted staged-object handoff and committing output associations, effects, task/run state and replay receipt together. Existing settlement already does much of the latter; remove its redundant byte passes through a narrowly scoped custody proof. R `service.py:8859` restricts today's verified-object shortcut to the media-import executor; it cannot simply be reused by a pack.
A one-shot **post-hoc record** endpoint is useful only if Runtime previously delegated bounded session authority (capability, policy, resources, epoch and allowed effects) and can authenticate the execution receipt. It must atomically deduplicate request+payload and publish all result/effect state; it is not an unrestricted “mark completed” door. It still cannot recover an unrecorded pre-POST intent. One caller request can span two durable boundaries; one transaction cannot safely stay open across GPU execution. Prefer preserving admission + terminal publication over inventing a weaker task lifecycle to save a few milliseconds.

**4. Floor I would plan around**

| Caller, optimized warm path | Linux expected budget | Windows expected budget |
|---|---:|---:|
| Resident SDK/agent/App, borrowed/provisional small output | 5–25 ms | 10–50 ms |
| Resident caller, small managed output, optimized durable admission/publication | 15–70 ms | 25–120 ms |
| Fresh tiny native CLI, same managed result | 20–90 ms | 40–180 ms |
| Fresh minimal Python CLI, same managed result | 40–220 ms | 100–620+ ms |

These are attainable planning ranges, not predictions for the current code or p99 commitments. Add queue wait, new-input transfer, large-output ingestion and cold compilation. An App UI may add a display-frame delay after the API returns. I believe **under 100 ms is plausible for resident callers on both OSes**, with Windows tail latency still unproven; I would not promise it for every fresh CLI or arbitrary workload.
The three most likely blockers are **(1)** bulk input/output custody, hashing and durable publication; **(2)** cache misses or retained workflow emission/source/schema validation, especially arbitrary custom-node validation; **(3)** Windows process startup, filesystem/filter-driver and scheduling tails. Independently, any competing Comfy job can violate the target through queue wait even if Astrid adds almost no CPU work.

**5. Build order and design-review gates**

1. First spike: resident minimal client + reusable HTTP + WS against the actual supported ComfyUI on Linux and the testers' Windows machines; prepared API graph, cached input, tiny output, no pack discovery/emission. Measure POST/validation, queue, Comfy execution, history visibility and return separately. Compare instant stand-in, real trivial graph, and warm-model graph; do not infer real validation cost from the stand-in. This spike proves only the transport floor.
2. Add the existing Runtime lifecycle and real managed-output publication unchanged to that spike, measuring each boundary; compare 1 MiB image and large video, one/two callers, native/Python CLI. Record p50/p95/p99 and bytes/flush counts, including Defender enabled. This establishes whether a Runtime redesign is actually necessary and prevents a misleading path-only win.
3. Introduce immutable admitted workflow snapshots and typed binding in VibeComfy; eliminate Python emission/reload for per-job values. Prove changed prompt/seed/model/variant and output namespace produce the intended distinct submissions. Cache inventories and schemas by admitted generation; retain a slow path on misses and dirty state.
4. Integrate the resident component with the existing pack host, refactor environment/signal globals, wake claims and SDK waiters promptly, stream bounded progress, and defer thumbnails. Keep ordinary pack children until the isolated resident-helper contract is proven.
5. Only then combine Runtime admission/claim and optimize one-pass publication if measurements require it. Exercise crash before POST, lost acceptance, crash after output/before commit, replayed settlement, cancellation crossing completion, WS restart, model replacement, watcher overflow and old-client/new-daemon update. Re-run Windows artifact mutation/sharing and cancellation tests against supported user Comfy versions.

Review **before implementation**: immutable-template approval versus executable Python; target generation/invalidation and honest verification claims; prompt ownership/idempotency/cancellation on older ComfyUI; stable output handoff and Windows publication durability; resident-helper authority/isolation; Runtime admission/effect atomicity and update draining. These are changes to guarantees, not local performance refactors.

**6. Decisions only the owner can make**

- Whether “success” means durable managed result, provisional availability, or a borrowed mutable path; which existing SDK/App guarantees may change, and acceptable crash-loss window.
- Whether 100 ms is a median or tail SLO, which Windows hardware/security setup it covers, and the supported graph/media-size bounds; queue wait must be reported explicitly.
- Whether the user's ComfyUI may require an optional extension/minimum version for atomic cancellation, instance identity, deduplication or private output handoff, versus preserving compatibility with uncontrolled servers.
- Whether unverified user-managed model/node identity is acceptable on the fast path, or strict byte identity requires a managed immutable execution environment; filesystem watching cannot make that product decision.
- Whether to ship/maintain a native thin CLI, how long old clients remain compatible, and whether updates drain, postpone or cancel active jobs.
- Whether execution should continue after the caller disconnects, and what the product presents when acceptance or completion cannot be recovered; automatic rerun must not be the accidental default.
