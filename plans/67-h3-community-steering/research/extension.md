# Plan 66 extension test: ten neighboring capabilities

Read-only research, 18 Nov 2026. This tests whether ten adjacent H3 capabilities can be represented with the proposed three families and six compiler mechanisms. “Exists” means source/schema evidence, not that an Astrid request compiler already exposes it or that quality was tested. Node source: [ComfyUI `nodes_minimax_h3.py` at 6bfaacc](https://github.com/Comfy-Org/ComfyUI/blob/6bfaacc/comfy_extras/nodes_minimax_h3.py); extension source: [H3 Motion Context MultiRef at 361624fb](https://github.com/seitanism/ComfyUI-H3-Motion-Context-MultiRef). Local evidence includes `comfy_extras@zz-official-6338e4bd.json` and `ComfyUI-H3-Motion-Context-MultiRef@cpu-runtime.json`. Plan definitions: `research/levers.md` and `research/skill-draft.md`.

## Result

The three families and six mechanisms cover all ten as controls inside one H3 pass. **Two qualifications:** multi-pass upscaling is a sequence of jobs, outside the single-job lever grammar; audio-to-video has a product/task distinction that needs an explicit generation mode or second entry point if it means soundtrack-conditioned video rather than joint AV generation. Neither calls for a seventh *merge mechanism*. CFG/guidance scheduling is the least established: there is no negative/CFG input in the inspected H3 nodes, and an implementation may require model-specific conditioning logic. Never claim unsupported capabilities merely because the grammar can name them.

The current official source exposes first/last frames as endpoint keyframes, arbitrary image/audio guides at a frame, image/video/audio reference slots, AV latent generation, and video/audio sigma shift. `MiniMaxH3AddGuide` appends `minimax_keyframes`; references become `minimax_refs`; conditioning is tokenized with the prompt (`nodes_minimax_h3.py` lines 105–218, 221–335). Fun ControlNet has an H3 model-patch implementation with strength and start/end percent inputs (lines 376–537). The extension cache confirms fractional video/audio denoise masks and source commits (cache JSON lines 2–29). These facts show useful lowerings, not universal support for every adapter or control type.

## Cross-family cases and reservations

- **Genuinely cross-family:** soundtrack can be Context audio guidance or exact Output audio ownership; mid-shot keyframes are exact Output placement or soft Context guides; IC-LoRA can be Process plus a required Context reference; camera/control may pair Process control with Context text. Represent dependencies explicitly (`requires`/`conflicts`) in the per-kind capability row. Do not make a lever belong to two families just because it references another lever.
- **No seventh mechanism indicated.** The six mechanisms remain latent/ownership mask, timed rows, untimed rows, text, model chain, sampler. Add kinds and merge functions to existing mechanisms. The only “new structure” suggested by this sample is job sequencing for multi-pass workflows, which belongs above a single H3 request and should not be smuggled into a seventh per-pass mechanism.
- **Reserve now:** stable `stream` and separate clip-time `during` from denoising `phase`; optional `params` per kind; `negative_prompt` as a distinct text channel if H3 supports it; prompt list form; `control` with phase bounds; references by stable IDs plus `requires`; audio ownership/edit granularity and exact composition; pass/job input-output links outside request; capability rows must say `unavailable`/`unverified` separately from `compiles` and `live-tested`.
- **Do not promise:** arbitrary conditioning per timestamp, IC-LoRA, camera trajectory, negative prompts/CFG, arbitrary exact keyframes, audio-word masks or exact soundtrack, until the H3-specific lowering and limits are evidenced. “Fits the grammar” is not “exists in MiniMax H3.”
