# Release 14 — Stability and elegance

**State:** Final
**Release manager:** the Release 14 [Lead](../skills/roles/astrid-dev-lead/SKILL.md), session `session_011EzfW3Zy19ncNecpQnKb7D` (named by the owner on 16 November 2026)

## Highlight

What Astrid already does, it does one way and dependably: a generation runs dependably on your own computer, a real video is finished with Astrid's own tools, and a green check means it works.

## Intent

Release 13 made generation work through one path. Using it, and the two Windows tester runs, showed where Astrid is slow, breaks, or does one job in several ways. This release fixes those at their cause and adds no capability. A good outcome has four parts:

- **Fast.** Speed moves to Release 15. Release 14 makes no speed claim. [Plan 55 decision](https://github.com/banodoco/astrid-dev/issues/796#issuecomment-7061778603)
- **Proven by real work.** Astrid's own editing and generation tools are proven on the release candidate: the live GPU cases (speaker references, masked mouth edit, still start frame, continuation, dynamic size), and every blocker found is fixed at its cause or filed. Finishing Into the Minkhole, and a weaker agent repeating the edit on another timeline, are NOT a publication condition. The film is finished with Release 14 after it publishes (owner, 21 Nov, about 19:20 UTC: "That shouldn't be a requirement... shouldn't hold this back.").
- **No new red against Release 13.** On the frozen tuple, one full CI per repository shows no unexplained pass-to-fail against published Release 13, by job and test ID. Tests red on both are the inherited list, committed in astrid-dev, which may only shrink. A missing ID counts as red until explained. Two parts of the original promise move to Release 15: every test runs, and every new failure is caught on every pull request (Plan 39's per-ID ceiling). [Owner decision](https://github.com/banodoco/astrid-dev/issues/796#issuecomment-7067000167)
- **One way to do each job.** The rules below hold for everything this release touches.

Hannah set this theme on 16 November 2026, in place of "Local speed": local speed was then the largest design in the release. It follows her decision of 15 November 2026 that version 0.1 is "focused on hardening, updates, stability and speed", with fixes and plans added on the fly from actual usage and user reports. See [Strategy](../strategy.md#decisions).

The slowness and the red tests are the two roughest edges Release 13 ships with, and Release 14 addresses the failures first: the release branch cannot be trusted until it is green ([#742](https://github.com/banodoco/astrid-dev/issues/742)).

## Approach

**What elegance means here.** Six rules from the second Windows tester run ([#727](https://github.com/banodoco/astrid-dev/issues/727)) and the four causes behind nearly every Release 13 failure ([#580](https://github.com/banodoco/astrid-dev/issues/580)) are the test for any change in this release: one implementation for each job; one owner for each fact; each limit declared once and known to both sides; messages carry references, not content; an unknown failure stops and says why, and is never retried forever; work that takes minutes is a task; and a contract is checked before a rented GPU or a person's computer finds it broken.

**Four strands, at the same time.** They touch different code, so none waits for another.

1. **Local speed (moved to Release 15)** ([Plan 55](../plans/55-local-speed/plan.md)). Designed from the work a warm local job fundamentally needs, not by trimming today's path: a resident session, a workflow prepared once, completion by push, checks only when the installation changes, and a default-delete list of everything else. Rented-machine speed is out of scope.
   21 Nov 2026 — The remaining speed work and its claim move to Release 15. The target is under 1 s of Astrid overhead. Keep the plan branch separate from Release 14. Before more speed code, profile 20 back-to-back SDK and CLI jobs on Release 13, plan-55 `e3795656` and the #408 head. Use real ComfyUI with its custom nodes, the default 1 MP workflow and a warm model, with one wall-clock profile on a rented GPU within the Lead’s $10 cap. The warm path may check size, mtime and inode, with content hashed at install or admit. [Plan 55 decision](https://github.com/banodoco/astrid-dev/issues/796#issuecomment-7061778603) · [Owner decision](https://github.com/banodoco/astrid-dev/issues/796#issuecomment-7061951208)
2. **A real video, finished** ([Plan 59](../plans/59-into-the-minkhole-proof-point/plan.md)). A work loop: take the next creative task, attempt it with Astrid's own tools, fix each blocker at its cause or file it, and write down what a weaker agent needs to repeat it. No workarounds.
3. **Green** ([Plan 39](../plans/39-green-mains/plan.md), phases 1 to 3). First make every test run: on 16 November the Runtime's unit job had 1,010 tests that errored before they ran, at least 718 of them for want of an Agent checkout or git history. Then fix what is left by cause, never by loosening a test. Then keep it green with required checks, one quarantine rule and a nightly report. It lands on `release/14/main`, and reaches each `main` when the release is published. Its [Release 14 scope](../plans/39-green-mains/evidence/release-14-record/plan.md#release-14-scope) says how the work fans out and what it leaves alone. The structural fixes and the release rule stay in [Release 15](15.md).
4. **The execution host, mapped** ([Plan 13](../plans/13-execution-host-refactor/plan.md), its first two steps). `generic_host.py` is 18,784 lines and Plan 55 changes it in three tasks. This release maps its responsibilities and pins their behaviour with tests, so the resident session arrives as a module of its own; the extraction waits for Release 15, after the fast lane has landed.

Where Plans 55, 39 and 59 stood on 16 November, what is proven and what each one's next manager does, is in its handover: [Plan 55](../plans/55-local-speed/handover.md), [Plan 39](../plans/39-green-mains/evidence/release-14-record/handover.md), [Plan 59](../plans/59-into-the-minkhole-proof-point/handover.md).

Also in the release: the last tasks of issue intake ([Plan 52](../plans/52-issue-intake/plan.md)), which is the route for user reports, and the vision's aspirations ([Plan 53](../plans/53-vision-aspirations/plan.md)), which includes tidying the vision page on the website.
