# Release 14 — Stability and elegance

**Release:** 14
**State:** Draft
**Release manager:** not yet named

## Highlight

What Astrid already does, it does one way and dependably: a generation on your own computer comes back in about the time the model takes, a real video is finished with Astrid's own tools, and a green check means it works.

## Intent

Release 13 made generation work through one path. Using it, and the two Windows tester runs, showed where Astrid is slow, breaks, or does one job in several ways. This release fixes those at their cause and adds no capability. A good outcome has four parts:

- **Fast.** Under 2 seconds of Astrid's own time for every caller on a person's own ComfyUI, and under a tenth of a second for a caller that is already connected, measured by a standing test on every build.
- **Proven by real work.** Into the Minkhole is finished through Astrid's own tools, every blocker fixed at its cause or filed, and a weaker agent repeats the edit on another timeline.
- **Green means working.** Every test runs and passes on `release/14/main` in Agent, Runtime and App, the checks are required on every pull request, and a new failure is told from an old one without a re-run.
- **One way to do each job.** The rules below hold for everything this release touches.

Hannah set this theme on 16 November 2026, in place of "Local speed": local speed stays, as the largest design in the release. It follows her decision of 15 November 2026 that version 0.1 is "focused on hardening, updates, stability and speed", with fixes and plans added on the fly from actual usage and user reports. See [Strategy](../strategy.md#decisions).

The slowness and the red tests are the two roughest edges Release 13 ships with, and neither can wait for the other: the release branch cannot be trusted, or a tester build cut from it, until it is green ([#742](https://github.com/banodoco/astrid-dev/issues/742)).

## Approach

**What elegance means here.** Six rules from the second Windows tester run ([#727](https://github.com/banodoco/astrid-dev/issues/727)) and the four causes behind nearly every Release 13 failure ([#580](https://github.com/banodoco/astrid-dev/issues/580)) are the test for any change in this release: one implementation for each job; one owner for each fact; each limit declared once and known to both sides; messages carry references, not content; an unknown failure stops and says why, and is never retried forever; work that takes minutes is a task; and a contract is checked before a rented GPU or a person's computer finds it broken.

**Four strands, at the same time.** They touch different code, so none waits for another.

1. **Local speed** ([Plan 55](../plans/55-local-speed/plan.md)). Designed from the work a warm local job fundamentally needs, not by trimming today's path: a resident session, a workflow prepared once, completion by push, checks only when the installation changes, and a default-delete list of everything else. Rented-machine speed is out of scope.
2. **A real video, finished** ([Plan 59](../plans/59-into-the-minkhole-proof-point/plan.md)). A work loop: take the next creative task, attempt it with Astrid's own tools, fix each blocker at its cause or file it, and write down what a weaker agent needs to repeat it. No workarounds.
3. **Green** ([Plan 39](../plans/39-green-mains/plan.md), phases 1 to 3). First make every test run: on 16 November the Runtime's unit job had 1,010 tests that errored before they ran, at least 718 of them for want of an Agent checkout or git history. Then fix what is left by cause, never by loosening a test. Then keep it green with required checks, one quarantine rule and a nightly report. It lands on `release/14/main`, and reaches each `main` when the release is published. Its [Release 14 scope](../plans/39-green-mains/plan.md#release-14-scope) says how the work fans out and what it leaves alone. The structural fixes and the release rule stay in [Release 15](15.md).
4. **The execution host, mapped** ([Plan 13](../plans/13-execution-host-refactor/plan.md), its first two steps). `generic_host.py` is 18,784 lines and Plan 55 changes it in three tasks. This release maps its responsibilities and pins their behaviour with tests, so the resident session arrives as a module of its own; the extraction waits for Release 15, after the fast lane has landed.

Also in the release: the last tasks of issue intake ([Plan 52](../plans/52-issue-intake/plan.md)), which is the route for user reports, and the vision's aspirations ([Plan 53](../plans/53-vision-aspirations/plan.md)), which includes tidying the vision page on the website.

**The standing lane.** From the Windows tester run of 15 November 2026, where a tester got image, edit and music generating on Windows for the first time: a watchdog that writes thread stacks to the log when a task makes no progress ([#669](https://github.com/banodoco/astrid-dev/issues/669)); the short generation folder left behind for kept or crashed attempts ([#670](https://github.com/banodoco/astrid-dev/issues/670)); a result file path too long for user names over 36 characters ([#671](https://github.com/banodoco/astrid-dev/issues/671)); shorter install paths ([#672](https://github.com/banodoco/astrid-dev/issues/672)); a path-length test ([#673](https://github.com/banodoco/astrid-dev/issues/673)); the Runtime permission check that misfires on Windows ([#674](https://github.com/banodoco/astrid-dev/issues/674)); the folder-permission message during install ([#675](https://github.com/banodoco/astrid-dev/issues/675)); VibeComfy loading its node library and numpy to read one constant ([#676](https://github.com/banodoco/astrid-dev/issues/676)); and the unverified leads from the code hunt ([#677](https://github.com/banodoco/astrid-dev/issues/677)). From the second run: saves the Runtime rejects ([#720](https://github.com/banodoco/astrid-dev/issues/720), [#732](https://github.com/banodoco/astrid-dev/issues/732)), certificate trust ([#721](https://github.com/banodoco/astrid-dev/issues/721)), model downloads ([#722](https://github.com/banodoco/astrid-dev/issues/722)), live-scene capture and its tests that run in no CI lane ([#734](https://github.com/banodoco/astrid-dev/issues/734)), and the Runtime's shutdown race on macOS ([#685](https://github.com/banodoco/astrid-dev/issues/685)). The seed in every receipt rides along. The first fix after Release 13, looking up a model's fingerprint and size from Hugging Face instead of refusing, ships before this release as an update.

**Issues that join a plan.** An issue is in the release by its label, and the list under [Issues](#issues) is pulled from GitHub. Added on 16 November 2026 because a plan in this release already works in the same code:

- with Plan 59, which meets them while importing, capturing and rendering: importing a valid export ([#635](https://github.com/banodoco/astrid-dev/issues/635)), composed visualize ([#748](https://github.com/banodoco/astrid-dev/issues/748)), forks in one commit ([#745](https://github.com/banodoco/astrid-dev/issues/745)), the first frame in WebKit ([#668](https://github.com/banodoco/astrid-dev/issues/668)) and the general fixes found in OpenShell ([#746](https://github.com/banodoco/astrid-dev/issues/746));
- with Plan 55, on the local generation path: the scan that reports harmless conditions as errors ([#724](https://github.com/banodoco/astrid-dev/issues/724)), `--inputs-json` replacing the other inputs ([#583](https://github.com/banodoco/astrid-dev/issues/583)), the two-second readiness probe ([#733](https://github.com/banodoco/astrid-dev/issues/733)) and parameter maps declared twice ([#610](https://github.com/banodoco/astrid-dev/issues/610));
- with Plan 39, the test and CI issues already filed against it, listed in its [Release 14 scope](../plans/39-green-mains/plan.md#release-14-scope);
- on their own, because they are small: the Updates setting left in the address ([#736](https://github.com/banodoco/astrid-dev/issues/736)) and the installer's friction for agents ([#723](https://github.com/banodoco/astrid-dev/issues/723)).

**Open owner decisions.** Whether a fix that changes only website files may go to the App's `main` without waiting for a release: the vision page's text already does, because the page reads it from astrid-dev, but layout and code fixes ride with a release since 16 November. And whether to add CI capacity: on 16 November jobs waited 30 to 68 minutes to start, and an Agent run takes about two hours.

Each release has one theme and a [standing lane](../skills/astrid-dev-shared/glossary.md).

## Included plans

- [Plan 55](../plans/55-local-speed/plan.md) — the design, the tasks and the standing speed test.
- [Plan 59](../plans/59-into-the-minkhole-proof-point/plan.md) — finish the Into the Minkhole edit and establish a reusable Astrid editing workflow, fixing creative blockers at their source.
- [Plan 39](../plans/39-green-mains/plan.md) — phases 1 to 3: every test runs, failures are fixed by cause, and the release branch is kept green by required checks.
- [Plan 13](../plans/13-execution-host-refactor/plan.md) — the execution host mapped and its behaviour pinned by tests, before anything is moved.
- [Plan 52](../plans/52-issue-intake/plan.md) — its last three tasks: one place for user and tester reports.
- [Plan 53](../plans/53-vision-aspirations/plan.md) — one short reference under the vision for each part of Astrid, and every gap measured against it.
