# Release 12 — Reliable updates and one generation path

**Release:** 12
**State:** Draft

## Highlight

Updating Astrid works reliably on every platform, and creators generate media through one path, locally or on a rented GPU they control.

## Intent

Release 12 began as the release that makes updating dependable: the fixes from Release 11's field failure, the review-round repairs, and every product regression found against Release 10. On 10 Nov 2026 Hannah folded the generation work into the same release, rather than holding it for a Release 13. That work is:
- one generation path ([Plan 32](../plans/32-generation-placement-targets/plan.md));
- rented-machine lifetime and cost controls ([Plan 40](../plans/40-machine-lifetime-controls/plan.md));
- the first-image onboarding pieces that depend on it ([Plan 20](../plans/20-zero-to-first-image/plan.md), phase 1.5 and staged work);
- their live GPU proof ([Plan 34](../plans/34-real-gpu-proof/plan.md)).

Both halves are close to done, and shipping them together means one qualification, one candidate and one publish instead of two.

**A good outcome:**
- one published tuple (Agent, App, Runtime, harness, and the VibeComfy, ComfyUI and runpod-lifecycle pins) that passes the gate below;
- every in-scope generation slot is proven on a real GPU through the product;
- Hannah confirms the update works on her Mac through the normal App path.

## Approach

The release runs as **two tracks that merge once**. Track B merges into Track A's candidate, and the merged candidate is qualified once and published.

| Track | Plans | What it finishes | Document |
|---|---|---|---|
| **A — Fixes** | 29 | The Release 12 candidate `cand/29-r12`: Agent fixes, App Direct Journey, harness, matrix. Then the merge, the final qualification and the publish | [releases/12/fixes.md](12/fixes.md) |
| **B — Generation** | 32, 40, 20, 34 | One generation candidate, composed from Plans 32, 40 and 20, CI-compared, reviewed and proven on GPU | [releases/12/generation.md](12/generation.md) |

**Structure.** As in the [orchestrator brief](../docs/handoffs/2026-11-10-orchestrator.md), the orchestrator runs **one manager per plan** (29, 32, 40, 20, 34). Each manager talks only to the orchestrator. Tracks group the plans; they are not extra management layers. Plan 32's manager owns composing the generation candidate (B5), because int/32 is the base the others build on. Plan 29's manager owns the candidate branches and the publish.

**Checkpoints:**
- **Checkpoint A:** the Agent fixes are reviewed, and the fixes-only tuple is green on App Tests, Direct Journey and the matrix, including the Windows rows.
- **Checkpoint B:** the generation candidate is composed. A **rehearsal merge** of it into Track A's current candidate gets one Agent CI comparison and **the one release review of the merge delta**, both clean, and the GPU cells pass. Reviewing at checkpoint B, not during the final round, means a blocker can't void the final runs.

**Keep the merge cheap.** Track B rehearses merging Track A's candidate every time it moves, on a rehearsal branch, as Plan 32 already does with `plan32/r12-reconcile`. Phase 2 then only repeats a reviewed merge.

### Gate (merged tuple)

1. The full `journey.yml` matrix, row=direct, all 11 rows green.
2. No regression against R10 `72462b04`, served R11 `a105de3a` / `4f5477cb` or `main`. D8 applies: product regressions against R10 are fixed here; stale or test-infra failures go to Plan 39.
3. App Tests and Direct Journey with 0 failures on the pinned App head.
4. Release review rounds done with no open blocker: Plan 29's rounds, plus the merge-delta round at checkpoint B, plus Plan 34's final review.
5. **Generation proof:** each in-scope slot passes on a real GPU through the product. The run happens on the final tuple, or on a candidate whose generation code, VibeComfy, ComfyUI and Runtime pins are identical to it. The pod's actual VibeComfy HEAD is verified against the pin.

**The bar** (Hannah): fix and question every failure; never weaken a check. "Test drift" is proven from the trace or it isn't drift.

### CI and runners

The runner freeze existed so that other work wouldn't starve Release 12. Generation is now Release 12, so the freeze becomes **scheduling by the orchestrator**:
- Track A's runs have priority.
- Track B runs **one** Agent CI comparison, on the rehearsal merge, which also stands in for Plan 32's and Plan 40's CI gates. First, the three collection errors that stopped Plan 32's last CI and its baseline must be fixed, so the comparison produces test ids.
- Nothing else pushes to `int/**` or dispatches CI until publish.
- Runtime and VibeComfy run CI on every push, so push to them only when the release needs it.

The CI-trigger prep (`plan32/release*-ci-prep`) stays **after publish**, as Hannah approved. It adds `cand/**` push triggers, so landing it now would start heavy CI on every candidate push.
