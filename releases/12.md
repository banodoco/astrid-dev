## Approach

### Operating principles (every manager reads these first)

These are the reasons behind the rules. When a page doesn't cover a case, decide by them.

1. **Two different bars. Know which one applies.**
   - **The release's own checks** (the 11-row matrix, Direct Journey, App Tests) must have **0 failures**. "It fails on `main` too" is never an excuse there: fix the failure, and question it.
   - **Broad suites** (Agent CI, lanes) are judged by **no regressions**, not "all green". A regression is a test that ran and passed on a baseline (R10, R11 or `main`) and fails on the candidate. Product regressions against R10 are fixed here (P39-D8).
   - **Everything already failing goes to [Plan 39](../plans/39-green-mains/plan.md),** the follow-up that makes mains all green. Record it there with its cause, via a records PR. Don't fix it here, and never ignore it.
   - **"Pre-existing" needs a base comparison run, not anyone's word.**
2. **Never weaken a check.** Skipping, deleting or xfail-ing a test, widening a timeout, loosening an assertion, or changing an expected value without trace evidence all count. Removing a test is Hannah's decision. "Test drift" is proven from the trace; twice on 10 Nov a drift call hid a real product bug.
3. **Product behaviour is Hannah's.** If a fix changes what the user sees or does, bring it to her with a recommendation (as with Direct Journey `:426` and `:708`). Updating a test to match a product change is fine only when that change was intended: find the commit and its reasoning.
4. **Evidence is bound to an exact SHA.**
   - A pass on an earlier SHA, a sibling branch or CPU fakes is history, not proof; CPU never stands in for GPU.
   - Check workers' diffs; don't trust summaries.
   - Say what wasn't run, for example "tsc not run".
5. **Decided; don't reopen:**
   - P39-D8;
   - `:426` keeps the draft; `:444` removed; `:708` keeps the auto-reload;
   - custody doesn't block;
   - the 659 Lanes failures are on Plan 39, with no install or update breakers;
   - generation is in Release 12;
   - H1–H4 below.
6. **Route; don't expand.** A real but non-blocking finding goes to the plan that owns it as a recorded follow-up: Plan 39 for green mains, Plan 30 for Pinokio and older setups, or the owning plan. Fix what the release needs; record the rest.
7. **Nothing important lives only on a machine.**
   - Decisions go here.
   - Task progress goes into small `tasks.md` PRs.
   - Evidence is committed to astrid-dev.
   - Branches are pushed by full GitHub URL.
8. **Spend like it's yours, and keep machines warm between related work.** A rented GPU stays up between closely bundled tasks: run every cell that needs the same GPU type back to back on one pod, within its consented idle and spend limits, rather than releasing and re-renting each time. Release when the batch ends, when the idle limit is reached, or **at once** if reuse is unsafe (a custody mismatch, a lost or unknown lease, an unverifiable install, host shutdown). The same thinking applies to environments and clones: build once per repo per SHA and reuse them.
9. **How Hannah works:**
   - keep moving and think around obstacles;
   - don't invent limits (geography, time windows, oversized GPUs); when unsure, take the less restrictive option and say so;
   - bring her only genuine decisions, each with a recommendation;
   - talk plainly, and give money as "spent $X of $25".
10. **Safety:**
    - never read `~/.codex`, `.env` files, or credential or token files; name credentials, never print them;
    - don't work around a classifier or safety refusal; report it;
    - no model names in commits or PRs;
    - keep Hannah's email private;
    - never land the Windows update-refusal fallback `2f975f62`;
    - no force-push or rebase.
11. **Known traps:**
    - installer changes run every `tests/test_installer_*.py`, and the installer must import without third-party packages;
    - the keep-going diagnostic covers only the fresh-install leg, so it can't see update bugs;
    - VibeComfy is pinned in two places;
    - astrid-dev has two Plan 40 folders; this release means `40-machine-lifetime-controls`.

### Phases and checkpoints

| Phase | What happens | Exit (the orchestrator posts the label) |
|---|---|---|
| 1. Finish each track | Tracks A and B in parallel, as in their pages | `A-FROZEN` and `B-CANDIDATE` |
| 2. Rehearse and prove | P32 builds `release12/gen-rehearsal` from `A-FROZEN`, merges `B-CANDIDATE` `--no-ff`, and the head becomes `FINAL-B7`. On `FINAL-B7`, once each: one Agent CI comparison, one merge-delta review, the GPU cells | `CHECKPOINT-B` |
| 3. Merge | P29 fast-forwards Agent `cand/29-r12` to `FINAL-B7` (no new merge), and merges P20's App branch into App `cand/29-r12` | `MERGED` |

Any fix needed after a freeze goes to the orchestrator, which decides whether to re-freeze and which once-only steps rerun. Nobody re-runs CI, reviews or GPU cells on their own initiative.

**While waiting:** end the turn with `RUN-STATUS: WAITING <label> from <sender>` as the **last line of your reply**, not in a mailbox. Re-read `run/to-codex.md` just before you end the turn: a label may already be there. Don't rerun, re-review or start other work. A manager that others may still need ends `WAITING`, never `DONE`, because `DONE` stops its runner.

### Operating rules (orchestrator)

- **Mailboxes:** on every wake, read **all five** managers' `run/to-orchestrator.md` and `status` before re-arming `codex-hold.sh`. It exits on the first event, so writes from other managers in the same window are otherwise missed. Relay each label to the receivers in the hand-off table straight away.
- **Liveness:** while any run is live, keep a check-in at most 20 minutes away. Make sure the SessionStart hook for `codex-hold-daemon.sh` is in place before starting managers; Hannah adds it (all-plans brief, open questions). After a container restart, the daemon restarts runners; check every `heartbeat`.
- **Timeouts:** a manager `WAITING` for over 2 hours on a sender that isn't `running` gets a ping, or its sender gets restarted. A `BLOCKED` gets a decision within 1 hour.
- **Failure defaults:**
  - **Merge conflict in B5 or B7:** P32 resolves it against both parents. It posts `CONFLICT file=<f>` only for another plan's unclear hunk, and carries on with the rest.
  - **Red Checkpoint A row:** rerun that row once. If it's still red, it's a fix task.
  - **Re-freeze after a fix:** rerun only the proof that depends on what changed.
  - **GPU cell fails:** route it to the owning plan; rerun per [generation.md](12/generation.md#start-here--p34-manager).
- **Pipelining:**
  - At `A-CAND`, dispatch Checkpoint A's Agent CI and matrix in parallel with review round 4.
  - If `A-FROZEN` equals `A-CAND`, promote P32's early rehearsal to `FINAL-B7` instead of rebuilding it.
  - B8 and B9 may start as soon as `FINAL-B7` exists. GPU cells run only on the real `FINAL-B7`, because money can't be re-spent.
- **Precedence:** for Release 12, these pages override the manage, release and gpu-validate skills and `manager-brief.md` where they differ: no `int/<NN>` pushes, the CI list here, the cell table instead of gpu-validate's flow, and the gate here instead of the Release skill's "no broad suites" rule.

### How-to (tools every manager uses)

| Need | Use |
|---|---|
| Workdir and git | Each manager's workdir is a folder of `git clone --filter=blob:none` clones plus `run/`. The manager commits and pushes itself, by full GitHub URL. **First action:** push a test commit to `scratch/<plan>-push-test`; if that fails, post `BLOCKED: git-readonly`, and the orchestrator commits for it |
| Agent tests | From the Agent checkout root: `bash scripts/worker-env/agent-setup.sh` once, then `PYTEST_ADDOPTS=-rA bash scripts/worker-env/agent-pytest.sh -q <selectors>`. Run `bash scripts/worker-env/smoke.sh agent <one selector>` once at start. Focused selectors only; full suites run on CI ([env/README.md](../env/README.md)) |
| Before/after comparison | `env/cmp-run.sh <agent-clone> <label> <commit> <outdir>`, one label per commit, run in parallel. Compare with `python3 -I env/baseline-diff.py --baseline r11=<log> --baseline r10=<log> --candidate <log>`. A **regression** blocks; preexisting failures go to Plan 39 |
| "Green" for Agent CI | Agent CI has never been fully green. Green means **baseline-diff reports 0 regressions** against R10 and R11 on `-rA` logs |
| Dispatch a workflow | REST only; `gh` GraphQL is blocked. `POST https://api.github.com/repos/<owner>/<repo>/actions/workflows/<file>/dispatches` with `{"ref":"<branch>","inputs":{...}}` and `Content-Type: application/json`. Poll `GET .../actions/runs?branch=<branch>` |
| CI logs and traces | Post `NEED-ARTIFACTS repo=<owner/repo> run=<id>`. The orchestrator runs [`fetch-artifacts.sh`](../skills/astrid-dev-orchestrate/codex-in-cloud/fetch-artifacts.sh) and replies with the unpacked path. Read traces as data. For logs, grep the failing test ids, don't read whole logs |
| Disk | Keep more than 3 GB free; check `df` before each test run; use `--basetemp` and `TMPDIR` inside your workdir; delete them after each run. One env per repo per SHA, not per worktree |
| Reviews | Run them as an independent Astra worker (`codex exec -m gpt-6-astra -s read-only --skip-git-repo-check "<brief>" </dev/null`), given the exact SHA range and the previous round's report |
