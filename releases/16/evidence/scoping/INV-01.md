## 2. Actual path and one ownership model

**Observed path:** public manifest pins integer release, Agent/Runtime/digest, tools, pack and dependencies. Mac/Linux public/install resolves validated manifest pins in a temporary bootstrap environment and hands the manifest/flags to Agent; install.sh redirects to that bootstrap. Windows public/install.ps1 uses owner-specific bootstrap directory/process and passes the manifest to the same package; its cleanup may report residue. [Bootstraps][bootstrap] [Windows][bootstrapwin]. These are not three installers. Local launcher and Pinokio may pass a local candidate manifest rather than the public URL. Pinokio's hosted backend Update invokes the bootstrap install path; local Update prepares/promotes editor then invokes installer and starts. [Pinokio update][pinupdate] [lib][pinlib].

Agent's [installation resolver][installidentity] is already the authority for active program/data/service label and selected release; R0 handoff becomes ordinary R1 selection with retained R0 provenance. [core][core] derives installed identity from immutable version manifest and marker, not directory name. The shared _run_update_transaction stages a candidate, records a durable operation with old selection/data/realm/backup/candidate and adapter context, fences Stop, backups/migrates, switches, activates/verifies, records outcome or rolls back. Direct and [app_update][appupdate] (Pinokio Runtime) and [local_update][localupdate] (ordinary fully-local launcher) are consumers; do not replace this with a new orchestration framework. [Runtime operator_upgrade][runtimeupgrade] handles the realm schema transition, so it must be authorized by the same operation. Runtime, Agent and the actual service process need a common custody identity; App and Pinokio are clients of a typed status/operation result, not competing owners. App [resolveUpdate][resolver] and [localUpdateStatus][localstatus] currently express distinct release/build/capability choices; consume a shared meaning instead of merging unrelated fields into an ambiguous boolean. Rollback/removal depend on exact selected old tuple, data custody and owner receipt, never mere exit code or presence of a folder.

| Asset / authority | Preserve and reconcile | Writer / receipt |
|---|---|---|
| Public release tuple, bootstrap bytes, version history, required floor | one immutable approved record; generated App delivery; live deployed hash; do not confuse build commit with installer release | P31 release record + validated sync and served receipt; App main generated copy is derivative |
| Managed program root / version dirs, current pointer, install marker | exact selected version manifest/lock, old version until recovery boundary; temp/bootstrap residue not active install | P09 installation resolver + core transaction and existing outcome receipt |
| Active data root / realm incl history, projects and uploads | authoritative selected realm, storage schema, ownership, pre-migration backup and post-write integrity; retained R0 provenance is not permission to delete | P35 state boundary, P63/P79 durable edits/uploads, Runtime migration under P09 operation; pre/post logical hashes and backup recovery receipt |
| Services, foreground process, local editor, launcher engine | owner mode, service registration, start/boot identity, actual process binding, task/attempt and exit | P38 process identity; P09 transaction fence; P30 direct service worker; P10 native launcher adapter |
| Managed engine, model/cache roots, user/external environments | exact engine recipe/receipt plus asset digests; preserve compatible reuse and user-owned assets; external ComfyUI not owned by Astrid | P94 setup owner, P35 roots/consent, P09 migration/removal integration; no blind reprovision |
| Bundled/default packs and user packs | signed/digested declared defaults, separate explicit user choice/tombstone, user-modified pack not disposable; unknown optional pack quarantine without deletion | P31 desired inventory, P35 user state, P09 reconcile via existing pack mechanism |
| User credentials/preferences, external paths | neither publication nor repair grants deletion/ownership; no raw secrets in logs | P35 and INV-04; redacted presence and restore proof only |

Use resolved roots rather than hardcoded home paths; record actual paths by role, owner and identity in redacted evidence. The authoritative operation receipt must join the selected tuple, old/candidate pointer, exact realm, launcher/editor, worker/process ownership, stage, backup and result. Existing install.json, per-version manifest.json, update-transaction.json and run receipt are evidence of different things; do not create another independent ledger. An old receipt is provenance, not proof a currently live process is the owner.

### INV-01-F01 — BLOCKING: one transaction exists but schema migration lacks a proven shared lifetime authority

**Evidence.** [core.py:562-656][coretxn] has common stage/stop/backup/migrate/switch/activate/verify and refusal/rollback. [app_update.py:500-625][appupdatetxn] obtains operation and app-update lock, notes same-schema path skips Runtime upgrade while custody owns lock, and uses selection lock. [backend.py:1785-1790][backendupgrade] calls Runtime upgrade; [operator_upgrade.py:209-229][runtimeupgrade] independently obtains the installed lifetime lock nonblocking. Same-schema P07 success does not prove a migration while this lock is owned. Existing fully-local Agent adapter is more mature than Pinokio's editor staging: it has durable recovery context (validated preparation, restore-checkout, release-app, etc.). This corroborates SC-09/29/30 without alleging a newly reproduced deadlock.

**Impact.** A schema-changing update may refuse or fail after the old Runtime is stopped; unlocking casually to let the child acquire risks a second installer, wrong realm or unowned migration. A recovery that only starts the old binary can expose changed data to an incompatible reader.

**Minimal change / owner.** P09 owns the single operation state machine, with P38 custody and Runtime migration owner reviewing a bounded delegation of the already-held lifetime authority to the exact migration child/operation (or a positively identified handoff that never leaves a race window). No skip-lock flag, arbitrary foreign PID kill, second transaction or unconditional data rollback. Record exact candidate and old manifest/realm/backup binding before mutation; preserve stop-refused as non-mutating and failures after stop as recoverable outcomes. Check the selected realm again at migration/activation; restore or roll forward only under verified compatible pair and no unaccounted writes. Amend existing P09 transaction/recovery acceptance and SC-29 UR update-path work, do not dispatch the same installer rewrite twice.

**Verification.** Real differing schema and same schema, concurrent update/repair, refusal while active task, wrong selected realm and foreign service, kill/crash between every durable stage, failed migrate/switch/verify and rollback, repeated recovery. Prove one worker, no unlock window or overwritten project, exact old/new binaries and realm data, successful editor reconnection. Native Windows/macOS/Linux and actual launcher variants required. Recovery after new user writes must preserve them or refuse; a restored stale backup is not success.
