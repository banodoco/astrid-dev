## 2. Verdict and ownership rule

REWORK at the seams, retain the selected R16 projects and 0.1.0 single integrated release. R16 needs one *authority per object and transition*, not a universal store, manager, process launcher, or sandbox. For each write, identify principal, scope, target/owner, accepted revision/epoch, and durable acknowledgement; a remembered preference, observed process, prior receipt, or matching hash is not fresh authorization. Conversely pending user work and unsettled paid obligations must not be discarded merely because authority moved. Establish contracts before implementation fans out. No whole P36/P15/P13/P83/P92 import; only named safety prerequisites below. BLOCKING means resolve and qualify before shipping the affected promised path; not that a historical failure is proved on final pins.

### INV-04.1 — BLOCKING — durable choice and pending recovery are different types of state

**Observed.** [Runtime tables](https://github.com/banodoco/astrid-runtime/blob/686ca695469bda48cd40a70824c4ccef2a137284/runtime_protocol/store.py#L500-L522) already carry actor-key/version app state, user preferences, documents and actor/scope project selection; [document service](https://github.com/banodoco/astrid-runtime/blob/686ca695469bda48cd40a70824c4ccef2a137284/runtime_protocol/service.py#L5189-L5302) uses expected version, idempotency and rejects direct timeline writes. Check whether URL-owned deletion can reach that write (inference, not established leak).
