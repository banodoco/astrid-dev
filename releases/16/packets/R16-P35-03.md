## What to do

1. In `RuntimeService` add constants: `GRANT_KINDS = ("pack", "model", "node")`, `GRANT_KEY_PREFIX = "grants."`, `GRANT_LIMIT_PER_KIND = 32`, `GRANT_SUBJECT_MAX = 96`, `GRANT_DIGEST = re.compile(r"sha256:[0-9a-f]{64}")`, `GRANT_REF = re.compile(r"[A-Za-z][A-Za-z0-9_.-]{0,63}")`. Each kind is one `user_app_state` row for the actor at key `grants.<kind>` (so each document stays under `APP_STATE_MAX_BYTES`, 16 KiB; the 32-entry cap with a 96-character subject keeps it there, and a test proves it). Content: `{"schema": "astrid.grants.v1", "kind": <kind>, "grants": {<grant_id>: {"subject", "digest", "state": "approved" | "revoked", "generation": int, "approved_at", "revoked_at", "credential_ref"?}}}`. `grant_id = f"{kind}-{sha256(canonical_json([kind, subject, digest])).hexdigest()[:24]}"`.
2. Protect the rows: in `update_app_state`, right after `_app_state_target`, raise `ValidationError("app-state keys starting with 'grants.' belong to the grant ledger")` when the key starts with `GRANT_KEY_PREFIX`. `get_app_state` of those keys stays allowed (read only). Write the ledger rows with direct SQL inside the grant methods (the same INSERT/UPDATE statements `update_app_state` uses), so the 16 KiB check is replaced by the 32-entry cap.
3. Add methods, each taking `identity` like `update_app_state` and using `_app_state_target` for the actor: `list_grants(kind=None, *, identity)`; `grant_status(kind, subject, digest, *, identity) -> {"grant_id", "state": "approved" | "revoked" | "absent", "authorized": bool, "generation": int}` (authorized only when state is `approved`; this reads the CURRENT row, never a recorded command result); and four `@_durable_mutation` methods that use `require_idempotency_key`, `_command_replay` and `_command_record` exactly as `update_app_state` does (command kinds `grant.approve`, `grant.revoke`, `grant.reapprove`, `grant.apply_revocations`; aggregate `f"grants:{actor}:{kind}"`): `approve_grant(kind, subject, digest, idempotency_key, *, identity, credential_ref=None)`, `revoke_grant(grant_id, idempotency_key, *, identity)`, `reapprove_grant(grant_id, idempotency_key, *, identity)`, `apply_revocations(entries, idempotency_key, *, identity)`; plus read-only `export_revocations(*, identity)`.
4. Rules. `approve_grant`: absent gives generation 1, state approved; already approved changes nothing (a new `credential_ref` replaces the old one); revoked raises `ConflictError("grant was revoked; re-approval is an explicit act", details={"grant_id": ...})`. `revoke_grant`: unknown id raises `NotFoundError`; approved becomes revoked with `revoked_at`; already revoked changes nothing. `reapprove_grant`: only from revoked, adds one to `generation`, state approved, clears `revoked_at`; on an approved grant it changes nothing; unknown id raises `NotFoundError`. An old recorded `approve_grant` result replayed with its old idempotency key returns that old result but never changes the row.
5. Revocation export and apply (the restore seam): `export_revocations` returns `[{"grant_id", "kind", "subject", "digest", "generation"}]` for every revoked entry, sorted by `grant_id`. `apply_revocations(entries, ...)` validates each entry (kind in `GRANT_KINDS`, subject, digest and id consistent: recompute `grant_id` and compare; integer `generation >= 1`) and then, per entry: id absent gives a revoked tombstone with that generation (so a later `approve_grant` is refused); id present and approved with `generation <= entry.generation` becomes revoked; id present and approved with a higher generation is left alone (a newer re-approval wins over a stale list); id already revoked is left alone. It returns `{"applied": n, "ignored_newer": m}`. It never turns a revoked grant back into an approved one.
6. Validation (all `ValidationError`): kind not in `GRANT_KINDS`; subject empty, not a string or longer than `GRANT_SUBJECT_MAX`; digest not matching `GRANT_DIGEST`; the 33rd entry of one kind (approved, revoked and tombstones all count); `credential_ref` that does not match `GRANT_REF` or whose lower-cased form starts with `sk-`, `rpa_`, `ghp_`, `github_pat_`, `hf_` or `xox` (a credential reference is a name only, never a value; resolving it is Plan 36's work, not this packet's).
7. Write `tests/test_user_grants.py` with the same `service` fixture as `tests/test_app_state.py` (copy the fixture; do not import from that file) and `identity={'actor': 'alice'}`. Cases: approve then status authorized, generation 1; the same idempotency key replays the identical result; revoke makes `authorized` false; approve of the revoked grant raises `ConflictError`; replaying the ORIGINAL approve key after the revoke returns the old result but `grant_status` still says revoked; reapprove gives generation 2 and authorized; revoke again leaves generation 2 revoked; `bob` sees `absent` and has an independent ledger; a direct `update_app_state('grants.pack', ...)` raises `ValidationError` while `get_app_state('grants.pack')` works and other keys such as `agent.choices` still write; each validation rule above; 32 maximum-length entries of one kind fit and the stored row is at most `RuntimeService.APP_STATE_MAX_BYTES` bytes of canonical JSON, the 33rd is refused; two realms: realm A approves, revokes and exports; realm B (fresh `tmp_path` realm, separate `RuntimeService`) approves the same grant (approved, generation 1), `apply_revocations(export)` makes it revoked with `applied == 1`; re-applying the same list is a no-op; after `reapprove_grant` (generation 2) the older list reports `ignored_newer == 1` and the grant stays approved; applying a list for an id realm B never saw creates a revoked tombstone and `approve_grant` of it raises `ConflictError`; an entry whose `grant_id` does not match its kind, subject and digest raises `ValidationError` and changes nothing.
