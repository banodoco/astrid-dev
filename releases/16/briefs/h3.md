## Outcome

- **For creators and agents:** one request describes a shot (what to keep exactly, what to generate or edit, how to steer), at whole-shot and frame level.
- **Placements, not modes:** continue, bridge and insert are placements of clips or frames on the timeline.
- **Exact means exact:** kept pixels and samples are verified in the final file.
- **The dry run tells the truth first:** before any GPU spend it states what is exact, soft, verified or untested, the cost, and the nearest option to any refusal.
- **For developers:** a new capability is one ordinary pack, a pinned node repository plus one YAML file per contribution and a hand-written skill section. It stacks with everything else through typed sockets, footprints and a test kit, with no Astrid engineering.
- **In Release 17,** one request can run several passes (de-rope, edit-then-extend, refine, repair).

## How it runs

**Option:** hosted

- **Start.** See [Toolkit check at start](#toolkit-check-at-start).
- **Managers.** When a plan's Starts when is met (Plan 66 now; 68, 70 and 67 after Plan 66 RS1's contract half), the orchestrator starts that plan's Codex manager, `h3-p<PP>-manager`, from the [manager start message](#start-messages) with `codex-runner.sh` ([how](../../../agent/guides/codex-in-claude-cloud/README.md#start-a-run)), on route X (Terra), in a work folder of partial clones plus `run/`. The orchestrator hosts every manager: it re-arms `codex-hold.sh` over all live runs at every check-in, keeps a hosting check-in at most 20 minutes away while any run is live, and splits the cores between managers ([hosting](../../../agent/guides/codex-in-claude-cloud/README.md#start-a-run)). Up to four managers at once.
- **Dispatch.** Each manager runs its plan's queue: for each unit whose Depends are merged it writes the [Codex worker brief](#start-messages) and runs it as a Codex sub-agent, or a child `codex exec` when the unit's route needs a different model, in its own `git worktree` on `task/<PP>/<unit>`. Never two workers on one function. T editorial work and reviews go to the orchestrator, which the manager tells with `READY: <unit>` in its mailbox. The older `releases/16/packets/R16-P66-*`, `-P67-*`, `-P68-*` and `-P70-*` files are history only.
- **Mailbox.** A manager writes notes, questions, `READY:` and `MERGED <unit> <sha>` to `run/to-orchestrator.md`, and reads `run/to-codex.md`; the orchestrator answers there and posts the lane's STATUS on the board ([mailbox](../../../agent/guides/codex-in-claude-cloud/README.md#mailbox)).
- **Fallback, per unit, said on the board:** if a model ID is refused, the sign-in is lost or a manager's run reaches `gave-up`, the orchestrator runs that plan's next units as Claude workers by the same route, from the [Claude worker start message](#start-messages), and restarts the manager when Codex works again. Codex counts as unavailable only once tried: a sign-in the owner hasn't completed by the next check-in has failed.
- **Baseline.** Before 66-U1 (whose Depends says `baseline`), the orchestrator records the test inventory on the starting versions: the hosted CI result on each plan branch at its cut SHA, starting one run per branch if none exists ([when a run is load-bearing](../../../agent/shared/run-contract.md#when-a-test-run-is-load-bearing)). It posts `BASELINE <plan> <sha> <run link>` on the board. That post is the "refreshed 59/64/65 baseline" Plan 66's critical path starts from, and it satisfies `baseline`.
- **Proof.** Each worker commits its own work on `task/<PP>/<unit>`. The plan's manager runs the unit's focused tests, by id, on the merged tree in a scratch worktree, merges it into the plan branch `--no-ff` and pushes; branches and merges follow [the pipeline](../../../agent/shared/pipeline.md#branches-and-pull-requests), with the manager in the accountable agent's place for its plan branch. No CI runs on these branches. H3 tests need [environment setup](../../../env/README.md) that fetches other repositories; each manager sets it up once in its work folder. Once Plan 66 CC-14 lands, its `engine_deps` lane is the one proof workflow for every unit and pack.
- **Reviews.**
  - The reviewer's ACCEPT is required at Plan 66 RS1 (job-record half, then contract half), on every S-route unit, at Plan 67 R (the programme's integrated review) and at Plan 107 R. Other units merge on their manager's proof.
  - An S-route unit's own review, of its head SHA, gates that unit's merge; a review stop after it (66-RS1a after 66-U1) is a separate review of the merged head. The orchestrator adds each finding as a row under the reviewed card in that plan's `tasks.md`, in its next progress PR: `RS1.<n>` at the RS1 stops, `R1.<m>` for a unit's own review, under its first card. They go back to the same author once, then to a fresh session.
- **Merges.**
  - The orchestrator merges `release/<N>/main` forward into each plan branch as it moves.
  - When a plan's units are merged, and its review stop accepted where it has one, the orchestrator makes the plan ready to land: it merges `release/<N>/main` forward, settles conflicts through a worker whose Scope is the conflicting files, and gets the full relevant suite green on CI on that head. It then opens the PR from the plan branch into `release/<N>/main` and posts it, `to: release <N> lead`, on the Lead's board. The Lead merges it, in order with the other lanes. Once it is merged, the orchestrator opens the plan's completion PR, ready for review, with `Completion: Yes` on the plan's own criteria; a later review stop that covers the plan (Plan 67 R) is named under Unproven, and the PR merges after it accepts.
  - The orchestrator also merges its own astrid-dev progress PRs on a green check, when they touch only this lane's plan status lines, `inputs.md` Scope decision lines, `tasks.md` rows and this brief.
  - It cuts later branches itself with `git push` from the base named in the release brief.
- **CI.** astrid-agent CI runs on PRs into `release/*/main` and pushes to it, and is shared with Plans 93, 94 and 38. The orchestrator dispatches `ci.yml` once per plan, on the plan branch's integrated head when it makes the plan ready, after checking the running `ci.yml` runs. The Release 16 Lead authorizes these dispatches and the baseline runs; `releases/16/run.md`'s no-dispatch rules belong to its superseded Delivery setup and do not bind this lane (Lead, 28 Nov 2026).
- **Check-ins.**
  - Each check starts by pulling banodoco/astrid-dev `main` (`git pull --ff-only` in its astrid-dev clone, and `skills install` again if `agent/` changed), so this brief and every `tasks.md` are current.
  - The orchestrator's hourly scheduled task (`create_trigger` on this session) is its wake path ([run contract](../../../agent/shared/run-contract.md#coordination-boards-and-check-ins)). Each check reads the lane board by cursor (`python3 agent/guides/codex-cloud/inbox.py banodoco/astrid-dev <board number> --after <cursor>`), acts, and posts one STATUS of 10 lines or fewer: units merged, units running, blocked items with their cause, the next units, `acted on:` and `cursor:`.
  - Anyone writes to the orchestrator by posting on the lane board with `to: h3-orchestrator` and a type (STATUS, READY-PROOF, REQUEST, DECISION, BLOCKED); the format is in the board's first post, copied from the [mailbox format](../../../agent/guides/codex-cloud/README.md#establish-the-mailbox) with `run: h3-lane`. It answers in the next STATUS or in a reply there.
  - Something that cannot wait an hour: a Claude session also rings the orchestrator's session id (in this brief's header) with `send_message`, and the owner can write in its session directly.
  - The reviewer posts its verdicts on the lane board. The orchestrator posts to the Release <N> Lead only on the Lead's board: each ready plan PR, release-level questions, and its closing note.
- **Skills** are hand-written editorial guides, mixing instruction and creative inspiration, and never generated. Plan 66 CC-6 and Plan 67 CS-8 write them; each pack ships its own written section.
