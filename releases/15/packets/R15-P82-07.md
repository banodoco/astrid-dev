## What the code looks like (scouted 24 November 2026; re-check)

- `astrid/core/pack/discovery.py`: a **request-scoped** cache already exists: `_DiscoveryCache` (about 63-88, deepcopy on read and publish, revoked on scope exit), `pack_discovery_scope()` (98-110), `_tree_fingerprint()` (113-146, hashes every file in the tree), `_discovery_fingerprint()` (149-175, `None` for custom scanners), `reuse_pack_projection()` (178-202). `discover_pack_metadata()` (def near 404): the hit at 543-555 happens **after** `active_source_inventory()` (537-541) and **before** the duplicate-name admission (`_admit_root_names`, 610-615) and the per-root `group_read_lock` (617-622); store at 809-814. A hit therefore skips duplicate-name admission and the pending-transaction check: that is PB-7c, and **a persistent hit must run both, in their original order, before it returns**. The roots at about 161 include `~/Astrid/packs` and the project root.
- `astrid/core/model_catalog/registry.py`: `load_default()` (105-119) reads `models.yaml` on every call, no cache; lines 120-127 reach generation-side assembly through `importlib` at call time. Called from `astrid/core/generation/entries.py` (`_ready_entry_rows`, 95-123; `ready_entries` 208; `action_entries` uses `reuse_pack_projection` 217-221; `runpod_engines`/`engine_table` are `lru_cache`d at 1149-1160).
- [Why each check](../../../plans/82-reuse-across-commands/evidence/2026-11-24-why-each-check/README.md): pack discovery and tree hash guard a duplicate pack id shadowing a core pack, symlinks, a dirty managed checkout and a pending pack install or update transaction; the registry guards the catalog against installed packs' backends and taxonomy; candidate qualification refusals are recomputed.

## Contract

- **Shipped roots only** (those under the install root, whose stamp P82-06 returns): the discovery result and the registry load are kept under a key of `stamp + root set + the discovery function's own fingerprint inputs`. **Own packs (`~/Astrid/packs`) and project packs are never read from or written to this cache** (Plan 92 owns their witness); they are discovered as today on every command.
- On a persistent hit the code **first** runs, in this order and unchanged: `active_source_inventory()`, the duplicate-name admission across **all** roots (so a new own or project pack that duplicates a shipped id is still refused as ambiguous, as today), the pending-transaction check, then managed inventory validation; only then does it return the kept shipped result. A refusal on a hit is the same refusal, same text, same order, as on a miss.
- No stamp (`None`) means no persistent cache: the command works as today and the counter says `miss` with the reason from the stamp helper.
- Entries are written atomically, carry their key and a content digest and are used only after both check; any other state is a miss with a reason and never an exception. Deleting the directory only slows the next command. Data root: the existing helper; no invented path.
- No wire, schema or store change; no pin. No flag that skips a check; no broad `except`; no silent fallback; the miss path is the same function as today's, not a second code path.
