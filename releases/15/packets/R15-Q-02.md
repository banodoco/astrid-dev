# R15-Q-02 — The save-loop sweep records the editor's `astrid.save.*` marks per row and cannot hang

**Source tasks:** `releases/15/qualification.md` Tier 1 row 2 (heavy timeline: open, edit, save); issue packet. Plan 89's SV-L2 puts four User Timing marks in the page; the sweep does not read them, so a failed or slow heavy save leaves no phase numbers, and the sweep hung 48 minutes after a failed row (Qualifier STATUS 14, astrid-dev #1834).
**Route:** X (Extra High): a harness change, proved by reading the code paths and the existing `*.test.mjs` style.
**Estimate:** about 1 engineering day.
**Repro:** On App `release/15/main` (`2e61a5db`) with Plan 89's build, `node scripts/save-loop/sweep.mjs --manifest M --results R --versions V` against a 616-clip fixture: row 1 (`video-move-same-track`) fails with "The save has not been confirmed", the results file has no `astrid.save.*` numbers, and the process never exits after that row (no `cleanup` or `cleanup_failure` record, no summary, browser left running). The marks are in the page: `performance.getEntriesByType('mark')`, names `astrid.save.<n>.{gesture-end,post-sent,200,saved-badge}` (source: `src/tools/video-editor/lib/timeline-save-marks.ts` on `origin/p89/sync-main-2`; at most 16 saves retained, `<n>` is a per-page counter).
**Outcome:** (1) every row in the results file (`type:"row"`, pass or fail) carries `save_marks`: `{marks_available: bool, saves: [{n, gesture_end, post_sent, ok_200, saved_badge}]}` with times in ms on the page's `performance.now()` clock, relative to that save's `gesture-end`, only for saves made during that row; `marks_available:false` (never an invented number) when the page exposes none (builds without SV-L2). (2) A row, its cleanup and the whole sweep each have a bounded wait; when a bound is hit the sweep writes a status record (`type:"sweep_aborted"`, which row, which bound, elapsed), closes the browser, and exits nonzero. (3) Both are covered by tests that run without the network or a browser (fake page object).
**Dependencies:** none. The marks only exist in builds that include Plan 89's SV-L2; the harness must work (with `marks_available:false`) on `release/15/main` today.
**Proof:** the new tests pass, and the existing `*.test.mjs` in `scripts/save-loop/` pass unchanged. The Qualifier proves it by an installed run on Plan 89's stack (not in the sandbox).
**PR destination:** astrid-app `p15q/R15-Q-02` → `release/15/q-save-marks` (cut from `release/15/main`), then to `release/15/main` through the Lead's gate.
**Authority:** [qualification dispatch](../run.md#qualification-dispatch); Lead ruling that the heavy save is proved by the Qualifier's installed run.

## Contract

1. Read the marks with one `page.evaluate` per row (after the row's save has settled or its wait has ended): filter `performance.getEntriesByType('mark')` by name prefix `astrid.save.`, group by `<n>`, keep only counters not seen before the row started (record the highest `<n>` before the gesture). Take times from `startTime`. Round to 0.1 ms. A save with only some phases records the missing ones as `null`.
2. Put the pure parts (parse names, group, relative times, "new since" filter) in a small module (for example `scripts/save-loop/save-marks.mjs`) with a `save-marks.test.mjs` in the style of the existing tests. Wire it into the row-recording path in `assert.mjs` (`runRow`) and, on a thrown row, in `sweep.mjs`'s catch (the thrown row record must carry `save_marks` too, read best effort with its own 5 s bound).
3. Bounds: default row bound = the row's own `settle`/`timeoutMs` plus 30 s; cleanup bound 120 s; whole-sweep bound from `SAVE_LOOP_SWEEP_MAX_MS` (default 2 hours). Each is implemented with a timer racing the awaited promise (never a bare `await` on a page call that can stall). On any bound: append the `sweep_aborted` record, close the browser with its own 10 s bound, `process.exit(1)`. Keep the existing signal handlers.
4. No change to any assertion, threshold (`2000` / `4000`), pass/fail rule, scenario list or fixture. The new fields are additive in the results file; `README.md` documents them in a short section.
5. If a part of the hang cannot be explained from the code you can read (which awaited call stalled), say so in the PR with the lines you suspect; do not guess a fix beyond the bounds.
