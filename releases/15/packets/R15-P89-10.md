**Outcome:** On a heavy project (616 clips) a commit takes 30 s or more (the Qualifier measured about 33 s on Plan 89's Runtime, `astrid-dev` #1834 STATUS 14; the Runtime does commit). Today the editor gives up and shows **"The save has not been confirmed. Your changes are kept."** about 23 s after the POST (the save watchdog's 31.5 s grace, `WATCHDOG_GRACE_MS = SAVE_DEBOUNCE_MS + BRIDGE_REQUEST_TIMEOUT_MS + 2 * SAVE_ERROR_RETRY_BASE_MS`, `src/tools/video-editor/hooks/useTimelinePersistence.ts:79-80`), even though the request is alive. Change ONLY when the watchdog gives up on a **live** request:
- while the commit request is in flight and the connection is alive (no transport error, no refusal, no lost-acknowledgement), keep the status "Saving…" up to a generous ceiling of **120 s** since the last progress (`noteSaveProgress`), then trip as today;
- **fail fast, unchanged:** a transport error, a refused request (4xx/5xx, rejected CAS, conflict), a lost acknowledgement and `lostEdit` (immediate trip) still show "not confirmed" at once;
- a late 200 still clears the banner and settles to Saved (`saveSuccess` -> `clearWatchdog`), as it does now.
Do not weaken what the watchdog detects.
**What the code says (read-only investigation, 24 Nov):** the trip points are `armWatchdog('timeout')` (`:592-609`, a `setTimeout` of `WATCHDOG_GRACE_MS`), `noteSaveProgress` (`:616-623`, restarts the same timer on each accepted intent) and `armWatchdog('lost-edit')` (immediate). Signals for a live request already exist: `isSavingRef.current` (set `:784`, cleared `:1035`), `session.activeAttempts` (`:788`/`:1033`), `errorRetryTimer`, `localSaveState.status` (`'saving'|'retry'|'blocked'|'conflict'|'error'`, `useTimelineSave.ts:1182`), `persistence.saveStatus` (`'retrying'|'error'`). A suggested shape: when the timer fires with reason `timeout`, if `isSavingRef.current && session.activeAttempts.size > 0 && !errorRetryTimer.current` and fewer than 120 s have passed since the last progress, re-arm for the remainder instead of tripping; the banner headline is already suppressed when `permanentSaveRejection` is set (`TimelineEditorShellCore.tsx:814`). `saveBar.ts:77` renders the headline for `watchdogTripped`; "Saving…" is the existing in-flight state. Check on the local-save-session path (`localDocumentSave`, commit via `provider.commitTimeline`) that a settled save emits `saveSuccess` (`useTimelineSave.ts:773`, `useTimelineState.ts:895`) so a late 200 clears the banner; add a test for exactly this.
