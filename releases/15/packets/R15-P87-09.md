**The defect:** the pinned pack's element sources import `../../../../rendering/shared/element_contracts` by relative path (about four files, for example `rendering/elements/_shared/…`). From `~/Astrid/packs/astrid_motion/rendering/elements/_shared` that path points at `~/Astrid/packs/rendering/shared/element_contracts`, which does not exist, so webpack fails: `Module not found: Can't resolve '../../../../rendering/shared/element_contracts' in '<home>/Astrid/packs/astrid_motion/rendering/elements/_shared'` (about 52 s, no output; even a 1-second image-only timeline). In the Agent tree the same relative path reaches the built-in rendering pack, which is why in-tree packs work. Plan 87's installed proofs used the Agent's projected pack (`414a6fd1…`, imports rewritten to `@astrid-rendering/shared/element_contracts`), never the manifest pin, so they did not cover it. The projection hash is not a commit in poms_packs, so re-pinning is not an option.

**The fix:** in `remotion/webpack-alias.mjs`, add one issuer-bound resolve rule next to the existing `selectedHostResource` / `hostResourcePlugin` mechanism (`beforeResolve` on the normal module factory). The rule maps a request only when all of these hold:
1. the request is a relative path that, taken literally, ends in `rendering/shared/element_contracts` (a chain of `../` followed by `rendering/shared/element_contracts`, nothing else);
2. the issuer is an absolute path inside an installed pack's tree: under the user packs root (`~/Astrid/packs` or the roots in `ASTRID_PACKS_PATH`; reuse the existing root discovery in this file);
3. the relative path does not already resolve to an existing file for that issuer.

The target is the built-in rendering pack's file, `<astridDir>/astrid/packs/rendering/shared/element_contracts` (the same root the file already uses for the `@astrid-rendering` alias, line ~569). If the built-in file is missing, throw a clear error; no silent fallback. Every other request, and every other issuer, is left exactly as it is today.
