# R15-P87-06 — Long renders no longer die on a recycled process id (RN-15)

**Source tasks:** [`plans/87-render-works/tasks.md`](../../../plans/87-render-works/tasks.md) — RN-15 (added 24 November 2026 on the Release 15 Lead's decision; top priority of Plan 87)
**Route:** S (ChatGPT mode: Pro; [run contract](../../../skills/shared/run-contract.md#chatgpt-session-modes))
**Estimate:** 1.5 days (inferred)
**Outcome:** A real render that runs longer than about four and a half minutes completes and keeps its outputs. A process id that the operating system has recycled is recognised as a different, later process, never as the one custody recorded, and never treated as that process exiting without proof.
**Dependencies:** none. Start from `release/15/plan-87` (astrid-agent head `5fb81ae3` or later). New branch `p87/rn15-pid-wrap` in astrid-agent.
**Finding to start from (orchestrator's measurement and root-cause read, HIGH confidence in the cause; the fix below is a recommendation to verify, not an instruction):**
- Measured: 10 alternating long renders (90 s, three video layers, 30 text clips, 1280x720; 5 to 7 minutes each) on the Linux installed stack: plan-87 head failed 3 of 5, the same tree without RN-9 failed 5 of 5. Every failure: `owned command cleanup uncertain: owned process identity was reused` (`CustodyError`, `executor_failed`, not retryable). Short renders (about 70 s) pass. The code is the same on `release/15/main` and `release/14/main`; a control run on `release/15/main` is in progress.
- Cause: the error is raised only in `astrid/core/execution/process_group.py` `_observe_tree` (about lines 604 to 615). It compares only the birth token (boot id plus start time from field 22 of `/proc/<pid>/stat`). Every descendant ever seen in a census stays in `known` (`_tree_members`, about 524 to 529); one that exits before `register()` opens a pidfd stays there with no exit proof (the Linux register path just returns, `custody_broker.py` about 3252 to 3281). The census spawns `ps` about every 10 ms and the host loop every 50 ms, so the box burns roughly 125 process ids a second; with `pid_max` 32768 the id space wraps about every 260 s. After a wrap a stale id can name a new process, the start time differs, and the render is aborted mid-run. Evidence: `run/rn15-rate/ROOTCAUSE.md` and the ten run folders on the orchestrator's box (the orchestrator will paste the exact figures and file:line evidence into the PR thread on request).
- The marker's pid is the generic host's own, not the failing process's; which pid was reused is not logged.
**Scope:**
1. Smallest correct fix in `_observe_tree` (Linux only, about 15 lines): when the boot id is the same and the new start tick is strictly later than the recorded one, that is positive proof the recorded process exited and was reaped. Tombstone the old entry, drop it from `known`, continue. Do **not** adopt the new process unless its parent chain leads to a live owned process (a new descendant at a recycled id adopted only when `register()` can replace a handle whose exit is proven). An unreaped-root mismatch, an earlier or equal start tick, or a different boot id must still raise. macOS tokens, the pidfd path and the absent-leader-is-uncertain rule are unchanged. Every existing custody check stays.
2. Add the disagreeing-field detail to the exception text at that raise (pid, both birth values, parent, whether it is the root, the handle type), so a future failure names itself in one run.
3. Reduce the id burn only if it is small and safe (read `/proc` directly instead of spawning `ps`, `process_group.py` about 96 to 118); otherwise leave it and say so.
4. Outputs: if the render's own result was verified (the process exited 0 and the result manifest is validated, hashed and copied into the attempt folder before cleanup) but cleanup custody is uncertain, keep and register the outputs, mark the result `cleanup_uncertain`, keep the marker and the retained attempt. This is a policy change: write it as a separate small commit with its own test, and state it plainly in the PR so the orchestrator can review it on its own. Never treat an absent, reused or different process as a verified exit, and never accept a live different process.
**Proof:** a synthetic-census test next to `tests/test_generic_host.py` (about line 1048): a child seen as `boot:500` with no handle, then the same pid showing as `boot:900` with its own child: no raise, neither adopted; the same shape with `boot:400` (earlier tick), a different boot id, or an unreaped root: still raises with the field detail in the message. A test for the outputs policy. Existing custody and generic-host tests stay unchanged. Then the orchestrator's real render proof (`READY-PROOF astrid-agent <PR> <head> <selectors>`): long renders on the installed stack, never hosted CI. This is an S card: it gets a high-judgment review.
