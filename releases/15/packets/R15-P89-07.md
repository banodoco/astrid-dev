# R15-P89-07 — Validate the unchanged clips once

**Source tasks:** [`plans/89-heavy-saves-in-seconds/tasks.md`](../../../plans/89-heavy-saves-in-seconds/tasks.md) — SV-L10
**Route:** X (ChatGPT mode: Extra High; [run contract](../../../agent/shared/run-contract.md#chatgpt-session-modes))
**Estimate:** 3 days (inferred; design first, then implementation and differential proof)
**Outcome:** A one-edit save on a 300-clip timeline no longer runs the JSON-schema validation over all 300 clips each time. The Runtime's commit validation (`validate_commit_value`, `runtime_protocol/timeline_commit_validation.py:231-250`, the `PreparedCommit` and `CommitRequest` checks) reuses a SUCCESS-ONLY result for each unchanged schema subtree (clip or track level, at the compiled `$ref` boundary), keyed by the schema contract and location plus the type-sensitive canonical bytes of the current owned value (never object identity), and still validates the envelope, every changed or new part, array-level and cross-item constraints and all the other checks, with identical accepted values and identical first refusals.
**Dependencies:** none to start; Runtime `release/15/plan-89` (head `9cdfc1a2` or later). Evidence: Plan 89's counters (Runtime #118, `tests/test_timeline_save_work_counters.py`, `-m integration`): at 300 clips one `PreparedCommit` validation is ONE value of 894 KB costing 1.91 s of schema time (instrumented) with a key cost of 7.9 ms, hit-eligible 0 as a whole value (it differs after the edit), so only a per-subtree memo can help; `CommitRequest` 77 KB, 0.35 s. Read the manager's `SCOPE: SV-L10` (in the run record): the existing 256-entry whole-CanonicalDocument memo (`timeline_commit_validation.py:203-229`) does not short-circuit a document nested inside a `PreparedCommit`; a standalone precheck plus the unchanged full walk saves nothing; source reading does NOT yet prove that per-clip memoization is equivalent to the full schema or that a hook exists at the compiled `$ref`/item boundary.
**Design first (a gate):** post a STATUS with the design BEFORE writing the implementation, and wait for the Orchestrator's DECISION: the unit (which `$defs` / items), how the validator is hooked (a custom `jsonschema` validator class, a `$ref` resolution wrapper, or per-item validation driven from the schema), the key and how it is computed without costing what it saves, what runs every time (finite/raw JSON and cycle/type checks, the envelope, array uniqueness and order, cross-item constraints, authentication/digest/owner/dependency/admission checks), bounded size by entries AND bytes, eviction, never retaining caller-owned mutable graphs, behaviour on encoding or recursion failure (use the uncached path), and a worked estimate. If the schema cannot be decomposed this way without changing a refusal, post a BLOCKED with the exact reasons instead of weakening anything.
**Proof:** SV-L10's focused proof, run by you as new tests and by the lane: an old/new differential on accepted bytes and the exact first refusal/error for valid and invalid nested objects, array uniqueness and order, cross-field cases, schema location or digest change, bool/int/float, non-finite, cycles, aliases, mutation after validation and during capture, hash-collision simulation (retained-bytes equality), eviction, invalid-first poisoning, concurrent calls and provider-supplied malformed values; the counters test at 3/30/300 clips shows the `PreparedCommit` schema work no longer growing with the number of unchanged clips (target: at least 70% less schema time at 300 clips). Existing tests unchanged; run only your new tests and the Plan 77 save inventory's validation tests; never a full suite and never hosted CI. Acceptance change: the Orchestrator reviews it on the high-judgment route.
