# Windows beta test — Astrid Release 15

**Give this page to your coding agent.** Your job is to use Astrid and say what worked, what felt awkward, what you expected, and what broke. Your agent handles setup, evidence, GitHub reporting and optional fixes. **A useful test is an honest experience report, even when every command passes or a test stops early.**

**Your agent must leave:** (1) one detailed testing-session issue, (2) separate linked issues for distinct actionable problems (or links to existing ones), and (3) an exact test/cleanup record. Fix pull requests are welcome, never required. Keep the tester's own words distinct from the agent's conclusions.

This guide tests **unpublished Release 15 Agent and Runtime** on Windows; it is **not** a test of the currently served web editor. The usual astrid.haus installer selects the published release and **does not qualify as a Release 15 test**.

## For your coding agent

Follow these steps in order. Read the [technical matrix](windows-test-matrix.md) only for the steps you are doing; it contains commands, evidence fields and optional GPU cells. Use the [Astrid setup skill](https://github.com/banodoco/astrid-agent/blob/release/15/main/astrid/packs/setup/docs/SKILL.md) for normal installation choices, launcher paths, ComfyUI discovery and first generation; use the **version at the exact frozen Agent commit**, not an unrelated installed copy. Use the [generation skill](https://github.com/banodoco/astrid-agent/blob/release/15/main/astrid/packs/generation/docs/SKILL.md) for execution, the [RunPod skill](https://github.com/banodoco/astrid-agent/blob/release/15/main/astrid/packs/runpod/docs/SKILL.md) for optional paid machines, and the [contributor skill](../../../skills/astrid-dev/SKILL.md) for issues and code changes. This guide overrides ordinary onboarding **only** where an approved unpublished tester build needs a different install path.

1. **Open the session issue first.** Search [astrid-dev issues](https://github.com/banodoco/astrid-dev/issues) for this tester's existing run; resume it if present. Otherwise open an [observation](https://github.com/banodoco/astrid-dev/issues/new?template=observation.yml) titled **"observation: Release 15 Windows test — <tester handle/date>"**. Add `What I saw` with "Session started", the testing purpose and expected scope. As you learn them, record the Windows/GPU/VRAM, own-ComfyUI type, fresh install vs update, exact build identities and tester-approved actions. Keep this **one issue for the entire session**. If GitHub authentication blocks filing, give the tester the prepared issue/form link and stop until its URL exists.
2. **Get an approved build and isolate the work.** Ask the Release 15 Lead for the **frozen, green tester bundle** (`install.ps1` and `install-manifest.json`) cut from `release/15/main`, as specified in the [release tester-build rules](../../../skills/shared/workstreams/astrid-dev-release/SKILL.md#tester-builds). Verify the manifest identifies Release 15 and record the full Agent/Runtime/VibeComfy SHAs and artifact hashes; verify the **active installed tuple** after installation. Never choose an old `windows/tester-*` branch just because it exists. If the Lead has not provided a qualified bundle, report **BLOCKED** on the session issue; the [manual local-source route](windows-test-matrix.md#part-2-install-or-update-to-frozen-release-15-main) is only for explicit maintainer-authorized qualification, not a silent fallback. For code investigation, make scratch clones from the tested `release/15/main` commits and create an isolated local tester branch (`tester/r15-<session>-<topic>`). Keep the initial product test on the **unmodified** frozen build.
3. **Onboard and test in the open.** Obtain explicit consent before an unpublished install/update, a model download, modifying saved settings or any paid RunPod use. Back up existing work; never modify the user's ComfyUI node packs or delete their models. Follow the setup skill with the approved-build exception, then run the [core matrix](windows-test-matrix.md#part-4-the-core-cells) and whatever optional creative workflows are practical. Record each outcome **passed / failed / refused / skipped / blocked**, actual time and what was observed; a RunPod result is **not** local-Windows proof. If a step cannot run, state why instead of improvising a substitute.
4. **Collect the experience, not just failures.** Keep a live timeline in the session issue: the task, the tester's expectation, what actually happened, confusing wording, hesitation, unnecessary steps, surprising delays, workarounds and **positive moments**. Note which observations are the tester's own words (quote only with permission) and which are the agent's hypotheses. Ask brief feedback questions **after setup, after first creation, and at the end**; don't interrupt every action. Testers who agreed to detailed feedback should get room to explore what they genuinely want to create.
5. **Open separate issues selectively.** When a finding has an independently actionable cause or user impact, search existing [astrid-dev issues](https://github.com/banodoco/astrid-dev/issues) first. Comment with new evidence if it already exists; otherwise create a `bug:` for a reproducible failure, an `observation:` for a concrete UX/friction problem, or an `idea:` for missing capability, using the [existing forms and intake rules](../../../docs/contribution-workflow.md#issues). Record reproduction, expected/actual behaviour, active SHA/version, sanitized logs and session-issue link as applicable. Link each issue back in the session report. **Do not file an issue for every passing cell, remark or fleeting hesitation.** The Lead/maintainer triages what enters Release 15; the tester does not assign release scope or approve work.
6. **Offer a fix where practical.** With the tester's permission, investigate on a clean local branch from the **same frozen Release 15 source**; add a focused regression test, validate, and prepare a PR or patch linked to the individual issue. Follow the [release's fix-branch/PR routing](../../../skills/shared/workstreams/astrid-dev-release/SKILL.md#how-a-release-runs): ask the Lead for the intended `release/15/<topic>` fix branch/target, rather than pushing to `main` or `release/15/main` directly. Never patch installed files and then count those results as an unmodified candidate pass. Limited access or an unfixable bug is fine: the issue and reproduction are still useful.
7. **Finish the record and clean up safely.** Post a final comment on the session issue with: overall experience; **what delighted and what frustrated** the tester; meaningful friction in severity order; results and skips; source and machine identities; issue/PR links; redacted diagnostics; and what remained unverified. Follow [cleanup and reporting](windows-test-matrix.md#part-6-clean-up-and-report), ask whether to keep or roll back the unpublished build, remove only test-added material after consent, and independently confirm RunPod termination and costs if used. **Never upload tokens, secret values, private paths or unreviewed raw logs.**

## Scope and done

**Core:** approved install or update; active-build identity; discovery/connection to the person's ComfyUI; first image and an immediate second run with timings, where hardware/models allow. **Extended:** image editing, music, speech, SFX, video, RunPod and tester-chosen creative tasks, with separate placement labels. Every test is recorded, even if skipped. The [technical matrix](windows-test-matrix.md) contains the precise model/entry commands, disk needs, task receipts, diagnostics and optional cells.

**Done** means the session issue holds a useful qualitative narrative, reproducible technical outcomes, linked distinct findings, and an honest cleanup/retention record. An early blocker is a valid completed report when its evidence and limits are recorded. **No user permission to install, change existing work, spend money or push a PR is implied by receiving this document.**
