# Test Astrid Release 15 on Windows or Linux

**For testers:** Give this page to your coding agent. Try Astrid, make something, and tell us what worked, what was awkward and what broke. You have agreed to give detailed feedback; the agent should handle the engineering and reporting rather than make you follow a long terminal checklist.

**The result:** one GitHub issue telling the whole story of your session, plus separate linked issues for actionable problems (or links to existing ones). A fix PR is a bonus, **not** a requirement. A blocked or unsuccessful test is still useful when reported accurately.

This tests an exact **Release 15 snapshot**. The installer covers Agent/Runtime; to test the actual Release 15 editor as well, run the [pinned local frontend](frontend-testing.md). The editor served at astrid.haus is not proof of the pinned App. Start from the [current release-branch preparation instructions](prepare-build.md), not the public installer or old tester branches. An exploratory snapshot is not a qualified official tester build; if Release 15 has since published, label the session accordingly.

## Agent workflow

1. **Start the session issue.** Ask permission to post feedback to public GitHub and show the tester the redacted draft, as the setup skill requires. Search [astrid-dev issues](https://github.com/banodoco/astrid-dev/issues) for this tester's existing run and reuse it if resuming. Otherwise open one [observation issue](https://github.com/banodoco/astrid-dev/issues/new?template=observation.yml): `observation: Release 15 <OS> test — tester/date`. Record **Session started**, the planned scope, OS/version/GPU/VRAM, existing ComfyUI, fresh install vs update, and the tester's permissions. Update this issue as you go. If you cannot create it, prepare a link for the tester and do not install until its URL exists.
2. **Prepare and verify the build.** Follow [Prepare the current Release 15 testing build](prepare-build.md). Resolve the current coherent release-branch snapshot, obtain its manifest and matching Windows or Linux installer by immutable SHA, validate the pins and save the receipt. No separate maintainer-provided bundle is required for opt-in exploratory testing. For an official qualified run use the exact approved tuple and record approval. Detect installation ownership before changing anything; never overwrite Pinokio-managed files. Record active installed identities, exact manifest and hashes. Resumed sessions reuse their receipt. Investigate fixes separately from the unmodified baseline.
3. **Set up and test.** Read the [Astrid setup skill](https://github.com/banodoco/astrid-agent/blob/release/15/main/astrid/packs/setup/docs/SKILL.md) **at the exact frozen Agent SHA** (replace `release/15/main` in the navigation link with the full commit from the verified session manifest). Reuse its installation detection, choices, consent, ComfyUI connection, first image and troubleshooting. **Do not run its normal published installer or preinstall helper**: only the verified session manifest and matching bootstrap install this test build. Use the [generation skill](https://github.com/banodoco/astrid-agent/blob/release/15/main/astrid/packs/generation/docs/SKILL.md) for creative commands and the [technical matrix](windows-test-matrix.md) for exact Release 15 tests, timings, output checks and optional GPU work. Core: install/update, verify build, connect the tester's ComfyUI, make an image and immediately repeat it where possible. Try additional image editing, audio, video or a tester-chosen project when feasible. Mark each cell **passed / failed / refused / skipped / blocked**; a RunPod result is not proof of generation on the tester's local machine.
4. **Test the actual editor, not just CLI generation.** Use [the frontend testing guide](frontend-testing.md) to start the exact App commit from the receipt, connect to the verified installed Runtime, create a disposable project, import/drag media, edit, save and reopen, and set up or use a supported agent in the editor. Ask the person to try the creative workflow themselves. Record UI cases separately, including time to Saved, retained edits and actual agent reply. If frontend setup is blocked, continue the installed-side tests and mark the frontend scope explicitly untested; never install the public release as a workaround.
5. **Record the actual experience.** Keep a live timeline in the session issue: what the tester tried and expected, what happened, what delighted them, confusing terminology, unnecessary steps, waits and workarounds. Preserve the tester's words separately from your interpretation; quote only with permission. Ask a short feedback question **after setup, after the first creation and at the end**, not after every click.
6. **File distinct problems separately.** When there is a concrete independently actionable problem, search existing [astrid-dev issues](https://github.com/banodoco/astrid-dev/issues). If found, get the tester's permission to add redacted evidence there; otherwise show the redacted draft and get consent before posting with the existing [intake forms](../../../docs/contribution-workflow.md#issues): `bug:` for failures, `observation:` for specific UX friction, `idea:` for missing capabilities. Add expected/actual behaviour, steps, active version/SHA, redacted evidence and a link to the testing session; link the finding from the session too. **Do not create a new issue for every hesitation or passing test.** Maintainers, not testers, decide Release 15 scope.
7. **Offer a focused fix, optionally.** With the tester's consent, investigate on a branch from the frozen Release 15 source, add regression proof, and submit an issue-linked patch or PR. Follow the [contributor skill](../../../agent/start.md) and ask the Lead for the authorized `release/15/<topic>` fix-branch destination. **Never push or merge straight into `main` or `release/15/main`.** Do not patch the installed candidate or misreport patched results as baseline results.
8. **Finish and clean up.** Post a short final comment on the session issue: overall verdict, positives, frustrations, most important frictions, test outcomes/skips, exact source and environment, issue/PR links, diagnostics and unanswered questions. Complete the [cleanup procedure](windows-test-matrix.md#part-6-clean-up-and-report), ask whether to keep or restore the prior installation, and record what was removed or retained. If RunPod was used, record approved/actual cost and independently verified termination.

**Safety:** Ask before installing/updating, changing saved settings, downloading models, starting a generation or spending on RunPod. Back up existing projects, never alter the tester's ComfyUI node packs or remove their pre-existing models, and redact tokens, private paths and personal data before posting. Follow the [RunPod skill](https://github.com/banodoco/astrid-agent/blob/release/15/main/astrid/packs/runpod/docs/SKILL.md) for paid machines. Record any failure to obtain consent as a skip or blocker.

**Done means meaningful feedback and honest evidence, not a perfect pass rate.** The [technical matrix](windows-test-matrix.md) is the detailed reference; this page is the only entrypoint for the tester.
