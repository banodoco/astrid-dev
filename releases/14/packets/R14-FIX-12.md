# R14-FIX-12 — A task with durable logs settles, first time and on retry

**Source tasks:** [Release 14 issues](../../14.md#issues) — [astrid-dev #926](https://github.com/banodoco/astrid-dev/issues/926) and [#958](https://github.com/banodoco/astrid-dev/issues/958), RS1.6.
**Estimate:** 3–4 engineering days.
**Outcome:** When an ordinary action fails after writing durable `job.stdout` and `job.stderr`, an owner-authorized retry of the same task settles successfully. Both attempts' logs remain readable with their original provenance, and Runtime continues to enforce immutability for successful outputs. A generation that writes the same durable logs settles on its first `generation.create_with_variant` or `generation.variant.append`, and a second creative output is still refused.
**Dependencies:** Start when [R14-FIX-11](R14-FIX-11.md) is Done (one Agent issue packet at a time). Coordinate changes to the shared Runtime store with [R14-P55-12](R14-P55-12.md), which scopes thumbnail log selectors to the leased attempt.
**Proof:** Use the unchanged ordinary CPU-action probe identified in the [mailbox evidence](https://github.com/banodoco/astrid-dev/issues/796#issuecomment-6992053151), SHA-256 `671648e5b9287ead292f2ded239d0af64fd64e6aeaa0e4a541bfcb59192a1e22`.
**PR destination:** Runtime, and Agent if its caller or pin needs to change. In each affected repository cut `release/14/926-retry-durable-logs` from the current `release/14/main` and target `release/14/main`. Name `banodoco/astrid-dev#926` and `#958` in each PR. Put any Agent re-pin in its own commit for the Lead's review. [Release skill](../../../skills/capabilities/astrid-dev-release/SKILL.md#how-a-release-runs)
**Authority:** [run board](../run.md#authority).

1. Reproduce the failure on the release bases and record both SHAs. The mailbox run on Agent `91cb4cb4` and Runtime `f3dc970a` used a real GenericPackHost and a native subprocess, with no generation or thumbnail. Both attempts wrote identical stdout bytes. The retry ran successfully, then settlement returned HTTP 409 on `job.stdout` because the same task and selector already owned a log with different `attempt_id` and `provenance_json`.
2. Scope durable log associations to the attempt so each attempt retains its own log identity. If the store already preserves readable per-attempt history, superseding only the failed attempt's active log association is also viable. Choose the smaller change that preserves both reads and the successful-output guard.
3. Make the two legacy creative validators, `generation.create_with_variant` and `generation.variant.append`, exclude canonical durable log outputs from the creative-output count (#958). Keep refusing two creative outputs. The failing-before cases are R14-P55-12's two-case service diagnostic, which fails on Runtime `f3dc970a` with HTTP 422 ([mailbox](https://github.com/banodoco/astrid-dev/issues/796#issuecomment-6996311467)). Both share this packet's setup (a real GenericPackHost writing durable logs) and its proof.
4. Run the identical probe on the fixed release heads and record the SHAs and passing settlement result. Through the supported read path, retrieve stdout and stderr for each attempt and verify each log's recorded attempt ID and provenance. Show that Runtime still rejects a conflicting association for a successful output. Run R14-P55-12's thumbnail retry and selector validation checks against the combined changes, including refusal of a selector for another attempt. Then run R14-P55-12's installed preserved-variant journey on the combined heads and record that its first settlement passes: this completes the proof R14-P55-12 could not finish.

One fresh packet session submits the fix PRs and proof. The Lead reviews, integrates and records the fix branches in the brief. The Orchestrator reports the handoff in its hourly STATUS.
