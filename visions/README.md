# Vision, gaps, plans and evidence

Start with **[Make Extraordinary Art Possible, Together](vision.md)**.

The vision contains four [pillars](vision.md#four-pillars)—**A Tool for Artistic Ambition, Agent-Powered Liquid Software, Intelligence That Compounds, Shared Creative Endeavour**—and three [cross-cutting principles](principles.md): **local-first/cloud-capable, open by design, creator-controlled**.

**[Gaps](gaps.md) → [Plans](../plans/) → Evidence → reassessment.** A gap may apply to one or several pillars and principles. The files live in **one** [`gaps/` directory](gaps/); they are not duplicated beneath their conceptual owners.

The current gaps are [AA-001](gaps/AA-001-sustained-creative-work.md), [LS-001](gaps/LS-001-portable-components.md), [LS-002](gaps/LS-002-agent-workspace-control.md), [LS-003](gaps/LS-003-full-stack-contributions.md), [CI-001](gaps/CI-001-agent-learning-loop.md), [CI-002](gaps/CI-002-federated-knowledge.md), [CA-001](gaps/CA-001-creative-challenge-culture.md), [CA-002](gaps/CA-002-contributor-ownership.md), and cross-cutting [F-001](gaps/F-001-platform-reliability.md), [F-002](gaps/F-002-safe-user-control.md), [F-003](gaps/F-003-creative-execution.md), [F-004](gaps/F-004-pack-lifecycle.md).

Existing gaps should be reused before proposing new ones. For example, **local/cloud deployment** is already partly addressed by F-001 and F-003; assess whether their closure criteria really need another independent gap before introducing one.

[Reference documents](references/) preserve the original Liquid Software philosophy, component/source maps, the proposed Hivemind protocol and a [dated assessment of current plans](references/plan-gap-assessment-2026-11-06.md). Plans own their gap links and the [plan catalog](../plans/index.md) alone owns status, priority and ownership. The documentation and public-content integrity checks run in CI; evidence-based gap reassessment still requires review.

## Public vision page (generated, not re-authored)

Astrid App should consume a build-time snapshot of the **existing** Markdown, generated by `python3 scripts/export_public_vision.py --revision <40-character-SHA> --output <path>.json`. The pinned commit identifies exactly what visitors see; internal Markdown links become GitHub permalinks at that revision.

- **Headline and pillar descriptors/order:** `vision.md`. **Pillar detail:** `pillars/*.md`. **Operating principles:** `principles.md`.
- **Gap title, assessment and desired/current state:** `gaps/*.md`, with relationships from `Applies to`. One assessment, even when applicable to several pillars/principles.
- **Project title, goal, status, owner and priority:** `../plans/index.md`; gap links come from each `plan.md`. **No copy of those fields belongs in Astrid App.** Every project links back to its version-pinned GitHub plan.
- **Page layout and visual behaviour:** Astrid App. Show a substantial slice of nonterminal plans in catalog order (for example 10–12, with an option to show the rest). Distinguish `active` from `queued`/`blocked`/`paused` honestly. No new public-summary metadata is required for this first version.

The exporter and its focused tests fail on invalid identities, missing fields, unresolved relationships and invalid local links. The actual page should additionally test that the rendered copy, project links and status labels come from the snapshot. Do not fetch GitHub from browsers on each page visit or maintain a second editorial record.

## Live public vision feed

After merging validated content to `main`, [the documentation workflow](../.github/workflows/docs.yml) publishes a **generated, versioned JSON feed** to the `vision-published` branch. The public endpoint is `https://raw.githubusercontent.com/banodoco/astrid-dev/vision-published/vision.json`. The published branch is **generated output only**: contributors edit the Markdown and plan catalog on `main`, never `vision-published`.

The exporter provides `schemaVersion: 1`, the exact source commit, pillar/operating-principle/gap content and the complete plan catalog with GitHub permalinks. Publication runs only after the documentation validator and content-contract tests pass. A failed validation leaves the previous published feed unchanged. A browser's normal HTTP cache may delay visibility briefly; this is not instant real-time updating. Astrid App reads the feed at runtime and owns only presentation. **No cross-repository sync PR or copied editorial snapshot is required.**

The public feed changes independently of Astrid App releases. Breaking schema changes must use a new version or be deployed compatibly; existing clients must not be silently broken.
