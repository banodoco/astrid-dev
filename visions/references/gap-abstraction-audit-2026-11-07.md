# Gap abstraction audit — 2026-11-07

**Purpose:** First-principles review of all 15 currently defined vision gaps against the [gap contract](../gaps.md) and [single project catalog](../../plans/index.md), following the question: *Would this missing outcome still matter if its proposed project were replaced?* This is a one-time editorial boundary review, **not** a second gap/status or plan ledger. Source snapshot: [Astrid Dev main before this audit](https://github.com/banodoco/astrid-dev/tree/b40bf0128d20cb822670c5bd0aa9ac8543e2ad4b).

**Decision:** Preserve existing IDs and their independently testable meanings. Refine language where a title describes a project or a bundled implementation more than the underlying user outcome. Do not invent an equal number of gaps per pillar, or make a new gap for every new project. Assessments remain evidence-limited and do not change merely because this audit was performed.

## Review findings and operating guidance

- **The apparent one-to-one pairs are not automatically duplicates.** F-005/Plan 25, F-006/Plan 26 and F-007/Plan 15 currently each have a main project, but the *gap is the outcome* and could survive a cancelled or replaced project. Their closure tests must not depend on a named provider or task checklist.
- **Cross-cutting outcomes are valid when scoped.** F-001, F-002 and F-003 cover distinct classes—operational reliability, creator agency and creative execution. They must state a bounded supported scenario/matrix and negative tests; don't claim that one small project fully closes them.
- **Some gaps legitimately have no dedicated project.** AA-001, CA-001 and CA-002 are still meaningful without inventing implementation plans. Future projects may link them when there is a concrete proposal.
- **Specific gap domains can overlap as evidence, without collapsing identity.** LS-001/002/003, CI-001/002, F-004/LS-003, F-002/F-007 and F-003/F-005 have different users, failure modes or closure evidence.
- **The audit is a judgment, not proof of missing features.** Historical source snapshots and project proposals ground the current assessments. Do not update assessment status from a wording review, and reconsider a gap when actual implementation evidence changes its boundary.

See [the proposed per-PR gap boundary decision gate](../gaps.md#reviewing-a-new-or-redefined-gap) for preventing future duplicate, project-shaped or untestably broad gaps. Preserve the [completion gate](../../AGENTS.md#completing-a-plan-one-decision-gate) as the independent evidence check for a project's transition to done.
