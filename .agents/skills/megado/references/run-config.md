# Run configuration semantics

`templates/run.yaml` supplies the default responsibility slots, independently replaceable model/reasoning bindings and available stage slots. It is a coordinator-readable contract, not an implemented scheduler/launcher. Copy it into the run, apply explicit user overrides, choose stages using the guide below and replace/delete placeholder triggers before dispatch. Link it from agent_goal.md as the single declaration. Do not ask for choices already set by defaults or the user; resolve unavailable models without silently substituting. Existing explicit run policies remain authoritative.

## Default roles and budgets

- Default model bindings: `coordinator` uses GPT-5.6 Luna at medium reasoning; `worker_normal` uses GPT-5.6 Luna at XHigh reasoning; `worker_xhard` and `oracle` use GPT-6.1 Sol at high reasoning; `reviewer_normal` and `final_reviewer` use GPT-6 Astra at medium reasoning; `reviewer_xhard` uses GPT-6 Astra at high reasoning. These are replaceable bindings, not role definitions; reviewers remain separate agents from implementers.
- Oracle: normally uncapped, used only for actual blockers or consequential judgment requests; an explicit run may set a cap.
- Intermediate review: at most two rounds per selected stage (initial check plus correction verification).
- Final holistic review: at most five rounds (initial integrated review plus correction verifications), stopping immediately on an uncontested PASS. The final allocated review stage may contain multiple rounds; only its last allocated round is the last review opportunity, when the final reviewer may return HARD_BLOCK for a directly evidenced unresolved in-scope blocker.

These are correction caps, not work to fill. Stop each stage on an uncontested PASS. Spend another round only after an actionable blocking finding, the affected correction, and fresh checks, or to retry an UNKNOWN caused by an access or identity problem within the remaining stage-round budget after that cause is resolved and the candidate and evidence identities are revalidated, or for a post-oracle verification round within the remaining stage-round budget when the oracle rejects all blockers so the reviewer can obtain PASS. The consumed UNKNOWN round still counts; the post-oracle verification uses an existing round and creates no extra round or budget. Do not use remaining rounds for generic hardening, repeated discovery, or reassurance. XHARD review replaces the normal reviewer for a justified hard review question within the same stage/budget; it is not an automatic extra stage. The oracle settles uncertain escalation within its call budget.

## Choosing review stages: a practical proxy

| Work shape | Review boundaries | Default maximum review calls |
| --- | --- | --- |
| Ordinary implementation with one completion point | One Astra review of the completed integrated outcome | 5 |
| Completed implementation followed by bulk migration or another consequential operation | Astra readiness review before the operation; Astra completion review afterward, covering the full agreed outcome | 2 + 5 = 7 |
| Two distinct consequential decisions before overall completion | Two scoped Astra boundary reviews, then Astra completion review; select only when each protects different dependent work | 2 + 2 + 5 = 9 |

These are scheduling examples, not mandatory stage counts. Concentrate review at completion and consequential boundaries; do not schedule routine per-task or per-wave reviews. Name the readiness/completion decision, the evidence to assess and the dependent work it protects. Passing tests and source evidence can support a model review; a mechanically untestable assumption is not a prerequisite. Merge stages assessing the same candidate and evidence. If a post-operation review completes the agreed scope, it serves as the final review. A schema/API change or repository crossing alone does not require a stage. Architecture or authority uncertainty goes to the oracle. Explicit user policies, including final-only review and different stage caps, take precedence. Factual exploration and ordinary tests do not consume review calls and cannot issue hidden review verdicts.

Stage counts/caps are fixed when adopted. New risk calls for a decision, not automatically more stages: use a remaining stage or replace its scope without replenishing spent calls; additional review budget needs user authorization. A required pre-operation validation remains necessary even without an extra model review. Planning-only work schedules no executable reviews. Microdo normally keeps one final stage and its single correction limit (at most two final rounds), unless the user explicitly changes its one-pass policy; the Megado five-round default does not silently override that narrower mode.

## Field semantics

- `mode`: planning_only or delivery. Planning-only never dispatches executable review stages. Changing a field cannot grant implementation or deployment authority.
- `roles`: the responsibility slots `coordinator`, `worker_normal`, `worker_xhard`, `reviewer_normal`, `reviewer_xhard`, `oracle` and `final_reviewer`, each with an independently replaceable model and reasoning binding. Reasoning applies only where supported by the selected runtime; resolve unsupported settings before invoking rather than silently substituting. A role is a responsibility, not a model identity: several slots may name the same model, and reviewer agents remain independent of workers even when their bindings match.
- `oracle.max_calls` (optional): if present, total oracle invocations for this run, including initial direction, diagnosis and follow-up decisions. When absent, there is no numeric ceiling. Reuse existing rulings when sufficient and never ask the oracle at every PASS; every call must address a new blocker or consequential judgment. An explicit cap never transfers authority to the coordinator when exhausted.
- `review_stages`: ordered named review boundaries. `after` references an actual task/checkpoint or all-required-work-and-tests. `reviewer_role` resolves through roles. `lens` is completion, strategic, or completion_and_strategy. `max_rounds` is the total invocation cap for that stage, including correction reviews—not the number of required passes. Each stage is a gate for its dependent work.

If both intermediate slots are explicitly selected alongside the final stage, with caps 2, 2 and 5, the run allows at most nine review calls, stopping early at each passed gate. Use that shape only for two distinct consequential decisions, not routine implementation waves. Oracle calls are separate and normally uncapped. There is no extra implicit final review, and changing classification/model/checkpoint names does not replenish counts. If an oracle commissions review, charge the review invocation to its stage budget; the oracle itself still must address a concrete blocker or consequential judgment. A model invocation cannot evade a cap by being relabelled advice. Pure factual workers do not adjudicate or issue hidden review verdicts.

Before dispatch, check unique stage IDs, valid role references/models, positive integer caps, meaningful task triggers, final-stage scope and consistency with user authorization. Do not start a coordinator expecting an unavailable model or a placeholder trigger. Record consumed counts and last candidate/evidence identity in existing status notes before invoking; record results afterward. Keep counters durable through crashes/restarts. If a process might have been invoked but its result is lost, recover evidence or conservatively charge it rather than assume a free retry.

Coordinator loop: dispatch ready work → dispatch prescribed tests and collect results plus mechanical readiness checks → invoke a ready review stage → advance only on uncontested PASS with required tests passing, or route clear in-scope defects to correction. An UNKNOWN caused by an access or identity problem may be retried within the stage's remaining round budget only after that cause is resolved and the candidate and evidence identities are revalidated; the consumed UNKNOWN round is not restored. A final-stage reviewer may still return REWORK with more tasks; PASS waits for their implementation and verification. On the last allocated round of the final allocated review stage, a directly evidenced unresolved in-scope blocker may return HARD_BLOCK. An oracle disposition rejecting all blockers does not itself replace the stage verdict; a remaining review round is needed to obtain PASS, otherwise surface the review-budget decision. Escalate disagreement, architecture/scope/authority changes, unclear XHARD routing or attempted exceptions using the oracle request template. Fix before the next review round. At a cap, do not cross the unresolved gate, dismiss a finding, weaken a test or launch an extra call; preserve the HARD_BLOCK or surface the needed authority/budget decision. User approval is needed to enlarge a fixed budget or authority; an oracle recommendation cannot grant it.

For final-only runs, declare just that stage and retain ordinary tests/integration checks. For Microdo, keep its one-pass/correction limit unless the user explicitly changes it; the shared role defaults do not override it. For an explicitly host-as-oracle run, record the actual host model in the oracle role and state that assignment in the goal; do not pretend a separate model ran. Existing run choices remain authoritative until changed, even when the skill default evolves.

Review packets: each adopted stage declares `scope_tasks`, `criteria` and `criteria_source` referring to real task/implementation-criterion IDs before execution. See [review-packets.md](review-packets.md) for the fixed assembly and reviewer questions; no new review objective is inferred from model choice.
